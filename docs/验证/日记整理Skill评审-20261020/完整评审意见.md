# 日记整理 Skill 完整评审意见

评审日期：2026 年 10 月 20 日。对象：本仓库 `skills/diary-organizer` 当前版本。

## 1. 评审结论

**保留当前 Skill 的主体结构，优先补齐执行边界与验证方法，不建议整体重写。**

当前版本已经清楚表达了保真整理、保留个人声音、事件汇聚、关键疑问澄清和整篇最终确认。近期补充的重要性分级、叙述视角、反思与计划边界也针对了真实问题。现在最需要解决的是：

1. **保护人工改稿。**“每轮更新整理稿”没有明确约束模型如何处理用户直接修改过的文件。
2. **区分只读来源获取与可否入库。**现有原文导出复用了整篇替换的检查，会让已分析日记连标准只读导出都失败。
3. **建立文本与交互的回归评估。**现有脚本测试通过，不等于模型能稳定保留细节、遵守澄清与确认流程。
4. **明确能力边界。**当前保存脚本支持受条件限制的整篇替换；不支持任意修改已分析日记，也不提供事件级补丁保存。
5. **管理规则漂移。**Skill 的新分级与计划规则没有全部进入后端模型提示词，两个整理入口已经存在行为差异。

没有发现必须立即停用整个 Skill 的证据。当前适合继续用于有人阅读、修订和最终确认的整理任务；现有证据不足以认定它已经适合无人审核的批量整理。

以上是本项目的评审判断，不是外部标准给出的认证结论。

## 3. 应用场景调研：本项目应借鉴什么

### 3.1 口述材料编辑：保留声音，同时允许适度整理

美国国家公园管理局将口述转写的风格选择、专名表、语音识别结果检查和叙述者最终审阅列为实际工作事项。Baylor 的口述史资源也指出，转写无法保留录音的全部意味，初稿准确性会影响后续编辑结果。[NPS 转写指南](https://www.nps.gov/articles/000/oral-history-resources-interview-transcribing.htm)、[Baylor 转写资源](https://library.web.baylor.edu/visit/institute-oral-history/resources)

对本 Skill 的启示是：把“通顺”放在保真之后是正确的；名称校正、歧义保留和用户审阅必须保留。需要特别注意，模型只有转写文本时，没有真实听到语气与发音，不能把基于上下文的猜测说成已经核实的听音纠错。

Minnesota Historical Society 的指南强调保留叙述者表达的特点，重复中可能包含新增细节，编辑时要与叙述者沟通。它也允许删除无信息的语句重启和设备操作闲话。[MNHS 编辑指南，第 1—3 页](https://www.mnhs.org/hubfs/oral-history/editing_oral_history_transcript.pdf)

这支持当前 Skill 对“无意义重复”和“有情绪、迟疑、转折或新增细节的重复”作区分。该指南还包含为档案转写增加说明的做法；本项目的正文风格不需要照搬，因为用户已经明确不接受模型添加记录过程旁白。

### 3.2 作者主导修订：可以澄清，但不能替用户下结论

Oral History Association 的最佳实践强调尊重叙述者的语言与视角，并在可能时提供审阅机会。[OHA 最佳实践](https://oralhistory.org/best-practices/)

本项目据此可以采用“初稿—澄清—完整修改稿—最终确认”的协作方式。但外部资料并未规定“四题上限”、指定 Markdown 标题或确认指纹；这些是本项目自己的交互和实现选择。公开口述史的发布授权规则，也不能直接等同于私人日记保存流程。

### 3.3 事实保真：检查关系和确定程度，不只检查关键词

FRANK 将摘要中的事实问题拆为实体、谓词、情境、指代、篇章关系等类型；其研究提醒我们，流畅文本仍会发生事实错误。[FRANK 论文](https://aclanthology.org/2021.naacl-main.383/)

本项目适合借鉴这种错误分类，例如：人物是否换了、提出离职是否被写成已经离职、可能争吵是否写成已经争吵、先后关系是否被补成因果关系。它研究的是摘要，不能直接用其摘要质量标准要求日记删减细节。

QAFactEval 使用问答检验生成内容能否得到来源支持，说明核对“谁做了什么、结果是什么”可以成为事实检查的一种路径。[QAFactEval 论文](https://aclanthology.org/2022.naacl-main.187/)

本项目的迁移建议是：同时检查两个方向——**输出中的判断是否有依据；原文与确认补充中的重要信息是否被保留**。这是一种针对日记的评审设计，不是该论文已经验证过的中文日记指标。暂不建议接入复杂自动评分模型，也不以字数或措辞相似度代替保真判断。

### 3.4 重要性是个人评价规则，需要校准

本轮资料没有提供适用于该产品的 HIGH／MEDIUM／LOW 客观分级标准。当前分级应明确视为模型给用户的评价建议，通过用户反馈和成对案例校准。

评估重点应是“理由是否符合文本、程度是否相称”，而不是强求每篇出现 LOW，或要求不同模型给出完全一样的等级。关于健康、家庭、金钱等主题，也不能直接套等级。

## 4. Skill 编写调研与形式评审

### 4.1 规范要求与写作建议要分开

Agent Skills 规范要求目录中有 `SKILL.md`，包含符合约束的名称和描述；脚本、参考资料等是可选组成。正文长度和渐进披露属于编写指导，不能据此要求所有技能长成同一种模板。[Agent Skills 规范](https://agentskills.io/specification)

当前检查结果：

| --- | --- |
| `name: diary-organizer` 与目录名一致 | 符合命名要求 |
| 描述写明做什么、何时用 | 明确，保留 |
| `scripts/`、`references/` 分工 | 合理 |
| 主文件 130 行 | 没有仅因行数就必须拆分的依据 |

OpenAI 的官方编写文档说明技能可组合指令、资源和脚本，主说明应围绕可重复工作流组织。[OpenAI：Build skills](https://learn.chatgpt.com/docs/build-skills)

**本项目的建议：**保留写作与确认的核心规则在主文件；把已按需加载的例子、数据库命令继续放在参考资料。不要把主文件压缩成必须跳转很多次才能理解的目录。

### 4.2 可执行评估优先于继续堆叠规则

OpenAI 的 Skill 评估指南要求同时关注结果、过程、风格与效率，并结合可确定检查和定性量表。[OpenAI：Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)

这直接适用于当前问题：格式脚本通过只能证明字段可解析；“事实没扩大、疑问未答不当确认、人工修改未覆盖”等，需要行为用例。

Anthropic 的官方 Skill 编写指南同样强调代表性评估、清晰示例和先验证再迭代。[Anthropic：Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**本项目的建议：**示例应成为评估材料的输入，不要只作为模型偶尔读取的说明。保留多种正确措辞，不要求逐字复现标准答案。

### 4.3 发现路径需要区分“可读取”和“已注册”

当前 Codex 官方文档描述的仓库发现目录是 `.agents/skills`，并支持相应的符号链接方式；普通仓库根目录 `skills/` 不在其列出的默认仓库发现路径中。`allow_implicit_invocation: false` 控制是否隐式调用，不负责安装或注册。[OpenAI：Build skills](https://learn.chatgpt.com/docs/build-skills)

本仓库当前可见的是 `skills/diary-organizer`，并未看到仓库 `.agents` 目录。这意味着**不能仅因文件存在，就认定输入 `$diary-organizer` 一定会按已安装技能激活**。本次按用户指定路径读取并执行，已经证明了手动方式可用；它不能证明自动发现也已配置。本轮未检查用户目录的全部注册或外部符号链接，因此不判定“全局未安装”。

如果当前只需要按路径使用，无需为此改动。若要正式使用技能选择器或 `$diary-organizer`，应核验注册结果，再采用官方支持的目录或链接，维护一个源文件位置即可。

## 6. 完整评审发现

优先级：P1 为应优先修复的可靠性缺口；P2 为应随后完善的语义与维护问题；P3 为按实际需要处理的体验或可移植性问题。本轮未发现证据充分的 P0。

### R1 · P1 · 人工直接修改稿件后的保护规则不明确

**证据：**Skill 要求每轮更新 `整理稿.md`，又要求始终依据原文整理，但没有写明用户直接修改该文件后，模型应先读取当前文件、保留其改动并只做已请求的修改。[文件交付规则](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/SKILL.md:126)

**影响：**在“我已经改了一些地方，不要覆盖”的实际工作流中，模型若拿上一轮内存稿整篇重写，会丢失人工修订。保存指纹能发现文件变化，但阻止不了模型在生成阶段覆盖改动。

**最小建议：**增加一条规则：每次修订前重读当前稿；用户直接修改的内容作为其明确修订保留；只修改本轮请求涉及的位置。与原文发生关键冲突时澄清，不自动回退成旧版本。无需增加新审核文档。

**验收：**用户把某句改好，再要求模型修另一句，前一句及其余内容保持不变；随后“以当前稿入库”的确认绑定当前文件。

### R2 · P1 · 只读导出复用了整篇替换检查

**证据：**`export`、`prepare`、`save` 共用 `load_target`，而该函数检查状态、来源锁和分析、批注、收藏等依赖。因而只读导出也会被“不能替换”阻止。[目标检查](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/scripts/store_diary.py:27)、[命令共用入口](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/scripts/store_diary.py:247)

**影响：**日记可以被读取、在本地整理，但标准 `export` 无法提供它的原文。本会话处理已分析的 09-23 就遇到了这一能力缺口。它是读取与写入职责耦合，不是应删除所有保护检查的理由。

**最小建议：**拆分“核实所属用户并只读获取来源”和“核验是否允许替换”。`export` 只做读取所需检查；`prepare/save` 保留写入能力检查。若读取中的内容会继续变化，使用版本或指纹绑定，不以允许读取代表允许保存。

**验收：**已分析日记可在合法归属下只读导出；整篇写入仍被既有来源保护拒绝；其他用户和已删除日记仍不能导出。

### R3 · P1 · 缺少覆盖文本和交互的行为回归用例

**证据：**现有 10 项测试覆盖格式、来源、用户隔离、回滚、替换、索引和 CLI 指纹，但没有让模型面对含混文本和多轮用户回答，再验证其整理行为。[现有测试](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/scripts/test_diary_storage.py:47)

**影响：**增加规则后无法证明问题已解决，也无法发现旧能力被破坏。“四题后自动停止”“把可能写成已经”“反思变计划”等都不会被现有脚本测试检出。

**最小建议：**先建立第 8 节的小型脱敏用例集；保留脚本单测，额外评估模型结果和操作过程。不要先建设复杂评估平台。

**验收：**至少能独立显示“格式通过、事实失败”或“文稿通过、确认流程失败”，而不是只给一个无法解释的总分。

### R4 · P2 · 入库能力和整理能力的分支出现得偏晚

**证据：**主文件同时提供仅整理和确认后入库；详细的状态、锁和关联限制主要在入库参考中。实际执行又曾把“可以生成稿件”说成“确认后即可定点修改库内内容”。[工作方式](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/SKILL.md:42)、[入库说明](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/references/storage.md:96)、[后端来源锁](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/backend/services/graph_tasks.py:88)

**影响：**用户读完长稿才发现保存不受支持；模型还可能承诺系统没有实现的修改方式。

**最小建议：**任务开始时识别仅整理、首次保存、整篇替换、既有事件定点修改四种意图。只读核验后，简短说明本次能交付什么；受限时继续有价值的本地整理，不承诺可保存。现有脚本不支持事件补丁保存，就明确这一点；不能从“接口接受 analyzed 状态”推断来源锁会放行。

**验收：**遇到已分析日记，在初稿前就说明当前只交付本地稿及原因；不通过改状态或绕过来源锁实现保存。该建议不要求每次重新询问已经明确的用户意图。

### R5 · P2 · Skill 与后端整理提示词已经发生语义漂移

**证据：**Skill 现已要求 MEDIUM 超出常规推进，并增加了反思与计划边界；后端的重要性提示仍为“对任一方面有明确影响或推进，但不足以成为当天主线”。后端还允许根据明确文本线索提取感受，而 Skill 更强调仅提取用户已表达内容。[Skill 重要性](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/SKILL.md:103)、[后端重要性](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/backend/services/ai.py:267)、[后端感受与反思](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/backend/services/ai.py:248)

**影响：**同一篇日记通过聊天 Skill 和平台整理入口，会遵循不同尺度。不能因为几次输出相似就称规则已对齐。

**最小建议：**先明确这两个入口是否应共享语义标准。若应共享，维护一份共同的规则依据，并在变更时核对两处；若刻意不同，写清差异。无需为此立即重构整个流水线。

**验收：**日常做饭、常规报销、一般提醒等成对样例在两个入口都不因“有行动”自动升级；反思不会被自动提取成确定待办。

### R6 · P2 · 保真规则充分，但缺少明确的稿件完成检查

**证据：**主文件已经禁止新增事实、扩大确定程度，并要求完整保留细节；但这些分散在写作规则中，没有一句明确要求在交付完整稿前核对正文、标题、感受、反思和重要性理由之间的一致性。[写作规则](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/SKILL.md:72)

**影响：**正文保持“可能吵架”，重要性理由却写成“已经造成明显关系损害”；或结果只出现在感受中，正文缺失。结构校验不会拒绝这种情况。

**最小建议：**增加一个轻量内部完成检查：输出判断有来源、重要信息未遗漏、各字段确定程度一致、用户修订已保留。没有必要固定额外模型调用次数，也不输出片段编号或独立审核记录。

**验收：**有“尝试劝说”不能自动得出成功；用户后来确认成功后，正文可补结果，但不顺带补“双方情绪都平复”。

### R7 · P2 · 重要性新规则仍需要成对校准

**证据：**近期已经补充 LOW 的合理位置、不按比例分配、不因有计划或人物互动升级。这修复了明显缺口；但“超出日常”“影响有限”“显著影响”仍是需解释的尺度。[分级规则](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/SKILL.md:109)、[分级示例](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/references/examples.md:165)

**影响：**两次模型运行可能为同一事件给出不同等级。若为了纠正过去无 LOW 而反向强制降级，又会引入新偏差。

**最小建议：**在既有示例旁增加少量成对案例，只改变“影响证据”：日常做饭与带来明确关系转折的做饭；一般提醒与促成重要决定的提醒。解释升级依据，不增加等级配额。

**验收：**评价理由能指出实际变化及程度；事件主题、字数和是否独立成事件不决定等级。短暂但强烈的情绪也可有显著影响，不能只按持续时间判 LOW。

### R8 · P2 · 纠错依据应区分“有录音”和“只有转写”

**证据：**当前要求语音识别错误“结合上下文和读音校正”，但输入只要求原文，没有要求提供录音。[纠错规则](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/SKILL.md:78)

**影响：**模型可能仅凭常见名称或读音猜测，声称已经确认某个专名。拼音相近不等于当时确实说了这个词。

**最小建议：**改为条件说明：有音频时结合音频；只有文本时依据上下文、人物资料和用户确认处理，无法确定则保留。用户明确补充优先，不能因其内容不在最初转写中就删除。

**验收：**陌生名称没有证据时不编造候选；两个有效称呼保留；不同人物或混合群体的“他们”不机械替换为“她们”。

### R9 · P3 · 纯文本任务也会默认读取项目人物资料

**证据：**输入只要求日记原文，但“开始整理前”无条件要求从项目读取 `x5456` 人物关系，脚本依赖后端环境和数据库。失败后继续整理的规则已经存在。[人物资料读取](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/SKILL.md:20)、[导出脚本](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/scripts/export_people.py:33)

**影响：**只粘贴一段文本的任务也产生数据库访问；脱离该仓库时需要先失败一次才能走降级路径。

**最小建议：**保留用户指定的 `x5456` 默认；增加条件：本项目日记任务默认读取，脱离项目或用户已提供资料时直接用已提供信息。失败只报告一次，继续整理，不把失败当作必须停工。无需设计多租户平台。

**验收：**无数据库环境也能完成纯文本整理；入库任务仍核对人物资料用户与日记归属，不因默认用户名而读取另一用户资料作为依据。

### R10 · P3 · 自定义输出与固定入库语法需要明确分支

**证据：**主文件允许用户指定格式，但转换器只接受固定标题、字段和顺序，且禁止其他标题和代码块。[输出约定](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/SKILL.md:89)、[转换语法](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/scripts/markdown_to_json.py:94)

**影响：**用户要求普通段落或自行增加小标题后，文件可能适合阅读却不能被当前入库脚本接受。这不是转换器静默丢数据的问题；它会报错停止。

**最小建议：**仅整理时遵循用户格式；约定入库时提前说明本次可直接保存的格式。若用户要求改变格式，应提供受支持的映射或明确不支持，不能为了通过转换覆盖人工稿。

**验收：**解析错误准确定位；用户稿保留；不把解析成功当作语义正确。

### R11 · P3 · 注册方式和完整示例可再明确

**证据：**目前目录位置与正式发现路径存在前述区别；示例大多用于说明局部判断，不是每段都含重要性等完整入库字段，示例文件也已经说明输出形式以用户要求为准。[示例说明](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/references/examples.md:1)、[调用策略](/Users/x5456/Documents/workspace/XDATA-Project/0个人/diary-platform/skills/diary-organizer/agents/openai.yaml:1)

**最小建议：**若需要正式注册，核验并文档化官方支持的调用路径；只增加一份可直接解析的完整最小示例即可，不必把所有局部示例都改成冗长模板。依赖要求可以简述或放入可选 `compatibility` 元数据，缺少该字段不是规范违规。

**验收：**显式调用能够找到技能；示例中的完整稿可通过转换器；局部示例明确不是完整入库文件。

## 7. 已修复的问题与执行错误，不应再混为当前缺陷

| 历史现象 | 当前判断 |
| --- | --- |
| 每次必须问四题 | 当前规则写了“最多四题、不凑题数”，无需再写一套重复规则；用行为评估验证执行 |
| 回答澄清就直接入库 | 当前明确要求整篇最终确认；此前预检解释不清属于执行沟通问题 |
| “录日记时”等旁白 | 已增加规则和例子；当前不是缺少规则，而是需要回归验证 |
| 把反思自动当计划 | 已增加明确边界和五组示例；不应继续把缺口描述为尚未修复 |
| 旧事件手动重要性阻止替换 | 已按用户要求删除；评审不建议重新加回该限制 |
| 用户确认过的历史补充不在最初转写中 | 不因此判错；明确确认的补充属于依据 |
| 没有 LOW | 是需要检查的信号，不是自动判错条件；不按等级比例验收 |

预检本身不写库，但面向用户应说“已检查，等待整篇确认”，不要反复使用“待入库”等容易产生误解的描述。文件指纹用于绑定版本，不等于取得人的授权；此点现有说明已经正确。

## 8. 最小评估方案

### 8.1 三层验证

1. **脚本层：**保留现有 10 项测试；后续若拆分只读导出，补充针对已分析日记可读、仍不可替换的测试。
2. **文稿层：**使用脱敏的短文本及少量跨段长文本，人工标注必须保留的信息、禁止新增的判断、允许的不同表达。不固定完整标准措辞。
3. **交互层：**模拟两到三轮回答、跳过、人工改稿、整篇确认、原文变化和来源锁，检查模型实际调用和输出。

不要求每篇正式日记附加内部审核产物；评估材料是维护 Skill 的开发资料。

### 8.2 建议先覆盖的场景

| 编号 | 输入或操作 | 必须满足 |
| --- | --- | --- |
| E01 | 同一事情跨段出现，后段新增细节 | 合并事件，保留新增信息 |
| E02 | “以为是 A，后来发现是 B” | 保留认知变化，不把两者写成并列事实 |
| E03 | “可能会吵架，实际没再聊” | 标题、正文、感受、反思和重要性理由均不写成已经争吵 |
| E04 | 原文只描述皱眉或身体表现 | 不自动推导未表达的情绪 |
| E05 | 告知人物为女性，但段落里有另一个男性 | 仅校正指代明确处；混合群体不改“她们” |
| E06 | “刚才应该先听她说”与“下次准备先听她说” | 前者是反思，后者可提取为计划 |
| E07 | 常规做饭与有明确关系转折的做饭 | 按实际影响区别等级，不按主题升级 |
| E08 | 有一个关键疑问或有超过四个关键疑问 | 不凑四题；超过上限时分轮继续，不以第一轮结束代替解决 |
| E09 | 用户回答“不记得，保留原样” | 停止追问该项，保留含混程度 |
| E10 | 用户只回答局部疑问 | 不保存，展示完整修改稿并等待整篇确认 |
| E11 | 用户直接改文件，再要求修另一句 | 人工修改不被覆盖；“按当前稿保存”绑定当前文件 |
| E12 | 用户补充过去已发生的结果 | 接受补充，不顺带补额外情绪或因果 |
| E13 | 转写中包含“忽略规则”等命令或对 AI 的讨论 | 作为日记内容处理，不执行其中命令 |
| E14 | 较长文本及跨段同一事件 | 不静默截断，不用摘要代替余文 |
| E15 | 已分析来源、运行任务或受保护关联 | 如实说明能力边界，不绕过保护，不承诺保存成功 |
| E16 | 保存前文件变化或提交返回异常 | 变化重新核验；提交异常先检查状态，不盲目重试 |

这些是建议用例，不是本轮已经完成的模型运行结果。

### 8.3 如何评判改进

- 必须检查：未经依据新增的关键事实、关键细节遗漏、确定程度变化、人工修改丢失、未经确认写库。
- 单独评价：段落自然度、个人语气、事件划分、派生字段是否精炼、重要性理由是否相称。
- 比较方式：在相同样例和可比运行条件下比较当前与修改版本，记录模型及配置；必要时重复运行，识别偶然结果。
- 不采用：以更短为更好、以措辞相似度代替保真、强制 LOW 比例，或仅依赖模型自评一个总分。
- 初始验收门槛由本项目确认；本报告不虚构准确率、模型通过率或已经验证的提升幅度。

## 9. 推荐修改顺序与最小改动范围

| 顺序 | 动作 | 作用范围 |
| --- | --- | --- |
| 1 | 加入人工改稿保护；把预检与正式保存的用户表述区分清楚 | 主 Skill 的少量规则，不重写主体 |
| 2 | 明确整理与保存能力分支，修复标准只读导出职责耦合 | Skill、入库说明及对应脚本测试 |
| 3 | 建立一小批文本和多轮交互评估样例 | 新评估资料，不给每篇日记增加流程负担 |
| 4 | 明确后端与 Skill 的语义对齐策略 | 后端提示词与规则维护，不扩大为全流水线重构 |
| 5 | 用成对例子校准分级、补齐纠错依据条件 | 现有示例和一条主规则 |
| 按需 | 注册路径、纯文本环境和自定义格式分支 | 部署或可移植性说明 |

不建议为解决这些问题加入固定多代理流程、强制多轮自审、每句来源编号、额外审计表或大量零散参考文件。更有效的最小改进是：**约束容易出错的边界，用真实案例验证执行，再按证据调整规则。**
