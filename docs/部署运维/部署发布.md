# 部署发布

> 核对日期：2026-10-29。依据当前 Dockerfile、启动脚本和代理配置整理。示例使用占位地址，各环境的真实配置独立维护。

## 1. 部署组成

| 文件或服务 | 职责 |
|---|---|
| [Dockerfile](../../docker/Dockerfile) | 构建前端、后端依赖和包含 Nginx 的应用镜像 |
| [start.sh](../../docker/start.sh) | 启动 Uvicorn、Nuxt 服务及 Nginx，监视子进程 |
| [应用内 Nginx](../../docker/nginx.conf) | 将 `/secret/` 转到 Nuxt，将 `/diary/` 转到后端 |
| `docker/docker-compose.prod.yml` | 本地维护的应用容器配置，Git 忽略 |
| `docker/docker-compose.infra.yml` | 本地维护的 PostgreSQL、MinIO、持久化目录配置，Git 忽略 |
| [外部网关配置](../../nginx/nginx.conf) | 单独部署的 Nginx 网关；根据环境拓扑启用 |

应用镜像包含 `backend/`、`skills/` 和前端构建结果。发布时保留 Skill 脚本，否则服务端固定 Skill worker 入口无法执行。

应用、数据库、对象存储分别管理。日常更新只更新应用；配置外部网关时，检查端口归属，避免网关和应用同时占用宿主机同一端口。

## 2. 发布前核对

1. 确认代码版本、目标架构、镜像标签和回退版本。
2. 核对数据库迁移与当前版本关系，记录已执行迁移；详见 [数据模型与迁移](../系统架构/数据模型与迁移.md)。
3. 备份需要保护的数据，并确认恢复所需的备份包主密钥可用。
4. 独立准备数据库、MinIO、签名与加密密钥、备份目录、`APP_ENV` 和 Skill API 的环境配置。
5. 确认容器可写备份目录，PostgreSQL 与 MinIO 数据目录有持久化存储。
6. 确认数据库已安装 pgvector；应用启动检查通过后再切换流量。

发布不包含自动迁移命令。`Base.metadata.create_all` 只创建缺失的 ORM 表，无法代替既有结构升级和历史数据处理。

## 3. 构建镜像

在项目根目录执行。示例目标为 x86 服务器：

```bash
docker buildx build --platform linux/amd64 -f docker/Dockerfile -t diary-platform:<版本> --load .
```

ARM 服务器按实际目标改用 `linux/arm64`。Dockerfile 的前端构建阶段使用构建机平台，运行镜像按目标平台构建。

构建配置见 [Dockerfile](../../docker/Dockerfile)，构建上下文排除项见 [Dockerfile.dockerignore](../../docker/Dockerfile.dockerignore)。

## 4. 选择一种镜像交付方式

部署目录先由维护者创建，并通过独立受控渠道交付目标环境的 Compose 和运行配置。示例：

```bash
scp docker/docker-compose.prod.yml <部署用户>@<服务器>:<部署目录>/docker-compose.prod.yml
scp docker/docker-compose.infra.yml <部署用户>@<服务器>:<部署目录>/docker-compose.infra.yml
```

这些文件包含各环境配置，上传前确认目标，保存时限制访问权限；每次发应用镜像不需要重新上传未变化的基础设施配置。

### 镜像仓库

```bash
docker tag diary-platform:<版本> <镜像仓库>/diary-platform:<版本>
docker push <镜像仓库>/diary-platform:<版本>
```

服务器的应用 Compose 使用该版本标签。仓库访问及传输配置由部署环境维护。首次使用自建仓库时，先部署并验证仓库存储、认证与传输，再确认构建机和服务器均可访问。镜像发布流程不包含自动创建仓库。

### 离线镜像包

```bash
docker save diary-platform:<版本> -o diary-platform-<版本>-amd64.tar
scp diary-platform-<版本>-amd64.tar <部署用户>@<服务器>:<部署目录>/
```

服务器加载：

```bash
docker load -i diary-platform-<版本>-amd64.tar
```

两种方式交付同一类应用镜像，选择其一即可。

## 5. 更新应用

以下命令在服务器部署目录执行，假设本地维护的 Compose 文件放在该目录。

先校验配置，不把展开后的认证值复制进日志或提交：

```bash
docker compose -f docker-compose.prod.yml config --quiet
```

镜像仓库方式：

```bash
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

离线方式加载镜像后运行：

```bash
docker compose -f docker-compose.prod.yml up -d
```

基础设施仅在首次部署或其配置变更时单独更新：

```bash
docker compose -f docker-compose.infra.yml up -d
```

日常应用更新保留 PostgreSQL 和 MinIO。停止基础设施时不要使用 `down -v` 删除数据卷。若启用外部网关，独立交付 `nginx/nginx.conf` 和本地维护的网关 Compose，在其自己的目录校验和更新：

```bash
scp -r nginx <部署用户>@<服务器>:<网关父目录>/
```

上传前检查目录内容。服务器进入网关目录，执行 `docker compose config --quiet` 和 `docker compose up -d`；保持上游地址、监听端口和应用部署拓扑一致。

## 6. 验证与回退

```bash
docker compose -f docker-compose.prod.yml ps
curl -I http://127.0.0.1/secret/
curl -I http://127.0.0.1/diary/docs
```

再核对登录、日记列表、目标功能和后台任务状态。HTTP 页面可访问只证明入口通畅，不能替代业务验证。

- 应用镜像回退：将 Compose 恢复到已记录的旧版本镜像，再运行 `up -d`。
- 数据库迁移与数据恢复单独评估；镜像回退不会撤销数据库结构或业务数据变更。
- 发布失败时检查应用启动日志、数据库迁移、环境标识和存储连通性，调试输出遵守 [开发约束](../../AGENTS.md)。
