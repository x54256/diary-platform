# 事件内容要点设计

## 1. 文档目的

本文档定义事件内容要点的生成结果、拆解规则、忠实重写规则和准确性校验标准。

事件内容要点用于将一篇较长的事件内容拆成若干容易阅读、定位和使用的内容单元，同时完整保留原事件表达的有效信息。

## 2. 数据来源与结果定位

事件内容要点的唯一事实来源，是用户完成修改和补全并点击分析时的事件内容。

原事件内容由日记系统完整保存，用于生成、校验和追溯。事件内容要点是知识图谱中事件实体的业务属性。

只有已经完成分析且重要性为“中”或“高”的事件生成事件内容要点，并进入第一层事实层。

## 3. 数据结构

事件内容要点是一个有序数组，每个数组元素称为“要点项”。

| 属性 | 含义 |
| --- | --- |
| 序号 | 要点项在当前事件中的顺序，从 1 开始递增 |
| 要点 | 用一句话说明该内容单元表达的内容 |
| 详细内容 | 对该内容单元对应原文的近乎无损忠实重写 |

表达示例：

```json
[
  {
    "序号": 1,
    "要点": "发现江西数据混乱并与童姐沟通",
    "详细内容": "查看江西数据时发现数据混乱并存在多个难以理解的问题，随后与童姐沟通确认。"
  }
]
```

要点项数量根据事件实际包含的内容单元确定，不设置固定数量。

## 4. 内容单元拆解规则

### 4.1 完整覆盖

事件内容中的全部有效信息都必须进入至少一个要点项，包括：

1. 人物及其行为。
2. 行为发生的原因和背景。
3. 事情的发展顺序与转折。
4. 具体结果和后续计划。
5. 明确表达的感受、判断和评价。
6. 推测及其确定性程度。

### 4.2 单元边界

当前已确认最终基线按完整主题组织、保留原文人称并忠实自然重写，具体实现遵循[实现设计方案](./系统设计/知识库/第一层事件要点提取技术方案.md)。以下类别拆分规则属于此前业务定义，当前基线不要求只因叙述从感受转向原因就拆项；完整主题规则优先。

一个要点项只表达一个语义完整的内容单元。以下内容分别建立要点项：

- 独立发生的行动或变化。
- 行动产生的明确结果。
- 与行动分离的心理反应。
- 对原因的个人推测。
- 对经历的进一步反思。
- 明确提出的后续计划。

同一行动的背景、过程和直接结果可以保存在同一个要点项中。事实、感受和个人判断需要分别表达，避免将主观判断写成客观事实。

### 4.3 顺序

要点项默认按照原事件内容的叙述顺序排列。调整相邻内容的顺序时，只能用于合并同一内容单元中分散的表达，不能改变事件的实际时间顺序和因果关系。

## 5. 要点生成规则

“要点”用于快速识别该内容单元，应满足以下要求：

- 使用一句完整、明确的话表达。
- 保留关键人物、行为或心理变化。
- 不增加原文没有的判断和因果。
- 不提高或降低原文的确定性程度。
- 原文表达推测时，要点中保留“认为”“推测”“可能”等含义。
- 避免使用无法从原文直接验证的抽象标签。

## 6. 详细内容忠实重写规则

详细内容对对应原文进行近乎无损的忠实重写。

### 6.1 允许的处理

- 删除“嗯、然后、反正”等不承载信息的语气词。
- 删除口吃、连续重复和无意义的转写噪声。
- 修正能够从上下文明确判断的转写错误。
- 调整语序和标点，使内容通顺。
- 合并同一内容单元中分散出现的句子。
- 指代对象明确时，将“他、这个事”等表达替换为具体人物或事情。

### 6.2 禁止的处理

- 补充原文没有表达的信息。
- 推测人物没有明确表达的动机、原因或结果。
- 将“可能、觉得、好像、不知道”等表达改成确定事实。
- 弱化或加强原文的情绪、判断和评价。
- 将他人的说法改写成已经验证的客观事实。
- 为了缩短文字而删除有意义的信息。
- 将相邻但没有明确联系的内容建立为因果关系。
- 使用外部知识修正或扩展事件内容。

原话本身具有特殊意义时，可以在详细内容中保留必要的原句，包括承诺、关键措辞和争议性表达。

## 7. 准确性与完整性校验

事件内容要点必须经过生成和核验两个阶段。

### 7.1 信息覆盖检查

在独立于生成的合并审核修正请求中逐句对照完整原文，检查有效信息是否在实际详细内容中保留。原句编号由程序提供，生成前不另行调用模型建立信息清单。存在未保留的有效信息时，结果不合格，必须补充或重写。

### 7.2 逐条准确性检查

每个要点项需要检查：

1. 每个陈述是否能够在原事件内容中找到依据。
2. 行为主体和涉及人物是否正确。
3. 他人陈述与个人判断是否保留了原有归属。
4. 确定事实、个人判断和推测是否得到区分。
5. 原文中的时间顺序是否改变。
6. 原文没有表达的因果关系是否被新增。
7. 数量、日期、地点和具体结果是否发生变化。
8. 原文的情绪和评价强度是否被弱化或加强。

核实审核意见后，实际存在错误的要点需要依据原事件内容修正并重新核验；候选与原文语义一致时保留原表达。

## 8. 处理流程

```text
分析后的事件内容
→ 按完整主题生成要点及忠实重写的详细内容
→ 独立请求双向对照原文，审核并修正
→ 发生修正后另一次请求独立复核，最多两轮
→ 保存候选及审核状态
→ 原文审阅确认后进入后续图谱处理
```

## 9. 完整示例

以下示例来源于“江西项目数据梳理与需求讨论”事件。

### 要点项 1

**要点：** 继续查看江西数据并发现多个问题

**详细内容：** 今天早晨到公司后，我继续查看江西提供的数据，想根据数据确定应该怎样设计数据库，才能更方便地实现需求。查看过程中，我越来越觉得这些数据很乱，也很难理解，存在很多需要确认的问题。

### 要点项 2

**要点：** 与童姐语音讨论数据和需求问题

**详细内容：** 我一开始在群里向童姐提问，但她回复得比较慢，于是询问她是否方便通过语音沟通。之后我们语音讨论了较长时间。沟通过程中，我认为童姐自己也没有把数据整理清楚，对数据中的一些内容也不完全清楚，但相关需求已经设计出来了。

### 要点项 3

**要点：** 田总加入前端相关问题的讨论

**详细内容：** 由于部分问题涉及前端，我将领导田总也拉进了讨论，三个人一起沟通了一些需要改动的内容。前端相关问题讨论结束后，因为此前的问题还没有全部问完，我继续向童姐询问其他问题。

### 要点项 4

**要点：** 田总在场时提问变得小心

**详细内容：** 继续询问问题时，我变得非常小心。我担心田总认为我能力太差，觉得我连这么简单的问题都听不明白，还需要继续询问，因此提问时特别小心翼翼。我认为自己可能已经在潜意识中真正把田总当成了领导。

### 要点项 5

**要点：** 推测此前的讨论经历影响了本次反应

**详细内容：** 此前讨论江西需求时，童姐讲解过一个地方的需求，但她的讲解没有让我听懂。我当时认为问题出在童姐没有讲清楚。讨论持续了一段时间后，田总以比较强势的方式加入，表示自己已经听懂了，并直接向我进行解释。我推测这次经历可能给自己留下了心理影响，从而使我在本次讨论中表现得格外小心，但不能确定这就是本次反应的原因。

### 要点项 6

**要点：** 反思自己为什么会畏惧田总

**详细内容：** 我认为这种小心和畏惧不是很好的反应，觉得该怎样沟通就应该怎样沟通，没有必要畏惧田总。我认为田总的资历不如我，能力也不如我，只是因为讨领导喜欢才成为领导，但他成为领导后仍然会让我产生畏惧。我由此想到，这可能就是权力带来的影响，有权力的人会让下面的人产生畏惧心理。不过，我也不能确定自己的反应是否就是由这个原因造成的。

### 要点项 7

**要点：** 基本完成数据梳理并准备开发接口

**详细内容：** 下午我继续处理江西数据，大体上已经将数据梳理清楚。按照当前进度，第二天可以开始对照需求文档开发接口。

## 10. 当前设计边界

- 事件内容要点只处理单个事件内部的信息拆解和忠实重写。
- 事件之间的关系按照《个人知识图谱实体模型》中的事件关系规则单独建立。
- 事件内容要点不生成新的实体类型。
- 事件内容要点不改变原事件内容，也不替代日记系统中的原始存储。
