# 知识库管理业务案例

> 用途：说明知识事件首版如何从日记触发、提取、恢复、发布和展示。案例用于解释规则，不作为固定模型输出样例。

## 1. 案例符号

| 符号 | 含义 |
|---|---|
| `D` | 日记 |
| `DE` | 结构化日记事件 |
| `T` | 知识沉淀任务 |
| `AE` | 正式知识事件 |
| `KD` | 日记成功沉淀记录 |

## 2. 单一完整事情

### 2.1 日记 D1

| 字段 | 内容 |
|---|---|
| 日记日期 | 2026-08-10 |
| 日记标题 | 知识库模型讨论 |
| 状态 | `analyzed` |

结构化事件 `DE1`：

| 字段 | 内容 |
|---|---|
| 标题 | 讨论知识库模型 |
| 正文 | 我与同事林舟讨论了日记平台的知识库。我提出使用时间、人物、事项和洞察组织知识，并以现有日记事件作为基础。讨论后，我发现一条现有日记事件经常包含多个不同的事情，因此知识库还需要拆出知识事件。我认为应当先确定概念边界，再考虑数据库设计。 |
| 感受 | 空 |
| 反思 | 应当先确定概念边界，再考虑数据库设计。 |

这些内容属于同一次讨论形成的连续认识和决定，上游将其整理为一个结构化事件，知识沉淀对应生成一个知识事件：

### 2.2 知识事件 AE1

| 字段 | 内容 |
|---|---|
| 标题 | 讨论知识库模型 |
| 事件内容 | `["我与林舟讨论日记平台知识库的基本模型，提出以现有事件为基础，通过人物、事项和洞察组织长期知识。讨论中明确结构化日记事件仍可能包含多个独立事情，因此上游整理需要识别事件边界；我认为设计顺序上应先确定概念边界，再进入数据库设计。"]` |
| 发生日期 | 2026-08-10 |
| 发生时刻 | 空 |
| 来源顺序 | 0 |

来源中虽然表达多个观点，但它们共同构成一次讨论的发展过程。

## 3. 上游将两件独立事情整理为两个事件

### 3.1 日记 D2

| 字段 | 内容 |
|---|---|
| 日记日期 | 2026-08-11 |
| 日记标题 | 买酱油后打游戏 |
| 状态 | `analyzed` |

结构化事件 `DE2`：

> 我先去打酱油，老板人挺好，多给了我一些。我给她 10 元，她找了我 2 元。

结构化事件 `DE3`：

> 买完酱油后，我回家和朋友打游戏。

上游已经将购物和打游戏整理为两个事件，知识沉淀分别生成一个知识事件。

### 3.2 知识事件 AE2

| 字段 | 内容 |
|---|---|
| 标题 | 去商店买酱油 |
| 事件内容 | `["我去商店买酱油，觉得老板人挺好，因为她多给了我一些；结账时我付了 10 元，她找给我 2 元。"]` |
| 发生日期 | 2026-08-11 |
| 发生时刻 | 空 |
| 来源顺序 | 0 |

老板的表现、我的判断、付款和找零共同构成购物过程，知识沉淀完整保留这些有回顾价值的信息。

### 3.3 知识事件 AE3

| 字段 | 内容 |
|---|---|
| 标题 | 回家和朋友打游戏 |
| 事件内容 | `["买完酱油后，我回家和朋友打游戏。"]` |
| 发生日期 | 2026-08-11 |
| 发生时刻 | 空 |
| 来源顺序 | 0 |

为了让事件能够独立理解，事件内容保留“买完酱油后”这一必要背景；该知识事件来源于 `DE3`。

## 4. 手动触发与任务状态

### 4.1 启动

用户打开 `D2` 详情页。系统确认：

- 用户拥有 `D2`。
- `D2` 已分析。
- 当前结构化事件有效。
- 尚无成功沉淀记录。
- 已配置独立 `knowledge` 模型。
- 当前用户没有其他活动知识任务。

用户点击“沉淀到知识库”，系统创建任务 `T2`：

```text
status       = QUEUED
current_step = VALIDATE_SOURCE
retry_count  = 0
thread_id    = T2.id
```

重复点击返回 `T2`，不创建第二个任务。

### 4.2 执行

```text
T2: QUEUED
  → RUNNING / VALIDATE_SOURCE
  → RUNNING / PREPARE_BATCHES
  → RUNNING / EXTRACT_BATCH
  → RUNNING / PUBLISH
  → SUCCEEDED
```

页面只显示“正在整理知识事件”，不展示节点、批次数量或百分比。

### 4.3 正式发布

发布事务同时完成：

1. 创建成功记录 `KD2`，`completed_stage=ATOMIC_EVENTS`。
2. 写入 `AE2` 和 `AE3`。
3. 把 `T2` 更新为 `SUCCEEDED`。

事务提交后，`PUBLISH` 节点返回，LangGraph 写入最终 checkpoint 并结束。worker 等整张图返回后清理 `T2` 的 checkpoint。任一步骤失败都会整批回滚，数据库中不会只存在 `AE2` 而缺少 `AE3`。

## 5. Token 分批与断点恢复

假设另一篇日记 `D3` 有 12 条结构化事件，装批后形成 3 个批次：

```text
批次 1：DE1 ～ DE5
批次 2：DE6 ～ DE9
批次 3：DE10 ～ DE12
```

执行过程：

1. 批次 1 成功，checkpoint 保存批次 1 结果和 `next_batch_index=1`。
2. 批次 2 成功，checkpoint 保存前两批结果和 `next_batch_index=2`。
3. 进程在批次 3 调用前中断，worker 租约随后过期。
4. 恢复器把同一任务重新置为 `QUEUED`。
5. 新 worker 使用相同 `task_id` 读取 checkpoint，直接调用批次 3。
6. 批次 1 和批次 2 不再次调用模型。

新 worker 使用新 `run_token`。旧 worker 即使稍后收到模型响应，也必须在返回节点结果前发现令牌或租约已经失效，因此不能写入 checkpoint。

一个结构化事件始终完整放在同一批。单个事件本身超过预算时独立形成一个超长批次，不截断内容。

## 6. 失败与重试

### 6.1 模型输出结构错误

模型第一次返回带 Markdown 包装或字段缺失的 JSON：

1. 程序使用现有 JSON 修复提示词重试一次。
2. 修复结果合法时保存该批 checkpoint 并继续。
3. 修复后仍不合法时，`T2` 进入 `FAILED`，错误码为 `MODEL_OUTPUT_INVALID`。
4. 用户点击重试后，同一 `T2` 重新排队，`retry_count + 1`，从失败批次继续。

### 6.2 来源变化

任务失败后，用户修改了结构化事件，结构化修订号发生变化：

1. 原任务不能沿用旧冻结输入发布。
2. 原任务以 `SOURCE_CHANGED` 保持失败状态。
3. LangGraph 退出后，worker 在图外清理旧 checkpoint；节点内部不执行清理。
4. 日记页面允许基于当前来源发起新任务。

### 6.3 发布后中断

发布事务已经提交，但进程在 LangGraph 返回和清理 checkpoint 前中断：

1. `T2` 和正式数据已经在同一事务中提交为成功，不会被作为过期 `RUNNING` 任务重新领取。
2. 启动时或定时清理器发现 `T2.status=SUCCEEDED` 且 `checkpoint_cleaned_at` 为空。
3. 清理器幂等删除 `T2` 的 checkpoint，并写入清理时间。
4. `AE2` 和 `AE3` 保持不变，不再次执行发布。

## 7. 列表与详情展示

以下字符图只表示卡片内容层级。实际页面与日记管理一致占满可用内容区，卡片随视口宽度伸缩。

### 7.1 知识库列表

`AE2` 和 `AE3` 都发生于 2026-08-11，系统继续使用发生时刻、写入时间和 ID 形成稳定顺序。卡片内容示例：

```text

│ 8月11日                       │
│ 回家和朋友打游戏               │
│ 买完酱油后，我回家和朋友打…   │
│ 来自《买酱油后打游戏》         │
└────────────────────────────────┘

┌────────────────────────────────┐
│ 8月11日                       │
│ 去商店买酱油                   │
│ 我去商店买酱油，觉得老板人…   │
│ 来自《买酱油后打游戏》         │
└────────────────────────────────┘
```

列表每次加载 20 条，滚动到底继续加载。事件内容最多显示三行。

### 7.2 知识事件详情

用户打开 `AE2`，页面展示：

1. “去商店买酱油”和发生日期。
2. 完整事件内容。
3. 来源日记《买酱油后打游戏》的入口。

来源日记标题通过 `diary_id` 动态查询，不复制到知识事件。模型文字始终按纯文本展示；合法时间标签只显示标签内文字。

## 8. 模型未配置

管理员尚未设置 `knowledge` 模型时，日记详情页显示：

```text
┌──────────────────────────────┐
│ 请先配置知识模型             │
│ [沉淀到知识库]（禁用）       │
└──────────────────────────────┘
```

系统不自动使用 `analysis`、`organize` 或 `review` 模型代替知识模型。

## 9. 案例体现的规则

- 事件拆分由上游完成，知识沉淀不拆分或合并事件。
- 同一事情的过程、交流、判断、结果和必要背景合并表达。
- 每个知识事件只来源于一个结构化事件，一个结构化事件严格对应一个知识事件。
- 事件内容使用自然段数组，并能够脱离原文独立理解。
- 首版只做结构校验，不做第二次 AI 语义审核。
- 每个批次完成后形成 checkpoint，中断后跳过已完成批次。
- `run_token` 不从 checkpoint 恢复，过期 worker 不能提交迟到的模型结果。
- 正式事件与成功记录在同一事务中写入。
- 成功 checkpoint 在 LangGraph 返回后清理，进程中断时由后台清理器补偿。
- `completed_stage=ATOMIC_EVENTS` 为后续阶段留下升级入口。
- 知识库首版只展示知识事件列表、详情和来源日记。
