# 知识库管理需求规格

> 功能状态：事件知识能力已实现，待并入首次日记分析管线
> 需求基线：2026-08-31 已确认方案
> 首版范围：用户对 `organized` 日记首次执行 AI 分析时，系统为全部结构化事件自动生成只读事件知识，并提供事件列表、详情和关系图入口。

## 1. 功能目标

知识库把结构化日记事件整理为能够脱离来源独立理解和回顾的事件知识。事件知识同时作为事件关系图谱的节点。

事件知识生成不再是独立的“知识沉淀”操作，而是首次日记分析的必经阶段。用户无需再次点击“沉淀到知识库”。

## 2. 范围与边界

### 2.1 纳入范围

- `organized` 日记首次执行 AI 分析时自动生成事件知识。
- 当前日记的全部结构化事件都进入生成范围，不按 `HIGH / MEDIUM / LOW` 重要性过滤。
- 每个结构化事件严格生成一个事件知识。
- Token 超长时按完整结构化事件分批调用模型。
- 保真凝练、`coverage` 覆盖对照、二次模型复核和结构校验。
- 关系识别已定位的原文证据作为凝练强制保留项。
- 事件知识列表、详情、来源日记入口和单事件关系图入口。

### 2.2 移除和废弃

- 移除日记详情中的“知识沉淀”卡片与“沉淀到知识库”按钮。
- 移除未沉淀、沉淀中、沉淀失败、已沉淀等独立页面状态。
- 不再创建或运行独立知识任务、事项升级任务和逐篇沉淀补偿流程。
- 事项匹配、事项全览更新和事项归属停止运行。相关表、接口、页面和代码保留为只读遗留能力，并标记废弃；新分析不新增、归属或更新事项。
- 事件知识向量及 `knowledge_atomic_events.embedding` 不再参与新流程，相关逻辑保留并标记废弃。

### 2.3 不提供

- 事件知识人工编辑、删除、合并或撤回。
- 事件知识历史版本和恢复。
- 人物、洞察或事项的新增沉淀阶段。
- AI 伙伴读取知识库。
- 存量已分析日记补跑。

## 3. 来源边界

- 事件知识的业务来源是当前日记的结构化事件。
- 凝练模型输入只包含事件标题、完整 `body`、日记日期和当前事件的强制保留关系证据。
- 日记原始全文、日记级摘要、感受、反思、分析结果和行动建议不作为凝练输入。
- 一个事件知识只能来源于一个结构化事件，不跨事件合并。
- 一个结构化事件中可包含多个可关联内容，但不因关联数量拆分事件知识。
- 结构化日记至少包含一个事件；任一事件的标题和正文全部为空时，首次分析不得启动。

## 4. 事件知识

### 4.1 定义与对应关系

事件知识是一件能够脱离其他内容独立理解和使用的完整事情。事件拆分由上游日记整理完成，知识生成不再拆分或合并事件。

每个来源结构化事件与事件知识保持 1:1 对应，该对应同时用于将来源事件间的临时关系映射为事件知识间的正式图谱边。

### 4.2 字段

| 字段 | 需求 |
|---|---|
| 标题 | 不超过 20 个字符，具体说明发生了什么 |
| 事件内容 | 非空字符串数组，每个元素是一个自然段；无固定长度，能够独立理解和回顾 |
| 发生日期 | `YYYY-MM-DD` |
| 发生时刻 | 能够确定到小时和分钟时使用 `HH:mm`，否则为空 |

### 4.3 内容保真

- 保持来源叙述视角、实际说话者、主体归属和原始顺序。
- 保留所有增加新语义的行为、事实、状态、观点、感受、判断、计划、原因、条件、转折、结果、时间、数字、对象和方案。
- 只可删除完全重复的表达、不承载语义的口头填充和明确已纠正的口误。
- 已执行但没有明确结果的行为不能补写结果；决定、承诺和计划不能改写为已执行或完成。
- 担忧、期待、感悟、判断和主观看法不能改写为客观事实、确定因果或实际结果。
- 来源存在歧义、矛盾、错误或缺失时保留原表达，不自行解释或裁定。
- 事件内容不输出 `<time>` 标签，保留标签内用户原本的自然时间说法。

### 4.4 关系证据与全量覆盖

- 关系识别在凝练之前完成，并为当前事件输出 `body_index + source_quote`。
- 每条当前事件关系证据都是凝练的强制保留项。
- 关系证据不是事件知识的全部内容边界。凝练结果仍须通过 `coverage` 覆盖对照，为原文每项独立信息提供保留表达或合法删除说明。
- `coverage` 不得存在未保留且未命中口头噪音封闭清单的信息。
- 二次模型复核必须同时检查遗漏、新增、主体变化、确定程度变化、完成状态变化和关系证据丢失。

### 4.5 时间

- 发生日期和时刻表示标题及事件内容所表达的核心行为、结果或决定实际发生的时间。
- 计划执行时间、截止时间和预约时间只保留在事件内容中。
- “今天”“昨天”等相对日期依据日记日期换算。
- 核心日期无法确定时使用日记日期；模糊时段或冲突时刻不写入发生时刻。

## 5. 触发与执行

### 5.1 触发条件

只有同时满足以下条件时才进入事件知识生成：

- 当前用户拥有该日记。
- 日记处于 `organized` 状态。
- 用户首次点击“AI 分析”。
- 结构化日记包含有效事件。
- 分析管线需要的分析、知识凝练、知识复核和 embedding 模型配置完整。

`analyzed` 日记的“重新分析”不进入事件知识生成，不新增或重建事件知识。

### 5.2 执行流程

1. 冻结本次结构化事件、来源修订和模型配置。
2. 关系识别完成后，汇总每个当前事件的强制保留证据。
3. 按 Token 预算将完整结构化事件划分批次。
4. 逐批执行保真凝练、`coverage` 校验和 JSON 结构校验。
5. 将原文、候选结果和强制保留证据交给复核模型，逐批修正。
6. 汇总当前日记的全部事件知识。
7. 继续执行核心分析、认知分析和行动项规划。
8. 在首次分析的最终发布事务中写入全部事件知识。

### 5.3 分批与恢复

- 一个结构化事件不能拆到两个批次。
- 单个事件本身超过预算时，仍作为独立批次完整传入。
- 每个批次完成后保存分析管线 checkpoint。
- 进程中断或任务执行权过期后，从未完成批次继续，已完成批次不重复调用。
- 模型临时错误按系统全局次数重试当前批次；JSON 结构错误最多使用一次修复提示词。
- 结构化来源修订变化时旧任务失效，旧 checkpoint 被清理。

## 6. 统一发布与一致性

- 事件知识不单独提交。
- 标签、分析结果、行动项、事件知识、统一检索向量、正式关系、LOW 候选关系和日记 `analyzed` 状态必须在一个数据库事务中提交。
- 任一模型调用、结构校验、向量化或发布失败时，本次不留下任何正式结果。
- 每个来源事件必须恰好对应一个事件知识；任一缺失、重复或顺序不连续都阻止发布。
- 发布节点重复执行不能重复创建事件知识或关系边。
- 成功发布后，来源原文和结构化 `title + body` 不得修改或重新整理，以保证知识内容、检索向量和图谱证据一致。
- 成功发布后允许重新分析，但重新分析不修改事件知识、检索向量或图谱关系。
- 任务完成后清理 checkpoint；清理失败由后台清理器补偿，不影响已提交结果。

## 7. 页面需求

### 7.1 导航与风格

- 保留底部导航“知识”入口及 `/knowledge` 页面。
- 页面沿用现有白色背景、圆角描边卡片和主色操作按钮。
- 知识页面容器统一为 `max-w-md`，以《日记事件关系图谱需求规格》的最新宽度基线为准。
- 按钮和链接点击区域高度不小于 44px。

### 7.2 日记详情

- 不再展示知识沉淀卡片、沉淀状态或沉淀操作。
- 事件知识生成进度纳入底部“AI 分析”的统一进度展示。
- 首次分析成功后进入分析页签，不额外弹出知识成功提示。

### 7.3 事件知识列表

- 每次加载 20 条，按发生日期、发生时刻、写入时间和 ID 倒序稳定排列。
- 滚动接近底部时自动加载下一页。
- 卡片展示发生时间、标题、最多三行事件内容和来源信息。
- 来源信息统一为“日记日期 ·《日记标题》· 对应的结构化事件标题”。
- 有正式关系的事件知识显示“图谱”按钮和关系数角标；无正式关系时不显示。

### 7.4 事件知识详情

- 展示标题、发生时间、完整事件内容和来源日记入口。
- 来源入口显示“日记日期 ·《日记标题》· 对应的结构化事件标题”。
- 模型文本按纯文本转义，不得作为 HTML 执行。
- 有正式关系时提供单事件关系图入口。

### 7.5 遗留事项页面

- 现有事项列表、详情与事件所属事项展示保留为只读遗留能力。
- 页面不再提供“整理事项”、升级或重试入口。
- 空数据时只展示空态，不再提示“沉淀新日记后自动生成事项”。

## 8. 权限、隐私与日志

- 首次分析任务、事件知识和关系边都以当前用户为边界。
- 用户只能查看自己的事件知识、来源日记和关系图。
- 模型请求正文和原始响应写入现有 AI 交互日志，每条最多保留前 2000 个字符，超长时同时记录原始长度。
- 认证头、API Key、日记完整原文和事件知识不得进入普通日志、指标标签或错误响应。
- checkpoint 按敏感数据处理；不保存解密后的 API Key。

## 9. 存量与重新分析

- 不对已处于 `analyzed` 状态的日记补生成事件知识。
- 重新分析不补生成或更新事件知识。
- 旧知识、旧事项和旧知识任务数据由用户在上线前通过独立 SQL 手动清理。
- 新流程不提供兼容迁移、自动清理或存量补跑。

## 10. 验收标准

- `organized` 日记首次分析时，全部结构化事件都生成且只生成一个事件知识。
- 日记详情不再展示独立知识沉淀入口、状态或重试操作。
- 事件知识输入只使用标题、`body`、日记日期和强制保留关系证据。
- 每条关系证据在事件知识中都有对应表达。
- `coverage` 覆盖原文全部独立信息，二次复核能修正遗漏、新增和语义状态变化。
- 任一事件知识生成、校验、复核或发布失败时，标签、分析、行动项、知识、向量、关系和日记状态全部不发布。
- 首次分析中断后从未完成 checkpoint 继续，已完成的模型批次不重复调用。
- 事件知识列表、详情、来源日记跳转和图谱入口可用。
- `analyzed` 日记重新分析时不新增或重建事件知识。
- 不运行事项匹配，不为新事件写入 `matter_id`。
- 列表按发生时间稳定分页，模型文本不作为 HTML 执行。
- 所有任务、事件知识和关系查询都执行用户所有权校验。
