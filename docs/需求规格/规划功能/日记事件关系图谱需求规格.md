# 日记事件关系图谱需求规格

> 功能状态：未实现（二轮试点验证已通过，待排期实现）
> 需求基线：2026-08-31 已确认方案（二轮试点终验 + 分析管线整合方案）
> 首版范围：用户对 `organized` 日记首次执行 AI 分析时，为全部结构化事件同步生成事件知识、统一 `body` 检索向量和五类直接关系边，并提供单事件关系图可视化探索页。不补跑存量已分析日记，不引入语义内容块实体。

## 1. 需求背景与目标

### 1.1 需求来源

用户在 2026-07-21 日记事件《对日记管理平台关联分析功能的思考》中提出（逐字保留）：

> “每天日记中的事件和前面有些是有关联的，可通过 tag 标签或限定范围的向量检索挖关联”

现状数据中事件间联系的已有承载机制均不完整：`event_tags` 只能表达主题相似，`diary_action_event_links` 只固化行动项与事件的关联，`knowledge_matters` 又将一个事件限制为最多归属一个事项。一个事件中的不同内容可分别支撑它与多个其他事件建立关系，现有机制无法准确表达。

### 1.2 目标

为日记事件建立关系图谱，让事件间千丝万缕的联系显性化。

图谱的长期用途包括可视化探索、增强搜索与问答、辅助回顾与凝练。首版交付范围为关系建立、存储和单事件可视化探索；搜索、问答和定期回顾的图谱消费方式在各自功能进入实施时另行定义。

## 2. 核心需求（第 1 步确认）

| 决策项 | 确认结论                                       |
|---|--------------------------------------------|
| 长期用途（多选） | ① 可视化探索；② 增强搜索与问答；③ 辅助回顾与凝练；首版实现①                |
| 节点粒度 | 图谱节点统一为事件知识（`knowledge_atomic_events`），边端点引用事件知识 ID。每个事件知识与一个来源结构化事件 1:1 对应；一个事件可因原文中的不同内容与多个其他事件建立事件级关系 |
| 来源分工 | 来源结构化事件的 `title + body` 用于关系判定与证据追溯；事件知识用于图谱节点展示与后续消费 |
| 建立时机 | 仅在 `organized` 日记首次点击“AI 分析”时建立；`analyzed` 日记的重新分析不新建、不重建图谱 |
| 事件范围 | 当前日记的全部结构化事件，不按重要性过滤 |
| 关系深度 | 仅建直接关系边；多跳遍历在查询时做，不预建传递边                   |

## 3. 类型体系（第 2、3 步确认，最终五类）

### 3.1 判定流（原则）

任意两事件判定关系时，先判同事项 / 跨事项：

1. **同一事项三问测试**通过 → `CONTINUATION` 事项延续。
   - 问 1 同一性：指向同一具体目标、问题、任务或处理过程，且实际对象 / 经历者一致；
   - 问 2 推进性：事实层有实际推进，纯心理反刍不算推进；
   - 问 3 参照性：三问测试仅支持证据，不引入推测。
2. **跨事项**时按下列顺序判定：
   - 事实层直接引发 → `CAUSAL` 因果；
   - 情绪/认知唤起（“让我想起”）→ `ASSOCIATION` 联想共鸣（有向：想起方 → 被想起方）；
   - 仅共享主题，且后事件有新推导 / 新呼应 → `THEMATIC` 主题（兜底类型）;
   - 跨事项实质引用（条件 / 筹码 / 时间节点 / 理由 / 对比对象）→ `REFERENCE` 弱引用。

### 3.2 五类边定义

#### 3.2.1 CONTINUATION 事项延续

- **定义**：同一事项在时间上的事实层推进，含“计划 → 执行”闭环。
- **方向**：时间先后（先事件 → 后事件）。
- **判定标准**：同一事项三问测试全部通过；推进必须发生在事实层。
- **反例边界**：纯心理反刍、重复叙述不构成推进（见 THEMATIC 反例）；实际对象或经历者不同时属于不同事项，不建 CONTINUATION 边。
- **真实例子**：预约牙医 → 补牙（试点 N1、N2：07-21《跟进牙齿问题并预约牙医》→ 07-30《牙医补牙及检查》，计划的执行验证）。

#### 3.2.2 CAUSAL 因果

- **定义**：跨事项，前事件在事实层直接引发后事件。
- **方向**：引发方 → 被引发方。
- **判定标准**：原文归因成立（有明确的引发关系表述或事实链条），且两事件分属不同事项。
- **反例边界**：仅时间相邻但无引发关系不建；同事项内的推进归 CONTINUATION 而非 CAUSAL（如试点 E10 改判）。
- **真实例子**：母亲确诊 → 劝父看腰（试点 N22：08-05 母亲确诊甲亢 → 08-07 劝父就医，母亲“拖成大病”的确诊冲击直接催生劝父“别把小病拖成大病”的行动）。

#### 3.2.3 ASSOCIATION 联想共鸣

- **定义**：情绪或认知唤起，一事件让人想起另一事件。
- **方向**：有向，想起方 → 被想起方。
- **判定标准**：存在唤起关系（显式唤起标记如“让我想起”，或经确认的情绪/记忆唤起）。
- **反例边界**：无唤起关系的主题相似归 THEMATIC；事件内部唤起的环节不建边，记为事件自注释（见 §11 后续完善）。
- **真实例子**：饭局裁员降薪 → 想起与德华聊第二职业（试点 N25：08-26 饭局中听到裁员降薪的危机感，唤起对 08-25 与德华讨论第二职业的记忆；原文无显式唤起标记，唤起归因来自用户校验，置信度 MEDIUM）。

#### 3.2.4 THEMATIC 主题（兜底）

- **定义**：跨事项仅共享主题，且后事件产生新推导或新呼应。
- **方向**：时间先后。
- **判定标准**（准入双条件）：① 主题可命名；② 后事件有新推导 / 新呼应。两者缺一不建边。
- **反例边界**：事项叙述中复述旧话不算新呼应，不建边（用户以试点 E13 案例确认：H1→H5 仅是复述，删除）。
- **真实例子**：李海东案例再反思（试点 N17：与小廖沟通离职 → 反思李海东案例，“通过李海东的案例，认识到即使能力不突出，勇敢走出去也可能找到不错的机会”，主题“离职观”可命名且后事件产生新反思）。

#### 3.2.5 REFERENCE 弱引用

- **定义**：跨事项，一事件被另一事件实质引用（作为条件、筹码、时间节点、理由或对比对象）。
- **方向**：引用方 → 被引用方。
- **判定标准**：被引用事件在引用语境中承担实质角色才建边；顺带一提不建。
- **反例边界**：仅提及名称而无实质角色不建边。
- **真实例子**：墨西哥投标在离职谈判中被引用为时间节点（试点 N26：08-17 与 CEO 离职谈判 → 08-06 墨西哥投标演示，方向为引用方 → 被引用方）。该边界案例是促成新增 REFERENCE 类型的直接依据，用户已最终裁定 N26 改判 REFERENCE（实质角色成立）。
- **展示层规则**：弱边，默认收起、降权展示。

### 3.3 关键规则

1. **同一对事件只建一条边**：在同一用户内，将两个端点视为无序事件对执行唯一性约束，关系方向由边类型和 `source` / `target` 保存；禁止建立起点与终点相同的自环边。
2. **“计划 → 执行”不独立成类**，并入 CONTINUATION 的闭环属性（闭环状态 + 计划来源，见 §4.1）。
3. **THEMATIC 准入**：主题可命名 + 后事件对新推导 / 呼应；事项叙述中复述旧话不建边（用户用 E13/E16 案例确认）。
4. **REFERENCE 准入**：实质角色才建，顺带一提不建；展示层降权（弱边 / 默认收起）。

## 4. 边属性与数据模型

### 4.1 边属性

| 属性 | 说明 | 约束 |
|---|---|---|
| 所属用户 | 边的数据边界 | **必填**；`user_id` 必须与两端知识原子事件的所属用户一致 |
| 方向 | 边端点顺序 | 按类型定义（ASSOCIATION 为想起方 → 被想起方） |
| 类型 | §3 五类之一 | 必填 |
| 关系状态 | `CONFIRMED` / `CANDIDATE` | 必填；HIGH、MEDIUM 直接为正式边 `CONFIRMED`，LOW 为待人工确认候选 `CANDIDATE` |
| 闭环状态 | 无 / `EXECUTED` / `EXECUTED_FAILED` | 计划 → 执行类 CONTINUATION 边属性 |
| 计划来源 | 本人 / 第三方 | 计划类边属性（如医嘱来源 = 第三方医生） |
| 置信度 | `HIGH` / `MEDIUM` / `LOW` | 必填；LOW 候选写入边表但不进入图谱查询结果，人工确认后转为正式边 |
| 证据 | 关系双方的来源结构化事件 ID、`body` 数组下标和原文连续引用 | 必填；判定依据须可回溯到原文 |
| 判定理由 | 说明关系类型成立的直接依据 | 必填 |
| 来源 | 建边来源（首次分析 / 人工确认） | 必填 |
| 时间基准 | 原子事件 `occurred_on` | 因事件日期 ≠ 发生日期（回溯叙述普遍），统一采用 `occurred_on`；试点实测：第二职业事件记于 08-26，实际发生于 08-25 |

### 4.2 存储方案

- 采用 **PostgreSQL 边表**存储，不引入专用图数据库。
- 拒绝图数据库的理由：数据规模为数千级、查询深度仅 1~2 跳、引入图库徒增运维负担、边表与图模型同构（未来需要时可平滑迁移）。
- 边表同时存储正式边与 LOW 候选，核心字段对应 §4.1 属性：`user_id`、`source`、`target`、`type`、关系状态、子状态、置信度、证据等。
- 数据库层必须保证两端事件与边的 `user_id` 一致、同一用户下无序事件对唯一，并禁止 `source = target`。

### 4.3 统一事件检索向量

- 向量归属来源结构化事件，不归属事件知识。
- 向量文本只使用 `body`，不包含标题、感受、反思或分析结果。
- 每个事件生成一个完整 `body` 向量，并为 `body` 的每个自然段生成一个辅助向量。
- 同一套向量同时供图谱候选召回和统一语义搜索使用。
- 向量仅在首次分析管线内生成，不由每日定时任务生成或补算。
- `knowledge_atomic_events.embedding` 及事项匹配中的事件知识向量不再参与新流程。

## 5. 建图与分析流程

### 5.1 流程总览

1. 校验权限、日记状态和结构化来源，冻结本次来源版本与模型配置。
2. 提取日记元数据、心情和事件标签，结果仅保存在任务状态中。
3. 为每个事件的完整 `body` 和各自然段生成统一检索向量。
4. 对当前日记内全部事件组成的无序事件对各判断一次。
5. 为每个当前事件召回历史来源事件，并完成关系判定与双方证据定位。
6. 使用当前事件一侧的关系证据约束事件知识凝练，再执行全量覆盖检查和二次复核。
7. 继续执行核心分析、认知分析和行动项规划。
8. 将标签、分析结果、行动项、事件知识、检索向量、正式关系和 LOW 候选关系在一个事务中统一发布，然后将日记置为 `analyzed`。

任一步失败时，本次不发布任何正式结果；任务通过 checkpoint 从未完成节点继续，已完成的模型步骤不重复调用。

### 5.2 技术检索分块与事件级关系

- 不识别、不持久化、不展示独立语义内容块。
- `body` 自然段只是向量检索的技术分块，不是业务实体，不作为图谱节点。
- 关系建立全部在事件级完成。一个事件可因原文中的不同内容与多个其他事件建立多条边。
- 关系模型读取关系双方完整的 `title + body`，不根据向量或事件知识直接下结论。
- 模型为关系双方各输出 `body_index + source_quote`，关系发布后仍使用来源原文作为证据。

### 5.3 历史候选召回

- 当前事件的完整 `body` 向量和每个自然段向量分别召回 Top-5。
- 合并、去重后使用事件标签加权，再按每个候选的最高相似度重排。
- 每个当前事件最多保留 15 个历史候选，一次模型调用完成该当前事件与所有候选的判定。
- 召回当前用户的全部历史，不设时间截断或时间衰减。
- 历史候选是来源结构化事件；候选必须已有 1:1 对应的事件知识，以便发布正式图谱边。
- 当前日记内的事件对不受候选上限影响，每个无序事件对只判定一次，关系方向由模型输出。

### 5.4 召回策略依据与回归要求

饭局 → 第二职业案例（N25）的召回可行性量化验证结论：

| 召回路径 | 实测结果 | 结论 |
|---|---|---|
| 纯标签召回 | 两事件标签零交集（仅共享 工作/domain） | **失败，不可行** |
| 纯相似度阈值 | 旧原子事件向量余弦仅 0.3575（弱相关），阈值法（如 >0.5）会漏召 | **会漏** |
| Top-K 近邻 | 使用旧原子事件向量时互为 Top5 近邻（第 2 位 / 第 4 位，0.358） | **可达**（K≥4，从第二职业侧召回更稳） |

旧试点证明 Top-K 近邻比固定相似度阈值更适合发现弱相关关系，但其数值来自旧原子事件向量，不能作为纯 `body` 向量的效果依据。实现阶段必须使用最终 embedding 模型和纯 `body` 多向量重放 N25；饭局事件召回第二职业事件并进入每事件最多 15 个候选，才算通过召回回归。

结论：实时管线采用「来源事件 `body` 多向量 Top-K + 标签加权」的混合召回，不使用固定相似度阈值作为准入条件。

### 5.5 关系证据对事件知识的约束

- 关系判定在事件知识凝练之前完成。
- 对当前日记中的每个事件，该事件一侧的全部关系证据都作为其凝练强制保留项，不得丢失或改变状态。当前日记内部关系的双方都按此规则分别约束各自的事件知识。
- 关系证据不是凝练的唯一保留范围；现有 `coverage` 覆盖对照与二次复核继续检查原文的全部独立信息。
- 发布时将来源事件间的临时关系映射为事件知识间的正式边。

### 5.6 计划执行识别与低置信度

- 历史事件中包含计划，且当前事件对该计划提供明确执行或执行失败证据时，建立 CONTINUATION 边并记录闭环属性。
- 图谱不为尚未出现回声的计划建立关系。
- 无显式唤起标记的联想边：以情绪标签簇作为触发信号（具体识别算法见 §12 未解决）。
- HIGH、MEDIUM 判定作为正式边入图。
- LOW 判定作为候选写入边表，不返回给图谱查询接口；人工确认后将关系状态从 `CANDIDATE` 改为 `CONFIRMED`，再进入图谱。

## 6. 计划执行关系

- 计划仅作为历史事件内容，不在图谱中建立独立计划实体。
- 没有后续事件证据时不建边，不由“未发现记录”推断计划未执行。
- 后续事件明确记录计划已执行时，边的闭环状态为 `EXECUTED`；明确记录已尝试但执行失败时，状态为 `EXECUTED_FAILED`。
- 日记行动项和日程继续由行动管理功能承载；图谱不创建、同步或维护行动项及待办状态。

## 7. 可视化探索需求（v2.1，用户已确认）

### 7.1 形态

单事件关系图页面（路由建议 `/knowledge/events/[id]/graph`）；一期不做全局图谱模式。

### 7.2 入口

知识页面事件列表卡片上，有关系的原子事件显示“图谱”按钮 + 关系数角标（如“关联 3”），无关系的不显示；列表接口需返回关系数。

### 7.3 页面结构（自上而下）

- **sticky 头部**：返回 + 事件标题（截断）；
- **筛选 chips**：横向滑动、多选、带计数，选项为 全部/延续/因果/联想/主题/弱引用；筛选结果上下联动（拓扑概览中未选类型边淡出、列表同步过滤）；
- **拓扑概览**：固定高度约 30% 屏，手写 SVG 实现、不引入图形库，小圆点 + 彩色边，中心点实色放大；每条边使用箭头明确表示 `source → target` 方向；点圆点 = 下方列表定位高亮（不切换中心）；
- **关联列表**：复用现有白底圆角卡片样式，卡片含 类型徽章 + 方向（当前事件 → 关联事件，或关联事件 → 当前事件）+ 日期 + 事件标题 + 证据摘要；操作按钮"以它为中心"（二步可逆操作）与"详情"（跳转现有事件详情页）。

页面整体结构示意（线框图，单事件关系图页）：

```text

│ ←  「陪母亲检查…确诊甲亢危象」         │ ← sticky 头部
├────────────────────────────────────┤
│ (全部5)(●延续3)(●因果1)(联想1)(主题)→│ ← 筛选 chips 横滑
├────────────────────────────────────┤
│            ○━━━●━━━○               │
│           ╱    ┃                   │ ← 拓扑概览 30dvh
│          ○     ○   （未选类型边淡出）│    点圆点=下方定位高亮
├────────────────────────────────────┤
│ ━━因果 08-07 劝说父亲就医            │
│ 证据："别把小病拖成大病…"             │
│              [以它为中心] [详情]      │ ← ≥44px 按钮
│ ──延续 08-05 商讨治疗方案            │
│              [以它为中心] [详情]      │
└────────────────────────────────────┘
```

### 7.4 边视觉约定

延续/因果/联想/主题/弱引用五色区分；弱引用虚线。图谱仅展示关系状态为 `CONFIRMED` 的正式边，LOW 候选不出现在图中。

### 7.5 空态

单事件无边提示“该事件暂无关联”；筛选无匹配提示“无符合筛选的关系”。

### 7.6 触控与移动适配

- 全程仅点按，无拖拽缩放；
- 所有触控目标 ≥44px（chips 视觉 32px、触控区 44px）；
- 本页无输入控件；未来若加搜索，须遵守移动端字号 ≥16px 约束。

### 7.7 实施约束

- 知识页面容器统一为 `max-w-md`（当前为 `w-full`，需同步修改前端契约测试 `knowledge-contract.test.ts`）；本约束是知识页面宽度的最新需求基线，替代《知识库管理需求规格》中的全宽容器约束；
- 后端新增图谱查询接口（节点 + 边、支持类型过滤参数），前端新增图谱视图组件；
- 后端当前无任何图谱接口，均为新开发。

### 7.8 存量边界

- 不对已处于 `analyzed` 状态的存量日记执行事件知识生成、向量化或建图。
- 存量日记的“重新分析”只更新分析结果，不补建图谱。
- 功能上线后，只有从 `organized` 状态首次进入分析管线的日记进入图谱。
- 旧知识数据由用户在上线前通过独立 SQL 手动清理；新流程不承担旧知识、旧事项和旧知识任务的数据兼容或迁移。

## 9. 语义归一化与用户隔离

- **别名识别**：关系判定时须识别同一人物的不同称谓。实例：媳妇/颂梅/小廖为同一人、田总/田银伟、徐恒总/徐珩总（标题与正文拼写不一致）、哒哒/达达。
- **标签同义并存**：事件标签存在同义并存现象（离职/离职沟通/离职思考等），召回与聚类时须做同义处理。
- **跨用户隔离**：候选召回、判定、存储和查询全程以 `user_id` 为边界，不跨用户建边（离职事项实测分属两个账号：A 线与 B 线零边）。
- 首版不持久化人物实体或别名映射，不为事件边增加人物主体字段。

## 10. 已知数据质量问题

1. **事件日期 ≠ 发生日期**：回溯叙述普遍，故边时间基准统一采用原子事件 `occurred_on`。
2. **一事件多关联内容**：一个结构化事件可同时提到多个不同内容，这些内容可分别支撑该事件与多个其他事件建立事件级关系；不因此将一个事件拆成多个图谱节点。
3. **同日总述事件与子事件叙述重叠**：本期不建包含边，记为原子化去重问题。
4. **计划不等于执行**：只有后续事件出现明确执行证据时才建立闭环边；没有后续记录时不推断未执行，不建边（§6）。
5. **多内容对单向量的稀释**：事件内不同内容在一个完整向量中可能相互稀释，因此同时生成完整 `body` 向量和自然段辅助向量（§4.3、§5.3）。
6. **`diary_events.event_tags` JSON 列为空**：标签实际只存在于关联表（`tags` + `event_tags`）。

## 11. 后续完善

用户原话（逐字保留）：

> “正常来说人物间关系、人物事件间关系、洞察和洞察之间的关系、洞察和事件关系都要在图谱中体现，但会增加复杂程度，现阶段酌情考虑即可，记录到需求文档中后续完善”

后续完善方向：

- **人物间关系**（上下级/亲属）、**人物-事件关系**、**洞察间关系**、**洞察-事件关系**纳入图谱。
- **失败后重试的边属性更新规则**：如核磁白跑（EXECUTED_FAILED）后改约周五，后续执行事件出现时应定义闭环状态的更新/接续规则。
- **跨用户全库主题洞察规则**（在跨用户隔离的建边约束之外，另行定义洞察层的聚合口径）。
- **事件内唤起记为事件自注释**：唤起发生在事件内部（无独立事件承载）时不建边，记为事件自注释，自注释的展示与后续承载形式待定。试点实例：健康避讳链中“反思自己讳疾忌医”环节无独立事件，存在于 08-05 商讨方案事件（H3）内部。
- **人工候选确认**：LOW 候选关系的人工确认入口在后续需求中定义。
