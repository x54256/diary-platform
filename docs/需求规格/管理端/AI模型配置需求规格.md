# AI 模型配置需求规格

> 功能状态：已实现  
> 事实基线：2026-07-31 代码  
> 本文保留原设计中的菜单、枚举、用途约束、页面、测试调用和验收细则。

## 1. 背景

原设计提出时，系统中语言模型和语音识别模型都由配置文件固定：

- 日记整理、分析、对话使用同一个语言模型配置。
- 语音转文字使用固定 ASR 模型配置。
- 管理端无法选择模型、维护调用渠道、启用或禁用模型。

本需求将模型选择从配置文件迁移到管理端，当前已实现。模型能力清单初始化入库后由管理端维护。

## 2. 核心原则

1. 模型厂商和调用渠道分离。
2. 模型清单描述模型能力，不保存 API Key。
3. 调用渠道描述 API 地址和密钥，不绑定厂商。
4. 渠道支持模型通过独立关系维护。
5. 业务用途只选择已经可调用的渠道模型。
6. `.env` 不再作为模型运行兜底；未在管理端完成配置时，对应 AI 功能不可用。

示例：

```text
模型：deepseek-chat
模型厂商：DeepSeek
调用渠道：阿里百炼 / DeepSeek 官方 / 私有网关
```

同一个模型可以被多个渠道调用，同一个渠道也可以同时支持语言模型和 ASR 模型。

## 3. 管理端菜单

新增三个管理端菜单：

```text
系统管理
├─ 备份与恢复
├─ 模型管理
├─ 渠道管理
└─ 模型设置
```

职责划分：

| 页面 | 职责 |
|---|---|
| 模型管理 | 管理模型能力清单，支持初始化模型和自定义模型 |
| 渠道管理 | 管理 API 调用渠道，以及渠道支持哪些模型 |
| 模型设置 | 配置整理、分析、对话、语音转文字当前使用的模型 |

## 4. 枚举定义

### 4.1 模型类型

```text
language
asr
```

### 4.2 调用协议

```text
openai_chat
dashscope_asr
```

协议不入库，由模型类型派生：`language` 使用 `openai_chat`，`asr` 使用 `dashscope_asr`。

### 4.3 业务用途

```text
organize        整理
analysis        分析
chat            对话
transcription   语音转文字
```

### 4.4 模型能力分类

语言模型能力分类描述模型本身能力，不描述日记平台业务用途。

语言模型：

```text
通用对话
深度推理
长上下文
代码能力
轻量高速
```

ASR 模型：

```text
实时语音识别
录音文件识别
```

## 5. 用途约束

| 用途 | 模型类型 | 协议 |
|---|---|---|
| organize | language | openai_chat |
| analysis | language | openai_chat |
| chat | language | openai_chat |
| transcription | asr | dashscope_asr |

保存 `model_settings` 时必须校验：

1. 渠道已启用。
2. 渠道已配置 API Key。
3. `channel_model` 已启用。
4. 模型类型符合用途约束。

保存不要求真实测试通过。

模型详情支持：

- 查看完整能力信息。
- 启用 / 禁用。
- 删除。
- 编辑渠道关系。

自定义模型新增后默认启用。自定义模型必须填写模型类型、厂商、模型名称、能力梯队、能力分类、分数、核心特点和适用场景。

能力梯队和能力分类使用固定选项，不允许自由输入。

- 渠道详情批量保存当前渠道的模型关联。

选择链路：

```text
业务用途固定模型类型
→ 选择渠道
→ 选择能力梯队
→ 选择能力分类
→ 选择模型
```

渠道变化后总是清空模型选择。

保存粒度：

- 四个用途一起保存。
- 页面展示未配置原因，例如“渠道未配置密钥”“渠道模型已禁用”。

## 7. 测试调用

语言模型支持固定最小测试：

```text
用户消息：返回 ok
期望：模型返回 ok 或包含 ok
```

测试调用不作为保存前置条件。

ASR 首版不做真实音频测试，只做静态校验。

## 8. 验收标准

1. 管理端可以查看、筛选、启用、禁用、新增和删除模型。
2. 管理端可以创建渠道、维护 API 地址和 API Key。
3. 管理端可以从渠道或模型两个入口维护渠道支持模型。
4. 管理端可以为整理、分析、对话、语音转文字分别选择模型。
5. 禁用、删除、清空密钥时不会破坏正在使用的模型设置。
6. 未配置模型设置时，对应 AI 功能不可用并返回明确错误。
7. 语言模型测试调用可用，但保存不依赖测试结果。

## 9. 当前能力补充

### 9.1 模型管理

- 维护模型类型、厂商、模型名称、能力梯队、能力分类、思考能力、特点、分数和启用状态。
- 支持按类型、梯队、分类、状态和关键词筛选。
- 系统预置模型允许更新运行属性；自定义模型允许新增和删除。
- 已被渠道或业务配置引用的模型不得直接删除。

### 9.2 渠道管理

- 维护渠道名称、API 地址、API 密钥、思考参数模板和启用状态。
- API 密钥必须加密存储，查询时不得返回明文。
- 管理员可以维护每个渠道实际支持的模型。
- 已被业务配置引用的渠道或渠道模型不得直接删除。

### 9.3 业务用途设置

系统为以下用途选择默认渠道模型：

- 日记整理。
- 日记分析。
- 日记对话。
- 语音转文字。

选择时必须校验模型类型、协议、渠道状态、模型状态和密钥可用性。未配置可用模型时，对应 AI 功能应明确失败，不使用环境变量静默兜底。

### 9.4 测试调用

- 管理员可以对当前选中的配置发起测试调用。
- 测试结果应明确返回成功或失败原因，但不得泄露 API 密钥。

### 9.5 验收标准

- 模型、渠道和业务用途设置能够查询、保存并在运行时生效。
- 禁用、类型不匹配、缺少密钥或未建立渠道模型关系的配置不能被选用。
- 被引用资源受到删除保护。
- 日记整理、分析、对话和语音转写分别使用其用途配置。

技术实现见 [AI模型配置设计](../../系统设计/管理端/AI模型配置设计.md)。


## 10. 思考能力

模型思考能力使用 `reasoning_mode` 表示：

| 值 | 规则 |
|---|---|
| `unsupported` | 不支持思考，只能关闭 |
| `switchable` | 支持管理员开启或关闭 |
| `always_on` | 强制开启 |

用途级和环节级配置均可保存 `thinking_enabled`；最终值必须满足所选模型能力。
