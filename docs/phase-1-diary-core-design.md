# 阶段一：日记核心详细设计

> 对应模块：模块一（日记记录与整理）+ 模块二（日记浏览与查找）+ 模块三（日记详情）

## 1. 阶段目标

阶段一要先跑通日记数据源头：记录原始文本，发布后锁定原文，手动触发 AI 整理，浏览、搜索并进入详情页围绕单篇日记对话。

---

## 2. 功能范围

### 2.1 模块一：日记记录与整理

#### 录入与组织

| 项目 | 说明 |
|---|---|
| 录入方式 | 粘贴语音转文字 + 直接打字输入 |
| 日记结构 | 一篇日记 = 一条文本，一天多篇就建多条独立日记 |
| 原始文本 | 保存原始文本，不可覆盖、不可删除 |
| 多端支持 | 手机和电脑端都能查看和管理 |

#### AI 整理

| 项目 | 说明 |
|---|---|
| 触发方式 | 用户随时手动触发，在日记详情页点击"整理"按钮 |
| 重复整理 | 可重新整理覆盖之前结果，也可手动修改 |
| 整理能力 | 保真结构化整理：修正错别字、语句通顺、合并重复表达、按事件重组结构 |
| 整理范围 | 一次完成：生成标题、生成摘要、规整内容、提取元数据 |
| 原文展示 | 默认显示整理版内容，原始文本可展开查看 |
| 可编辑性 | 所有 AI 生成内容（含元数据）均可手动修改 |

#### AI 整理后正文格式

整理后的正文包含两部分：

1. **结构化日记**：把录音转文字产生的混乱文本整理成保真、好读的自然日记，不做内容压缩。
2. **日记分析**：基于结构化日记进行分析，具体格式后续细化。

> 第一阶段优先保证结构化日记的正确性和可读性。结构化日记只整理原文明确表达的内容，不推断、不补充、不拔高。

整理结果采用两层格式：

- **内部存储格式：JSON**。用于程序处理、内容检查、搜索、后续画像沉淀和结构化扩展。
- **用户展示格式：Markdown / 富文本**。用于日记详情页阅读和人工编辑。

#### AI 输出约束

AI 输出约束分为两层：结构化日记改写边界、日记分析推导边界。

**结构化日记允许改写：**

- 修正错别字。
- 修正语病。
- 删除口头禅和无意义重复。
- 合并重复表达。
- 调整语序。
- 把口语化表达整理成通顺句子。
- 按事件重新组织内容。
- 剔除不承载信息价值的口头语言噪音，用书面逻辑重新组织表达。例如：
  - 根据上下文推测并修正语音识别错误（如"spilm和看奶"→"Scrum 和看板"）
  - 补全口语中隐含的逻辑连接词（如"所以""但""反而"）
  - 将口语过渡语简化为书面时间标记（如"再讲一个今天早晨的事"→"今天早上"）
  - 理顺语音转文字中时间线混乱的表述，按实际时间先后重组
  - 删除元叙述（关于写日记行为本身的表述，如"闲着也是闲着就说两句""刚讲到哪了"）
  - 将意识流问答式表达改为紧凑的书面叙述

**结构化日记禁止改写：**

- 新增原文没有的信息。
- 替用户补事实。
- 替用户补动机。
- 替用户补结果。
- 替用户补反思。
- 把模糊表达改成确定结论。
- 删除关键事实。
- 改变事件因果关系。
- 改变情绪强度。
- 把用户原本的不确定表达改成确定表达。

**日记分析允许推导：**

- 基于当天事实分析情绪触发点。
- 基于当天行为提炼当天应对方式。
- 基于当天表达分析关注点、需求与自我理解。
- 识别明显认知偏差并温和校准。
- 给出低成本、具体、可执行建议。

**日记分析禁止推导：**

- 引用当天日记以外的信息。
- 做长期人格判断。
- 做心理诊断。
- 给用户贴标签。
- 没有依据地强行纠错。
- 否定用户感受。
- 输出命令式建议。
- 输出高成本建议。
- 把推导写成绝对事实。

#### 结构化日记规则

**总体原则**

- 结构化日记是证据层，目标是把口述流水账整理成清晰、稳定、可追溯、可阅读的日记记录。
- 可以修正错别字、语病、不通顺表达，可以合并重复内容，可以调整内容顺序。
- 不允许补充原文没有表达的动机、结果、感受、反思或经验。
- 不展示原文没有明确表达的内容，不写：`原文未明确`。
- 重复表达只保留信息最完整、表达最清楚的一版。
- 对模糊表达采用“保留原始表达 + 标注未明确点”的方式处理，不强行解释成明确结论。
- 用户展示格式以自然叙事为主，避免把事实信息拆成表单。
- 整理不是总结。生活细节、人物互动、玩笑、情绪表达、临时转念、观点推演、具体计划默认保留，不能因为不影响主线就删除。
- 观点类内容必须保留推理过程，不能只保留结论。
- 原文中无法归入事件、琐事、后续计划的开场白或闲聊内容，应提取为日记开头的背景引入段。
- 引入段仅整理原文已有内容，AI 不主动生成。
- **最高准则**：尊重事实但不过度尊重原文。整理结果必须让人能看懂，这是给人读的。
- **剔除无信息价值的口头语言**：语音转文字中大量存在不属于日记内容的语言噪音（录音过程自语、叙述过渡、走神重复、无意义填充等），只要不承载事件、情感或认知信息，都应剔除。
- **事件描述围绕事件本身，用书面逻辑组织**：事件正文只包含与事件相关的信息（时间、地点、人物、经过、感受、思考），用书面逻辑重新组织表达，按时间先后单向叙述，补全隐含的逻辑关系，结合上下文修正语音识别错误，确保可读性。

  样例（以下均为上述原则的具体推导，不作为独立规则）：
  - 元叙述（关于写日记行为本身的表述，如"闲着也是闲着就说两句""刚讲到哪了"）不承载事件信息，应剔除
  - 口语过渡语（如"再讲一个今天早晨的事"）中"今天早上"是事件时间信息要保留，"再讲一个...的事"是叙述噪音要去掉
  - 口语中隐含的逻辑转折需补全连接词（如"下楼腿都在抖，走起路来就好很多"→"下楼腿都在抖，但走起路来就好很多"）
  - 时间线来回跳跃（如今→昨→今→明）应按实际时间先后单向重组
  - 语音识别乱码需结合上下文推测修正（如"spilm和看奶"→"Scrum 和看板"）
  - 同一信息只保留一次，不因原文在多处提及就重复出现

**事件拆分规则**

- 采用**自然日记整理格式**，一篇日记可以拆分为多个事件。
- 事件按**目标**拆分为主：只要“想解决的问题 / 想完成的事”不同，就拆成不同事件。
- 时间、地点、人物、场景、主题作为辅助判断，不作为主拆分标准。
- 没有展开讲、但有记录价值的内容归入“琐事”。
- 明确指向未来安排的内容归入“后续计划”。
- 不把未来安排混入已经发生的事件正文。
- 不把未展开的工作进展、生活插曲强行并入不相关事件。
- 同一段原文中涉及多个独立工作事项（如软件过程文档、东莞项目收尾、前端 DUS 工作），即使原文未明确分隔，也应依据事项本质拆分为独立事件。

**生成流程**

1. **轻度清洗**：修正语病、错别字、断句，删除口头禅和明显重复。保留原文表达结构，不改变含义，只做基础文本修正。
2. **深度重组**：剔除不承载信息价值的口头语言噪音，理顺时间线混乱的表述，补全隐含的逻辑连接词，改写口语表达为书面叙述，结合上下文修正语音识别错误，去除重复内容。用书面逻辑重新组织表达，整理力度要足够。
3. **事件识别**：识别原文中提到了哪些事，形成事件列表；同时识别原文开头无法归入事件、琐事、后续计划的开场白或闲聊内容，提取为引入段（introduction）。
4. **事件归类**：把原文中分散在不同位置的内容归到对应事件下，完成同一事件的信息聚合。
5. **事件内文本重组**：对每个事件内部的信息按实际发生的时间先后顺序重新排列，采用单向时间流叙述（不回跳时间），生成逻辑清晰、读起来通顺的事件文本；用书面逻辑重新组织表达，不是轻度清洗原文。
6. **自然日记格式生成**：把每个事件整理为"事件标题 + 事件正文 + 可选感受 + 可选反思与成长"。事件正文合并原来的背景、动机、过程、结果，写成自然段。
7. **内容检查与修正**：检查是否存在编造原文没有的内容、推断动机、推断感受、推断反思或成长、过度总结、事件归类错误、事实拆分过碎、生活细节丢失、思考链条被压缩、观点只剩结论、时间线来回跳跃、元叙述未删除、重复内容未去重、语音识别乱码未修正、口语表达未改写为书面通顺表述、输出不让人能看懂等问题；发现问题时直接生成修正版并替换初稿，修正后不再重新检查。
8. **正式存储**：将通过检查或已完成修正的内容保存为正式整理结果。

**内容检查记录**

- 内容检查记录内部保留，用户不可见。
- 用途是调试整理质量、排查提示词问题、辅助后续优化。
- 第一阶段采用最小记录结构，不设计复杂审计系统。

| 字段 | 说明 |
|---|---|
| check_item | 检查项 |
| status | 通过 / 已修正 |
| issue | 发现的问题 |
| fix | 修正动作 |
| before | 修正前片段 |
| after | 修正后片段 |

**单个事件展示格式**

```markdown
## 事件：事件标题

事件正文。把背景、动机、过程、结果合并成一段或多段自然语言，按阅读顺序整理，不强制拆字段。

### 感受

### 反思与成长
```

**完整整理结构**

整理后的日记按以下顺序组织：

1. **开头引入段**（可选）：原文中无法归入事件、琐事、后续计划的开场白或闲聊内容的整理版
2. **事件**（一个或多个）：`## 事件：事件标题`
3. **琐事**（可选）：`## 琐事`
4. **后续计划**（可选）：`## 后续计划`
5. **日记分析**：基于结构化日记进行分析（见下方"日记分析"章节）

**事件正文表达规则**

- 事件正文承载原来的背景、动机、过程、结果。
- 事件正文写成自然段，不默认使用编号。
- 只有原文步骤非常清晰、且编号能明显提升可读性时，才使用编号。
- 事件正文可以包含当时发生的即时感受，但不展开心理分析。
- 事实信息优先合并写，避免被拆成过细字段。
- 生活细节默认保留，包括具体行为、人物互动、玩笑、吐槽、临时插曲和有记忆点的表达。
- 思考类事件要保留思考链条，包括触发原因、推理过程、尝试方向、工具选择、判断变化和阶段性结论。
- 观点类事件要保留观点推演，包括原始判断、支撑理由、类比、转折、保留意见和后续认知方向。
- 事件标题要具体概括“发生了什么”，不使用过泛的主题词。
- 事件标题优先使用“具体人物 / 具体对象 + 具体动作 / 变化”的句式。

示例：

```markdown
## 事件：今天早晨林萧鹏问我版本管理平台是否有用，他准备把它重新做出来

今天早晨林萧鹏突然问我管理平台当时用起来感觉怎么样，有没有效果。我说有效果，但后来被合并到超图后就被否定了。他说现在准备重新搞一套，因为他在做 AI 项目版本管理时也遇到了一些问题。我想把原来的版本管理平台捡起来继续做，一方面是给自己一个学习软件开发全流程的机会，另一方面也是把之前没完成的遗憾补上。
```

**琐事展示格式**

```markdown
## 琐事

1. 琐事内容一
2. 琐事内容二
3. 琐事内容三
```

- 标题固定为 `## 琐事`。
- 内容使用编号列表。
- 琐事为可选块，只有原文存在未展开但有记录价值的内容时才展示。
- 琐事指无实质价值、仅简单提及、未展开描述（缺乏细节、情感或因果逻辑）的内容，通常篇幅短、信息密度低。
- 已归入事件的内容不得再出现在琐事中（去重约束）。

**后续计划展示格式**

```markdown
## 后续计划

1. 计划内容一
2. 计划内容二
```

- 标题固定为 `## 后续计划`。
- 内容使用编号列表。
- 后续计划为可选块，只有原文存在明确指向未来安排的内容时才展示。
- 后续计划按重要性排序，而非按原文时间顺序排列。
- 反思与成长中提到的后续计划，也需同步列入后续计划部分。
- 后续计划条目需改写为语义清晰的书面表述，不保留口语化的模糊表达。

**感受表达规则**

- 事件正文里可以写具体经过中的即时感受。
- 独立的感受字段只总结整个事件的情绪变化。
- 感受字段不复述过程细节。
- 只有原文明确表达情绪时，才展示感受字段。

示例：

```markdown
### 感受
这件事里的情绪从烦躁、被忽视，转为被回应后的轻松和高兴。
```

**反思与成长表达规则**

- "反思与成长"可以承载反思、感悟、成长、自我认识等内容，但展示时不拆成内部小标题。
- 只有原文明确表达了对应内容时才整理。
- 原文没有明确表达时，不展示该字段。
- 有多条反思时，使用编号列表展示。
- 只有一条反思时，直接写自然段，不加编号。

示例：

```markdown
### 反思与成长
我意识到以后遇到这种不回应的情况，不能一直重复找同一个人，而是要更早判断是否需要换一种推进方式。
```

**模糊表达处理规则**

- 当原文出现模糊表达时，保留原始表达，并标注具体未明确的点。
- 不根据上下文强行解释成明确结论。
- 不把模糊表达改写成原文没有支撑的判断。

示例：

```markdown
## 事件：处理一件挺麻烦的事

我提到这件事“挺麻烦”，但原文未明确麻烦具体来自哪里。
```

#### 日记分析

日记分析是整理结果的第二部分，基于结构化日记进行分析。

**指导思想：日记分析的目标是帮助用户认清自己。**

日记分析不是评价用户，也不是替用户下结论，而是帮助用户从当天记录中看见：

- 自己当时有什么情绪变化。
- 自己采取了什么行为和决策。
- 自己真正关注什么。
- 这些关注背后反映了什么当下需求。
- 自己如何理解这件事。
- 这件事反映出自己看重什么。
- 自己对世界、他人、自己、知识或方法的理解是否存在明显偏差。
- 接下来可以做什么低成本、具体、可执行的调整。

日记分析属于解释层，允许基于当天事实进行推导，但必须遵守以下边界：

- 只分析当天这篇日记，不引用长期历史。
- 不做长期人格判断。
- 不做心理诊断。
- 不给用户贴标签。
- 较强推断必须写依据，依据来自当天结构化日记中的具体事件或事实。

当前日记分析包含：

1. **情绪分析**：用自然语言描述主要情绪、情绪变化和触发点，不使用百分比。
2. **行为与决策分析**：先描述当天具体行为和决策，再基于当天事实提炼当天体现出的行为模式线索。
3. **关注点、需求与自我理解**：分析用户当天真正关注什么，以及这些关注背后反映出的当下需求、自我叙事和价值排序。
4. **认知校准**：识别用户对世界、他人、自己、知识、方法或事件因果的理解是否存在明显偏差，并在有依据时进行温和纠正。
5. **可行动建议**：给出 1-3 条具体、低成本、可执行的建议。

**情绪分析** 的定义：

分析用户在当天事件中的主要情绪、情绪变化路径，以及触发这些情绪变化的具体原因。

分析内容：

- 用户出现了哪些主要情绪。
- 情绪是如何变化的。
- 哪些事实触发了情绪变化。
- 情绪背后反映了什么被触动。

禁止项：

- 不用百分比量化。
- 不做心理诊断。
- 不把短期情绪说成长期状态。
- 不写“你是一个情绪化的人”。

承接的自我认识角度：

- 情绪触发点。
- 控制感与不确定性带来的情绪反应。

**行为与决策分析** 的定义：

分析用户当天面对事件时采取了什么行动、做了什么选择，以及这些行为和选择体现出的当天应对方式。

分析内容：

- 用户先做了什么，后做了什么。
- 用户在关键节点做了什么选择。
- 用户是主动推进、等待观察、寻求外部帮助，还是回避处理。
- 行为背后体现出的当天应对方式。
- 行为带来了什么结果或影响。

禁止项：

- 不上升为长期人格。
- 不写“你一直都是……”。
- 不写“你有控制欲”“你是回避型人格”等标签。
- 不脱离当天事实分析行为模式。

承接的自我认识角度：

- 行为反应方式。
- 决策方式。
- 问题处理路径。

**关注点、需求与自我理解** 的定义：

分析用户当天真正被什么牵动，这些牵动背后反映了什么当下需求、未说出口的期待、边界感、自我叙事和价值排序。

分析内容：

- 用户真正关注的是什么。
- 用户当下想要什么。
- 用户害怕或抗拒什么。
- 用户正在维护什么。
- 用户对这件事形成了什么理解。
- 这件事反映出用户看重什么。

内部分析框架：

- 用户真正想要什么。
- 用户害怕或抗拒什么。
- 用户正在维护什么。
- 用户如何理解这件事。
- 用户看重什么。

这些问题只作为内部分析框架，不必在展示层显式拆成小标题。输出时应使用自然段，帮助用户理解自己为什么会被这件事牵动。

常见分析方向：

- 真正想要什么：被回应、被理解、结果明确、责任清楚、关系稳定、事情推进。
- 害怕或抗拒什么：被忽视、不公平、失控、责任模糊、投入没有回报。
- 正在维护什么：边界、尊严、秩序感、投入感、公平感、掌控感。
- 如何理解这件事：用户把事件解释成什么，例如“我的表达没有被看见”“又是我一个人在推动”。
- 看重什么：效率、公平、尊重、确定性、责任、关系、自主性。

禁止项：

- 不做心理诊断。
- 不写长期人格结论。
- 不把推导写成绝对事实。
- 不写“你缺乏安全感”“你很依赖认可”。
- 不替用户扩展到原文没有支撑的人生经历。

承接的自我认识角度：

- 未说出口的期待。
- 边界感。
- 控制感与不确定性。
- 自我叙事。
- 价值排序。

**认知校准** 的定义：

识别日记中用户对世界、他人、自己、知识、方法或事件因果的理解，判断其中是否存在明显的过度概括、绝对化、误解、片面理解或事实性错误，并在有依据时进行温和纠正。

分析对象：

- 对世界的判断。
- 对他人的判断。
- 对自己的判断。
- 对事件原因的判断。
- 对知识点、方法论、工作方法的理解。
- 对经验教训的归纳。

允许项：

- 指出过度概括。
- 指出绝对化表达。
- 指出事实支撑不足。
- 指出知识理解错误。
- 补充更准确的理解。
- 把“情绪中的判断”和“事实可支持的判断”分开。

禁止项：

- 不否定用户感受。
- 不站在道德高地教育用户。
- 不把所有负面判断都改成积极话术。
- 不在不确定时强行纠错。
- 不对专业知识胡乱纠正。
- 不把认知校准写成行动建议。

与其他模块的边界：

- **关注点、需求与自我理解**：解释“用户为什么这样看”。
- **认知校准**：检查“用户这样看是否准确、是否过度、是否需要补充”。
- **可行动建议**：给出“下次可以怎么做”。

处理规则：

- 对世界、他人、自我的整体判断，要优先区分情绪表达和事实可支持的结论。
- 对知识点、方法论、工作方法的错误理解，如果有足够把握，可以直接指出并补充更准确理解。
- 如果原文信息不足或模型没有足够把握，应写“原文不足以判断该理解是否准确”，不能装作确定。

**可行动建议** 的定义：

基于当天分析，给出用户下次遇到类似情况时可以尝试的低成本、具体、可执行行动。

分析内容：

- 用户下次可以尝试怎么表达。
- 用户下次可以如何降低不确定性。
- 用户下次可以如何区分事实、情绪和解释。
- 用户下次可以如何保护边界。
- 用户下次可以如何把需求说清楚。

承接的自我认识角度：

- 从自我理解走向下一次行动。
- 把情绪、需求、边界转化为具体做法。

**可行动建议** 的表达规则：

- 使用“下次可以尝试……”这类建议式表达。
- 不使用“你应该……”这类命令式表达。
- 建议服务于下一次遇到类似情况时的具体行动。
- 建议必须低成本、具体、可执行。
- 不输出泛泛而谈的鸡汤。
- 不输出高成本建议，例如辞职、结束关系、重大关系决策等，除非原文明确表达相关打算。

**日记分析内部检查机制：**

- 生成日记分析后，进行一次内部检查。
- 如果发现问题，直接生成修正版替换分析初稿。
- 修正后不重新检查。
- 检查记录内部保留，用户不可见。

检查项：

- 是否引用了当天日记以外的信息。
- 是否做了长期人格判断。
- 是否贴标签或做心理诊断。
- 较强推断是否缺少依据。
- 认知校准是否否定了用户感受。
- 认知校准是否在依据不足时强行纠错。
- 可行动建议是否具体、低成本、可执行。
- 是否出现“你应该……”这类命令式表达。
- 是否出现鸡汤式、空泛建议。
- 是否出现原文没有支撑的高成本建议。

**标签类型**

标签不是为了把日记简单分类，而是为了给后续检索、AI 对话、人物画像、心路历程和知识沉淀提供入口。

| 类型 | 作用 | 示例 |
|---|---|---|
| 领域标签 | 粗粒度筛选日记 | 工作、生活、关系、健康、学习、娱乐 |
| 主题标签 | 串起长期反复出现的具体事项 | 版本管理平台、AI 开发、小红书爬虫、遛狗 |
| 人物 / 对象标签 | 串起具体人物、关系和重要对象 | 林萧鹏、田总、媳妇、达达 |
| 心理主题标签 | 串起情绪、需求和内在模式 | 不确定性、控制感、遗憾、无奈、成就感 |
| 知识点标签 | 串起学习内容、方法、概念和做事方式 | 软件工程、软件开发流程、需求分析、原型设计、AI 辅助开发、做事方式、项目管理、版本管理 |

**标签提取规则**

- AI 优先提取主题标签、人物 / 对象标签、心理主题标签、知识点标签。
- 领域标签作为辅助粗分类。
- 标签必须来自原文或整理内容中的明确依据。
- 不生成空泛评价型标签，例如“成长”“感悟”“重要”“日常”。
- 心情已有独立字段，不用“开心”“难过”等单纯心情词作为标签。
- 用户可以修改 AI 提取的标签，也可以手动新建标签。

#### 日记状态

| 状态 | 说明 | 原始文本 | 参与分析 |
|---|---|---|---|
| 草稿 | 保存后，可继续编辑 | 可修改 | 否 |
| 已发布 | 发布后，原始文本锁定，可触发整理 | 不可改 | 否 |
| 已整理 | AI 整理完成，整理内容可手动修改 | 不可改 | 是 |

> 状态流转：草稿 →（发布）→ 已发布 →（整理）→ 已整理

### 3.5 AI 提示词设计

**日记整理提示词**

输入：日记原始文本
输出：标题、摘要、心情、地点、标签、结构化日记正文

提示词要点：
- 润色文字，修正错别字，语句通顺，不改变原意，不压缩核心内容
- 按自然日记整理格式重组内容，一篇日记可拆成多个事件
- 事件按目标拆分为主，场景、主题、人物、时间作为辅助判断
- 按"轻度清洗 → 深度重组 → 事件识别 → 事件归类 → 事件内文本重组 → 自然日记格式生成 → 内容检查与修正 → 正式存储"的流程生成结构化日记
- 原文中无法归入事件、琐事、后续计划的开场白或闲聊内容，提取为日记开头的背景引入段，引入段仅整理原文已有内容，不主动生成
- 完整整理结构为：开头引入段（可选）→ 事件（一个或多个）→ 琐事（可选）→ 后续计划（可选）→ 日记分析
- 每个事件固定包含事件标题和事件正文
- 事件正文合并背景、动机、过程、结果，写成一段或多段自然语言
- 感受、反思与成长为可选块，只有原文明确表达时才展示
- 反思与成长有多条时使用编号列表，只有一条时直接写自然段
- 琐事标题固定为 `## 琐事`，内容使用编号列表
- 后续计划标题固定为 `## 后续计划`，内容使用编号列表
- 只整理原文明确表达的内容，不推断、不补充、不拔高
- 原文没有明确表达的内容不展示，不写"原文未明确"
- 重复表达合并，只保留信息最完整的一版
- 整理不是总结，生活细节、人物互动、玩笑、情绪表达、临时转念、观点推演、具体计划默认保留
- 思考类事件保留完整思考链条，不能只输出概括性结论
- 观点类事件保留观点推演过程，不能只保留最终观点
- 事件标题必须具体概括发生了什么，不使用"日常""工作与学习""认知提升"等泛主题词
- 不把未来计划混入已经发生的事件正文，明确未来安排归入"后续计划"
- 不把未展开的工作进展、生活插曲强行并入不相关事件，没有展开但有记录价值的内容归入"琐事"
- 事件正文默认不用编号，只有步骤非常清晰、且编号能明显提升可读性时才使用编号
- 语音转文字输入需结合上下文推测并修正识别错误，不能原样保留乱码
- 补全口语中隐含的逻辑连接词（所以、但、反而等），使因果关系清晰
- 口语过渡语简化为书面时间标记，不保留"再讲一个""刚讲到哪了"等口语
- 事件内叙述按实际时间先后单向排列，不回跳时间
- 元叙述（关于写日记行为本身的表述）应从正文中剔除
- 意识流问答式表达应改为紧凑的书面叙述，不保留"为什么？因为..."的口语风格
- 同一段中多个独立事项应拆分为独立事件
- 已归入事件的内容不再出现在琐事中（去重）
- 后续计划按重要性排序
- 反思中提到的后续计划需同步列入后续计划部分
- 整理力度要足够，用书面逻辑重新组织表达，不能只是轻度清洗原文
- 琐事指无实质价值、仅简单提及、未展开描述的内容
- 后续计划条目需改写为语义清晰的书面表述
- 感受块只总结整个事件的情绪变化，不复述过程细节
- 反思与成长字段不拆内部小类，且不整理原文未明确表达的隐含经验
- 元数据从内容中推断
- 标签按五类提取：领域标签、主题标签、人物 / 对象标签、心理主题标签、知识点标签
- 标签提取优先级：主题标签、人物 / 对象标签、心理主题标签、知识点标签优先，领域标签作为辅助粗分类
- 标签必须有明确文本依据，不生成"成长""感悟""重要""日常"等空泛评价型标签
- 心情已有独立字段，不用"开心""难过"等单纯心情词作为标签
- 采用两次清洗策略：第一次轻度清洗（基础文本修正），第二次深度重组（书面逻辑重组）
- 各阶段使用 Few-shot 样例引导模型，通过模仿学习提升输出质量
- 温度分层：轻度清洗和检查阶段使用低温度（0.3）确保事实准确，深度重组、事件整理和模板填充使用较高温度（0.5）鼓励表达重组
- CHECK 阶段以读者视角通读全文，对读不通顺的地方直接改写为通顺表达

**反思对话提示词**

输入：当前日记内容 + 近期日记（关联参考）+ 对话历史 + 用户最新消息
输出：AI 回复

提示词要点：
- 围绕日记内容提问和引导反思
- 帮助用户深入思考事件背后的感受和原因
- 语气温暖真诚，像朋友聊天
- 不做泛泛的建议

## 4. AI 整理流水线详细设计

### 背景

当前日记处理流程需要从“多段清洗 + 事件整理 + 结构化”的方式，调整为更稳定的流水线：

```text
文本清洗 -> 清洗审核 -> 事件整理 -> 三字段结构化 -> 内容审核 -> 元数据提取
```

设计原则：

- 原文是最高事实来源。
- 清洗结果是后续处理的基准文本，但必须经过清洗审核。
- 每个环节只做自己的事，不提前做后续环节的工作。
- 能提升可读性，但不能改写事实。

### 技术实现方案

#### 技术框架：LangGraph

流水线采用 [LangGraph](https://github.com/langchain-ai/langgraph) 框架构建，将 6 阶段流水线建模为线性状态图。

**核心概念映射：**

| 概念 | 在本项目中的对应 |
|---|---|
| StateGraph | 将 6 阶段流水线建模为线性图，节点间通过 Edge 串联 |
| Node | 每个 AI 调用环节映射为一个 Node 函数，接收 State、返回 State 更新 |
| State | 共享数据结构（TypedDict），包含所有中间产物，节点间通过 State 传递数据 |

**图的拓扑结构：**

```
START → text_clean → clean_check → event_organize → template_fill → content_check → metadata_extract → END
```

每个 Node 对应一次独立的 LLM 调用，Node 内部只读取 State 中自己需要的字段、写入自己产出的字段，不跨节点直接通信。

#### LLM 接入方式

使用官方 `langchain-deepseek` 包的 `ChatDeepSeek` 替代现有 httpx 直调。DeepSeek API 完全兼容 OpenAI 格式，LangChain 原生支持。

切换动机：

- LangGraph Node 内部需要返回 LangChain 消息对象，使用 `ChatDeepSeek` 可无缝对接。
- LangChain 提供统一的重试、超时、回调机制，减少手动管理 httpx 请求的样板代码。
- 与 LangGraph 的 State 传递、Checkpoint 序列化天然兼容。

#### 断点续跑机制（Checkpoint）

流水线包含 6 次串行 LLM 调用，任意一次失败都可能导致整体中断。断点续跑机制确保失败后能从断点恢复，而非从头重跑。

**核心原则：**

- 每个 super-step（节点执行完成）自动保存 State 快照到 checkpoint。
- 恢复时复用相同标识，LangGraph 自动跳过已完成的节点。
- 整理完成后主动清理 checkpoint，避免存储膨胀。

**实现方案：**

| 项目 | 方案 |
|---|---|
| Checkpoint 存储 | `langgraph-checkpoint-postgres` 的 `AsyncPostgresSaver`，复用现有 PostgreSQL |
| 线程标识 | `thread_id` 复用 `task_id`（UUID），无需额外映射 |
| 断点恢复 | 失败后用户重新触发整理，系统检测 checkpoint 存在，使用相同 `thread_id` 调用，LangGraph 自动从断点恢复 |
| 清理策略 | 整理成功后主动调用 `checkpointer.adelete_thread()` 清理 checkpoint |

#### 数据库驱动统一

项目统一使用 psycopg3 替代 psycopg2：

- SQLAlchemy 连接串前缀从 `postgresql+psycopg2://` 改为 `postgresql+psycopg://`。
- 消除 psycopg2/psycopg3 共存问题。
- psycopg3 原生支持 async，与 FastAPI 异步架构更契合。
- `langgraph-checkpoint-postgres` 依赖 psycopg3，统一驱动后避免版本冲突。

#### 依赖变更

新增依赖：

| 包名 | 用途 |
|---|---|
| `langgraph` | 流水线状态图框架 |
| `langchain-core` | LangChain 核心抽象 |
| `langchain-deepseek` | DeepSeek LLM 接入 |
| `langgraph-checkpoint-postgres` | Checkpoint 持久化存储 |

替换依赖：

| 移除 | 替换为 | 原因 |
|---|---|---|
| `psycopg2-binary` | `psycopg` | 统一为 psycopg3，原生 async 支持 |

#### State 数据结构

State 使用 TypedDict 定义，承载流水线全生命周期的数据流转：

```python
class PipelineState(TypedDict):
    # ── 输入字段 ──
    original_text: str          # 日记原文
    task_id: str                # 整理任务 ID（UUID）
    diary_id: str               # 日记 ID
    user_id: str                # 用户 ID

    # ── 阶段 1 产物：文本清洗 ──
    cleaned_text: str

    # ── 阶段 2 产物：清洗审核 ──
    checked_text: str
    clean_check_log: list

    # ── 阶段 3 产物：事件整理 ──
    introduction: str
    events_raw: list            # 事件整理的原始事件列表
    trivia: list
    plans: list

    # ── 阶段 4 产物：三字段结构化 ──
    structured_events: list     # 结构化后的事件列表

    # ── 阶段 5 产物：内容审核 ──
    final_introduction: str
    final_events: list
    final_trivia: list
    final_plans: list
    check_log: list

    # ── 阶段 6 产物：元数据提取 ──
    title: str
    summary: str
    mood: str
    location: str
    event_tags: list

    # ── 进度追踪 ──
    current_step: str           # 当前执行步骤，同步更新到 organize_tasks.current_step
```

每个 Node 只读取自己需要的输入字段、写入自己产出的输出字段。未执行的节点对应字段为空或缺省值。

#### 前端适配说明

Node 内部继续更新 `organize_tasks.current_step` 字段，前端轮询机制无需改动。LangGraph 的引入对前端完全透明，前端仍通过轮询 `GET /api/diaries/{id}` 获取整理进度和结果。

### 各环节 Temperature 配置

| 环节 | Temperature | 说明 |
|------|------------|------|
| 环节1：文本清洗 | 0.3 | 事实准确性优先，不需创造性 |
| 环节2：清洗审核 | 0.3 | 审核需要严格 |
| 环节3：事件整理 | 0.5 | 识别+汇聚需要理解灵活度 |
| 环节4：三字段结构化 | 0.5 | 结构化重组需要灵活度 |
| 环节5：内容审核 | 0.3 | 审核需要严格 |
| 环节6：元数据提取 | 0.3 | 提取需要精确 |

### 环节 1：文本清洗

#### 环节定位

文本清洗用于合并原来的“轻度清洗”和“深度清洗”两个步骤。

目标是把语音转文字整理成一份可读的基准文本，供后续事件整理使用。

文本清洗可以负责“变顺”，但不负责最终判真；事实纠偏交给下一步“清洗审核”。

#### 输入

```json
{
  "original_text": "原始语音转文字内容"
}
```

#### 输出

```json
{
  "cleaned_text": "清洗后的文本"
}
```

#### Prompt

```text
你是一个日记文本清洗助手。请对用户提供的日记原文（语音转文字）进行清洗整理，生成一份可读的基准文本，供后续事件整理使用。

## 最高准则
尊重事实，但不过度尊重原始口语形态。整理结果必须让人能看懂，这是给人读的。

## 清洗目标
在不改变原文事实含义的前提下，删除语音噪音，修正明显错误，整理断句和表达，使文本通顺、自然、可读。

## 规则
1. 修正语病、错别字、断句错误。
2. 删除口头禅和无意义填充词，例如“嗯、啊、然后、反正、就是、那个”等。
3. 删除明显重复表达。同一句话或同一意思连续重复时，只保留信息最完整、表达最清楚的一版。
4. 剔除不承载信息价值的口头语言噪音，包括录音过程自语、叙述过渡、走神重复、无意义填充等。
5. 保留承载事件、情感、判断、偏好、计划、反思的信息，不要因为表达口语化就删除。
6. 可以结合上下文修正明显的语音识别错误，但不能强行猜测无法确定的人名、地名、产品名、专有名词。
7. 可以在同一句或相邻短句内调整局部语序、合并断裂表达，使表达通顺。
8. 可以补充标点，以及原文关系已经明确的过渡词；不要补充原文没有明确表达的因果、目的、动机。
9. 不要跨事件重组内容，不要合并相隔较远的内容，不要提前做事件拆分。
10. 按原文叙述顺序整理，整体时间线不要倒置。
11. 不要改写成摘要，不要输出结构化事件。
12. 不新增原文没有的事实、原因、情绪、评价或反思。
13. 保留原文的语气和风格，不要改成过度正式、文学化或总结式表达。
14. 如果原文表达含混，只做可读性整理，不要强行解释成确定结论。

## 输出要求
请严格按以下 JSON 格式返回，不要包含 markdown 代码块标记：

{"cleaned_text": "清洗后的文本"}
```

#### 关键边界

- 能顺句子，不能改事实。
- 能清噪音，不能删信息。
- 能局部整理，不能跨事件重组。
- 能修正明显错误，不能猜测不确定内容。

> 注：原文中的开场白（如"闲着也是闲着就说两句"）属于引入段，不是需要剔除的噪音，清洗时应保留并整理为通顺表达，供后续事件整理阶段作为 introduction 提取。

### 环节 2：清洗审核

#### 环节定位

清洗审核是新增环节，用于对照原文审核文本清洗结果。

它同时承担两个职责：

1. 发现 `cleaned_text` 中由清洗阶段造成的问题。
2. 直接给出修正后的完整文本 `checked_text`。

清洗审核不输出替换指令，不由程序执行局部替换。程序直接使用 `checked_text` 作为后续环节的基准文本。

选择该方案的原因：

- 文本清洗错误不一定是机械替换，可能涉及遗漏恢复、句子重排、局部语义修正。
- 让模型直接输出完整修正版，实现更简单，流程更稳定。
- 通过 `clean_check_log` 保留关键修正记录，兼顾可追踪性。

#### 输入

```json
{
  "original_text": "原始语音转文字内容",
  "cleaned_text": "文本清洗结果"
}
```

#### 输出

```json
{
  "checked_text": "审核修正后的完整文本",
  "clean_check_log": [
    {
      "issue": "发现的问题",
      "before": "清洗结果中的问题片段",
      "after": "修正后的片段",
      "reason": "修正原因"
    }
  ]
}
```

#### Prompt

```text
你是一个日记清洗审核助手。请对照原始日记文本，审核文本清洗结果是否准确，并直接修正清洗结果中的问题。

## 任务目标
检查 cleaned_text 是否忠实保留 original_text 的事实、情感、判断、偏好、计划和细节。
如果发现清洗阶段造成了误改、遗漏、过度改写或新增内容，请直接修正，输出更可靠的 checked_text。

## 最高准则
original_text 是最高事实来源。
checked_text 应以 cleaned_text 为基础，只修正审核发现的问题，不重新清洗全文，不整体改写表达风格。

## 审核规则
1. 检查 cleaned_text 是否改变了原文事实含义。
2. 检查 cleaned_text 是否遗漏了有信息价值的内容，包括事件、时间、地点、人物、行为、结果、感受、判断、计划。
3. 检查 cleaned_text 是否新增了原文没有的事实、原因、情绪、评价或反思。
4. 检查 cleaned_text 是否强行猜测无法确定的人名、地名、产品名、专有名词。
5. 检查 cleaned_text 是否把原文中的含混、犹豫、矛盾表达强行改成确定结论。
6. 检查 cleaned_text 是否存在明显不通顺、断句错误、指代不清的问题。
7. 只修正必要问题，不重新清洗全文，不做事件拆分，不做摘要，不做结构化整理。

## 修正规则
1. 发现问题时，直接在 checked_text 中修正。
2. 每个实质性修正都记录到 clean_check_log。
3. 如果 cleaned_text 没有明显问题，checked_text 可以等于 cleaned_text，clean_check_log 为空数组。
4. clean_check_log 只记录影响事实、信息完整性或可读性的实质问题，不记录标点、轻微措辞这类小调整。

## 输出要求
请严格按以下 JSON 格式返回，不要包含 markdown 代码块标记：

{
  "checked_text": "审核修正后的文本",
  "clean_check_log": [
    {
      "issue": "发现的问题",
      "before": "清洗结果中的问题片段",
      "after": "修正后的片段",
      "reason": "修正原因"
    }
  ]
}
```

#### 关键边界

- 能修正清洗错误，不能重新清洗全文。
- 能恢复遗漏信息，不能新增原文没有的信息。
- 能让基准文本更准确，不能提前做事件整理。
- `checked_text` 是后续事件整理的输入基准。

### 环节 3：事件整理

#### 环节定位

事件整理用于解决语音日记中的思维跳跃问题。

语音日记常见情况是：说一件事的过程中插入另一件事，说完后又回到原来的事情。这个环节的核心职责不是按原文连续段落切分，而是：

1. 识别日记里有哪些事。
2. 按照这些事情，把散落在不同位置的相关文本汇聚到一起。

事件整理只做识别、归类和汇聚，不做三字段结构化，不生成 `feeling`、`reflection` 字段。

#### 输入

```json
{
  "checked_text": "清洗审核后的基准文本"
}
```

#### 输出

`trivia` 使用字符串数组。

```json
{
  "introduction": "引入段文本，无则空字符串",
  "events": [
    {
      "event_title": "事件标题",
      "organized_text": "同一事件汇聚后的文本"
    }
  ],
  "trivia": [
    "琐事内容"
  ],
  "plans": [
    "后续计划"
  ]
}
```

#### Prompt

```text
你是一个日记事件整理助手。请对清洗审核后的日记文本进行事件识别、归类和汇聚。

## 任务目标
日记中经常出现思维跳跃：说一件事时插入另一件事，之后又回到前一件事。
你的任务是识别日记中提到的所有事情，并把属于同一件事的散落内容汇聚到一起。

## 整理规则
1. 先识别日记中有哪些事情。
2. 同一件事即使在原文中分散出现，也要汇聚到同一个 events 项中。
3. 不同事情不要混在同一个 events 项中。
4. 每个事件内部按实际发生顺序整理。

- 以"事情"为核心：想解决的问题不同、目标不同，就是不同的事。
```
