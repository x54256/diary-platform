# 阶段一：日记核心详细设计

> 对应模块：模块一（日记记录与整理）+ 模块二（日记浏览与查找）+ 模块三（日记详情）

## 1. 阶段目标

阶段一要先跑通日记数据源头：记录原始文本，发布后锁定原文，手动触发 AI 整理，浏览、搜索并进入详情页围绕单篇日记对话。

---

## 2. 功能范围

### 2.1 模块一：日记记录与整理

#### 录入与组织

| 项目 | 说明 |
|---|---|
| 录入方式 | 粘贴语音转文字 + 直接打字输入 |
| 日记结构 | 一篇日记 = 一条文本，一天多篇就建多条独立日记 |
| 原始文本 | 保存原始文本，不可覆盖、不可删除 |
| 多端支持 | 手机和电脑端都能查看和管理 |

#### AI 整理

| 项目 | 说明 |
|---|---|
| 触发方式 | 用户随时手动触发，在日记详情页点击"整理"按钮 |
| 重复整理 | 可重新整理覆盖之前结果，也可手动修改 |
| 整理能力 | 保真结构化整理：修正错别字、语句通顺、合并重复表达、按事件重组结构 |
| 整理范围 | 生成标题、生成摘要、规整内容、提取地点 |
| 原文展示 | 默认显示整理版内容，原始文本可展开查看 |
| 可编辑性 | 所有 AI 生成内容（含元数据）均可手动修改 |

#### AI 整理后正文格式

整理后的正文包含两部分：

1. **结构化日记**：把录音转文字产生的混乱文本整理成保真、好读的自然日记，不做内容压缩。
2. **日记分析**：基于结构化日记进行分析，具体格式后续细化。

> 第一阶段优先保证结构化日记的正确性和可读性。结构化日记只整理原文明确表达的内容，不推断、不补充、不拔高。

整理结果采用两层格式：

- **内部存储格式：JSON**。用于程序处理、内容检查、搜索、后续画像沉淀和结构化扩展。
- **用户展示格式：Markdown / 富文本**。用于日记详情页阅读和人工编辑。

#### AI 输出约束

AI 输出约束分为两层：结构化日记改写边界、日记分析推导边界。

**结构化日记允许改写：**

- 修正错别字。
- 修正语病。
- 删除口头禅和无意义重复。
- 合并重复表达。
- 调整语序。
- 把口语化表达整理成通顺句子。
- 按事件重新组织内容。
- 剔除不承载信息价值的口头语言噪音，用书面逻辑重新组织表达。例如：
  - 根据上下文推测并修正语音识别错误（如"spilm和看奶"→"Scrum 和看板"）
  - 补全口语中隐含的逻辑连接词（如"所以""但""反而"）
  - 将口语过渡语简化为书面时间标记（如"再讲一个今天早晨的事"→"今天早上"）
  - 理顺语音转文字中时间线混乱的表述，按实际时间先后重组
  - 删除元叙述（关于写日记行为本身的表述，如"闲着也是闲着就说两句""刚讲到哪了"）
  - 将意识流问答式表达改为紧凑的书面叙述

**结构化日记禁止改写：**

- 新增原文没有的信息。
- 替用户补事实。
- 替用户补动机。
- 替用户补结果。
- 替用户补反思。
- 把模糊表达改成确定结论。
- 删除关键事实。
- 改变事件因果关系。
- 改变情绪强度。
- 把用户原本的不确定表达改成确定表达。

**日记分析允许推导：**

- 基于当天事实分析情绪触发点。
- 基于当天行为提炼当天应对方式。
- 基于当天表达分析关注点与需求。
- 识别明显认知偏差并温和校准。
- 给出低成本、具体、可执行建议。

**日记分析禁止推导：**

- 引用当天日记以外的信息。
- 做长期人格判断。
- 做心理诊断。
- 给用户贴标签。
- 没有依据地强行纠错。
- 否定用户感受。
- 输出命令式建议。
- 输出高成本建议。
- 把推导写成绝对事实。

#### 结构化日记规则

**总体原则**

- 结构化日记是证据层，目标是把口述流水账整理成清晰、稳定、可追溯、可阅读的日记记录。
- 可以修正错别字、语病、不通顺表达，可以合并重复内容，可以调整内容顺序。
- 不允许补充原文没有表达的动机、结果、感受、反思或经验。
- 不展示原文没有明确表达的内容，不写：`原文未明确`。
- 重复表达只保留信息最完整、表达最清楚的一版。
- 对模糊表达采用“保留原始表达 + 标注未明确点”的方式处理，不强行解释成明确结论。
- 用户展示格式以自然叙事为主，避免把事实信息拆成表单。
- 整理不是总结。生活细节、人物互动、玩笑、情绪表达、临时转念、观点推演、具体计划默认保留，不能因为不影响主线就删除。
- 观点类内容必须保留推理过程，不能只保留结论。
- 原文中无法归入事件、琐事、后续计划的开场白或闲聊内容，应提取为日记开头的背景引入段。
- 引入段仅整理原文已有内容，AI 不主动生成。
- **最高准则**：尊重事实但不过度尊重原文。整理结果必须让人能看懂，这是给人读的。
- **剔除无信息价值的口头语言**：语音转文字中大量存在不属于日记内容的语言噪音（录音过程自语、叙述过渡、走神重复、无意义填充等），只要不承载事件、情感或认知信息，都应剔除。
- **事件描述围绕事件本身，用书面逻辑组织**：事件正文只包含与事件相关的信息（时间、地点、人物、经过、感受、思考），用书面逻辑重新组织表达，按时间先后单向叙述，补全隐含的逻辑关系，结合上下文修正语音识别错误，确保可读性。

  样例（以下均为上述原则的具体推导，不作为独立规则）：
  - 元叙述（关于写日记行为本身的表述，如"闲着也是闲着就说两句""刚讲到哪了"）不承载事件信息，应剔除
  - 口语过渡语（如"再讲一个今天早晨的事"）中"今天早上"是事件时间信息要保留，"再讲一个...的事"是叙述噪音要去掉
  - 口语中隐含的逻辑转折需补全连接词（如"下楼腿都在抖，走起路来就好很多"→"下楼腿都在抖，但走起路来就好很多"）
  - 时间线来回跳跃（如今→昨→今→明）应按实际时间先后单向重组
  - 语音识别乱码需结合上下文推测修正（如"spilm和看奶"→"Scrum 和看板"）
  - 同一信息只保留一次，不因原文在多处提及就重复出现

**事件拆分规则**

- 采用**自然日记整理格式**，一篇日记可以拆分为多个事件。
- 事件按**目标**拆分为主：只要“想解决的问题 / 想完成的事”不同，就拆成不同事件。
- 时间、地点、人物、场景、主题作为辅助判断，不作为主拆分标准。
- 没有展开讲、但有记录价值的内容归入“琐事”。
- 明确指向未来安排的内容归入“后续计划”。
- 不把未来安排混入已经发生的事件正文。
- 不把未展开的工作进展、生活插曲强行并入不相关事件。
- 同一段原文中涉及多个独立工作事项（如软件过程文档、东莞项目收尾、前端 DUS 工作），即使原文未明确分隔，也应依据事项本质拆分为独立事件。

**生成流程**

1. **轻度清洗**：修正语病、错别字、断句，删除口头禅和明显重复。保留原文表达结构，不改变含义，只做基础文本修正。
2. **深度重组**：剔除不承载信息价值的口头语言噪音，理顺时间线混乱的表述，补全隐含的逻辑连接词，改写口语表达为书面叙述，结合上下文修正语音识别错误，去除重复内容。用书面逻辑重新组织表达，整理力度要足够。
3. **事件识别**：识别原文中提到了哪些事，形成事件列表；同时识别原文开头无法归入事件、琐事、后续计划的开场白或闲聊内容，提取为引入段（introduction）。
4. **事件归类**：把原文中分散在不同位置的内容归到对应事件下，完成同一事件的信息聚合。
5. **事件内文本重组**：对每个事件内部的信息按实际发生的时间先后顺序重新排列，采用单向时间流叙述（不回跳时间），生成逻辑清晰、读起来通顺的事件文本；用书面逻辑重新组织表达，不是轻度清洗原文。
6. **自然日记格式生成**：把每个事件整理为"事件标题 + 事件正文 + 可选感受 + 可选反思与成长"。事件正文合并原来的背景、动机、过程、结果，写成自然段。
7. **内容检查与修正**：检查是否存在编造原文没有的内容、推断动机、推断感受、推断反思或成长、过度总结、事件归类错误、事实拆分过碎、生活细节丢失、思考链条被压缩、观点只剩结论、时间线来回跳跃、元叙述未删除、重复内容未去重、语音识别乱码未修正、口语表达未改写为书面通顺表述、输出不让人能看懂等问题；发现问题时直接生成修正版并替换初稿，修正后不再重新检查。
8. **正式存储**：将通过检查或已完成修正的内容保存为正式整理结果。

**内容检查记录**

- 内容检查记录内部保留，用户不可见。
- 用途是调试整理质量、排查提示词问题、辅助后续优化。
- 第一阶段采用最小记录结构，不设计复杂审计系统。

| 字段 | 说明 |
|---|---|
| check_item | 检查项 |
| status | 通过 / 已修正 |
| issue | 发现的问题 |
| fix | 修正动作 |
| before | 修正前片段 |
| after | 修正后片段 |

**单个事件展示格式**

```markdown
## 事件：事件标题

事件正文。把背景、动机、过程、结果合并成一段或多段自然语言，按阅读顺序整理，不强制拆字段。

### 感受

### 反思与成长
```

**完整整理结构**

整理后的日记按以下顺序组织：

1. **开头引入段**（可选）：原文中无法归入事件、琐事、后续计划的开场白或闲聊内容的整理版
2. **事件**（一个或多个）：`## 事件：事件标题`
3. **琐事**（可选）：`## 琐事`
4. **后续计划**（可选）：`## 后续计划`

> 日记分析（心情、标签、分析六部分）不在整理结构中，而是在 AI 智能分析阶段独立生成（见"AI 智能分析"章节）。

**事件正文表达规则**

- 事件正文承载原来的背景、动机、过程、结果。
- 事件正文写成自然段，不默认使用编号。
- 只有原文步骤非常清晰、且编号能明显提升可读性时，才使用编号。
- 事件正文可以包含当时发生的即时感受，但不展开心理分析。
- 事实信息优先合并写，避免被拆成过细字段。
- 生活细节默认保留，包括具体行为、人物互动、玩笑、吐槽、临时插曲和有记忆点的表达。
- 思考类事件要保留思考链条，包括触发原因、推理过程、尝试方向、工具选择、判断变化和阶段性结论。
- 观点类事件要保留观点推演，包括原始判断、支撑理由、类比、转折、保留意见和后续认知方向。
- 事件标题要具体概括“发生了什么”，不使用过泛的主题词。
- 事件标题优先使用“具体人物 / 具体对象 + 具体动作 / 变化”的句式。

示例：

```markdown
## 事件：今天早晨林萧鹏问我版本管理平台是否有用，他准备把它重新做出来

今天早晨林萧鹏突然问我管理平台当时用起来感觉怎么样，有没有效果。我说有效果，但后来被合并到超图后就被否定了。他说现在准备重新搞一套，因为他在做 AI 项目版本管理时也遇到了一些问题。我想把原来的版本管理平台捡起来继续做，一方面是给自己一个学习软件开发全流程的机会，另一方面也是把之前没完成的遗憾补上。
```

**琐事展示格式**

```markdown
## 琐事

1. 琐事内容一
2. 琐事内容二
3. 琐事内容三
```

- 标题固定为 `## 琐事`。
- 内容使用编号列表。
- 琐事为可选块，只有原文存在未展开但有记录价值的内容时才展示。
- 琐事指无实质价值、仅简单提及、未展开描述（缺乏细节、情感或因果逻辑）的内容，通常篇幅短、信息密度低。
- 已归入事件的内容不得再出现在琐事中（去重约束）。

**后续计划展示格式**

```markdown
## 后续计划

1. 计划内容一
2. 计划内容二
```

- 标题固定为 `## 后续计划`。
- 内容使用编号列表。
- 后续计划为可选块，只有原文存在明确指向未来安排的内容时才展示。
- 后续计划按重要性排序，而非按原文时间顺序排列。
- 反思与成长中提到的后续计划，也需同步列入后续计划部分。
- 后续计划条目需改写为语义清晰的书面表述，不保留口语化的模糊表达。

**感受表达规则**

- 事件正文里可以写具体经过中的即时感受。
- 独立的感受字段只总结整个事件的情绪变化。
- 感受字段不复述过程细节。
- 只有原文明确表达情绪时，才展示感受字段。

示例：

```markdown
### 感受
这件事里的情绪从烦躁、被忽视，转为被回应后的轻松和高兴。
```

**反思与成长表达规则**

- "反思与成长"可以承载反思、感悟、成长、自我认识等内容，但展示时不拆成内部小标题。
- 只有原文明确表达了对应内容时才整理。
- 原文没有明确表达时，不展示该字段。
- 有多条反思时，使用编号列表展示。
- 只有一条反思时，直接写自然段，不加编号。

示例：

```markdown
### 反思与成长
我意识到以后遇到这种不回应的情况，不能一直重复找同一个人，而是要更早判断是否需要换一种推进方式。
```

**模糊表达处理规则**

- 当原文出现模糊表达时，保留原始表达，并标注具体未明确的点。
- 不根据上下文强行解释成明确结论。
- 不把模糊表达改写成原文没有支撑的判断。

示例：

```markdown
## 事件：处理一件挺麻烦的事

我提到这件事“挺麻烦”，但原文未明确麻烦具体来自哪里。
```

#### 日记分析

日记分析在 AI 智能分析阶段执行，不在整理阶段生成。分析阶段基于整理后的结构化日记和原始文本，通过独立流水线生成心情、标签和日记分析六部分。

**指导思想：日记分析的目标是帮助用户认清自己。**

日记分析不是评价用户，也不是替用户下结论，而是帮助用户从当天记录中看见：

- 自己当时有什么情绪变化。
- 自己采取了什么行为和决策。
- 自己真正关注什么。
- 这些关注背后反映了什么当下需求。
- 自己如何理解这件事。
- 这件事反映出自己看重什么。
- 自己对世界、他人、自己、知识或方法的理解是否存在明显偏差。
- 自己随手记录的想法可以如何整理成更完整的知识框架。
- 自己在日记中提出的问题可以如何获得清晰回答。
- 接下来可以做什么低成本、具体、可执行的调整。

日记分析属于解释层，允许基于当天事实进行推导，但必须遵守以下边界：

- 只分析当天这篇日记，不引用长期历史。
- 不做长期人格判断。
- 不做心理诊断。
- 不给用户贴标签。
- 较强推断必须写依据，依据来自当天结构化日记中的具体事件或事实。

当前日记分析包含：

1. **情绪分析**：帮助用户理解情绪怎么来的，并找到改变路径，包括当下如何化解情绪、未来如何减少坏情绪和增加好情绪。
2. **行为与决策分析**：分析用户当天做了什么、做了什么选择、遇到问题时如何处理、行为带来了什么结果或可能风险，其中核心是判断问题处理方式是否有效，以及如何改进。
3. **关注点与需求**：分析用户当天真正关注什么、当下真正想要什么、正在维护什么，以及用户自己也可能尚未意识到的心理诉求和需求满足方式。
4. **认知校准**：识别用户对世界、他人、自己、知识、方法或事件因果的理解是否存在明显偏差，并在有依据时进行温和纠正。
5. **可行动建议**：基于前三类核心分析结果，给出事件级建议和日记级建议。日记级建议不必是事件级建议的合并，可以包含不归属于任何单个事件、但基于整篇日记整体分析得到的建议。
6. **问题解答与认知完善**：先找出并回答日记中的明确问题和隐性问题，再把日记中的零散知识、随想、判断、类比和问题解答结果，转化为更完整、可复用的认知体系。

**情绪分析** 的定义：

帮助用户理解情绪怎么来的，并找到改变路径：当下如何化解，未来如何减少坏情绪、增加好情绪。

输出分为两层：

- 事件级情绪分析：展示在对应事件的 Tab 中。
- 日记级情绪总结：展示在分析 Tab 中。

情绪分析只基于结构化日记中的 events，不再回到原始文本查找额外依据。

分析内容：

- 用户出现了哪些主要情绪，属于好情绪、中性或轻度压力情绪，还是坏情绪。
- 情绪是如何变化的，强度如何。
- 哪些具体事实触发了情绪变化。
- 情绪背后反映了什么被触动，例如需求、边界、控制感、确定性、价值排序或自我叙事。
- 情绪背后的真实冲突是什么，例如人的期待与现实规律、控制期待与对象天性、个人需求与对方限制之间的冲突。
- 当下如何化解情绪。
- 未来如何减少坏情绪、增加好情绪。
- 可以区分表层情绪和更深层的情绪，但必须有事件依据。
- 如果某个事件没有明显情绪线索，事件级情绪分析返回空数组。
- 如果整篇日记没有明显情绪线索，日记级情绪总结返回空数组。

处理流程：

1. 识别事件中的主要情绪，区分好情绪、中性或轻度压力情绪、坏情绪，并判断情绪强度。
2. 找出触发情绪的具体事实，不脱离 events 推断。
3. 分析情绪背后的真实冲突，不只站在用户角度，也要看对方、对象或现实条件的客观规律。
4. 挖掘深层根因，例如期待落空、控制感丧失、边界被侵犯、不确定性、价值感受损、责任不清、想改造无法改造的对象。
5. 给出当下化解方向：好情绪分析如何更多创造，中性情绪分析如何转化为行动信号，坏情绪分析如何先降低扩大。
6. 给出未来预防方向：治标是解决这件具体事的根因，治本是通过工作方式、沟通方式、边界设置、预期管理、工具流程或心态调整，减少类似情绪再次触发。

禁止项：

- 不用百分比量化。
- 不做心理诊断。
- 不把短期情绪说成长期状态。
- 不写“你是一个情绪化的人”。
- 不输出无依据的深层解释。
- 不把改变目标写成强行改造他人、动物或不可控条件。

承接的自我认识角度：

- 情绪触发点。
- 控制感与不确定性带来的情绪反应。
- 当下化解方式。
- 未来预防方式。

**行为与决策分析** 的定义：

帮助用户看清当天遇到问题时的处理方式，判断这种方式是否有效、有什么结果和风险，并找到更好的处理策略。

输出分为两层：

- 事件级行为与决策分析：展示在对应事件的 Tab 中。
- 日记级行为与决策总结：展示在分析 Tab 中。

行为与决策分析只基于结构化日记中的 events，不再回到原始文本查找额外依据。

分析内容：

- 用户先做了什么，后做了什么。
- 用户在关键节点做了什么选择。
- 用户遇到问题时怎么处理，这是本模块的分析核心。
- 用户是主动推进、等待观察、反复确认、寻求外部帮助、暂时回避，还是先处理情绪再处理事情。
- 行为背后体现出的当天应对方式，例如无效重复、短期压制、回避拖延、过度控制或误判问题机制。
- 行为带来了什么结果或影响。
- 可以评价行为有效性。
- 如果事件已有结果，基于结果评价。
- 如果事件还没有结果，可以基于当天事实适当推测后续风险。
- 下次更合理的问题处理方式是什么。
- 如果某个事件没有明显行为或决策线索，事件级行为与决策分析返回空数组。
- 如果整篇日记没有明显行为或决策线索，日记级行为与决策总结返回空数组。

处理流程：

1. 识别用户当天做了什么，以及做了哪些选择。
2. 找出用户遇到的具体问题，并把问题处理方式作为分析核心。
3. 判断当前处理方式是否有效：哪些部分解决了问题，哪些部分没有解决问题。
4. 识别做事方式类型，例如主动推进、等待观察、反复确认、寻求帮助、回避拖延、短期压制、过度控制、无效重复。
5. 分析行为已经带来的结果，以及继续使用该方式可能带来的风险。
6. 如果同一方式重复多次仍无效，要指出问题不是力度不够，而是处理机制可能不对。
7. 给出改进方向：保留有效部分，停止无效重复，换成更符合问题机制的方法。

禁止项：

- 不上升为长期人格。
- 不写“你一直都是……”。
- 不写“你有控制欲”“你是回避型人格”等标签。
- 不脱离当天事实分析行为模式。
- 不把风险推测写成确定结论。
- 不输出高成本建议。
- 不把无效重复解释成单纯不够努力。

承接的自我认识角度：

- 行为反应方式。
- 决策方式。
- 问题处理路径。
- 有效做法与无效做法。
- 行为风险与改进方向。

**关注点与需求** 的定义：

帮助用户理解自己模糊、未说出口甚至尚未意识到的心理诉求，包括真正关注什么、真正想要什么、正在用什么方式满足需求，以及这种满足方式是否健康、稳定、可持续。

输出分为两层：

- 事件级关注点与需求分析：展示在对应事件的 Tab 中。
- 日记级关注点与需求总结：展示在分析 Tab 中。

关注点与需求分析只基于结构化日记中的 events，不再回到原始文本查找额外依据。

分析内容：

- 用户表面关注什么。
- 用户真正关注的是什么。
- 用户当下真正想要什么。
- 用户正在维护什么。
- 用户对这件事形成了什么理解。
- 这件事反映出用户看重什么。
- 用户没有说出口、自己也可能尚未意识到的心理诉求。
- 用户满足需求的方式是否健康、稳定、可持续。
- 可以分析未说出口的期待，例如希望对方主动回应、希望事情有明确进展、希望自己的投入被看见、希望责任边界更清楚。
- 可以写“你真正想要的是……”，但必须有事件依据。
- 如果某个事件没有明显线索，事件级关注点与需求分析返回空数组。
- 如果整篇日记没有明显线索，日记级关注点与需求总结返回空数组。

内部分析框架：

- 用户表面关注什么。
- 用户真正想要什么。
- 用户正在维护什么。
- 用户如何理解这件事。
- 用户看重什么。
- 用户是否存在自己尚未意识到的隐性需求。
- 用户满足需求的方式是否单一、脆弱或过度依赖外部反馈。

这些问题只作为内部分析框架，不必在展示层显式拆成小标题。输出时应使用自然段，帮助用户理解自己为什么会被这件事牵动。

处理流程：

1. 识别用户表面关注的内容，例如成绩、表现、输赢、对错、对方反应。
2. 从事件、情绪、行为和反复出现的在意点里，推断用户真实关注的内容。
3. 分析用户未说出口、自己也可能尚未意识到的需求，例如陪伴、连接、被看见、被选择、归属感、认可、安全感、掌控感。
4. 判断是否存在关注点错位：表面关注某个指标，实际想要另一种心理满足。
5. 分析需求满足方式是否健康、稳定、可持续，例如是否过度依赖某个人、某个反馈或单一快乐来源。
6. 给出更健康的满足方向：不是否定需求，而是拓宽需求满足路径，让快乐、价值感和支持来源更稳定。

常见分析方向：

- 真正想要什么：被回应、被理解、结果明确、责任清楚、关系稳定、事情推进。
- 害怕或抗拒什么：被忽视、不公平、失控、责任模糊、投入没有回报。
- 正在维护什么：边界、尊严、秩序感、投入感、公平感、掌控感。
- 如何理解这件事：用户把事件解释成什么，例如“我的表达没有被看见”“又是我一个人在推动”。
- 看重什么：效率、公平、尊重、确定性、责任、关系、自主性。
- 关注点错位：表面关注成绩、表现、对错，实际关注陪伴、连接、被看见、被选择或归属感。
- 需求满足方式风险：快乐来源过于单一、过度依赖某个人的反馈、把价值感建立在外部关注上。
- 更健康的满足方向：保留关系中的快乐，同时培养爱好、个人成长、稳定作息或更丰富的支持来源。

禁止项：

- 不做心理诊断。
- 不写长期人格结论。
- 不把推导写成绝对事实。
- 不写“你缺乏安全感”“你很依赖认可”。
- 对“填补内心空虚”这类强心理解释要谨慎，除非 events 有明确依据；更稳妥的写法是指出可能在寻求情绪陪伴、被关注、被选择或归属感。
- 不替用户扩展到原文没有支撑的人生经历。

承接的自我认识角度：

- 未说出口的期待。
- 边界感。
- 控制感与不确定性。
- 自我叙事。
- 价值排序。
- 关注点错位。
- 需求满足方式。

**认知校准** 的定义：

识别日记中用户对世界、他人、自己、知识、方法或事件因果的理解，判断其中是否存在明显的过度概括、绝对化、误解、片面理解或事实性错误，并在有依据时进行温和纠正。

分析对象：

- 对世界的判断。
- 对他人的判断。
- 对自己的判断。
- 对事件原因的判断。
- 对知识点、方法论、工作方法的理解。
- 对经验教训的归纳。

允许项：

- 指出过度概括。
- 指出绝对化表达。
- 指出事实支撑不足。
- 指出知识理解错误。
- 补充更准确的理解。
- 把“情绪中的判断”和“事实可支持的判断”分开。

禁止项：

- 不否定用户感受。
- 不站在道德高地教育用户。
- 不把所有负面判断都改成积极话术。
- 不在不确定时强行纠错。
- 不对专业知识胡乱纠正。
- 不把认知校准写成行动建议。

与其他模块的边界：

- **关注点与需求**：解释“用户为什么这样看”。
- **认知校准**：检查“用户这样看是否准确、是否过度、是否需要补充”。
- **可行动建议**：给出“下次可以怎么做”。

处理规则：

- 对世界、他人、自我的整体判断，要优先区分情绪表达和事实可支持的结论。
- 对知识点、方法论、工作方法的错误理解，如果有足够把握，可以直接指出并补充更准确理解。
- 如果结构化事件信息不足或模型没有足够把握，应返回空数组，不能装作确定。
- 认知校准输出事件级和日记级两层：事件级结果展示在对应事件的 Tab 中，日记级结果展示在分析 Tab 中。
- 如果某个事件没有明显需要校准的判断，该事件认知校准返回空数组。
- 如果整篇日记没有明显需要校准的判断，日记级认知校准返回空数组。

**可行动建议** 的定义：

基于前三类核心分析结果，给出用户下次遇到类似情况时可以尝试的低成本、具体、可执行行动。

输出分为两层：

- 事件级可行动建议：展示在对应事件的 Tab 中，只针对单个事件中能明确落地的动作。
- 日记级可行动建议：展示在分析 Tab 中，可以来自某个关键事件、多个事件共同呈现的问题、当天整体情绪/行为/需求分析，或不适合归属到单个事件的整体调整动作。

分析内容：

- 用户下次可以如何化解当下情绪、减少坏情绪触发、创造更多好情绪。
- 用户下次可以如何停止无效重复、保留有效方式、换成更符合问题机制的方法。
- 用户下次可以如何更健康地满足真实需求、减少单点依赖、拓宽快乐、价值感和支持来源。
- 用户下次可以尝试怎么表达。
- 用户下次可以如何降低不确定性。
- 用户下次可以如何区分事实、情绪和解释。
- 用户下次可以如何保护边界。
- 用户下次可以如何把需求说清楚。
- 用户下次可以如何推进事情的下一步小动作。

输出规则：

- 每条建议使用“下次可以尝试……”表达。
- 不限制建议数量，但只输出有依据、可执行的建议，不为凑数量生成建议。
- 可以基于 events 中的具体事实。
- 必须基于情绪分析、行为与决策分析、关注点与需求分析。
- 可行动建议是前三类分析的汇总落地，不重新做一套脱离分析依据的建议。
- 如果某个事件没有明显可行动建议，该事件建议返回空数组。
- 如果整篇日记没有明显可行动建议，日记级建议返回空数组。

处理流程：

1. 从情绪分析中提取情绪触发点、根因、当下化解方式和未来预防方向。
2. 从行为与决策分析中提取有效做法、无效做法、行为风险和改进方向。
3. 从关注点与需求分析中提取真实诉求、心理依赖、需求满足方式问题和更健康的满足路径。
4. 将前三类分析压缩成少量具体动作，避免重复分析。
5. 过滤掉无依据、泛泛而谈、高成本或不可执行的建议。
6. 按事件级和日记级分别输出：事件级建议针对单个事件，日记级建议针对整篇日记呈现出的共性问题。

承接的自我认识角度：

- 从自我理解走向下一次行动。
- 把情绪、需求、边界转化为具体做法。
- 把有效/无效做事方式转化为下次处理策略。

**可行动建议** 的表达规则：

- 使用“下次可以尝试……”这类建议式表达。
- 不使用“你应该……”这类命令式表达。
- 建议服务于下一次遇到类似情况时的具体行动。
- 建议必须低成本、具体、可执行。
- 不输出泛泛而谈的鸡汤。
- 不输出高成本建议，例如辞职、结束关系、重大关系决策等，除非原文明确表达相关打算。

**问题解答与认知完善** 的定义：

日记中有些内容不是事件复盘，而是用户在当下记录的随想、知识片段、模糊判断、类比、疑问或尚未想清楚的推理。问题解答与认知完善的目标，是先把日记中的问题回答清楚，再把零散知识和问题解答结果转化为更完整、可复用的认知结构。

认知完善不是认知校准。认知校准检查“这个理解是否准确、是否过度”；认知完善回答“这个念头可以如何变成更完整的知识体系”。

输出分为两层：

- 事件级问题解答与认知完善：展示在对应事件的 Tab 中。
- 日记级问题解答与认知完善：展示在分析 Tab 中，可以综合多个事件中共同出现的随想、问题和知识线索。

处理顺序：

- 先找出日记中的明确问题和隐性问题。
- 直接给出问题和回答，回答必须突出核心重点；复杂问题可以在回答文本内部简要拆解。
- 最后基于日记中的零散知识、随想、判断、类比和问题解答结果，整理成体系化认知。

问题解答内容：

- 回答日记中明确提出的问题。
- 识别并回答“我不知道……”这类隐性问题。
- 回答“这个有什么用”这类价值问题。
- 回答“这个该归到哪里”这类分类问题。
- 回答“这个到底好不好”这类判断问题。
- 如果问题没有可靠答案，拆成“能回答的部分”和“不能可靠回答的部分”。

认知完善内容：

- 把零散想法整理成概念、关系、因果链、适用边界和反例。
- 对日记中提到的知识点补充背景、分类、框架或理解路径。
- 区分事实、观点、推测和价值判断。
- 提炼可以沉淀下来的知识点。
- 给出后续可以继续理解的方向，但不把它写成行动建议。

输出规则：

- 只基于 events 和本环节前序问题解答结果，不输入、不引用原始文本。
- 可以使用模型已有的通用知识进行解释，但不能编造具体事实、数据、来源或确定性结论。
- 没有问题时，问题解答返回空数组。
- 没有需要完善的认知时，认知完善返回空数组。
- 如果问题需要实时信息、专业事实核查或日记信息不足，应拆成“能回答的部分”和“不能可靠回答的部分”。
- 不做心理诊断，不做长期人格判断，不输出行动建议。

#### 元数据

| 元数据 | 生成阶段 | 说明 |
|---|---|---|
| 地点 | 整理阶段 | AI 整理时自动提取，用户可修改 |
| 心情 | 分析阶段 | AI 分析时自动提取，用户可修改 |
| 标签 | 分析阶段 | AI 分析时自动提取，用户可修改，也可手动新建标签 |

> 不额外增加其他元数据字段。

**标签类型**

标签不是为了把日记简单分类，而是为了给后续检索、AI 对话、人物画像、心路历程和知识沉淀提供入口。

| 类型 | 作用 | 示例 |
|---|---|---|
| 领域标签 | 粗粒度筛选日记 | 工作、生活、关系、健康、学习、娱乐 |
| 主题标签 | 串起长期反复出现的具体事项 | 版本管理平台、AI 开发、小红书爬虫、遛狗 |
| 人物 / 对象标签 | 串起具体人物、关系和重要对象 | 林萧鹏、田总、媳妇、达达 |
| 心理主题标签 | 串起情绪、需求和内在模式 | 不确定性、控制感、遗憾、无奈、成就感 |
| 知识点标签 | 串起学习内容、方法、概念和做事方式 | 软件工程、软件开发流程、需求分析、原型设计、AI 辅助开发、做事方式、项目管理、版本管理 |

**标签提取规则**

- AI 优先提取主题标签、人物 / 对象标签、心理主题标签、知识点标签。
- 领域标签作为辅助粗分类。
- 标签必须来自原文或整理内容中的明确依据。
- 不生成空泛评价型标签，例如“成长”“感悟”“重要”“日常”。
- 心情已有独立字段，不用“开心”“难过”等单纯心情词作为标签。
- 用户可以修改 AI 提取的标签，也可以手动新建标签。

#### AI 智能分析

AI 智能分析是整理之后的独立阶段，基于整理后的结构化日记和原始文本，生成心情、标签和日记分析六部分。

| 项目 | 说明 |
|---|---|
| 触发方式 | 用户在已整理状态的日记详情页点击"分析"按钮 |
| 数据源 | 整理后的结构化日记 + 原始文本 |
| 重新分析 | 可触发"重新分析"覆盖之前结果 |
| 可编辑性 | 分析结果只读展示，不可编辑 |

**分析流水线**

分析阶段分为 3 个环节，并行执行：

1. **环节 1：心情 + 标签提取**（精确任务）— 提取当天整体心情和各事件的结构化标签
2. **环节 2：核心分析 + 可行动建议**（描述性、解释性与行动导向推导）— 情绪分析、行为与决策分析、关注点与需求、可行动建议
3. **环节 3：认知校准 + 问题解答 + 认知完善**（校准性与知识整理推导）— 先校准认知，再解答问题，最后把零散知识和问题解答转化为体系化认知

环节 1、2、3 之间没有输入依赖，可由程序并行调用；三个环节都完成后再合并写入分析结果。

> 各环节的详细 Prompt 和流水线设计见第 4 节。日记分析各子任务的定义见上方"日记分析"章节。

**分析内容**

- **心情**：当天整体情绪状态
- **事件级标签**：5 类（领域 / 主题 / 人物对象 / 心理主题 / 知识点），展示在事件卡片内，不同类型用不同颜色区分，用小尺寸样式
- **日记级标签**：所有事件级标签去重汇总，展示在日记顶部
- **日记分析六部分**：情绪分析、行为与决策分析、关注点与需求、认知校准、可行动建议、问题解答与认知完善

**展示方式**

在日记详情页以独立 Tab（分析 Tab）展示，与日记 Tab 并列。分析 Tab 包含心情、日记分析六部分，均为只读。

#### 日记状态

| 状态 | 说明 | 原始文本 | 参与分析 |
|---|---|---|---|
| 草稿 | 保存后，可继续编辑 | 可修改 | 否 |
| 已发布 | 发布后，原始文本锁定，可触发整理 | 不可改 | 否 |
| 已整理 | AI 整理完成，整理内容可手动修改 | 不可改 | 是 |
| 已分析 | AI 分析完成，分析结果只读 | 不可改 | 是 |

> 状态流转：草稿 →（发布）→ 已发布 →（整理）→ 已整理 →（分析）→ 已分析

**状态操作规则**

| 状态 | 编辑原文 | 编辑结构化结果 | 重新整理 | 触发/重新分析 |
|---|---|---|---|---|
| 草稿 | ✅ | — | — | — |
| 已发布 | ❌ | — | ✅ | — |
| 已整理 | ✅ | ✅ | ✅ | ✅ 触发分析 |
| 已分析 | ❌ | ✅ | ❌ | ✅ 重新分析 |

关键原则：进入已分析状态 = 整理定稿，原文和整理流程均锁定；结构化结果始终可编辑；分析结果只读。

### 2.2 模块二：日记浏览与查找

#### 浏览

- **默认视图**：日历视图，可切换到时间线视图
- **日历视图展示**：每天显示心情颜色 + 整理/分析状态标记（未整理的日记有灰色点等特殊标记）
- **时间线视图**：按时间倒序列出日记

#### 筛选

- **按标签筛选**：通过标签分类过滤日记

#### 搜索

- **全文搜索**：仅搜索整理后的内容（标题、摘要、正文），不搜索原始文本

### 2.3 模块三：日记详情（含 AI 对话）

> 从模块二点击进入，展示日记整理后的内容，同时可围绕该篇日记与 AI 展开反思对话。

#### 日记详情展示

- 展示 AI 整理后的结构化日记内容，包括开头引入段（可选）、事件（事件正文 + 可选感受 + 可选反思与成长）、琐事（可选）、后续计划（可选）
- 原始文本可展开查看
- 元数据（标签、心情、地点）可编辑
- 显示与该篇日记关联的待办事项（见模块九）

**按状态展示差异：**

- **已整理状态**：显示编辑按钮 + AI 分析按钮 + 重新整理按钮，原文可展开编辑
- **已分析状态**：日记 Tab（结构化内容 + 标签展示）+ 分析 Tab（心情 + 日记分析六部分，只读）

**标签展示规则：**

- 事件级标签展示在事件卡片内，5 类标签用不同颜色区分
- 日记级标签汇总展示在日记顶部

**分析展示规则：**

- 分析 Tab 只在 `已分析` 状态展示；分析 Tab 展示日记级分析。
- 事件卡片内的 AI 分析按数据是否存在展示，不强依赖日记状态；后端返回了 `event.analysis` 且其中任一字段有内容时显示。
- 日记级分析和事件级分析使用同一套字段名，通过所在层级区分：
  - `organized.analysis` 表示日记级分析。
  - `organized.events[].analysis` 表示事件级分析。
- 分析内容分为两组展示：
  - **自我理解与行动**：情绪分析、行为与决策分析、关注点与需求、可行动建议。
  - **认知整理**：认知校准、问题解答、认知完善。
- 事件卡片展开后先展示事件正文、感受、反思与成长，再用“AI 分析”标题分隔 AI 解释层。
- 两个分析分组使用浅色区块承载；模块内容使用条目列表展示。
- `question_answers` 使用问答卡片展示，元素只包含 `question` 和 `answer` 两个字段。
- 空模块隐藏；如果某个分组下所有模块都为空，则隐藏整个分组；如果分析 Tab 完全无分析内容，则显示“暂无分析数据”。
- 分析 Tab 顶部保留醒目的“今日心情”展示。

#### 反思对话

- **入口**：日记详情页内嵌对话区域
- **上下文范围**：以当前日记为主，AI 可参考近期日记做关联分析
- **交互方式**：问答式 + 引导反思式

#### 数据反哺

- 对话内容作为数据源，24h 无新消息后自动沉淀到人物画像、心路历程和认知洞察模块

```json
            "一条事件级认知完善"
          ]
        },
        "sort_order": 0
      }
    ]
  }
}
```

接口约束：

- `organized.analysis` 是日记级分析，只在已有分析结果时返回；无分析结果时返回 `null`。
- `organized.events[].analysis` 是事件级分析；该事件没有任何事件级分析时返回 `null` 或省略该字段。
- 日记级和事件级分析字段名必须一致，不能使用 `diary_` / `event_` 前缀。
- 所有分析数组字段没有内容时返回空数组，不返回空字符串。
- `question_answers` 的元素只能包含 `question` 和 `answer` 两个字段；无法可靠回答的内容直接写入 `answer`。
- `mood` 只出现在日记级 `organized.analysis` 中；事件级 `analysis` 不包含 `mood`。

| POST | /api/tags | 新建标签 |

**对话接口**

### 3.5 AI 提示词设计

#### 日记整理提示词

整理阶段采用 5 环节流水线（文本清洗 → 清洗审核 → 事件整理 → 三字段结构化 → 内容审核）；标题、摘要、地点在分析阶段环节 7 与心情、标签一并生成。

**输出**：标题、摘要、地点、结构化日记正文（引入段 + 事件 + 琐事 + 后续计划）

**提示词要点：**

- 结构化日记只做保真整理，不做内容压缩、推断或补充
- 地点从内容中推断，多个地点用中文顿号连接
- 事件按目标拆分，同一事件散落内容汇聚
- 事件三字段：正文、感受（需有原文线索）、反思与成长（需有原文表达）
- 内容审核对照原文检查编造、遗漏、推断等问题
- 各环节详细 Prompt 见第 4 节

#### AI 分析提示词

分析阶段分三个环节执行：

**环节 7：元数据 + 心情 + 标签提取**

输入：结构化日记
输出：标题（title）、摘要（summary）、地点（location）、心情（mood）、事件级标签（event_tags，按 5 类分组：domain / topic / person_object / psychological / knowledge）

提示词要点：

- 心情用一个短词表示当天整体情绪，必须有明确线索支撑
- 标签按五类提取，事件级标签与事件一一对应
- 标签必须有明确文本依据，不生成空泛评价型标签
- 心情词不重复作为标签

**环节 8：核心分析 + 可行动建议**

输入：结构化日记中的 events
输出：事件级 + 日记级三类核心分析，以及可行动建议：

- 情绪分析（event_emotion_analyses、diary_emotion_analyses）
- 行为与决策分析（event_behavior_decision_analyses、diary_behavior_decision_analyses）
- 关注点与需求（event_self_understanding_analyses、diary_self_understanding_analyses）
- 可行动建议（event_action_suggestions、diary_action_suggestions）

提示词要点：

- 只分析当天日记，不引用长期历史
- 不做人格判断、心理诊断或贴标签
- 较强推断必须写依据
- 没有明显分析线索时返回空数组
- 没有明显建议时返回空数组
- 事件级分析展示在对应事件卡片内，日记级总结展示在分析 Tab
- 日记级建议可以包含不归属于任何单个事件、但基于整篇日记整体分析得到的建议

**环节 9：认知校准 + 问题解答 + 认知完善**

输入：结构化日记中的 events
输出：事件级 + 日记级认知校准、问题解答和认知完善：

- 认知校准（event_cognitive_calibration_analyses、diary_cognitive_calibration_analyses）
- 问题解答与认知完善（event_question_answers、diary_question_answers、event_cognitive_enhancements、diary_cognitive_enhancements）

提示词要点：

- 认知校准识别明显偏差并温和纠正
- 区分事实、情绪、解释和判断
- 先找出日记中的问题，直接输出问题和回答；回答突出核心重点，再做认知完善
- 认知完善基于日记中的零散知识、随想、判断、类比和问题解答结果
- 输出事件级和日记级两层结果
- 没有明显需要校准的判断时返回空数组
- 没有问题时返回空数组
- 没有需要完善的认知时返回空数组
- 依据不足时不强行纠错

> 各环节的详细 Prompt 和流水线设计见第 4 节。

## 4. AI 智能整理与理解详细设计

### 背景

当前日记整理流程采用 5 阶段流水线，将语音转文字的原始文本逐步整理为结构化日记；元数据在后续分析阶段生成：

```text
文本清洗 → 清洗审核 → 事件整理 → 三字段结构化 → 内容审核 → 输出
```

最终输出包含标题、摘要、地点和结构化日记正文（引入段、事件、琐事、后续计划）。

设计原则：

- 原文是最高事实来源。
- 清洗结果是后续处理的基准文本，但必须经过清洗审核。
- 每个环节只做自己的事，不提前做后续环节的工作。
- 能提升可读性，但不能改写事实。

### 技术实现方案

#### 技术框架：LangGraph

流水线采用 [LangGraph](https://github.com/langchain-ai/langgraph) 框架构建，将 5 阶段整理流水线建模为线性状态图。

**核心概念映射：**

| 概念 | 在本项目中的对应 |
|---|---|
| StateGraph | 将 5 阶段整理流水线建模为线性图，节点间通过 Edge 串联 |
| Node | 每个 AI 调用环节映射为一个 Node 函数，接收 State、返回 State 更新 |
| State | 共享数据结构（TypedDict），包含所有中间产物，节点间通过 State 传递数据 |

**图的拓扑结构：**

```
START → text_clean → clean_check → event_organize → template_fill → content_check → output → END
```

每个 Node 对应一次独立的 LLM 调用，Node 内部只读取 State 中自己需要的字段、写入自己产出的字段，不跨节点直接通信。

#### LLM 接入方式

使用官方 `langchain-deepseek` 包的 `ChatDeepSeek` 替代现有 httpx 直调。DeepSeek API 完全兼容 OpenAI 格式，LangChain 原生支持。

切换动机：

- LangGraph Node 内部需要返回 LangChain 消息对象，使用 `ChatDeepSeek` 可无缝对接。
- LangChain 提供统一的重试、超时、回调机制，减少手动管理 httpx 请求的样板代码。
- 与 LangGraph 的 State 传递、Checkpoint 序列化天然兼容。

#### 断点续跑机制（Checkpoint）

流水线包含 6 次串行 LLM 调用，任意一次失败都可能导致整体中断。断点续跑机制确保失败后能从断点恢复，而非从头重跑。

**核心原则：**

- 每个 super-step（节点执行完成）自动保存 State 快照到 checkpoint。
- 恢复时复用相同标识，LangGraph 自动跳过已完成的节点。
- 整理完成后主动清理 checkpoint，避免存储膨胀。

**实现方案：**

| 项目 | 方案 |
|---|---|
| Checkpoint 存储 | `langgraph-checkpoint-postgres` 的 `AsyncPostgresSaver`，复用现有 PostgreSQL |
| 线程标识 | `thread_id` 复用 `task_id`（UUID），无需额外映射 |
| 断点恢复 | 失败后用户重新触发整理，系统检测 checkpoint 存在，使用相同 `thread_id` 调用，LangGraph 自动从断点恢复 |
| 清理策略 | 整理成功后主动调用 `checkpointer.adelete_thread()` 清理 checkpoint |

#### 数据库驱动统一

项目统一使用 psycopg3 替代 psycopg2：

- SQLAlchemy 连接串前缀从 `postgresql+psycopg2://` 改为 `postgresql+psycopg://`。
- 消除 psycopg2/psycopg3 共存问题。
- psycopg3 原生支持 async，与 FastAPI 异步架构更契合。
- `langgraph-checkpoint-postgres` 依赖 psycopg3，统一驱动后避免版本冲突。

#### 依赖变更

新增依赖：

| 包名 | 用途 |
|---|---|
| `langgraph` | 流水线状态图框架 |
| `langchain-core` | LangChain 核心抽象 |
| `langchain-deepseek` | DeepSeek LLM 接入 |
| `langgraph-checkpoint-postgres` | Checkpoint 持久化存储 |

替换依赖：

| 移除 | 替换为 | 原因 |
|---|---|---|
| `psycopg2-binary` | `psycopg` | 统一为 psycopg3，原生 async 支持 |

#### State 数据结构

State 使用 TypedDict 定义，承载流水线全生命周期的数据流转：

```python
class PipelineState(TypedDict):
    # ── 输入字段 ──
    original_text: str          # 日记原文
    task_id: str                # 整理任务 ID（UUID）
    diary_id: str               # 日记 ID
    user_id: str                # 用户 ID

    # ── 阶段 1 产物：文本清洗 ──
    cleaned_text: str

    # ── 阶段 2 产物：清洗审核 ──
    checked_text: str
    clean_check_log: list

    # ── 阶段 3 产物：事件整理 ──
    introduction: str
    events_raw: list            # 事件整理的原始事件列表
    trivia: list
    plans: list

    # ── 阶段 4 产物：三字段结构化 ──
    structured_events: list     # 结构化后的事件列表

    # ── 阶段 5 产物：内容审核 ──
    final_introduction: str
    final_events: list
    final_trivia: list
    final_plans: list
    check_log: list

    # ── 阶段 6 产物：元数据（标题/摘要/地点） ──
    title: str
    summary: str
    location: str

    # ── 进度追踪 ──
    current_step: str           # 当前执行步骤，同步更新到 organize_tasks.current_step
```

每个 Node 只读取自己需要的输入字段、写入自己产出的输出字段。未执行的节点对应字段为空或缺省值。

#### 前端适配说明

Node 内部继续更新 `organize_tasks.current_step` 字段，前端轮询机制无需改动。LangGraph 的引入对前端完全透明，前端仍通过轮询 `GET /api/diaries/{id}` 获取整理进度和结果。

### 各环节 Temperature 配置

| 环节 | Temperature | 说明 |
|------|------------|------|
| 环节1：文本清洗 | 0.3 | 事实准确性优先，不需创造性 |
| 环节2：清洗审核 | 0.3 | 审核需要严格 |
| 环节3：事件整理 | 0.5 | 识别+汇聚需要理解灵活度 |
| 环节4：三字段结构化 | 0.5 | 结构化重组需要灵活度 |
| 环节5：内容审核 | 0.3 | 审核需要严格 |
| 环节6：元数据生成 | 0.3 | 提取需要精确 |

### 环节 1：文本清洗

#### 环节定位

文本清洗用于合并原来的“轻度清洗”和“深度清洗”两个步骤。

目标是把语音转文字整理成一份可读的基准文本，供后续事件整理使用。

文本清洗可以负责“变顺”，但不负责最终判真；事实纠偏交给下一步“清洗审核”。

#### 输入

```json
{
  "original_text": "原始语音转文字内容"
}
```

#### 输出

```json
{
  "cleaned_text": "清洗后的文本"
}
```

#### Prompt

```text
你是一个日记文本清洗助手。请对用户提供的日记原文（语音转文字）进行清洗整理，生成一份可读的基准文本，供后续事件整理使用。

## 最高准则
尊重事实，但不过度尊重原始口语形态。整理结果必须让人能看懂，这是给人读的。

## 清洗目标
在不改变原文事实含义的前提下，删除语音噪音，修正明显错误，整理断句和表达，使文本通顺、自然、可读。

## 规则
1. 修正语病、错别字、断句错误。
2. 删除口头禅和无意义填充词，例如“嗯、啊、然后、反正、就是、那个”等。
3. 删除明显重复表达。同一句话或同一意思连续重复时，只保留信息最完整、表达最清楚的一版。
4. 剔除不承载信息价值的口头语言噪音，包括录音过程自语、叙述过渡、走神重复、无意义填充等。
5. 保留承载事件、情感、判断、偏好、计划、反思的信息，不要因为表达口语化就删除。
6. 可以结合上下文修正明显的语音识别错误，但不能强行猜测无法确定的人名、地名、产品名、专有名词。
7. 可以在同一句或相邻短句内调整局部语序、合并断裂表达，使表达通顺。
8. 可以补充标点，以及原文关系已经明确的过渡词；不要补充原文没有明确表达的因果、目的、动机。
9. 不要跨事件重组内容，不要合并相隔较远的内容，不要提前做事件拆分。
10. 按原文叙述顺序整理，整体时间线不要倒置。
11. 不要改写成摘要，不要输出结构化事件。
12. 不新增原文没有的事实、原因、情绪、评价或反思。
13. 保留原文的语气和风格，不要改成过度正式、文学化或总结式表达。
14. 如果原文表达含混，只做可读性整理，不要强行解释成确定结论。

## 输出要求
请严格按以下 JSON 格式返回，不要包含 markdown 代码块标记：

{"cleaned_text": "清洗后的文本"}
```

#### 关键边界

- 能顺句子，不能改事实。
- 能清噪音，不能删信息。
- 能局部整理，不能跨事件重组。
- 能修正明显错误，不能猜测不确定内容。

> 注：原文中的开场白（如"闲着也是闲着就说两句"）属于引入段，不是需要剔除的噪音，清洗时应保留并整理为通顺表达，供后续事件整理阶段作为 introduction 提取。

### 环节 2：清洗审核

#### 环节定位

清洗审核是新增环节，用于对照原文审核文本清洗结果。

它同时承担两个职责：

1. 发现 `cleaned_text` 中由清洗阶段造成的问题。
2. 直接给出修正后的完整文本 `checked_text`。

清洗审核不输出替换指令，不由程序执行局部替换。程序直接使用 `checked_text` 作为后续环节的基准文本。

选择该方案的原因：

- 文本清洗错误不一定是机械替换，可能涉及遗漏恢复、句子重排、局部语义修正。
- 让模型直接输出完整修正版，实现更简单，流程更稳定。
- 通过 `clean_check_log` 保留关键修正记录，兼顾可追踪性。

#### 输入

```json
{
  "original_text": "原始语音转文字内容",
  "cleaned_text": "文本清洗结果"
}
```

#### 输出

```json
{
  "checked_text": "审核修正后的完整文本",
  "clean_check_log": [
    {
      "issue": "发现的问题",
      "before": "清洗结果中的问题片段",
      "after": "修正后的片段",
      "reason": "修正原因"
    }
  ]
}
```

#### Prompt

```text
你是一个日记清洗审核助手。请对照原始日记文本，审核文本清洗结果是否准确，并直接修正清洗结果中的问题。

## 任务目标
检查 cleaned_text 是否忠实保留 original_text 的事实、情感、判断、偏好、计划和细节。
如果发现清洗阶段造成了误改、遗漏、过度改写或新增内容，请直接修正，输出更可靠的 checked_text。

## 最高准则
original_text 是最高事实来源。
checked_text 应以 cleaned_text 为基础，只修正审核发现的问题，不重新清洗全文，不整体改写表达风格。

## 审核规则
1. 检查 cleaned_text 是否改变了原文事实含义。
2. 检查 cleaned_text 是否遗漏了有信息价值的内容，包括事件、时间、地点、人物、行为、结果、感受、判断、计划。
3. 检查 cleaned_text 是否新增了原文没有的事实、原因、情绪、评价或反思。
4. 检查 cleaned_text 是否强行猜测无法确定的人名、地名、产品名、专有名词。
5. 检查 cleaned_text 是否把原文中的含混、犹豫、矛盾表达强行改成确定结论。
6. 检查 cleaned_text 是否存在明显不通顺、断句错误、指代不清的问题。
7. 只修正必要问题，不重新清洗全文，不做事件拆分，不做摘要，不做结构化整理。

## 修正规则
1. 发现问题时，直接在 checked_text 中修正。
2. 每个实质性修正都记录到 clean_check_log。
3. 如果 cleaned_text 没有明显问题，checked_text 可以等于 cleaned_text，clean_check_log 为空数组。
4. clean_check_log 只记录影响事实、信息完整性或可读性的实质问题，不记录标点、轻微措辞这类小调整。

## 输出要求
请严格按以下 JSON 格式返回，不要包含 markdown 代码块标记：

{
  "checked_text": "审核修正后的文本",
  "clean_check_log": [
    {
      "issue": "发现的问题",
      "before": "清洗结果中的问题片段",
      "after": "修正后的片段",
      "reason": "修正原因"
    }
  ]
}
```

#### 关键边界

- 能修正清洗错误，不能重新清洗全文。
- 能恢复遗漏信息，不能新增原文没有的信息。
- 能让基准文本更准确，不能提前做事件整理。
- `checked_text` 是后续事件整理的输入基准。

### 环节 3：事件整理

#### 环节定位

事件整理用于解决语音日记中的思维跳跃问题。

语音日记常见情况是：说一件事的过程中插入另一件事，说完后又回到原来的事情。这个环节的核心职责不是按原文连续段落切分，而是：

1. 识别日记里有哪些事。
2. 按照这些事情，把散落在不同位置的相关文本汇聚到一起。

事件整理只做识别、归类和汇聚，不做三字段结构化，不生成 `feeling`、`reflection` 字段。

#### 输入

```json
{
  "checked_text": "清洗审核后的基准文本"
}
```

#### 输出

`trivia` 使用字符串数组。

```json
{
  "introduction": "引入段文本，无则空字符串",
  "events": [
    {
      "event_title": "事件标题",
      "organized_text": "同一事件汇聚后的文本"
    }
  ],
  "trivia": [
```

### 分析流水线详细设计

分析流水线是整理流水线之后的独立阶段，基于整理后的结构化日记和原始文本，生成心情、标签和日记分析六部分。

**指导思想：日记分析的目标是帮助用户认清自己。**

分析流水线采用 [LangGraph](https://github.com/langchain-ai/langgraph) 框架构建，将 3 个环节建模为并行状态图。

**图的拓扑结构：**

```
              ┌→ mood_tag_extract ──┐
START ── fork ┼→ core_analysis ─────┼→ join → END
              └→ cognition_analysis ┘
```

三个环节并行执行，每个 Node 对应一次独立的 LLM 调用，Node 内部只读取 State 中自己需要的字段、写入自己产出的字段，不跨节点直接通信。三个环节全部完成后再合并写入分析结果。

```python
    task_id: str                # 分析任务 ID

    user_id: str
```

#### 分析流水线 Temperature 配置

| 环节 | Temperature | 说明 |
|------|------------|------|
| 环节7：心情+标签提取 | 0.3 | 提取需要精确 |

#### 分析流水线断点续跑机制（Checkpoint）

分析流水线复用整理流水线的同一套 Checkpoint 机制（AsyncPostgresSaver），确保失败后能从断点恢复，而非从头重跑。

**实现方案：**

| 项目 | 方案 |
|---|---|
| Checkpoint 存储 | 复用 `langgraph-checkpoint-postgres` 的 `AsyncPostgresSaver`，与整理流水线共用同一实例 |
| 线程标识 | `thread_id` 复用分析任务的 `task_id`（UUID），与整理流水线的 checkpoint 天然隔离 |
| 断点恢复 | 失败后用户重新触发分析，系统检测 checkpoint 存在，使用相同 `thread_id` 调用，LangGraph 自动从断点恢复 |
| 清理策略 | 分析成功后主动调用 `checkpointer.adelete_thread()` 清理 checkpoint |

```text
- 用户做了什么。

4. 判断是否存在关注点错位：表面关注某个指标，实际想要另一种心理满足。
5. 分析需求满足方式是否健康、稳定、可持续，例如是否过度依赖某个人、某个反馈或单一快乐来源。

- 对"填补内心空虚"这类强心理解释要谨慎，除非 events 有明确依据；更稳妥的写法是指出可能在寻求情绪陪伴、被关注、被选择或归属感。
- 事件级分析只分析该事件，不引用其他事件。
- 日记级分析需要综合所有事件，整理成当天整体关注点与需求总结。
- 如果某个事件没有明显线索，该事件 self_understanding_analyses 返回空数组。
- 如果整篇日记没有明显线索，diary_self_understanding_analyses 返回空数组。
- 帮助用户理解自己，不评价用户。

## 可行动建议
为每个事件生成 action_suggestions，并基于整篇日记生成 diary_action_suggestions。

核心目标：基于前三类分析结果，生成低成本、具体、可执行的下一步行动，帮助用户下次在类似情境中做得更好。

处理流程：
1. 从情绪分析中提取情绪触发点、根因、当下化解方式和未来预防方向。
2. 从行为与决策分析中提取有效做法、无效做法、行为风险和改进方向。
3. 从关注点与需求分析中提取真实诉求、心理依赖、需求满足方式问题和更健康的满足路径。
4. 将前三类分析压缩成少量具体动作，避免重复分析。
5. 过滤掉无依据、泛泛而谈、高成本或不可执行的建议。
6. 按事件级和日记级分别输出：事件级建议针对单个事件，日记级建议针对整篇日记呈现出的共性问题。

分析依据：
- 可以基于 events 中的具体事实。
- 必须基于本次输出中的情绪分析、行为与决策分析、关注点与需求分析。
- 建议必须服务于用户下次遇到类似情况时的具体行动。

建议类型：
- 情绪建议：如何化解当下情绪、减少坏情绪触发、创造更多好情绪。
- 做事建议：如何停止无效重复、保留有效方式、换成更符合问题机制的方法。
- 需求建议：如何更健康地满足真实需求、减少单点依赖、拓宽快乐、价值感和支持来源。
- 表达方式建议。
- 降低不确定性的动作。
- 区分事实、情绪和解释。
- 边界保护。
- 推进事情的下一步小动作。
- 其他低成本、具体、可执行动作。

生成规则：
- 事件级建议只针对单个事件中能明确落地的动作。
- 日记级建议不必是事件级建议的合并，可以包含不归属于任何单个事件、但基于整篇日记整体分析得到的建议。
- 日记级建议可以来自某个关键事件、多个事件共同呈现的问题、当天整体情绪/行为/需求分析，或不适合归属到单个事件的整体调整动作。
- 可行动建议是前三类分析的汇总落地，不重新做一套脱离分析依据的建议。
- 建议要具体到动作，优先调整方法、环境、表达、预期和行动，不要求用户改变人格。
- 每条建议使用"下次可以尝试…"、"建议…"表达。
- 不限制建议数量，但只输出有依据、可执行的建议，不为凑数量生成建议。
- 不输出泛泛而谈的鸡汤。
- 不输出高成本建议，例如辞职、分手、拉黑、放弃项目、重大关系决策。
- 只有 events 明确表达相关打算时，才允许涉及高成本建议。
- 如果某个事件没有明显可行动建议，该事件 action_suggestions 返回空数组。
- 如果整篇日记没有明显可行动建议，diary_action_suggestions 返回空数组。
```

### 环节 9：认知校准 + 问题解答 + 认知完善

#### 环节定位

基于结构化日记中的 events，进行认知校准、问题解答和认知完善。

环节 9 的处理顺序固定为：

1. 先做认知校准：识别用户对世界、他人、自己、知识、方法或事件因果的理解中是否存在明显偏差，并在有依据时温和纠正。
2. 再做问题解答：找出日记中的明确问题和隐性问题，直接给出问题和回答，回答必须突出核心重点。
3. 最后做认知完善：基于日记中的零散知识、随想、判断、类比和问题解答结果，整理成更完整、可复用的认知体系。

数组含义：`event_cognitive_calibration_analyses`、`diary_cognitive_calibration_analyses` 的每一项是一条独立认知校准文本；`event_question_answers`、`diary_question_answers` 的每一项是一组问题与回答；`event_cognitive_enhancements`、`diary_cognitive_enhancements` 的每一项是一条独立认知完善文本。
