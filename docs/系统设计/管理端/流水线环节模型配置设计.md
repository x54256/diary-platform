# 环节模型与思考模式配置设计

> 文档状态：现行  
> 事实基线：2026-07-31 代码  
> 对应需求：[流水线环节模型配置需求规格](../../需求规格/管理端/流水线环节模型配置需求规格.md)

## 1. 背景

当前管理端已经支持为以下四类业务用途选择模型：

- 整理
- 分析
- 对话
- 语音转文字

原设计提出时，运行时只能按业务用途选择模型，整理和分析内部的多个 LLM 调用环节共用同一个模型。当前已通过 `model_step_settings` 实现环节级覆盖。

系统已经具备以下思考模式基础能力：

- 模型通过 `reasoning_mode` 声明不支持、支持开关或强制开启思考。
- 渠道通过 `thinkmode` 保存开启和关闭思考时需要发送的请求参数。
- 变更前的整理流水线通过 `organize_pipeline_settings.thinking_steps` 保存部分环节的思考开关；当前字段已经迁移到 `model_step_settings.thinking_enabled` 并被删除。

原思考配置存在两个问题，当前已由用途级与环节级配置解决：

1. 缺少整理、分析和对话三个业务用途的默认思考开关。
2. `organize_pipeline_settings` 同时保存整理和分析环节的思考设置，职责不清晰。

## 2. 目标

在现有四类模型配置的基础上：

1. 为整理、分析和对话增加默认思考开关。
2. 允许整理的 5 个环节分别覆盖模型和思考模式。
3. 允许分析的 5 个环节分别覆盖模型和思考模式。
4. 环节未配置某个字段时，继承所属业务用途的对应字段。
5. 语音转文字继续只配置模型，不提供思考开关。
6. 管理端修改配置后，尚未开始执行的环节读取最新配置。
7. 升级后保持现有任务的模型选择和思考行为不变。

## 3. 范围

### 3.1 整理环节

| 环节标识 | 页面名称 |
|---|---|
| `text_clean` | 文本清洗 |
| `clean_check` | 清洗审核 |
| `event_organize` | 事件整理 |
| `template_fill` | 三字段结构化 |
| `content_check` | 内容审核 |

### 3.2 分析环节

| 环节标识 | 页面名称 | 所属流程 |
|---|---|---|
| `mood_tag_extract` | 元数据、心情与标签 | 普通分析 |
| `core_analysis` | 核心分析 | 普通分析 |
| `cognition_analysis` | 认知分析 | 普通分析 |
| `feedback_core_analysis` | 反馈核心分析 | 反馈重分析 |
| `feedback_cognition_analysis` | 反馈认知分析 | 反馈重分析 |

普通分析和反馈重分析是两条不同的执行路径，一次普通分析不会连续执行全部 5 个分析环节。配置层面仍将它们统一归入“分析”，并允许分别覆盖。

### 3.3 不在本次范围内

- 修改各环节 Prompt。
- 配置 Temperature、超时时间或重试次数。
- 模型自动推荐或故障自动切换。
- 为单个用户、单篇日记或单次任务设置模型。
- 保存配置变更历史。
- 固定任务启动时的模型配置快照。

## 4. 核心规则

### 4.1 两级配置

配置分为业务用途默认配置和环节覆盖配置：

```text
业务用途默认配置
└─ 环节覆盖配置
```

有效配置分别计算：

```text
有效模型 = 环节模型覆盖 ?? 业务用途默认模型
有效思考状态 = 环节思考覆盖 ?? 业务用途默认思考状态
```

模型与思考模式独立继承。例如，某环节可以指定模型，同时继续继承所属业务用途的思考状态。

### 4.2 思考状态

业务用途默认思考状态只有两种：

- 开启
- 关闭

环节思考配置有三种：

- 继承
- 开启
- 关闭

数据库使用可空布尔值表达环节三态：

| 数据值 | 含义 |
|---|---|
| `NULL` | 继承 |
| `TRUE` | 开启 |
| `FALSE` | 关闭 |

### 4.3 模型能力约束

模型的 `reasoning_mode` 决定有效思考状态是否合法：

| `reasoning_mode` | 合法状态 |
|---|---|
| `unsupported` | 只能关闭 |
| `switchable` | 可以开启或关闭 |
| `always_on` | 只能开启 |

保存配置时必须校验所有业务用途和环节的最终有效组合。存在任一冲突时，整批保存失败，不自动修正配置。

示例：

- 分析默认开启思考。
- `mood_tag_extract` 指定了不支持思考的模型。
- 该环节的思考配置仍为“继承”。
- 最终组合为“不支持思考的模型 + 开启思考”，因此禁止保存。

管理员需要将该环节显式设置为“关闭”，或者选择支持思考的模型。

### 4.4 生效时机

每个环节创建 LLM 客户端前读取一次最新配置。

因此：

- 已经开始调用模型的环节不受配置修改影响。
- 尚未开始的环节使用最新配置。
- 失败重试的环节重新读取最新配置。
- 同一任务的不同环节可能使用不同时间点的配置。

这是本次明确接受的运行规则，不保存任务级配置快照。

## 5. 数据设计

### 5.1 扩展 `model_settings`

在现有业务用途模型配置表中增加：

```text
thinking_enabled BOOLEAN NULL
```

约束：

- `organize`、`analysis`、`chat` 必须保存布尔值。
- `transcription` 必须为 `NULL`。
- `channel_model_id` 继续保存业务用途默认模型。

### 5.2 新增 `model_step_settings`

```text
id                  UUID PRIMARY KEY
step_key            VARCHAR(50) NOT NULL UNIQUE
channel_model_id    UUID NULL REFERENCES channel_models(id)
thinking_enabled    BOOLEAN NULL
updated_by          UUID NULL REFERENCES users(id)
updated_at          TIMESTAMP NOT NULL
```

字段含义：

- `step_key`：固定环节标识。
- `channel_model_id`：为空表示继承业务用途默认模型。
- `thinking_enabled`：为空表示继承业务用途默认思考状态。

当两个覆盖字段都为空时，可以删除该环节配置记录。接口返回时仍根据固定环节清单生成完整视图。

### 5.3 不保存阶段字段

`model_step_settings` 不保存 `setting_key`。后端通过固定映射确定环节归属：

```python
STEP_SETTING_KEYS = {
    "text_clean": "organize",
    "clean_check": "organize",
    "event_organize": "organize",
    "template_fill": "organize",
    "content_check": "organize",
    "mood_tag_extract": "analysis",
    "core_analysis": "analysis",
    "cognition_analysis": "analysis",
    "feedback_core_analysis": "analysis",
    "feedback_cognition_analysis": "analysis",
}
```

这样可以避免数据库中的阶段归属与代码实际调用关系不一致。

### 5.4 引用保护

现有渠道、模型和渠道模型的禁用及删除保护，需要同时检查：

- `model_settings.channel_model_id`
- `model_step_settings.channel_model_id`

被业务用途默认配置或环节覆盖配置引用的渠道模型，不允许禁用或删除。

## 6. 接口设计

### 6.1 查询配置

继续使用：

```http
GET /api/admin/model-settings
```

建议返回统一结构：

```json
{
  "settings": {
    "organize": {
      "channel_model_id": "uuid",
      "thinking_enabled": false
    },
    "analysis": {
      "channel_model_id": "uuid",
      "thinking_enabled": true
    },
    "chat": {
      "channel_model_id": "uuid",
      "thinking_enabled": false
    },
    "transcription": {
      "channel_model_id": "uuid",
      "thinking_enabled": null
    }
  },
  "steps": [
    {
      "step_key": "event_organize",
      "setting_key": "organize",
      "channel_model_id": null,
      "thinking_enabled": true,
      "effective_channel_model_id": "uuid",
      "effective_thinking_enabled": true
    }
  ]
}
```

接口同时返回覆盖值和最终有效值，前端不自行复制后端继承规则。

### 6.2 保存配置

继续使用：

```http
PUT /api/admin/model-settings
```

请求包含完整的业务用途默认配置和环节覆盖配置。保存必须在一个数据库事务中完成：

1. 校验业务用途与模型类型。
2. 校验渠道、密钥、模型和渠道模型状态。
3. 合并所有环节的有效配置。
4. 校验模型思考能力与有效思考状态。
5. 全部合法后统一保存。

任一配置不合法时不保存任何修改。

### 6.3 测试配置

扩展现有接口：

```http
POST /api/admin/model-settings/test
```

允许传入：

- `setting_key`
- 可选的 `step_key`
- 当前页面尚未保存的模型与思考配置

语言模型测试必须使用最终思考参数发起真实请求，不能只测试模型连通性。语音转文字继续维持现有的非真实音频测试规则。

## 7. 运行时设计

### 7.1 统一解析入口

运行时统一通过以下接口解析：

```python
resolve_model_setting(setting_key, step_key=None)
```

返回内容至少包括：

```text
setting_key
step_key
model_type
protocol
api_base_url
api_key
model_name
reasoning_mode
thinking_enabled
thinkmode
```

处理规则：

- 未传 `step_key` 时返回业务用途默认配置。
- 传入 `step_key` 时验证环节归属，并合并环节覆盖配置。
- 语音转写不接受 `step_key` 和思考配置。
- 解析结果必须再次执行完整运行时校验，不能只依赖保存时校验。

### 7.2 调用点

整理和分析流水线在每次 `_get_llm` 时传入实际 `step_key`。

对话调用读取 `chat` 的默认模型和思考开关，并通过 `resolve_thinking_payload` 生成请求参数。

语音转写继续读取 `transcription` 默认模型，不处理思考参数。

### 7.3 移除旧配置读取

完成迁移后：

- `pipeline.py` 不再读取 `organize_pipeline_settings.thinking_steps`。
- `organize_pipeline_settings` 只保留整理流程本身的启停配置。
- 思考模式只由 `model_settings` 和 `model_step_settings` 决定。

## 8. 管理端页面设计

继续使用现有“模型设置”页面，按业务用途纵向分组。

### 8.1 整理

先展示默认配置：

- 默认模型
- 默认思考状态

然后展示 5 个整理环节。每个环节包含：

- 模型：继承默认模型或指定模型。
- 思考：继承、开启或关闭。
- 最终生效模型。
- 最终生效思考状态。
- 测试按钮。

### 8.2 分析

结构与整理相同，展示普通分析和反馈重分析共 5 个环节。页面需要标明两个反馈环节仅在反馈重分析流程中执行。

### 8.3 对话

只展示：

- 模型
- 思考开关
- 最终能力状态
- 测试按钮

### 8.4 语音转文字

只展示：

- 模型
- 测试按钮

不展示思考开关。

### 8.5 交互规则

- 模型覆盖默认选择“继承”。
- 环节选择“继承”时，页面实时显示继承来源和最终值。
- 冲突配置在页面中立即标红，并由后端再次拒绝。
- 批量保存失败时明确指出业务用途或环节名称及冲突原因。
- 修改后的移动端 `input`、`textarea`、`select` 实际字号不得小于 `16px`。
- 必须验证 iOS Safari 聚焦表单时页面不会自动放大。

## 9. 数据迁移

> 本节记录已经执行的历史迁移规则，用于解释现有数据来源，不表示运行时仍读取旧字段。

迁移目标是保持升级前后的实际行为不变。

### 9.1 默认模型

保留现有 `model_settings` 中四个业务用途的 `channel_model_id`。

### 9.2 默认思考状态

初始化为：

| 业务用途 | 默认值 |
|---|---|
| `organize` | 默认关闭；强制思考模型初始化为开启 |
| `analysis` | 默认关闭；强制思考模型初始化为开启 |
| `chat` | 默认关闭；强制思考模型初始化为开启 |
| `transcription` | `NULL` |

### 9.3 环节思考覆盖

迁移时为 10 个环节写入升级前的最终实际值：

| 环节 | 旧默认值 |
|---|---|
| `text_clean` | 关闭 |
| `clean_check` | 关闭 |
| `event_organize` | 开启 |
| `template_fill` | 关闭 |
| `content_check` | 关闭 |
| `mood_tag_extract` | 关闭 |
| `core_analysis` | 开启 |
| `cognition_analysis` | 开启 |
| `feedback_core_analysis` | 开启 |
| `feedback_cognition_analysis` | 开启 |

如果 `organize_pipeline_settings.thinking_steps` 已保存某个环节的值，以数据库中的值为准；否则使用上表中的旧代码默认值。迁移还要按模型能力换算最终状态：不支持思考的模型写入关闭，强制思考模型写入开启，支持开关的模型保留原值。

迁移后的环节模型覆盖全部为空，继续继承原有业务用途模型。

### 9.4 旧字段处理

确认新运行时和新管理端不再读取旧字段后，删除：

```text
organize_pipeline_settings.thinking_steps
```

不得长期保留两套可写思考配置源。

## 10. 验收标准

### 10.1 继承

- 环节模型为空时使用所属业务用途默认模型。
- 环节思考为空时使用所属业务用途默认思考状态。
- 模型和思考可以分别覆盖。
- 页面展示值与后端实际解析值一致。

### 10.2 能力校验

- 不支持思考的模型不能与“开启”组合。
- 强制思考模型不能与“关闭”组合。
- 支持开关的模型允许两种状态。
- 继承后产生的冲突同样必须被拒绝。
- 批量保存任一项失败时不写入任何配置。

### 10.3 运行时

- 整理 5 个环节分别读取自己的有效配置。
- 分析 5 个环节分别读取自己的有效配置。
- 对话按默认思考开关发送对应渠道参数。
- 语音转写不读取或发送思考参数。
- 修改配置后，尚未开始或重新重试的环节使用最新配置。

### 10.4 迁移

- 四个业务用途原有模型选择不变。
- 10 个环节升级前后的实际思考状态一致。
- 新代码不再读取旧 `thinking_steps`。
- 原有渠道模型引用保护继续有效，并覆盖环节模型引用。

### 10.5 前端

- 管理员可以在同一页面完成全部配置。
- 页面明确区分配置值、继承来源和最终有效值。
- 错误信息能定位到具体业务用途或环节。
- 移动端表单字号不小于 `16px`。
- iOS Safari 聚焦表单时页面不自动放大。
