# 知识库 AI 流水线与提示词设计

> 文档状态：当前运行设计
> 设计基线：2026-08-13
> 对应需求：[知识库管理需求规格](../../需求规格/规划功能/知识库管理需求规格.md)
> 系统设计：[知识库系统设计](知识库系统设计.md)

## 1. 设计目标

知识沉淀把已经整理过的结构化日记事件转换为准确、可独立理解、可回顾、可检索和可追溯的事件记录。

结构化事件的拆分由上游日记整理完成。知识沉淀的首要任务是依据每个事件的完整正文凝练事实和关键内容。每个结构化事件默认在当前 `event_no` 的 `atomic_events` 数组中生成一条事件记录；仅当某部分不属于核心事情的连续事实链，且自身能够构成另一件完整事情时，模型才为其单独生成记录。

## 2. 核心决策

- 使用单阶段模型调用，同时生成 `title`、`source_fragments`、`content`、`occurred_on` 和 `occurred_time`。
- 模型配置步骤键为 `knowledge_event_extract`，归属 `knowledge` 模型用途。
- 每个输入事件只提供 `event_no`、`title` 和完整 `body`；`feeling`、`reflection` 不参与知识事件凝练。
- 模型必须先依据完整 `title + body` 理解和凝练事件，再选择 `source_fragments`。
- `source_fragments` 是核验结果的逐字证据，不限定模型理解事件的信息范围。
- 每个 `event_no` 独立处理，不跨结构化事件补充或合并信息。
- 一个结构化事件完整放入同一批次，不按 Token 预算拆开正文。
- 任一批次调用失败、结构校验失败或结果覆盖不完整时，整篇沉淀失败。
- 全部批次成功后，在同一事务中写入事件记录、沉淀成功记录和任务成功状态。

## 3. 流水线

```text
VALIDATE_SOURCE
  → PREPARE_BATCHES
  → EXTRACT_BATCH ─┐
       ↑           │ 还有批次
       └───────────┘
  → PUBLISH
```

### 3.1 来源校验

程序校验日记所有权、日记状态、结构化修订号、结构化事件和模型配置，并冻结：

- `diary_date`；
- 按结构化事件顺序排列的 `event_no`、`title` 和完整 `body`；
- 本次任务使用的非密钥模型配置。

结构化事件的 `title` 和 `body` 均为空时，任务失败。

### 3.2 分批

程序按照结构化事件顺序贪心装批：

1. 加入下一事件后超过 `KNOWLEDGE_EVENT_INPUT_TOKEN_BUDGET` 时，结束当前批次；
2. 单个结构化事件的 `title` 和完整 `body` 始终位于同一批次；
3. 单个事件超过预算时，作为独立超长批次完整传入。

### 3.3 事件凝练

模型按 `event_no` 独立处理输入，内部顺序为：

1. 阅读完整 `title` 和 `body`；
2. 识别主体、行为或判断、对象、状态、说话者，以及信息之间的原始关系；
3. 根据删除后是否改变事件过程、决定、结论、结果或状态，确定关键事实链；
4. 判断是否存在不属于核心事情连续事实链、且自身构成完整事情的异常内容；
5. 生成 `title` 和 `content`，逐项核对关键事实及其关系；
6. 最后选择覆盖全部关键信息的逐字 `source_fragments`；
7. 确定发生时间并输出完整结构。

模型不得先选少量来源片段，再仅围绕片段生成内容。

### 3.4 发布

程序按批次和 `event_no` 顺序合并结果，检查全部冻结事件均被完整覆盖且没有重复。随后在一个事务中写入：

- `knowledge_deposits` 成功记录；
- 全部 `knowledge_atomic_events`；
- 任务成功状态。

## 4. 程序与模型职责

### 4.1 程序职责

- 校验来源、所有权、结构化修订和模型配置；
- 冻结本次处理输入和模型配置；
- 生成稳定的 `event_no`；
- 估算输入 Token 并划分批次；
- 校验 JSON 字段、编号、数量、顺序、覆盖、唯一性和类型；
- 将不合法或缺失的日期回退为 `diary_date`；
- 将不合法的时刻置为 `null`；
- 合并批次结果并执行事务发布；
- 保存批次游标和临时结果，支持任务恢复。

### 4.2 模型职责

- 依据当前事件的完整 `title` 和 `body` 理解上下文；
- 准确凝练事实和影响事件理解、发展、结果、状态或回顾价值的关键内容；
- 保持主体、人物关系、事实状态、确定性、因果强度和说话者归属；
- 默认保持上游事件边界，只对明确混入的多件独立事情进行异常拆分；
- 生成便于回顾的标题和完整事件内容；
- 为标题和内容选择可逐字追溯的来源片段；
- 解析核心事情实际发生或相关决定、判断、认识形成的时间。

## 5. 模型输入与输出

### 5.1 输入 Schema

```json
{
  "diary_date": "2026-08-05",
  "events": [
    {
      "event_no": 1,
      "title": "结构化事件标题",
      "body": ["结构化事件正文"]
    }
  ]
}
```

输入规则：

- `event_no` 按结构化事件顺序从 1 开始生成，在全部批次中保持稳定；
- `title` 用于辅助理解事件主题；
- 完整 `body` 是事实来源；
- `<time value="...">原文</time>` 同时提供上游解析时间和用户原本的时间表达；
- 输入不包含 `feeling` 和 `reflection`。

### 5.2 输出 Schema

```json
{
  "results": [
    {
      "event_no": 1,
      "atomic_events": [
        {
          "title": "事件标题",
          "source_fragments": ["逐字来源片段"],
          "content": "准确凝练后可独立理解和回顾的事件内容",
          "occurred_on": "2026-08-05",
          "occurred_time": null
        }
      ]
    }
  ]
}
```

输出规则：

- `results` 与当前批次输入的 `events` 顺序一致；
- `event_no` 原样返回且只出现一次；
- 每个 `atomic_events` 至少包含一条记录；
- 默认每个输入事件的 `atomic_events` 只包含一条记录；仅满足边界兜底条件时，才为每件独立事情各生成一条记录，并按事情在正文中的出现顺序排列；
- 每条记录只包含 `title`、`source_fragments`、`content`、`occurred_on` 和 `occurred_time`；
- `source_fragments` 至少包含一个从 `body` 逐字摘录的非空片段；
- `occurred_on` 使用 `YYYY-MM-DD`；
- `occurred_time` 使用 `HH:mm` 或 `null`。

## 6. 内容凝练原则

### 6.1 关键内容

关键内容包括：

- 核心事情；
- 理解事情所必需的主体、对象、背景、触发原因和过程；
- 影响理解、判断、决定或结果的数字、金额、日期、比例和名称；
- 影响事情发展的重要变化；
- 已形成的结果和当前状态；
- 尚未解决的问题和明确的下一步行动；
- 与事情直接相关的重要决定、结论、判断、观点、推测、担忧或认识。

删除某项信息会改变用户对事件本身、发展过程、结果、当前状态或相关认识的理解时，该信息必须保留。模型只删除重复表达、口语填充和无关枝节；不得为了更短或更流畅而删除独立的关键事实，也不得用空泛结论代替具体内容。

### 6.2 关系保真

- 保留关键事实之间原本的时间先后、因果、转折、条件和对比关系；
- 保留行动—结果、问题—处理和判断—依据关系；
- 不省略影响决定、结论或状态的中间步骤；
- 来源只表达先后、相关或并列关系时，不添加因果关系；
- 可以重组句序，但不得改变事实顺序所表达的逻辑。

### 6.3 事实保真

- 不添加来源没有表达的信息；
- 不改变主体、人物关系、时间、状态、因果关系和确定程度；
- 已发生的事情保持为已发生；
- 计划、意图、预约、承诺和待办保持未完成状态；
- 推测、担忧、期待和不确定归因保留限定；
- 判断和认识明确归属于原说话者；
- 设想、建议或准备执行不得写成已经完成；
- 个人判断不得写成客观事实，不确定表达不得写成已经验证的结论；
- 单方提出不得写成双方商定；
- 保留影响后续决定、结论或当前状态的条件、原因和转折；
- 来源只表达先后、相关或并列关系时，不添加因果关系；
- 来源存在矛盾、歧义或信息不足时，不自行解释、裁定或补全。

### 6.4 边界兜底

每个结构化事件默认在当前 `event_no` 的 `atomic_events` 数组中对应一条事件记录，模型不主动寻找拆分点。仅当某部分既不属于核心事情的背景、过程、条件、转折、决定、结果、反思或后续安排，又能够独立构成另一件完整事情时，才单独生成记录。

共同人物、项目或宽泛主题不能单独作为合并依据；出现不同子话题也不能单独作为拆分依据。模型判断内容是否共同构成同一核心事情的连续事实链；无法明确判断时保持一条记录。

### 6.5 来源证据

- `source_fragments` 在标题和内容生成后选择；
- 片段覆盖标题和内容中的全部关键信息；
- 每个片段是当前 `body` 某一个字符串中连续出现的逐字原文，不改写、不解释、不补充、不跨位置拼接；
- 禁止使用 `...`、`……` 或其他省略符删除片段中间的原文；无法连续覆盖时拆成多个片段；
- 多个片段按原文出现顺序排列；
- 片段保留完整 `<time>` 标签；
- `content` 不输出标签，保留标签内用户原本的时间说法。

## 7. 时间规则

- `occurred_on` 和 `occurred_time` 表示核心事情实际发生，或相关决定、判断、认识实际形成的时间；
- 计划执行时间、预约时间和截止时间不作为事件发生时间；
- 优先使用核心事情对应的 `<time value="...">`；没有对应标签时，以 `diary_date` 为基准换算相对日期；
- 无法确定具体日期或模型返回非法日期时，程序使用 `diary_date`；
- 只有来源能够确定小时和分钟时才返回 `HH:mm`，否则返回 `null`；
- `content` 保留来源原本的时间说法。

## 8. 系统提示词

运行时系统提示词位于：

`backend/prompts/knowledge_atomic_event.txt`

提示词必须与本文的输入范围、处理顺序、事实保真、边界兜底、字段规则和输出 Schema 保持一致。任务统一定义为“凝练事件内容”，避免使用带有过度压缩倾向的术语。

## 9. 程序校验

- 顶层必须包含 `results`；多余字段忽略并记录警告；
- `results` 数量和顺序与当前批次输入一致；
- 每个结果包含 `event_no` 和非空 `atomic_events`；
- 每条记录具有非空 `title`、`source_fragments` 和 `content`；
- 超过 20 个字符的标题由程序截断并记录警告；
- 非法 `occurred_on` 回退为 `diary_date`；
- 非法 `occurred_time` 置为 `null`；
- 全部批次结果必须完整覆盖冻结的结构化事件，且 `event_no` 不重复；
- 任一强校验失败时，不发布正式数据。

## 10. 模型配置、失败与恢复

- 模型用途：`knowledge`；
- 步骤键：`knowledge_event_extract`；
- 每批调用使用全局 `LLM_MAX_ATTEMPTS` 处理临时错误；
- JSON 结构错误最多执行一次结构修复，结构修复不得改变内容语义；
- 每批结果通过校验后写入 LangGraph checkpoint；
- 任务恢复时从当前未完成批次继续；
- 任一批次失败时不写入正式事件；
- 发布事务一次写入全部事件、成功记录和任务成功状态。
