# 知识库系统设计

> 文档状态：知识事件首版目标设计。
> 设计基线：2026-08-11 已确认方案  
> 对应需求：[知识库管理需求规格](../../需求规格/规划功能/知识库管理需求规格.md)  
> AI 设计：[知识库 AI 流水线与提示词设计](知识库AI流水线与提示词设计.md)

## 1. 首版目标

首版建立一条可独立使用的知识事件沉淀链路：用户从已分析日记手动触发任务，系统异步提取知识事件并正式落库，用户可以在知识库中按时间浏览事件和查看来源。

首版包含：

- 日记详情页手动触发、状态展示和失败重试。
- 独立 `knowledge` 模型配置和 `knowledge_event_extract` 步骤配置。
- LangGraph 分批提取、PostgreSQL checkpoint 和任务断点恢复。
- 知识事件、任务和沉淀成功记录三张业务表。
- 知识库事件列表、事件详情和来源日记入口。

人物、事项和洞察作为后续沉淀阶段。成功记录通过 `completed_stage` 标明当前完成到 `ATOMIC_EVENTS`，后续升级任务基于已有知识事件继续处理。

## 2. 总体结构

```text
日记详情页
  │ 手动触发
  ▼
Knowledge API
  │ 创建 knowledge_tasks
  ▼
Knowledge Worker
  │ 领取任务、续租、恢复
  ▼
LangGraph + PostgreSQL Checkpointer
  │ VALIDATE_SOURCE
  │ PREPARE_BATCHES
  │ EXTRACT_BATCH（循环）
  │ PUBLISH
  ▼
PostgreSQL
  ├─ knowledge_tasks
  ├─ knowledge_deposits
  └─ knowledge_atomic_events
       │
       ▼
知识库事件列表与详情
```

PostgreSQL 是首版知识数据和 checkpoint 的存储。列表查询使用普通关系索引，不增加图数据库、GraphRAG、向量召回或知识搜索索引。

## 3. 数据模型

### 3.1 `knowledge_tasks`

任务表表达一次知识事件沉淀的执行状态。

| 字段 | 类型与说明 |
|---|---|
| `id` | UUID 主键，同时作为 LangGraph `thread_id` |
| `user_id` | 当前用户 |
| `diary_id` | 当前日记 |
| `source_diary_organized_id` | 触发时的结构化日记 |
| `source_structured_revision` | 触发时的结构化修订号 |
| `status` | `QUEUED/RUNNING/SUCCEEDED/FAILED` |
| `current_step` | 当前 LangGraph 节点 |
| `retry_count` | 用户手动重试次数，默认 0 |
| `lease_until` | worker 租约到期时间 |
| `run_token` | 本次领取令牌，隔离过期 worker |
| `error_code` | 稳定错误码 |
| `error_message` | 可直接展示的脱敏错误信息 |
| `checkpoint_cleaned_at` | checkpoint 成功清理时间；为空表示仍需清理或保留 |
| `started_at` | 首次开始执行时间 |
| `completed_at` | 本次进入终态的时间 |
| `created_at` / `updated_at` | 审计时间 |

`current_step` 使用以下值：

```text
VALIDATE_SOURCE
PREPARE_BATCHES
EXTRACT_BATCH
PUBLISH
```

约束与索引：

```sql
UNIQUE (user_id)
WHERE status IN ('QUEUED', 'RUNNING');

UNIQUE (diary_id, source_structured_revision)
WHERE status IN ('QUEUED', 'RUNNING');
```

冻结输入、批次游标和临时结果只保存在 LangGraph checkpoint。来源未变化时，失败任务原地重新排队并继续使用同一 checkpoint。

### 3.2 `knowledge_deposits`

成功记录表达一篇日记已完成到哪个知识沉淀阶段。

| 字段 | 类型与说明 |
|---|---|
| `diary_id` | 主键兼日记外键 |
| `user_id` | 用户隔离 |
| `task_id` | 完成首版沉淀的任务，唯一 |
| `source_diary_organized_id` | 使用的结构化日记 |
| `source_structured_revision` | 使用的结构化修订号 |
| `completed_stage` | 首版固定为 `ATOMIC_EVENTS` |
| `deposited_at` | 首次正式沉淀时间 |
| `updated_at` | 后续阶段推进时间；首版等于沉淀时间 |

一篇日记只存在一条成功记录。后续阶段完成时更新 `completed_stage`，不会重新提取首版知识事件。

### 3.3 `knowledge_atomic_events`

| 字段 | 类型与说明 |
|---|---|
| `id` | UUID 主键 |
| `user_id` | 用户隔离 |
| `diary_id` | 外键指向 `knowledge_deposits(diary_id)` |
| `source_diary_event_id` | 来源 `diary_events.id` |
| `source_order` | 固定为 0，保留用于现有排序与唯一约束 |
| `title` | `VARCHAR(20)`，具体事件标题 |
| `content` | JSONB，至少包含一个非空字符串的自然段数组 |
| `occurred_on` | DATE，事件发生日期 |
| `occurred_time` | TIME，可为空，精确到分钟 |
| `created_at` | 正式写入时间 |

首版知识事件只有标题、事件内容和时间三类业务字段。人物、事项和洞察字段不提前加入本表。

约束与索引：

- `source_order >= 0`。
- `char_length(title) BETWEEN 1 AND 20`。
- `jsonb_typeof(content) = 'array' AND jsonb_array_length(content) > 0`；成员类型和非空内容由发布服务校验。
- 唯一索引 `(user_id, diary_id, source_diary_event_id, source_order)`。
- 列表索引 `(user_id, occurred_on DESC, occurred_time DESC NULLS LAST, created_at DESC, id DESC)`。
- 日记、结构化日记事件和成功记录均使用限制删除。

### 3.4 关系

```text
diaries 1 ── 0..1 knowledge_deposits
   │                    │
   │                    └── 1..* knowledge_atomic_events
   │                                      │
   └── diary_organized 1 ── 1..* diary_events
                                          ▲
                                          └── source_diary_event_id
```

## 4. 模型配置

- 在 `model_settings` 支持的用途列表中增加 `knowledge`。
- 管理端模型设置页增加“知识沉淀”配置项。
- 迁移不复制 `analysis`、`organize` 或 `review` 的当前模型；`knowledge` 未配置时功能不可启动。
- `model_step_settings` 增加 `knowledge_event_extract`，模型和思考模式默认继承 `knowledge`，允许单独覆盖。
- 任务在 `VALIDATE_SOURCE` 时解析并冻结本次模型、渠道和思考模式，后续批次使用同一配置。
- checkpoint 只保存 `channel_model_id`、模型标识、接口地址、推理模式、思考开关和非密钥调用参数。解密后的 `api_key` 不进入 LangGraph state。
- 每批调用前根据冻结的 `channel_model_id` 从数据库读取并解密当前渠道密钥；密钥只存在于本次调用的内存中。

## 5. LangGraph 状态与节点

### 5.1 状态

checkpoint 保存以下状态：

```text
task_id
user_id / diary_id
source_structured_revision
frozen_model_config
frozen_diary_date
frozen_events
batches
next_batch_index
batch_results
```

`frozen_events` 仅包含 `event_no/title/body/feeling/reflection`。`frozen_model_config` 是不含 `api_key` 的配置快照。checkpoint 包含用户正文，应使用现有数据库权限保护，不写入普通日志或错误响应。

`run_token` 不属于 checkpoint state。worker 通过 LangGraph 非持久化运行时上下文传入本次 `run_token`，使任务恢复时始终使用新 worker 的令牌，不从旧 checkpoint 读取，也不把令牌写入 checkpoint 元数据。

### 5.2 `VALIDATE_SOURCE`

1. 校验任务仍处于 `RUNNING`、由运行时传入的 `run_token` 持有且租约未过期。
2. 校验用户、日记所有权和日记状态。
3. 校验结构化日记及其修订号与任务冻结来源一致。
4. 校验该日记尚无 `knowledge_deposits`。
5. 解析独立 `knowledge` 模型设置。
6. 校验结构化事件数量至少为 1；没有结构化事件时以 `EMPTY_STRUCTURED_DIARY` 失败。
7. 按结构化事件顺序冻结输入。
8. 任一结构化事件的标题、正文、感受和反思全部为空时，以 `EMPTY_STRUCTURED_EVENT` 失败。

字段映射：

| 模型字段 | 来源 |
|---|---|
| `diary_date` | `diaries.diary_date` |
| `event_no` | 按 `diary_events.sort_order/id` 从 1 编号 |
| `title` | `diary_events.event_title`，空值转换为空字符串 |
| `body` | 解析后的正文数组 |
| `feeling` | 解析后的感受数组，空值使用空数组 |
| `reflection` | 解析后的反思数组，空值使用空数组 |

### 5.3 `PREPARE_BATCHES`

按冻结模型和完整提示词估算 Token，依照结构化事件顺序装批：

- 单个结构化事件不跨批拆分。
- 加入下一事件超过预算时开始新批次。
- 单个事件本身超出预算时仍完整形成独立批次，由模型接口决定是否接受。
- 批次计划写入 checkpoint，任务表不保存批次数量和进度。

### 5.4 `EXTRACT_BATCH`

每次节点执行只处理 `next_batch_index` 指向的一个批次：

1. 节点开始前校验 `status=RUNNING`、运行时 `run_token` 匹配且租约未过期。
2. 调用 `knowledge_event_extract`。
3. 对超时、限流等临时接口错误按全局 `LLM_MAX_ATTEMPTS` 重试当前批次。
4. JSON 或字段结构错误最多使用一次修复提示词。
5. 执行确定性结构校验。
6. 模型返回后再次校验任务所有权并续租；令牌变化或续租失败时抛出执行权丢失异常，节点不得成功返回。
7. 将批次结果追加到 `batch_results`，递增游标。
8. 节点成功返回后由 LangGraph 写 checkpoint。
9. 仍有批次时回到 `EXTRACT_BATCH`，否则进入 `PUBLISH`。

程序不执行来源文字比对或第二次 AI 语义审核。

### 5.5 `PUBLISH`

发布节点执行短事务：

1. 按任务、日记、结构化日记的固定顺序加锁。
2. 校验 `task_id + run_token + status=RUNNING` 且租约未过期。
3. 重新校验结构化日记及其修订号。
4. 校验不存在其他成功沉淀记录。
5. 校验全部冻结事件都有且只有一组结果。
6. 插入 `knowledge_deposits`，`completed_stage=ATOMIC_EVENTS`。
7. 生成正式 UUID 并批量写入知识事件。
8. 将任务改为 `SUCCEEDED`，清空租约并设置完成时间。
9. 一次性提交。

`PUBLISH` 节点内部不删除 checkpoint。节点返回后 LangGraph 仍会写入最终 checkpoint；worker 必须等待整张图调用返回，再在图外执行清理。

事务提交后的异常处理只能把仍处于 `RUNNING` 且匹配当前 `run_token` 的任务改为失败，不能把已经提交为 `SUCCEEDED` 的任务降级。

### 5.6 来源写入守卫

以下现有入口在成功沉淀后都可能改变知识事件来源，必须统一增加守卫：

- 日记软删除。
- 重新整理和重新分析触发。
- 整体修改结构化结果。
- 修改单个结构化事件。
- 整理任务和分析任务的后台最终提交。

这些写入口与 `PUBLISH` 使用相同的日记、结构化日记加锁顺序，并在写入前查询 `knowledge_deposits`；存在成功记录时拒绝修改。普通的无锁“先查询再写入”不能作为来源冻结保证。

日记软删除还必须先执行既有业务规则：只要日记处于 `analyzed`，无论是否已经沉淀，都拒绝删除。

知识任务启动时拒绝存在活动整理或分析任务的日记；知识任务处于 `QUEUED/RUNNING` 时，新的整理、分析、来源修改和删除请求也必须被拒绝。知识任务触发、整理或分析触发及来源写入口都先锁定同一日记，再检查冲突任务或成功记录并创建任务或写入，避免双方同时通过检查。`PUBLISH` 仍重新校验结构化来源修订号，作为最终并发保护。

## 6. Worker、恢复与重试

- 使用独立 knowledge worker 和数据库任务队列。
- worker 使用 `FOR UPDATE SKIP LOCKED` 领取 `QUEUED` 任务，写入 `RUNNING`、`lease_until` 和随机 `run_token`。
- 模型调用期间不持有业务事务，worker 独立定期续租；续租失败时立即停止当前图执行。
- 每个节点开始前都校验 `status + run_token + lease_until`，步骤更新必须带相同条件。`EXTRACT_BATCH` 在模型返回后再次校验，避免过期 worker 返回结果并写入 checkpoint。
- 通用异常处理只有在以下条件更新成功时，才能把任务改为 `FAILED`。执行权校验失败属于旧 worker 退出，不记录任务失败；条件更新影响 0 行时不得修改新 worker 已领取的任务。

```sql
UPDATE knowledge_tasks
SET status = 'FAILED', error_code = :error_code,
    error_message = :error_message, completed_at = CURRENT_TIMESTAMP
WHERE id = :task_id
  AND status = 'RUNNING'
  AND run_token = :run_token
  AND lease_until > CURRENT_TIMESTAMP;
```

- 应用启动及定时恢复把租约过期的 `RUNNING` 任务重新置为 `QUEUED`，保留相同 `task_id`。
- 用户重试失败任务时，来源未变化则同一行改为 `QUEUED`，`retry_count + 1`，清空错误和完成时间，沿用 checkpoint。
- 重复触发或重复重试返回当前活动任务，不创建第二次执行。
- 结构化来源修订号变化时，节点抛出 `SOURCE_CHANGED` 并退出图；worker 在图调用退出后把仍由当前令牌持有的任务改为失败，再在图外清理 checkpoint。用户基于当前来源创建新任务。
- LangGraph 调用完全返回后，worker 对 `SUCCEEDED` 任务执行 `adelete_thread(task_id)`；成功后写入 `checkpoint_cleaned_at`。清理失败只记录任务 ID 和错误类型，不回滚正式数据。
- 节点内部不得调用 `adelete_thread`。启动时和定时清理器使用以下条件查找任务，幂等删除 checkpoint 并补写清理时间。普通可重试的 `FAILED` 任务继续保留 checkpoint。

```text
checkpoint_cleaned_at IS NULL
AND (
  status = SUCCEEDED
  OR (status = FAILED AND error_code = SOURCE_CHANGED)
)
```

## 7. 状态推导

日记页面状态按以下顺序推导：

| 条件 | 页面状态 | 操作 |
|---|---|---|
| 存在 `knowledge_deposits` | `DEPOSITED` | 查看知识 |
| 存在 `QUEUED/RUNNING` 任务 | `PROCESSING` | 无 |
| 当前来源最近任务为 `FAILED` | `FAILED` | 重试 |
| 以上均不存在 | `NOT_DEPOSITED` | 沉淀到知识库 |

每个用户最多存在一个活动知识任务。用户在其他日记已有活动任务时，当前页面提示先等待该任务完成。
入口不可用时，状态接口通过 `unavailable_reason` 返回具体原因；页面直接展示该原因，不再合并为通用的来源错误。

## 8. API 设计

| 方法与路径 | 用途 |
|---|---|
| `GET /api/diaries/{diary_id}/knowledge-status` | 获取入口可用性、不可用原因、沉淀状态和当前任务 |
| `POST /api/diaries/{diary_id}/knowledge-deposit` | 创建或返回当前活动任务 |
| `GET /api/knowledge-tasks/{task_id}` | 轮询任务状态 |
| `POST /api/knowledge-tasks/{task_id}/retry` | 原地重试失败任务 |
| `GET /api/knowledge/events?limit=20&cursor=...` | 按发生时间游标分页 |
| `GET /api/knowledge/events/{event_id}` | 获取事件详情和来源日记摘要 |

列表游标编码以下稳定排序键：

```text
occurred_on DESC
occurred_time DESC NULLS LAST
created_at DESC
id DESC
```

事件响应不复制来源展示字段。查询时通过 `diary_id` 关联 `diaries.diary_date` 和当前结构化日记标题，通过 `source_diary_event_id` 关联 `diary_events.event_title`，返回 `source_diary_date`、`source_diary_title` 和 `source_event_title`。所有接口同时按资源 ID 和 `user_id` 校验所有权。

## 9. 页面设计

### 9.1 视觉与交互基线

页面复用日记管理现有的响应式布局和视觉风格：

- `NavBar`：44px 粘性白色顶栏、底部分隔线、居中标题。
- `BottomTabBar`：使用默认布局的主页面保留 52px 固定底栏并新增第六项“知识”，图标使用 `📚`，路由 `/knowledge`。
- 页面主体和主内容区使用 `w-full` 占满可用宽度，不设置 `max-width`、固定像素宽度或居中定宽容器。
- 主内容区复用日记管理的 `px-4 py-4`，宽度变化时内容自然扩展。
- 事件和状态使用 `w-full rounded-lg border border-neutral-200 bg-white p-4` 卡片，卡片随父容器伸缩。
- 主操作使用现有 `primary-600`；失败使用红色文字和浅红背景；辅助文字使用中性灰。
- 按钮和链接点击区域最小高度 44px。
- 首版页面没有可编辑控件；后续新增输入控件时实际字号必须不小于 16px。

页面主体全宽不改变现有公共导航组件的内部布局：`NavBar` 和 `BottomTabBar` 的操作项容器继续沿用当前组件行为，包括底部标签项的 `max-w-md`。该限制只作用于导航项排列，不限制知识页面主体宽度。

## 10. 错误处理

| 错误码 | 含义与处理 |
|---|---|
| `KNOWLEDGE_MODEL_NOT_CONFIGURED` | 禁止启动并提示管理员配置 |
| `DIARY_NOT_ANALYZED` | 当前日记不满足触发条件 |
| `EMPTY_STRUCTURED_DIARY` | 当前日记没有结构化事件，不创建批次 |
| `EMPTY_STRUCTURED_EVENT` | 结构化事件没有可提取文字 |
| `ACTIVE_TASK_EXISTS` | 当前用户已有其他活动任务 |
| `ALREADY_DEPOSITED` | 当前日记已成功沉淀 |
| `SOURCE_CHANGED` | 来源变化，清理旧 checkpoint 后重新发起 |
| `LLM_CALL_FAILED` | 模型调用重试耗尽，可原地重试 |
| `MODEL_OUTPUT_INVALID` | JSON 修复后仍不符合结构，可原地重试 |
| `PUBLISH_FAILED` | 正式事务失败，可原地重试 |

`knowledge_event_extract` 在请求发出前和响应收到后分别写入现有 `ai_pipeline` 交互日志，请求正文和原始响应每条最多保留前 2000 个字符，超长时附原始长度。日志不包含认证头和 API Key。其他普通日志、指标标签和错误响应不包含日记正文、模型完整输入输出或事件内容。

## 11. 测试设计

### 11.1 后端

- 来源所有权、日记状态和结构化修订号校验。
- 空事件数组、空结构化事件、缺少模型配置和已沉淀日记拦截。
- Token 装批不拆分单个结构化事件。
- 每批完成后 checkpoint 包含新游标和结果。
- 中断后从未完成批次恢复，不重复调用已完成批次。
- 临时接口错误重试与 JSON 修复一次。
- 输出字段、日期、时间、顺序和覆盖校验。
- 同一用户活动任务唯一，重复触发和重复重试幂等。
- 租约过期、旧 `run_token` 写入隔离和应用启动恢复；模型返回后的失效令牌不能产生 checkpoint，也不能把新 worker 的任务改为失败。
- 发布事务全成功或全回滚，发布节点重复执行不重复写入。
- 来源变化使任务失败并清理 checkpoint。
- 列表稳定游标、用户隔离和详情越权访问。
- checkpoint state 和日志不包含解密后的 API Key。
- 图调用返回后的成功清理、提交后进程中断和定时补偿清理。
- 日记软删除、重新分析、结构化修改和后台分析提交与发布并发时执行统一锁定守卫。

### 11.2 前端

- 日记页四种状态及模型未配置状态。
- 处理中轮询、失败重试和成功跳转。
- 默认布局页面中第六个底部标签的路由高亮和安全区布局；日记详情保持 `auth` 布局且不出现底部标签栏。
- 事件列表三行截断、无限加载、空状态和错误重载。
- 详情自然段顺序、来源日记跳转和安全时间标签渲染。
- 在 320px、768px 和 1280px 视口下，页面内容随宽度变化且没有横向溢出；320px 下六个底部标签仍可辨识、可点击且不重叠。

### 11.3 真实模型手工验证

提供默认跳过的手工测试，读取指定日记并打印脱敏后的结构摘要，用真实 `knowledge` 模型验证：单事件、明显多事件、时间标签、Token 多批次和 JSON 修复。手工测试不写入正式知识。

## 12. 后续阶段

人物、事项和洞察将作为 `completed_stage` 的后续阶段设计。它们读取首版知识事件，不改变首版来源、顺序和正文；对应数据表、提示词、升级任务和页面在进入开发前单独确认。
