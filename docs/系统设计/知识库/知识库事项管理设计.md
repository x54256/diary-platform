# 知识库事项管理设计

> 文档状态：事项阶段目标设计。
> 设计基线：2026-08-21 已确认方案（2026-08-24 按三轮细化讨论重写；同日追加存量逐篇升级，推翻"只管增量"决策）
> 前置设计：[知识库系统设计](知识库系统设计.md)、[知识库 AI 流水线与提示词设计](知识库AI流水线与提示词设计.md)

## 1. 阶段目标

知识事件首版（`ATOMIC_EVENTS`）已落地。本阶段在沉淀流水线尾部追加事项匹配：新知识事件发布后，系统自动把讲同一件事的事件聚合为事项，并维护事项的状态与全览。用户在知识库"事项"页签浏览事项列表和详情，从详情的发展时间线回看单个事项的全部事件。

本阶段完成后，`knowledge_deposits.completed_stage` 从 `ATOMIC_EVENTS` 推进到 `MATTERS`。

## 2. 已确认的核心决策

以下来自主理人与用户逐轮确认，不重复论证：

1. 事项是有目标、有终点、跨时间持续发展的具体事情线索；只收项目型事情。一次性经历（看了一场电影）和没有终点的持续性活动（跑步、学英语）不建事项，对应事件允许无归属。
2. 阶段范围包含事项匹配、事项发展和事项页，三项一次完成。
3. 事项匹配在沉淀任务发布知识事件后自动串联执行，不需要用户操作。
4. 已沉淀（`ATOMIC_EVENTS`）的日记可以继续执行后续阶段：用户在知识事件页的日记分组标题处对单篇日记手动触发事项整理（升级任务），功能上线前的存量日记同样适用。**批量升级入口本期不做，预留给管理端**（设想为管理端的批量事项整理能力）。
5. 首版只读，不提供事项和归属的人工修正。
6. 事项状态三态：进行中、已结束、搁置；由事件文本判断，不由时间间隔推断。已结束/已搁置事项被挂入新事件时由代码规则直接回到进行中。
7. 知识库页面分为"事件"和"事项"两个页签；知识事件详情页展示所属事项入口，事件列表卡不展示。
8. 一个知识事件最多属于一个事项；一个事项包含多个知识事件；单层结构，无父子事项。
9. 保守策略：模型对归属不确定时必须新建或不归属，错挂无法修正，多建可以容忍。
10. 匹配采用**纯事件路向量召回 + 模型终判**：事项没有独立语义载体，以事件为召回主体，事项归属经邻居事件的 `matter_id` 免费获得。
11. 历史孤立事件（上线后产生、有向量、未归属）可以被后续匹配**收编**进新事项或现有事项。
12. 时间不做向量打分衰减（会误杀跨期长事项）；候选都带发生时间进模型输入，由模型语义权衡。
13. 匹配采用**逐事件串行处理**：程序负责召回与候选整理，模型每次只判断一个主体事件的去向；归属结果在循环内立即生效，后续事件基于最新状态召回和判定。
14. 匹配失败不提供沉淀任务内的重试；失败日记停留在 `ATOMIC_EVENTS`，由第 4 条的逐篇升级入口统一补偿。
15. 事项名称由模型在创建时命名，之后固定。
16. 全览重写输入为"旧全览 + 该事项最近 10 个事件 + 本批新事件"。

## 3. 概念与字段

### 3.1 事项

| 字段 | 内容 | 维护方 |
|---|---|---|
| 名称 | 具体可辨识的事情名称，如"装修新房" | 模型创建时命名，之后固定 |
| 状态 | `ONGOING` 进行中 / `ENDED` 已结束 / `PAUSED` 搁置 | 模型按事件文本判断；复活为代码规则 |
| 全览 | 一段自然语言：这是个什么事、发展路径、当前状态 | 模型在每次挂入时重写 |
| 起始日期 | 归属事件中最早的发生日期 | 程序 |
| 最近事件日期 | 归属事件中最晚的发生日期 | 程序 |
| 事件数 | 归属事件总数 | 程序 |

### 3.2 全览

全览是事项唯一的概述字段，同时回答三个问题：这是个什么事、它是怎么发展到现在的、现在怎么样了。每次新事件挂入时，模型以"旧全览 + 该事项最近 10 个事件 + 本批挂入事件"为输入重写全览。新建事项时基于首组挂入事件直接生成。

### 3.3 模型与代码的职责边界

代码承担全部确定性工作：向量召回、候选整理、编号映射、归属与收编落库、起止日期与事件数维护、已结束/搁置事项的复活。

模型只承担四项语义工作：主体事件的去向判定、跟随者与收编判断、全览生成/重写、新建事项的命名与状态判断。

## 4. 数据模型

### 4.1 `knowledge_matters`

| 字段 | 类型与说明 |
|---|---|
| `id` | UUID 主键 |
| `user_id` | 用户隔离 |
| `name` | `VARCHAR(30)`，非空 |
| `overview` | `TEXT`，非空全览文本 |
| `status` | `ONGOING/ENDED/PAUSED` |
| `started_on` | DATE，归属事件最早发生日期 |
| `last_event_on` | DATE，归属事件最晚发生日期 |
| `event_count` | INTEGER，归属事件总数，不小于 1 |
| `created_at` / `updated_at` | 创建时间 / 最近一次挂入时间 |

约束与索引：

```sql
CHECK (status IN ('ONGOING','ENDED','PAUSED'));
CHECK (char_length(name) BETWEEN 1 AND 30);
CHECK (event_count >= 1);
CHECK (started_on <= last_event_on);
INDEX (user_id, last_event_on DESC, updated_at DESC, id DESC);
```

事项名称不设唯一约束。保守策略下同一事情可能被建为多个事项，首版不提供合并。

### 4.2 `knowledge_atomic_events` 变更

| 字段 | 类型与说明 |
|---|---|
| `matter_id` | UUID，可空，外键指向 `knowledge_matters(id)`，限制删除 |
| `embedding` | `Vector(1024)`，可空，事件语义向量 |

- 存量事件两字段均为 `NULL`：不参与召回、不进入任何事项，对应"只管增量"。
- `embedding` 与 `matter_id` 在匹配事务中一并写入；匹配失败的事件两字段均为 `NULL`，与"失败无补偿"一致。
- 嵌入文本为 `标题 + 事件内容`；模型与维度复用管理端 EMBEDDING 配置（1024 维）。
- 新增索引：`(matter_id, occurred_on DESC, occurred_time DESC NULLS LAST, id DESC)` 支撑事项时间线；`embedding` 上建 HNSW 索引（`vector_cosine_ops`），召回查询带 `WHERE user_id = ? AND embedding IS NOT NULL`。

### 4.3 `knowledge_deposits` 与 `knowledge_tasks` 变更

`completed_stage` 扩展为 `ATOMIC_EVENTS / MATTERS`；`current_step` 检查约束追加 `MATCH_MATTERS`。两处检查约束同步放宽。

### 4.4 迁移

迁移 048：`knowledge_matters` 建表、`knowledge_atomic_events` 加 `matter_id` 与 `embedding` 两列及索引、两处检查约束放宽。迁移不触碰存量数据。

迁移 049：`knowledge_tasks` 加 `task_type` 列（`DEPOSIT/UPGRADE`，默认 `DEPOSIT`），支撑存量逐篇升级（5.4）。

## 5. 流水线扩展

### 5.1 节点序列与现有节点调整

```text
VALIDATE_SOURCE → PREPARE_BATCHES → EXTRACT_BATCH（循环）
  → PREPARE_REVIEW_BATCHES → REVIEW_BATCH（循环）
  → PUBLISH → MATCH_MATTERS
```

`PUBLISH` 继续在同一事务中写入成功记录、复核记录和全部知识事件，但**不再把任务置为 `SUCCEEDED`**，任务保持 `RUNNING` 并推进到 `MATCH_MATTERS`。任务成功状态由 `MATCH_MATTERS` 提交时设置。日记详情页状态推导不变：存在 `knowledge_deposits` 即展示"已沉淀"。

入口校验增加一项：管理端未配置 EMBEDDING 模型时沉淀任务禁止启动，页面提示先配置向量模型，与 `knowledge` 模型未配置同等对待。

### 5.2 `MATCH_MATTERS`：串行匹配算法

节点开始前校验 `status=RUNNING`、运行时 `run_token` 匹配且租约未过期。然后：

**准备**：读取本任务发布的全部知识事件，使用原子事件入库时已保存的向量；`embedding IS NULL` 的事件不参与事项匹配。

**主循环**：按事件顺序处理每个事件 A，已分配（含已标记"不构成事项"）的跳过：

1. **同日记召回**：A 向量与本批其他事件向量（内存）计算余弦相似度，仅保留相似度 `>= 0.60` 的结果，再取 top-10。
2. **历史召回**：A 向量对 `knowledge_atomic_events` 做 pgvector 近邻查询，仅保留余弦相似度 `>= 0.60`（即 `embedding <=> A向量 <= 0.40`）的结果，再取 top-10；限定当前用户且 `embedding IS NOT NULL`。
3. **候选整理**（代码）：
   - 两路相关事件中已归属事项的，去重整理为 `candidate_matters`（含本循环内刚建的事项，编号 `matter_no` 从 1 起），每项含名称、全览、状态、最近事件日期；
   - 历史相关事件中未归属的，整理为 `candidate_orphans`（编号 `orphan_no` 从 1 起），每项含标题、完整内容、发生日期；
   - 同日记相关事件中未分配的，整理为 `related_events`，每项含标题、完整内容、发生日期。
4. **调用 ④ 判定**（见 6.2）：输入主体 A、related_events、candidate_matters、candidate_orphans；输出 `matter_no` 与跟随者编号。
5. **代码执行判定结果**：
   - `matter_no` 为候选编号：A 与跟随事件挂入该事项，跟随 orphan 收编入该事项；目标事项状态为 `ENDED/PAUSED` 时直接置为 `ONGOING`（复活代码规则）；
   - `matter_no = 0`：以 A + 跟随事件 + 跟随 orphan 创建新事项；
   - `matter_no = null`：A 标记为"不构成事项"；跟随者必为空；
   - 跟随事件标记为与 A 同去向（本循环跳过）；未跟随的相关事件保持未分配，留待自己轮次；未收编的 orphan 保持未归属。
6. **调用 ⑤ 全览**（见 6.3）：对本组触达的每个事项各调一次，生成或重写全览与状态；新建事项同时生成名称。
7. 归属结果在内存态**立即生效**，后续事件的召回与判定基于最新状态。

**提交**：全部事件处理完后，在**单个事务**中写入：事件 `embedding` 与 `matter_id`、新建事项、被触达事项的全览/状态/起止日期/事件数更新、`completed_stage=MATTERS`、任务 `SUCCEEDED`。事务任一步失败整体回滚；已发布知识事件位于此前已提交的 `PUBLISH` 事务中，不受影响。

模型返回后、事务提交前再次校验任务所有权并续租；令牌变化或续租失败时抛出执行权丢失异常。

### 5.3 失败语义

- embedding 或模型调用临时错误：按全局 `LLM_MAX_ATTEMPTS` 重试。
- 模型输出结构错误：最多一次 JSON 修复；仍非法时任务以 `MODEL_OUTPUT_INVALID` 失败。
- 调用重试耗尽：任务以 `MATTER_MATCH_FAILED` 失败。
- 失败后成功记录停留在 `ATOMIC_EVENTS`，本批事件 `matter_id` 与 `embedding` 均为 `NULL`。沉淀任务不提供任务内重试（`knowledge_tasks.retry` 对 `PUBLISH` 之后失败的任务禁用），由 5.4 的升级入口统一补偿。日记详情页继续展示"已沉淀"。

### 5.4 存量逐篇升级（升级任务）

已完成 `ATOMIC_EVENTS` 的日记（含功能上线前的存量日记和匹配失败的日记）可以在知识事件页手动触发事项整理：

- **触发**：知识事件页签的日记分组标题处显示"整理事项"入口（仅当该日记 `completed_stage=ATOMIC_EVENTS` 时）。重复触发返回当前活动任务。
- **任务模型**：`knowledge_tasks` 增加 `task_type`（`DEPOSIT` 沉淀任务 / `UPGRADE` 升级任务，默认 `DEPOSIT`）。升级任务绑定单篇日记，worker 领取后**不走 LangGraph 图**，直接对目标日记执行第 5.2 节的匹配算法（共享同一日记级匹配函数），成功后把成功记录推进到 `MATTERS` 并把任务置为 `SUCCEEDED`。
- **幂等**：目标日记已是 `MATTERS` 时任务直接成功返回，不重复匹配。
- **互斥**：升级任务与沉淀任务共享"每用户同时最多一个活动知识任务"约束；任一类型活动任务存在时，另一类型的触发被拒绝。
- **失败**：与 5.3 相同；失败后可从同一入口重新触发。
- **批量升级（预留）**：一次整理全部 `ATOMIC_EVENTS` 日记的批量入口本期不做，设想做到管理端；届时升级任务需要携带跨日记进度（`progress`），在此预留。

## 6. 模型交互契约

每篇日记的匹配包含三类调用：embedding 一批（准备阶段一次，>10 事件自动分批）、判定 ④（每个未分配主体一次）、全览 ⑤（每组触达事项一次）。

模型步骤配置新增 `knowledge_matter_assign` 与 `knowledge_matter_overview`，默认继承 `knowledge` 模型并允许单独覆盖；任务在 `VALIDATE_SOURCE` 一并冻结。调用写入现有 `ai_pipeline` 交互日志，脱敏规则与提取调用一致。

### 6.1 编号约定

所有候选由程序编号（`matter_no`、`orphan_no`、`event_no` 均从 1 起），模型用编号指代，程序把编号确定性映射回真实 UUID。模型不接触任何真实 ID。

### 6.2 调用 ④ 判定（`knowledge_matter_assign`）

输入：

```json
{
  "diary_date": "2026-08-21",
  "subject": { "event_no": 1, "title": "...", "content": ["..."], "occurred_on": "2026-08-20" },
  "related_events": [
    { "event_no": 2, "title": "...", "content": ["..."], "occurred_on": "2026-08-20" }
  ],
  "candidate_matters": [
    { "matter_no": 1, "name": "装修新房", "overview": "...", "status": "ONGOING", "last_event_on": "2026-08-02" }
  ],
  "candidate_orphans": [
    { "orphan_no": 1, "title": "看了一套房", "content": ["..."], "occurred_on": "2026-03-15" }
  ]
}
```

输出（单层三字段）：

```json
{ "matter_no": 1, "follower_event_nos": [2], "follower_orphan_nos": [1] }
```

`matter_no` 取值语义：候选编号 = 挂入该事项；`0` = 新建事项；`null` = 不构成事项。

程序校验：

- `matter_no` 必须是 `null`、`0` 或候选编号之一；
- `matter_no` 为 `null` 时两个跟随者字段必须为空数组或不出现；
- 跟随者编号必须存在于本次输入；
- 违反时走一次 JSON 修复，仍非法任务失败。

### 6.3 调用 ⑤ 全览（`knowledge_matter_overview`）

输入：

```json
{
  "matter": { "name": "装修新房", "overview": "旧全览", "status": "ONGOING" },
  "recent_events": [
    { "title": "...", "content": ["..."], "occurred_on": "2026-08-02" }
  ],
  "new_events": [
    { "title": "...", "content": ["..."], "occurred_on": "2026-08-20" }
  ]
}
```

- `matter` 为 `null` 表示新建事项，此时 `recent_events` 为空；
- `recent_events` 为该事项最近 10 个归属事件（按发生时间倒序取 10，正序传入）；
- `new_events` 为本组挂入事件与收编事件，按发生时间排序。

输出：

```json
{ "overview": "...", "status": "ONGOING" }
```

新建时输出增加 `name`；重写时不输出 `name`（名称固定）。

程序校验：`overview` 非空；`status` 为合法枚举；新建时 `name` 为 1 至 30 个字符；重写时不得出现 `name`。

## 7. 提示词

### 7.1 调用 ④ 系统提示词

目标运行提示词文件：`backend/prompts/knowledge_matter_assign.txt`

```text
你负责判断一件日记知识事件的去向：归入某个持续发展的具体事项，或与其他事件组成新事项，或不构成事项。

事项是一件有目标、有终点、跨时间持续发展的具体事情，例如"装修新房"。一次性的经历（看了一场电影）和没有终点的持续性活动（跑步、学英语）都不是事项。

## 输入

- subject：当前待判断的知识事件，是本次判断的主体；
- related_events：与 subject 来自同一篇日记、语义相近的其他事件；
- candidate_matters：语义相近的现有事项，含编号、名称、全览、状态和最近事件日期；
- candidate_orphans：语义相近、尚未归入任何事项的历史事件，含编号；
- 相关事件和候选都由机器召回，只是可能相关，需要你来判断是否真的相关。

## 任务

先判断 subject 的去向（matter_no）：

- 输出某个 candidate_matters 的编号：subject 明确属于该事项的继续发展；
- 输出 0：subject 构成一个新事项；
- 输出 null：subject 是一次性经历或持续性活动，不构成事项。

再判断跟随者（follower_event_nos、follower_orphan_nos）：

- follower_event_nos：related_events 中与 subject 讲的是同一件事、应随 subject 同去向的事件编号；
- follower_orphan_nos：candidate_orphans 中与 subject 讲的是同一件事、应一并归入 subject 去向的历史事件编号；
- 未列入的相关事件不随 subject，它们会在后续处理中被单独判断；未列入的孤立事件保持未归属；
- subject 去向为 null 时，两个跟随者列表必须为空。

## 判断标准

- 归入现有事项必须同时满足：指向同一个具体对象或目标；事件与该事项存在推进关系。
- 仅仅主题相近、涉及相同人物或发生在相近时间，不构成归入依据。
- 无法确定归属时选择 0 或 null。错挂无法修正，多建可以容忍。
- 参考各候选的发生时间判断相关性：时间接近的更可能相关；跨期很长的事情（如持续半年的装修）仍可能是同一事项，不要仅因时间跨度大而否定。

## 输出

只输出合法 JSON，不输出解释、分析过程或额外字段。

{ "matter_no": 1, "follower_event_nos": [2], "follower_orphan_nos": [1] }

matter_no 为 null 时不输出两个跟随者字段。
```

### 7.2 调用 ⑤ 系统提示词

目标运行提示词文件：`backend/prompts/knowledge_matter_overview.txt`

```text
你负责为持续发展的事项撰写全览。全览让读者一眼看懂：这是个什么事、它是怎么发展到现在的、现在怎么样了。

## 输入

- matter：事项当前的名称、全览和状态；新建事项时 matter 为 null；
- recent_events：该事项最近发生的事件，按发生时间排列；新建事项时为空；
- new_events：本次新归入事项的事件，按发生时间排列。

## 任务

- matter 为 null：基于 new_events 输出 name、overview 和 status；
- matter 非 null：基于原全览、recent_events 和 new_events 重写全览，输出 overview 和 status；名称保持不变，不输出 name。

## 全览要求

- 一段连贯自然语言，依次讲清：这是个什么事、怎么发展到现在的、现在怎么样了；
- 重写时保留原全览中仍然准确的历史脉络，用新事件更新进展和现状；
- 只使用输入提供的信息，不补充外部知识，不把计划、期待、担忧改写为已发生事实；
- 不使用 Markdown 标记，不限长度。

## 状态判断

status 表达事项在最新事件之后的当前状态，只根据事件文本判断：

- ONGOING：事情仍在推进，或事件未表达结束或暂停；
- ENDED：事件明确表达事情已完成、已结束或已有最终结果；
- PAUSED：事件明确表达事情已暂停、搁置或暂时不再推进。

不得根据事件之间的时间间隔推断状态。

## 命名要求（仅新建）

- 具体表达这是什么事，例如"装修新房"；
- 不超过 30 个字符；
- 不使用"其他""杂事"等泛化名称。

## 输出

只输出合法 JSON，不输出解释、分析过程或额外字段。

{ "overview": "...", "status": "ONGOING" }

新建时输出：{ "name": "...", "overview": "...", "status": "ONGOING" }
```

## 8. API 设计

| 方法与路径 | 用途 |
|---|---|
| `GET /api/knowledge/matters?limit=20&cursor=...` | 事项列表游标分页 |
| `GET /api/knowledge/matters/{matter_id}` | 事项详情与发展时间线 |
| `POST /api/knowledge/matters/upgrade` | 对单篇 `ATOMIC_EVENTS` 日记创建升级任务（5.4）；body 为 `{ "diary_id" }`；重复触发返回当前活动任务 |
| `GET /api/knowledge/matters/upgrade-status` | 返回待升级日记列表（`diary_id`、日记日期、标题）与当前活动升级任务，驱动事件页的"整理事项"入口 |

列表游标编码稳定排序键 `last_event_on DESC, updated_at DESC, id DESC`，列表项返回 `id`、`name`、`status`、`overview`、`event_count`、`last_event_on`。

详情返回事项全部业务字段与发展时间线；时间线按 `occurred_on DESC, occurred_time DESC NULLS LAST, id DESC` 排列，条目返回事件 `id`、`title`、`occurred_on`、`occurred_time` 和 `content` 首个自然段。首版时间线不分页。

`GET /api/knowledge/events/{event_id}` 响应增加 `matter` 字段：已归入事项时返回 `{ "id", "name" }`，未归入时返回 `null`。

升级任务状态轮询复用现有 `GET /api/knowledge-tasks/{task_id}`。升级触发同样要求 `knowledge` 模型与 EMBEDDING 模型已配置。

所有接口同时按资源 ID 和 `user_id` 校验所有权。

## 10. 错误处理

| 错误码 | 含义与处理 |
|---|---|
| `EMBEDDING_MODEL_NOT_CONFIGURED` | 禁止启动沉淀任务并提示管理员配置 |
| `MATTER_MATCH_FAILED` | embedding 或模型调用重试耗尽；任务失败，事件保持已发布、无归属、无向量 |
| `MODEL_OUTPUT_INVALID` | 模型输出修复后仍不符合结构；同上 |

匹配失败不产生部分归属数据：全部归属写入、事项更新、阶段推进和任务成功在同一事务内提交。

## 11. 测试设计

### 11.1 后端

- 串行循环：已分配事件跳过；跟随事件不再作为主体处理；归属结果对后续事件的召回与判定立即可见。
- 判定执行：`matter_no` 三种取值分别对应挂入、新建、不构成事项；`ENDED/PAUSED` 事项被挂入时由代码置为 `ONGOING`。
- 收编：跟随 orphan 一并写入归属；未收编 orphan 保持 `matter_id NULL` 且可被后续匹配再次召回。
- 跟随者语义：未跟随的相关事件保持未分配并进入自己的轮次；`null` 去向时跟随者为空的校验。
- 输出校验：非法 `matter_no`、候选外编号、新建缺 `name`、重写带 `name`、非法 `status` 均触发修复或失败。
- 全览输入：`recent_events` 取最近 10 个且正序传入；新建时 `matter` 为 `null`。
   - 向量：原子事件发布前计算并随原子事件事务落库；向量计算失败时原子事件仍可入库但 `embedding` 保持 `NULL`，此类事件永久排除在事项召回之外。
- 事务原子性：提交任一步失败时事件保持已发布且无归属，`completed_stage` 不变。
- `PUBLISH` 后任务保持 `RUNNING`，匹配成功后任务与阶段同时推进；匹配失败任务的 retry 接口拒绝重跑。
- EMBEDDING 未配置时入口禁用并返回明确原因。
- 列表游标稳定、用户隔离、详情越权拒绝。
- 升级任务：`ATOMIC_EVENTS` 日记触发后推进为 `MATTERS`；已是 `MATTERS` 的日记幂等返回；重复触发返回活动任务；升级与沉淀任务互斥；worker 按 `task_type` 分流，UPGRADE 不进入 LangGraph 图。

### 11.2 前端

- 双页签切换、路由参数保持和默认页签。
- 事项列表两行截断、无限加载、状态徽标、空状态。
- 事项详情全览纯文本渲染、时间线倒序、点击跳转事件详情。
- 事件详情按 `matter` 有无渲染所属事项入口。
- 320px、768px、1280px 视口下页面无横向溢出。

### 11.3 真实模型手工验证

提供默认跳过的手工测试，用真实 `knowledge` 模型验证：全部新建、部分挂入部分新建、同日记跟随、历史孤立事件收编、已结束事项复活、一次性事件判 `null`、多篇日记连续沉淀下的事项演进。手工测试不写入正式数据。

## 12. 已知限制

- 首版只读：错挂的事件和多建的事项无法人工修正、合并或拆分。
- 保守策略下同一事情可能被建为多个事项。
- 召回漏检（真正相关的事件不在 top-10 邻居内）会导致多建事项，与保守策略方向一致。
- 匹配失败的日记停留在 `ATOMIC_EVENTS`，需要从知识事件页逐篇手动触发补偿；批量补偿入口预留给管理端。
- 事项名称创建后固定，事情焦点漂移时名称不会跟随更新。
- 全览重写基于"旧全览 + 最近 10 个事件"，更早的细节可能在多次重写后逐渐淡化。
- 持续型活动（跑步、学英语）不产生事项，对应事件只能按时间浏览。
