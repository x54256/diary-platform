# 第一层事件要点数据库设计

状态：记录当前已确认的存储方向；具体字段和约束为本轮设计草案。尚未执行数据库迁移。

## 1. 范围与依据

本文定义知识图谱第一层事件要点的正式存储及检索数据。依据：

- [个人知识图谱第一层实体模型](../../个人知识图谱第一层实体模型.md)。
- 本轮对话已确认的事件要点生成与审核约定。

已确认的方向：

1. 一个来源日记事件对应一个图谱事件，复用现有日记事件表及事件 ID。
2. 要点独立存储，每个要点保存序号、标题和详细内容。
3. 跨日语义召回基于详细内容，新要点与历史要点使用相同的输入字段。
4. 要点标题用于展示，并随完整事件提供给关系判断模型，不参与候选检索。

本文不展开人物、关系、任务队列和审核记录表。发生日期提取及整日发布由后续设计承接。

## 2. 复用日记事件

复用 `diary_events`，其主键作为图谱事件标识。标题、原始正文、用户归属及来源日记从现有日记数据读取，不在新增事件表中重复保存。

准入条件：事件已经完成分析，有效重要性为中或高。有效重要性优先使用用户设置，未设置时使用 AI 设置。

满足准入条件只表示可以处理；要点生成成功、模型审核通过、人工确认及整日图谱发布是不同阶段。查询历史图谱时，必须限定此前已经完成全流程并发布的事件；查询当天候选时，只使用已经核验通过的事件。不能仅凭存在日记事件或要点记录判断事件已经入图。

在 `diary_events` 增加字段：

| 字段 | 类型 | 可空 | 默认值 | 含义 |
| --- | --- | --- | --- | --- |
| `is_in_graph` | BOOLEAN | 否 | `false` | 该事件是否已完成全流程并正式入图 |

整日图谱核验通过后，在发布事务中将当天准入事件的 `is_in_graph` 设置为 `true`，与本次正式关系等发布数据一起提交。失败时保持 `false`。历史候选查询只读取 `is_in_graph = true` 的事件；当天已核验候选通过当前流程单独提供。

该字段只表达正式入图状态，不承担任务进度或错误记录。

## 3. 要点表 `graph_event_points`

每个正式要点独立一行，一个日记事件对应多个有序要点。

| 字段 | 类型 | 可空 | 含义 |
| --- | --- | --- | --- |
| `id` | UUID | 否 | 要点唯一标识，主键，默认 `gen_random_uuid()` |
| `event_id` | UUID | 否 | 来源事件 ID，外键引用 `diary_events.id` |
| `no` | INTEGER | 否 | 事件内序号，从 1 开始连续递增 |
| `summary` | TEXT | 否 | 要点标题，对应提取结果的 `summary` |
| `detail` | TEXT | 否 | 详细内容，对应提取结果的 `detail` |
| `embedding` | VECTOR(1024) | 是 | 由 `detail` 生成的 1024 维语义向量 |
| `embedding_model` | TEXT | 是 | 向量模型及版本的稳定标识 |

`embedding` 和 `embedding_model` 是检索辅助数据，不属于第一层事件的业务知识属性。

向量允许暂时为空，以保存已经确认的事实内容。查询语义候选时排除向量为空的记录；检索准备尚未完成时，不允许把该记录视为已完整参与候选发现。检索失败应记录并重试，不能当作没有关联事件。

### 3.1 数据库约束

- `id` 为主键，数据库默认值为 `gen_random_uuid()`。
- `event_id` 建立外键，删除策略采用 `RESTRICT`。后续事件删除流程需要先处理要点及引用这些要点的关系。
- `(event_id, no)` 唯一。
- `no > 0`。
- `summary`、`detail` 均为非空且去除首尾空白后非空的文本。
- `embedding` 与 `embedding_model` 同时为空或同时有值；模型标识不得为空白。
- 向量维度已于 2026-10-12 确认为 1024，正式迁移采用 `vector(1024)`。模型响应和查询向量均需校验为 1024 维；不同模型的向量不能仅因维度相同而混用。

程序在提交正式要点时检查序号为 `1..N`，既不缺号也不重复。普通唯一约束只能防止重复，不能保证连续。

保存一个事件的完整要点数组时，在事务内先通过 `SELECT ... FOR UPDATE` 锁定对应 `diary_events` 行，再检查正式要点是否存在，并按候选数组顺序一次性写入 `1..N`。所有正式保存入口遵循同一加锁规则。模型生成与审核在该短事务之前完成，不在持锁期间调用模型。

不通过 `max(no)+1` 逐条分配序号。普通事务中的该查询不能独立防止并发冲突，且本流程本身是完整数组提交。

### 3.2 字段注释

迁移中为各字段添加数据库注释。PostgreSQL 使用独立的 `COMMENT ON COLUMN` 语句，例如：

```sql
COMMENT ON COLUMN graph_event_points.embedding_model
IS '生成详细内容向量的模型及版本标识';
```

### 3.3 关系证据定位

`id` 用于稳定引用具体要点；`no` 用于按事件顺序展示，并表达业务文档中的源要点序号和目标要点序号。

后续关系设计应引用要点 ID，并校验要点属于对应关系端点事件。要点 ID 不代替关系语义核验。正式要点发生新增、删除、拆分、合并或重排时，必须重新核验受影响的事件关系；具体操作流程另行设计。

## 4. 语义检索

### 4.1 索引清单

| 索引 | 建立方式 | 用途 |
| --- | --- | --- |
| `id` 主键索引 | 主键自动建立 | 定位要点和关系证据 |
| `(event_id, no)` 唯一 B-tree 索引 | 唯一约束自动建立 | 序号去重、事件关联查询和有序读取 |

首版不重复建立单列 `event_id` 索引；复合索引的首列已经是 `event_id`。近似向量索引不列入首版必建项。

向量模型仅接收 `detail`，不拼接要点标题或事件标题。

```text
历史 detail → 向量模型 → embedding
新 detail   → 同一模型 → 查询向量 → 距离计算 → 候选要点
```

- 应用调用向量模型，数据库保存向量并进行距离计算。
- 初始采用精确向量检索；是否增加近似向量索引由数据规模、延迟和召回验证结果决定。
- 语义候选使用可配置的最低相似度过滤，当前值为余弦相似度不低于 0.5。要点命中按历史事件聚合，每个当前事件保留语义分数前 5 个历史事件。完整查询规则及验证范围见《第一层事件关系识别技术方案》；阈值和候选数量不新增数据库字段。
- 增加近似索引时，明确指定与距离度量一致的 operator class；IVFFlat 的 `lists` 和查询 `probes` 依据数据量和召回测试确定，不固定照搬 `lists = 100`。
- 模型版本及距离度量需要配套确定，不能只根据向量维度判断兼容性。
- 不同模型产生的向量不得直接比较。更换模型时，需要重算参与检索的数据并制定切换流程。
- 超过向量模型输入限制时必须显式处理，不能静默截断详细内容；具体策略在模型接入设计中确定。

## 5. 正式保存与使用

1. 按事件要点提取方案保存生成候选及审核过程。
2. 完成原文审阅确认后，在短事务中锁定来源事件、检查是否已保存，再一次性写入全部正式要点。
3. 应用生成并保存语义向量。
4. 后续图谱流程使用已经核验并完成检索准备的数据；整日发布事务设置 `is_in_graph = true`。

候选与审核记录需要另行持久化，不能只存内存，也不应依靠先写入正式要点再删除来表达审核失败。

重复提交同一事件时，不能追加第二套正式要点。程序检查该事件是否已经保存正式结果，数据库唯一约束作为并发写入的最后保护。更新与重新生成的入口及关系重核验流程另行确定。

要点表不复制原始正文。生成任务仍需按已确认提取方案保存来源快照、模型与提示版本，以及各阶段结果，保证候选处理可追溯。

## 7. 技术依据

- [PostgreSQL 多列索引](https://www.postgresql.org/docs/current/indexes-multicolumn.html)：首列 `event_id` 的复合 B-tree 索引支持事件关联查询。
- [PostgreSQL 行级锁](https://www.postgresql.org/docs/current/explicit-locking.html)：正式保存时锁定来源事件。
- [PostgreSQL 字段注释](https://www.postgresql.org/docs/current/sql-comment.html)：使用 `COMMENT ON COLUMN`。
- [pgvector 官方说明](https://github.com/pgvector/pgvector)：`vector` 与 `vector(n)`、精确检索及近似索引的维度、距离和参数要求。

本文按已确认需求设计，不依据项目现有检索实现推导新方案。
