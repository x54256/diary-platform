# 知识沉淀真实调用审查报告

> 用途：提供给无项目上下文的第三方 AI 审查知识沉淀提示词、模型输出与程序约束。  
> 测试日期：2026-08-13  
> 测试模型：`qwen3.7-max-2026-06-08`

## 1. 系统目标

这是一个日记管理平台。用户先写日记，系统在上游“日记整理”环节将内容整理为多个结构化事件。知识沉淀读取这些已经整理过的事件，生成可长期回顾和检索的知识事件。

知识沉淀的首要目标不是重新拆分原子事件，而是：

1. 准确凝练事件事实；
2. 保留用户以后独立理解和回顾所需的关键内容；
3. 删除重复和不影响理解的枝节；
4. 保持来源中的主体、状态、条件、转折、因果强度和确定程度；
5. 为生成内容保留可逐字追溯的原文证据。

上游已经完成事件拆分。因此，每个结构化事件默认只生成一条知识事件。只有一个 `body` 明确混入多件互不相关、各自独立成立且无法由同一核心事情概括的事情时，才允许拆成多条。

无法明确判断时，必须保持一条，不主动寻找拆分边界。

## 2. 当前实现

### 2.1 单阶段调用

当前不是两阶段流程。每个输入事件由一次模型调用同时生成：

- `title`
- `source_fragments`
- `content`
- `occurred_on`
- `occurred_time`

输入仅包含：

```json
{
  "diary_date": "2026-08-05",
  "events": [
    {
      "event_no": 1,
      "title": "结构化事件标题",
      "body": ["完整结构化事件正文"]
    }
  ]
}
```

`feeling` 与 `reflection` 不参与本次知识事件凝练。

### 2.2 输入、输出与发布约束

- 每个 `event_no` 独立处理，不跨事件合并信息。
- 一个结构化事件完整传入同一批次，不按 Token 预算拆开正文。
- 模型输出中，每个 `event_no` 返回一个 `atomic_events` 数组。
- 默认 `atomic_events` 只有一条记录；异常拆分时，数组中每条记录对应一件独立事情。
- 发布前当前程序仅校验 JSON 字段、编号、数量、日期、时刻等结构，不校验 `source_fragments` 是否真实出自 `body`。
- 成功发布后，会写入正式知识事件并锁定来源日记，不能再次沉淀或修改结构化来源。

相关代码：

- 运行提示词：`backend/prompts/knowledge_atomic_event.txt`
- 模型调用与结构校验：`backend/services/knowledge_ai.py`
- 工作流和发布：`backend/services/knowledge_workflow.py`
- 模型测试：`backend/tests/test_knowledge_atomic_events.py`
- 流程设计：`docs/系统设计/知识库/知识库AI流水线与提示词设计.md`

## 3. 当前提示词的关键规则

当前提示词已经要求模型：

1. 先完整阅读当前事件的 `title` 和全部 `body`；
2. 先凝练事实并生成 `title`、`content`，最后才选择 `source_fragments`；
3. `source_fragments` 仅用于核验，不是模型理解事件的信息边界；
4. 不得把设想、建议、准备执行写成已完成；
5. 不得把个人判断写成客观事实；
6. 不得把“可能、觉得、应该”等写成已经验证的结论；
7. 不得把单方提出写成双方商定；
8. 必须保留会影响后续决定、结论或当前状态的条件、原因和转折；
9. 不得把先后、相关或并列关系强化为因果；
10. 每个 `source_fragments` 元素必须是单个 `body` 字符串中连续出现的逐字原文；禁止 `...`、`……` 等省略，禁止跨位置拼接。

完整提示词见：`backend/prompts/knowledge_atomic_event.txt`。

## 4. 真实测试

测试日记 ID：`567d5606-f5f4-49c6-9d57-933bb72045a9`

测试步骤：

1. 删除该日记此前生成的 7 条正式知识事件和 1 条成功沉淀记录；
2. 临时将知识沉淀模型切换为 `qwen3.7-max-2026-06-08`；
3. 通过正式知识任务队列执行沉淀；
4. 任务成功后恢复默认知识模型 `qwen3.7-max`；
5. 读取 7 个来源结构化事件与 7 条新生成知识事件，人工逐条审查。

结果：

- 任务成功；
- 7 个结构化事件生成 7 条知识事件；
- 默认模型已恢复；
- 模型没有主动过度拆分；
- 但第 6 个结构化事件本应异常拆分为两条，模型没有拆分；
- 多条 `source_fragments` 仍使用了 `...`，不是连续逐字原文；
- 多条 `content` 仍存在事实状态、归属、确定程度或因果关系失真。

## 5. 真实输出的主要问题

### 5.1 来源片段违反逐字追溯要求

提示词已禁止省略与拼接，但模型仍输出如下形式：

```text
人家医生也说问题不在他那...但是他想要离职的话，那就离职吧
```

该字符串不是 `body` 任一字符串中的连续子串，而是用 `...` 删除中间内容后的改写片段。

同类问题出现在第 2、5、6、7 个事件。当前程序不校验来源片段与 `body` 的关系，导致违规结果被发布。

### 5.2 异常拆分未触发

第 6 个结构化事件的正文包含两件无关事情：

1. 晚上决定由小廖是否愿意一起遛狗，决定带狗走大圈还是自己跑步；
2. 小廖离职、心理咨询后的安排，以及由此产生的平台提醒功能想法。

这两件事没有共同目标、过程或结果，应在当前 `event_no` 的 `atomic_events` 中生成两条记录。模型仍合并为一条。

### 5.3 事实状态与归属失真

以下是人工已确认的典型失真。

#### 事件 1：把设想写得更确定

原文：用户觉得标红加粗任务“可能”放在事件分类步骤更合理，并已取消结构化步骤中的该任务。

模型本次已改进，保留了“我认为……更合理”，此项基本合格。

#### 事件 2：周总结功能

该事件保持一条是正确的。周总结功能设计、额度安排、人物画像计划、事项分类方法和认知提升理念共同属于同一段平台建设和方法反思。

本次较上次明显改进：

- 正确表达“仅沟通周总结设计方案就消耗 25% Token”；
- 正确保留“额度与颂梅共用，需要给颂梅预留一些”的含义。

但仍有轻微强化：原文只说额度重置后“再猛干”，模型写为“再高强度使用 CoderX”，将行动工具说得更确定。

#### 事件 4：辽宁报告改造

模型写“双方沟通后生成了规格”。原文是用户让 Qoder 查看代码、与它沟通并生成规格。“双方”容易暗示平等协商关系，宜保持为“与 Qoder 沟通后生成规格”。

#### 事件 5：日记与日程管理价值

模型仍将未来规划写成当前能力：

```text
平台能通过搜索、总结及识别重复错误等功能帮助成长
```

原文中搜索是当前功能；总结、识别重复错误是未来要做的功能，必须保留计划状态。

模型还把用户对日程管理价值的期待强化为已经证实的“督促执行”“导致放弃”。

#### 事件 6：小廖离职与心理咨询

模型输出存在多个问题：

- 没有拆分遛狗安排和离职议题；
- 将用户“感觉他心理问题不是很大”写成“医生认为其心理问题不大”；
- 将用户判断“阻塞点已经不在了”写成客观事实；
- 将此前用户提出过的安排写成“此前商定”；
- 缺少关键转折：用户支持小廖离职，但认为此前需要先休息的理由在自己看来已经不存在，因此准备重新和小廖商量“离职空档期边工作边找工作”。

#### 事件 7：母亲甲亢药物与无碘盐

模型将用户个人判断强化为医疗事实，例如：

- “需换用无碘盐”；
- “父亲吃海鲜已足够补碘”；
- “忌食海鲜”。

原文只是用户在了解药理后形成的想法、联想和建议，必须写明是用户的判断或建议，不能当作医学结论。

模型还将“小卖部没有”放大为“丹东无无碘盐售卖”，并把“可能有助于决策”的感受写成已经验证的结论。

## 6. 第三方 AI 需要完成的任务

请基于以上上下文完成审查，并给出可以直接落地的修改建议。

### 6.1 提示词审查

审查当前提示词是否仍存在：

- 对模型不够明确的规则；
- 重复、冲突或会分散重点的规则；
- 导致模型过度拆分或不拆分的表达；
- 导致模型把用户判断、建议、计划、推测、体验写成客观事实或已完成结果的表达；
- 导致模型遗漏影响结论的条件与转折的表达；
- 导致模型忽略来源片段逐字可追溯规则的表达。

请输出一份精简、可执行、重点明确的完整提示词。不要把“原子事件拆分”作为主任务；拆分只能是异常兜底。

- 事件 2 不拆分；

## 7. 约束

- 不改变数据库字段或 API 输出结构：`results -> event_no -> atomic_events[]`。
- 每条知识事件仍只包含 `title`、`source_fragments`、`content`、`occurred_on`、`occurred_time`。
- `source_fragments` 必须保留用户原文中的 `<time>` 标签；`content` 不应输出标签。
- 用户日记内容属于事实来源，第三方 AI 不得把其中的医疗、饮食或心理判断当作需要自行验证的专业结论；目标是忠实记录其表达性质。
- 保持单阶段模型调用，不引入两阶段架构。
- 保持 KISS，优先最小且可验证的修改。
