# 第一层事件关系识别技术方案

状态：2026-10-14，最终方案。跨日候选只使用语义召回；每个候选事件对由判定器和盲判验证器分别判断，结论不一致时由裁决器输出最终修正结果；所有模型调用显式启用思考模式。执行基线为语义阈值 `0.5`、每个当前事件保留语义分数前 5 个历史事件。当天事件完整两两比较。设计演变、实验参数、结果及局限统一记录在[第一层事件关系识别方案实验记录](./第一层事件关系识别方案实验记录.md)，不作为正式运行规则。

## 1. 目标与范围

基于已确认的事件要点，发现当天事件之间及当天事件与历史事件之间的事实关系，输出关系类型、方向、双方证据和关系描述。

依据：

- [个人知识图谱第一层实体模型](../../个人知识图谱第一层实体模型.md)：关系定义、方向和证据标准。
- 本轮对话已确认的要点输入及确认条件。
- [第一层事件要点数据库设计](./第一层事件要点数据库设计.md)：事件复用、要点存储、入图状态及检索字段。

识别只接收已经核验并经原文审阅确认的事件要点。人物身份统一及人物相关关系暂不展开；本方案的检索不依赖独立人物节点。

本方案覆盖候选召回、两次独立判断、分歧裁决、证据定位及程序完整性检查。正式关系存储和整日发布由后续设计承接。

## 2. 基本约定

1. 要点是检索证据单位，历史事件是召回排序和截断单位，关系判断单位是事件对，模型调用单位是批次。一个批次可包含多个待判断事件对。
2. 跨日语义召回使用要点的 `detail`；`summary` 不参与候选检索。
3. 批次输入由去重后的事件内容池和明确的事件对清单组成。每对判断读取对应双方全部要点，包括序号、标题及详细内容。
4. 事件使用现有日记事件 ID，不合并不同日记中的事件。
5. 所有查询和输出校验均限定当前用户。
6. 按日记日期逐日处理，当前日完成生成与核验后再处理下一日。来源日记日期决定处理范围，不直接决定关系方向。
7. 判定器 A 和验证器 B 必须分别读取同一份冻结事件要点；B 不接收 A 的状态、关系、理由或证据。
8. A、B 都判断全部候选事件对。验证不能只处理 `RELATED`，否则无法发现首次判断的漏判。
9. A、B 的关键结论完全一致时形成最终结果；任一关键字段不一致时，由裁决器 C 读取原始要点和双方结果，输出最终修正结果。

## 3. 整体流程

```text
读取当天已确认的事件要点
→ 检查检索准备情况
→ 对每个当前事件：
    使用全部要点语义检索历史要点
    按历史事件聚合，取语义分数前 5 个历史事件
→ 加入当天事件的完整比较对
→ 对事件对去重
→ 收集待判断事件，构造去重内容池及事件对清单
→ 在输入与输出预算内优先合为一个批次，超限则拆批
→ 判定器 A 批量判断全部候选事件对
→ 验证器 B 在看不到 A 结果的独立请求中重新判断全部候选事件对
→ 分别检查 A、B 的响应完整性和结构
→ 对同一 pair_id 比较状态、类型、方向、确定性和证据
    ├─ 完全一致：形成最终结果
    └─ 存在分歧：交给裁决器 C 重新读取双方要点和两份结果
                   输出最终修正结果
→ 对最终结果执行程序完整性检查
→ 保存最终关系、无关系或依据不足记录
→ 交给整日发布流程
```

检索匹配、A 或 B 单独返回 `RELATED` 都不等于关系已经正式入图。只有双判一致结果或裁决结果通过程序完整性检查后，才能交给发布流程。

## 4. 候选发现

### 4.1 比较范围

历史候选同时满足：

- 属于当前用户。
- 来源日记日期早于当前处理日记日期。
- `is_in_graph = true`。

不以固定的最近天数排除较早历史。历史事件允许实际发生日期与来源日记日期不同。

当天所有准入且已确认要点的事件进行完整两两比较，不依赖历史检索；每对仅处理一次。可以先完成当天各事件的要点核验，再开展关系判断。当前事件不与自身比较。

### 4.2 检索准备检查

- 当前要点及参与语义检索的历史要点必须具有同一模型版本的 1024 维向量。
- 当前向量缺失或维度错误、已入图历史向量未准备完成、检索服务失败时，记录明确错误并先补齐或重试。
- 不能把检索失败或历史向量缺失当作没有关联；跨日语义召回失败时不得产出正常结果。

### 4.3 跨日语义召回

对当前事件的每个要点，使用完整 `detail` 的 1024 维向量查询历史要点。当前与历史向量的模型版本必须一致。采用精确余弦距离计算，最低余弦相似度为可配置参数，最终值为 `0.5`。

语义查询先过滤用户、历史日期、入图状态及向量模型版本，再过滤相似度。符合阈值的要点命中按历史事件分组；一个当前事件与一个历史事件的语义分数，取双方所有要点组合中的最高余弦相似度。按事件分数降序、历史事件 ID 升序稳定排序，每个当前事件保留前 5 个历史事件；不足 5 个时不补足。

要点命中不能在事件聚合前按固定数量截断，否则同一历史事件的多个要点可能挤掉其他历史事件。数据规模增大后如需增加要点级检索窗口，该窗口必须大于事件级候选数，并通过召回率验证后配置。

保存每个候选历史事件的事件分数，以及产生该分数的当前要点 ID、历史要点 ID、余弦距离、相似度和向量模型标识。相似度只用于候选召回，不作为关系成立依据。

### 4.4 事件候选去重

每个当前事件最多得到 5 个跨日语义候选历史事件。

同一事件对在不同要点中重复出现时，待判断清单只保留一次，正常执行只分配到一个批次；失败补判另行记录。程序用无序事件 ID 对作为去重键，不能把该键的排列当成关系方向。

语义检索失败、向量缺失或模型版本不一致时阻断跨日候选发现。

## 5. 事件对判断

### 5.1 批量模型输入与分批

判定器 A、验证器 B、裁决器 C 及各自失败补判请求必须显式启用思考模式，请求携带当前渠道“开启思考”参数。任务开始时分别冻结三种角色的模型、渠道、思考参数和提示版本；同一角色在整个任务中保持一致。三个角色统一使用 `deepseek-v4-pro`，通过独立请求和不同职责提示隔离上下文。所选渠道不能显式启用思考时，任务在模型调用前失败，不能退回关闭思考或服务默认配置。

检索完成后，将当天完整比较对和跨日候选对合并、去重。程序为每个无序事件对分配稳定的 `pair_id`，同一次任务补判沿用该 ID。`event_a_id`、`event_b_id` 仅用于定位双方，不决定关系方向。

模型请求包含两部分：

- `events`：当前批次涉及的事件内容池，按事件 ID 去重；每个事件的完整要点只传一次。
- `pairs`：当前批次明确要求判断的事件对清单，每项包含 `pair_id` 及双方事件 ID。

```json
{
  "events": [
    {
      "id": "事件 A 的 UUID",
      "title": "事件原标题",
      "diary_date": "2026-08-25",
      "occurred_on": null,
      "points": [{"no": 1, "summary": "要点标题", "detail": "详细内容"}]
    },
    {
      "id": "事件 B 的 UUID",
      "title": "事件原标题",
      "diary_date": "2026-08-26",
      "occurred_on": null,
      "points": [{"no": 1, "summary": "要点标题", "detail": "详细内容"}]
    }
  ],
  "pairs": [
    {
      "pair_id": "pair-001",
      "event_a_id": "事件 A 的 UUID",
      "event_b_id": "事件 B 的 UUID"
    }
  ]
}
```

每个事件包含 ID、原标题、来源日记日期、已确定的实际发生日期及全部有序要点。未知发生日期为空，不用来源日记日期代替。真实要点 ID 由程序持有，用于解析模型返回的序号。命中片段和分数用于诊断，不作为关系成立的事实依据。

模型逐对独立判断，必须返回清单中的每一对，包括没有关系及依据不足的结果。它不能自行增加内容池中的其他组合；不能用第三个事件的内容替代本对双方的证据，也不能通过关系传递补出新关系。

分批规则：

1. 无待判断事件对时不调用模型；所有对及完整事件内容符合预算时，合为一个批次。
2. 超限时，将事件对按稳定的无序事件 ID 键排序，依次装入批次。加入一对时，只新增批次中尚未出现的事件内容。
3. 每次加入前同时检查输入和输出预算。输入计入提示词、完整内容池、事件对清单及输出结构说明；为整批逐对输出预留预算，不能只检查输入是否放得下。
4. 达到预算即关闭当前批次，再开始下一批。同一事件可因参与不同批次而重复传入，但每个批次内部只出现一次。
5. 一个事件对单独成批仍超限时，记录明确的输入或输出预算错误，阻断该对处理。不能截断要点、静默漏掉该对或记成无关系。

模型输入预算、输出预算和每对结果的输出预留量通过配置提供，按所选模型限制及真实响应验证后冻结。本轮旧脚本的 32,000 字符限制仅是逐对测试保护，不能直接当作批量调用的 Token 预算。模型因输出上限截断时按响应失败处理，后续缩小批次重试；不把被截掉的结果记成无关系。

每个角色的每批调用都保存事件 ID 集合、事件对清单、完整请求快照、预算计算及实际 Token，保证分批可重放。A 和 B 使用相同候选清单，但分别计算批次；B 的请求不得包含 A 的任何输出。批次合并不跨越逐日处理边界；历史准备日和当前处理日分别调用，正常处理当前日不重复判断已处理完的历史事件之间的关系。

### 5.2 判断顺序与方向

| 优先顺序 | 成立条件 | 类型 | 方向 |
| --- | --- | --- | --- |
| 1 | 同一具体事项产生新行动、新状态或新结果 | 后续事件 | 前序事件 → 后续事件 |
| 2 | 原文表达一方信息、体验或结果促使另一事项发生，或明确表达对此联系的推测 | 引发事件 | 触发事件 → 被触发事件 |
| 3 | 一方引用、回忆、比较或联想到另一具体事件，且不构成前两类 | 提及事件 | 提及方 → 被提及方 |

同一事件对只输出一种关系，按核心语义选择。同人物、同项目、相似主题、相邻日期不足以建立关系。

判断时先定位双方全部要点中表达联系的事实，再应用上述类型规则。联系可以由单个要点直接表达，也可以由同篇日记上下文补全省略的指代、原因或事项；上下文必须给出唯一明确的指向。不能先因标题不同或共同人物、主题而排除已有的明确联系；每对检查两个方向。后续关系可以根据具体动作与状态变化识别，不要求后者逐字引用前一条日记，但必须有新行动、状态或结果的证据。

同一事项再次出现在较晚日记中，不直接认定为新进展。若明确回忆另一具体事件，按提及关系判断；若存在具体事项联系但无法区分新进展与重复回顾，且无其他充分关系证据，使用 `UNRESOLVED` 并说明缺失事实。不能仅根据记录日期决定先后。

计划与行动、推测与事实、他人陈述与已确认事实必须保持原有区别。原文明确表达“可能因某事造成”时，可以建立推测性引发关系，必须保留“可能”等含义；不能只因推测用语就拒绝关系，也不能改为确定因果。

已有 A→B 和 B→C 不自动产生 A→C；每条关系都必须有自身直接证据。前序事项在多次记录中出现时，具体连接哪些事件依据直接证据判断，不能仅按最近日期选取。

### 5.3 关系确定性

每条关系增加必填字段 `certainty`，表达原文对关系的陈述方式：

| 值 | 展示名称 | 含义 |
| --- | --- | --- |
| `EXPLICIT` | 明确表达 | 原文直接表达该关系，未将关系限定为推测 |
| `SPECULATIVE` | 推测 | 原文明确表达关系，同时保留“可能”“推测”“不能确定”等关系限定 |

确定性属于关系证据属性，不是模型置信分数。`EXPLICIT` 不代表外部客观验证，也不改变他人陈述或个人判断的归属。判定针对当前关系，不能只因要点其他句子出现“可能”就将整条关系标成推测。

原文及其同篇上下文必须能确定具体事件之间的联系。省略的信息具有唯一明确指向时，可以通过上下文补全；补全后的关系仍按原文陈述方式确定 `certainty`。只有共同人物、主题或时间相邻，无法形成唯一指向的联系不生成关系。

触发因素可以只是事件中的部分信息或事前安排。例如聚餐事件中的“于海昕要来广州并约饭”，可以作为怀念事件的推测性触发因素；描述应指向这部分信息，不能写成“晚上的聚餐行为使下午开始怀念”。不因此新增事件节点。

该例调整后的预期关系为：聚餐 → 引发事件 → 怀念过去，`certainty = SPECULATIVE`，双方证据为 `[1]`、`[1]`，描述为“我推测，于海昕要来广州可能促使自己再次怀念过去。”2026-10-12 的实测识别出该组合，2026-10-13 的逐对复测漏判；该例作为固定正例检查批量判断是否正确，不能把合并调用本身视为漏判修复。

### 5.4 输出状态

| 状态 | 含义 | 关系字段 |
| --- | --- | --- |
| `RELATED` | 证据支持明确表达的关系或原文明示的推测关系 | 必须完整输出并标记确定性 |
| `NO_RELATION` | 本次完整检查未发现符合定义的关系 | 为空 |
| `UNRESOLVED` | 无法定位具体对应事件，或无法证明原文确实表达该联系 | 为空；单纯推测性措辞不属于该状态 |

批量响应顶层为 `results`，每项通过 `pair_id` 对应请求清单中的一个事件对，逐对结果结构如下：

```json
{
  "results": [
    {
      "pair_id": "pair-001",
      "status": "RELATED",
      "reason": "该事件继续执行此前的就医安排，并产生检查结果。",
      "relation": {
        "source_event_id": "事件 A 的 UUID",
        "target_event_id": "事件 B 的 UUID",
        "relation_type": "后续事件",
        "certainty": "EXPLICIT",
        "source_point_nos": [1],
        "target_point_nos": [1],
        "description": "此前约定的检查得到执行，并产生新的检查结果。"
      }
    }
  ]
}
```

`results` 必须与请求 `pairs` 一一对应，每个 `pair_id` 恰好出现一次，程序按 ID 匹配而不依赖返回顺序。`reason` 是处理记录，不是额外的图谱关系属性。`NO_RELATION` 和 `UNRESOLVED` 的 `relation` 为 `null`，`reason` 说明判断原因。

缺失、重复、额外事件对以及请求失败均为执行错误，不能映射为上述任何语义状态。A 或 B 的单份有效输出只用于双判比较，不能单独成为最终关系。

### 5.5 批量提示词与固定回归样例

最终 A 提示词保存为 [layer1_relation_batch_prompt_v4.txt](../../../backend/scripts/fixtures/layer1_relation_batch_prompt_v4.txt)，B 提示词保存为 [layer1_relation_blind_verify_v3.txt](../../../backend/scripts/fixtures/layer1_relation_blind_verify_v3.txt)，C 提示词保存为 [layer1_relation_adjudicate_v3.txt](../../../backend/scripts/fixtures/layer1_relation_adjudicate_v3.txt)。三个版本共同加入“同一具体事项持续进展”和“唯一上下文指向的省略补全”边界。历史构造样例保存在 [layer1_relation_regression_v3.json](../../../backend/scripts/fixtures/layer1_relation_regression_v3.json)，本轮 28 对用户确认参照保存在 [confirmed-reference-labels.json](../../../knowledge-graph/validation-2026-08-26/unseen-blind-verify-20261014/confirmed-reference-labels.json)。实验脚本和大体量原始响应已在方案冻结后清理；历次参数、结果和语义审阅结论记录在[方案实验记录](./第一层事件关系识别方案实验记录.md)，生产执行入口在代码实现阶段接入。

提示词按“逐对定位具体联系 → 检查两个方向 → 判断新进展、局部触发或明确提及 → 保留原文限定 → 选取最小证据 → 校验批次覆盖”执行。理由同样要求可定位于双方事实，不补充人物身份、诊断或场景。

样例覆盖明确与推测触发、共同人物负例、计划执行、新进展、明确回顾旧成果、主题重合、联系指向不足、他人陈述归属及禁止第三事件补证。真实样例必须区分用户确认答案和原文审阅预期。

构造样例与真实样例分别评估，不把构造样例通过率当作真实日记质量。等待确认的样例不计入正确率；真实负例的原文审阅预期与用户确认标签分别标记。完整预期答案只用于结果核对，不与待判断样例一起发送给模型。

固定回归同时核对状态、类型、方向、certainty、证据序号和描述忠实性，不要求描述逐字一致。真实已确认正例出现漏判时记录失败，不用总候选数量或结构通过率掩盖该失败。

## 6. 独立盲判与分歧裁决

### 6.1 判定器 A

A 按第 5 节规则批量判断全部候选事件对，输出每对的状态、理由和关系。A 的目标是完整识别关系，不承担自我复核职责。

### 6.2 验证器 B

B 使用独立请求重新判断 A 处理过的全部候选事件对。B 接收与 A 相同的冻结事件要点、事件对清单、关系定义和输出结构，不接收 A 的任何输出，也不能读取 A 的运行记录。

B 的提示词按固定问题顺序判断每个事件对：

1. 双方是否存在可由具体要点定位的联系；
2. 是否属于同一具体事项；
3. 后一事件是否产生新的行动、状态或结果；
4. 原文是否表达一方引发另一方；
5. 原文是否明确引用、回忆或比较另一具体事件；
6. 关系方向、确定性及双方最小充分证据是什么。

B 使用与 A 相同的输出 Schema。验证范围包含 `RELATED`、`NO_RELATION` 和 `UNRESOLVED`，不能只验证 A 识别出的关系。

### 6.3 一致性比较

程序按 `pair_id` 比较 A、B。满足以下条件才属于完全一致：

- `status` 相同；
- 两者均为 `NO_RELATION` 或均为 `UNRESOLVED`；或者两者均为 `RELATED`，且 `source_event_id`、`target_event_id`、`relation_type`、`certainty`、`source_point_nos`、`target_point_nos` 和去除首尾空白后的 `description` 全部相同。

完全一致时采用 A 的完整结果作为最终结果，并同时保留 B 的独立判断作为质量记录。`reason` 是过程记录，不参与一致性比较。关系数量通常远少于无关系结果，因此两份 `RELATED` 描述只要不同就进入裁决，以较小的额外调用换取可执行的语义纠错。

### 6.4 裁决器 C

下列事件对进入裁决：

- A、B 的状态不同；
- 两者均为 `RELATED`，但类型、方向、确定性、任一侧证据或描述不同。

C 每批只处理分歧事件对，接收双方完整冻结要点、A 结果和 B 结果。A、B 结果使用中性编号，不标明哪个是首次判定或验证结果，避免角色标签影响选择。C 必须重新依据原始要点判断，可以保留任一结果，也可以输出不同的新结果；证据不足时输出 `UNRESOLVED`。C 直接输出与第 5.4 节相同的最终结果结构，不输出评分或多数票。

裁决结果替换 A、B 的候选结论。C 返回无效结构时只重试对应分歧项；达到重试上限仍失败，则任务保持未完成，不能选择 A 或 B 兜底。

### 6.5 最终结果来源

每个事件对记录最终来源：

| 值 | 含义 |
| --- | --- |
| `AGREEMENT` | A、B 完全一致，直接形成最终结果 |
| `ADJUDICATED` | A、B 存在分歧，由 C 输出最终修正结果 |

最终结果仍须通过程序完整性检查。`AGREEMENT` 表示两次独立判断一致，不代表绝对正确；方案质量以冻结真实样本的召回率、准确率和分歧裁决结果衡量。

## 7. 证据定位

模型输出关系时，同时选择源、目标要点序号和关系描述。

1. **直接性**：所选要点直接表达关系需要的事实，不能只包含共同名称或主题。
2. **充分性**：只读取所选双方要点，仍能判断关系类型和描述成立。
3. **最小性**：逐个尝试移除要点，移除后关系仍完整成立的要点不予保留。
4. **一致性**：描述中的关键事实均能在所选要点中定位；每个所选要点都提供必要依据。
5. **确定性忠实**：`certainty` 和描述与证据中的关系限定一致，保留推测程度及表达者归属。

源、目标序号均为非空、无重复整数数组。程序校验序号属于对应事件，再转换为真实要点 ID；核验不通过时不保存为正式关系。

若原文支持关系而已确认要点缺失关键事实，应报告要点问题并交回修正流程。不能绕过要点证据要求，直接使用未定位原文发布关系。

## 8. 程序检查与运行记录

程序检查：

- 请求内容池内事件 ID 唯一；事件对 ID 唯一；双方事件存在且不同，属于当前用户。
- 响应顶层及结果数组合法；按 `pair_id` 检查无缺失、无重复、无额外事件对。

- 输出字段、状态及关系类型合法。
- `RELATED` 的 `certainty` 必须为 `EXPLICIT` 或 `SPECULATIVE`；其是否忠实于证据需要语义核验，不能只靠程序检查关键词。
- `RELATED` 必须具有完整关系，其他语义状态的关系为空。
- 源和目标恰为该 `pair_id` 指定的事件对，不得相同或引用其他用户的事件。
- 双方序号均存在、非空、无重复；描述非空。
- 事件对只产生一个候选关系。

程序检查不能证明自然语言证据真实支持关系，也不能纠正模型结论。语义纠错由第 6 节的独立盲判和分歧裁决完成；本节程序检查只作为执行完整性与数据合法性护栏。

每次运行保留来源事件及要点快照、候选命中记录、提示版本、模型配置标识、批次事件池与事件对清单、原始响应、逐对解析结果和错误类型。记录每个事件对所属批次、补判次数及实际 Token；认证信息不进入运行记录。

批量响应错误处理：

- 顶层 JSON 无法解析或响应截断时，整批无法确认完成，保留失败响应，并按配置重新划分批次处理。
- 可解析响应中的各项独立校验；A、B 的有效结果保存为双判记录，C 的有效结果保存为裁决记录。缺失或结构无效的对进入对应角色的待补判清单；重复 ID 对应的结果不能任选一个接受；额外 ID 的结果拒绝并留档。
- 只补判未完成的事件对，重新构造所需事件池，保留原响应与补判响应。正常情况下不重复调用已经结构有效的事件对。
- 所有计划事件对均取得 A、B 有效结果，且全部分歧事件对取得有效裁决结果后，任务才算识别阶段完成。达到重试上限仍有缺失时标记未完成，不进入后续整日发布。

这种局部保存与补判只处理执行完整性，不改变关系语义结论。

区分检索失败、向量准备失败、A/B/C 模型调用失败、输出结构失败及 `UNRESOLVED`。失败结果保留用于恢复，不将其记为无关系。每个角色的每个批次最多执行 2 次请求：首次请求失败或结构无效时允许 1 次修正重试；仍未取得有效结果时标记任务未完成。

## 9. 真实数据验证

在小规模、已确认要点的连续日记样本上完整比较范围内事件对，再结合原文人工核验，形成参照。模型完整比较的输出本身不能直接当作真值。

分别评估：

| 环节 | 检查内容 |
| --- | --- |
| 候选召回 | 已确认存在关系的事件对有多少进入候选，以及哪些被遗漏 |
| 关系识别 | 候选中的真实关系是否被识别，是否产生错误关系 |
| 关系类型与方向 | 后续、引发、提及是否正确，方向是否正确 |
| 关系确定性 | 是否保留原文明示的推测，是否错误升级为确定关系，是否纳入模型自行推断的联系 |
| 证据 | 双方依据是否直接、充分、最小，描述是否忠实 |
| 双判纠错 | A、B 一致率、分歧类型，以及 B 发现的首次漏判和误判 |
| 裁决质量 | C 是否依据原始要点修正分歧，是否引入新的关系错误 |
| 批量完整性 | 指定事件对是否逐对返回；是否遗漏、重复、增加组合或混用其他事件证据 |
| 成本 | 候选数量、批次数、补判数、重复输入量、模型调用数、Token、耗时和费用 |

样本包含：当天关系、跨日进展、较早历史引用、仅主题相似的负例、推测因果、计划尚未执行、日记日期与发生日期不同，以及关系只来自某个要点局部内容的情况。

批量方案使用相同冻结事件、要点、候选对及关系标准与逐对结果比较。候选对集合相同，才能区分调用方式变化与检索变化；旧模型输出不当作真值。验证包含固定推测性引发正例、同一事项的新进展与重复回顾区分，以及批量响应遗漏、重复、额外事件对、跨对证据引用、超限拆批和局部补判。

设计方案的每次实验必须在[独立实验记录](./第一层事件关系识别方案实验记录.md)中登记假设、冻结输入、变更项、对照组、完整结果、局限和结论。正式设计文档不混入只对某次样本成立的统计数据。

## 10. 实现边界

| 项目 | 当前结论 |
| --- | --- |
| 检索文本 | 双方要点的详细内容 |
| 语义实现 | `qwen3.7-text-embedding` 生成 1024 维向量，精确余弦检索；按历史事件聚合 |
| 历史候选数量 | 每个当前事件保留语义分数前 5 个历史事件 |
| 最低语义相似度 | 余弦相似度 0.5，可配置 |
| 当天比较 | 完整两两比较，事件对去重 |
| 判断调用 | 批量请求：批次内事件内容去重，明确指定事件对，逐对返回；超预算拆批 |
| 思考模式 | 当天关系、跨日关系及失败补判全部显式启用；不依赖服务默认值 |
| 响应完整性 | 每个 pair_id 恰有一个有效结果；缺失或无效进入补判，不记为无关系 |
| 原文明示的推测关系 | 允许识别，必填 `certainty = SPECULATIVE`，保留归属和限定 |
| 独立核验与纠错 | A、B 对全部候选独立盲判；完全一致直接接受，其他结果由 C 裁决并输出修正版 |
| 向量模型及距离度量 | `qwen3.7-text-embedding`，1024 维，余弦相似度 |
| 关系判断模型与提示词 | `deepseek-v4-pro`；A v4、B v3、C v3；全部显式开启思考模式 |
| 输入与输出预算 | 按模型上下文限制配置；批次必须完整容纳事件内容、事件对和逐对输出预留，超限时拆批，不截断要点 |
| 关系记录与判断记录的表结构 | 后续数据库设计 |
| 整日发布 | 核验通过后发布，与事件入图状态一起提交 |

## 11. 调研依据及适用范围

- [Microsoft GraphRAG 流程](https://microsoft.github.io/graphrag/index/default_dataflow/)：参考模型从文本生成结构化关系的方法。本方案按项目既定关系类型和证据规则定制。
- [pgvector 官方说明](https://github.com/pgvector/pgvector)：精确向量检索、距离度量及同维度存储。
- [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)：所测任务显示长上下文位置影响模型表现，支持控制单次上下文；不直接证明本项目事件对判断的质量。
- [Chain-of-Verification](https://arxiv.org/abs/2309.11495)：参考将验证问题独立回答，减少初始答案对验证过程的影响。
- [Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798)：无外部反馈的自我纠错可能无法改正错误，因此不采用 A 查看自身输出后直接自检。
- [Chain of Thought with Explicit Evidence Reasoning for Few-shot Relation Extraction](https://aclanthology.org/2023.findings-emnlp.153/)：参考先定位显式证据再判断关系。
- [HCRE](https://aclanthology.org/2026.findings-acl.1985/)：参考关系预测后的多视角验证结构。
- [LLM-as-the-Judge for Biomedical Relation Extraction](https://aclanthology.org/2025.acl-long.1238/)：关系抽取中的通用模型评审可靠性有限，结构化输出只能改善评审，不能替代独立证据判断。

候选发现和识别质量以项目真实数据验证为准，不能直接套用外部检索或问答任务的实验指标。
