# 每日周回顾素材重新设计

> 文档状态：已确认，待实施
> 设计目标：将一天内的中高重要事件整理成信息保真的周回顾素材，解决现有每日提炼过度概括、关键细节丢失的问题。
> 设计方法：从周回顾的信息需求反推每日素材结构。

## 1. 问题定义

一天可能包含大量日记内容，周回顾无法直接消费整周原始记录，因此需要日级中间材料。

该中间材料的核心任务是：

> 在减少无关生活细节的同时，完整保留重要事项的推进、情绪影响、行为与结果、持续关注、后续事项以及明确表达的感悟和成长。

现阶段重点解决过度概括。跨日事项的发展主线由周回顾负责识别。

## 2. 产品定位

原“每日提炼”重新定位为“每日周回顾素材”。

它是供周回顾模型使用的结构化中间数据，需要回答：

> 今天有哪些重要事项发生了实质变化；用户在其中经历了什么、采取了什么行为、得到什么结果、在意什么、学到了什么，以及哪些内容需要继续观察或处理。

每日素材采用单层完整结构。`day_overview` 和 `core_changes` 提供阅读索引，完整事项内容是周回顾的正式输入。

## 3. 设计原则

### 3.1 语义完整优先

- 每日长度随有效信息量变化。
- 事项数量随当天中高重要事件变化。
- 每个字段按独立语义保留多条内容。
- 每一条独立含义分别保留。
- 具体过程、行为、结果和变化优先于抽象概括。

### 3.2 内容边界

- 所有内容以输入事件中的明确表达为依据。
- 心理原因、因果关系、感悟和成长需要输入中的明确表述支持。
- 担忧归入 `CONCERN`，期待归入 `EXPECTATION`，计划和已执行行为分别记录。
- 没有对应内容的字段使用空数组。

### 3.3 来源可追溯

- 每个事项必须关联来源事件。
- 模型返回代码生成的简短事件序号。
- 代码把事件序号映射为真实事件 ID，并保存事项级来源关系。
- 关键表述必须逐字等于对应来源事件 `body`、`feeling` 或 `reflection` 中的一条原句，代码负责核验。
- 来源关系保留在事项层级。

### 3.4 完整事项为正式输入

- `day_overview` 用于快速了解当天重要变化。
- `core_changes` 用于快速了解单个事项的实质变化。
- 周回顾形成结论时必须读取事项的完整字段。
- 七天的完整事项共同构成周回顾输入。

## 4. 输入范围

### 4.1 事件筛选

每日素材只处理当天已经评定为以下等级的事件：

- `HIGH`：高重要度；
- `MEDIUM`：中重要度。

事件重要度由上游分析环节提前评定，每日素材直接读取评定结果。

每日素材的事件覆盖范围由上游重要度评估质量决定。

### 4.2 关联内容

输入内容均需关联到中高重要事件：

- 事件事实和过程；
- 用户明确表达的情绪和状态；
- 用户采取的行为；
- 行为产生的结果；
- 用户明确表达的关注、担忧和期待；
- 后续需要观察或处理的内容；
- 用户明确表达的感悟、成长和学习；
- 能承载关键事实、情绪或认识的原句。

### 4.3 每日素材来源

每日素材直接使用当前结构化事件中的：

- `event_title`：事件标题；
- `body`：事件事实和过程；
- `feeling`：与事件相关的感受和状态；
- `reflection`：与事件相关的反思和成长；
- 与该事件明确关联的用户评论或修正。

事件标题用于事项识别，具体事实、情绪和认识以事件正文、感受、反思及关联用户内容为准。

## 5. 标准化输入契约

业务代码先筛选事件，再用临时序号替换真实事件 ID，形成以下输入：

```json
{
  "date": "2026-08-03",
  "events": [
    {
      "event_no": 1,
      "title": "项目方案评审",
      "body": [
        "上午提交方案。",
        "评审中临时补充了两个方案的风险对比，最后团队决定采用 A 方案。"
      ],
      "feeling": [
        "评审前一直担心整个方向被否掉。",
        "方案通过后没有完全轻松，因为接口还是没人给准话。"
      ],
      "reflection": [],
      "related_user_notes": []
    }
  ]
}
```

字段约束：

| 字段 | 说明 |
|---|---|
| `date` | 当前素材所属自然日 |
| `event_no` | 代码按当天事件顺序生成的临时正整数，用于表达合并关系 |
| `title` | 原结构化事件的 `event_title` |
| `body` | 原结构化事件的事实和过程列表 |
| `feeling` | 原结构化事件的感受和状态列表 |
| `reflection` | 原结构化事件的反思和成长列表 |
| `related_user_notes` | 与该事件明确关联的用户评论或修正 |

代码在调用前保存 `event_no → event_id` 映射。模型返回参与每个事项的 `event_no`，代码再补齐真实事件 ID 和持久化来源关系。

## 6. 单次模型调用

每个有中高重要事件的自然日执行一次模型调用，同时完成：

1. 识别同一天属于同一现实事项的事件；
2. 合并同一事项的多次记录；
3. 保留过程、转折和阶段性变化；
4. 将信息分类到规定字段；
5. 提取关键原文；
6. 生成事项核心变化；
7. 生成当天概览。

## 7. 输出契约

```json
{
  "day_overview": {
    "main_changes": [
      "项目方案通过评审，进入执行准备阶段"
    ],
    "overall_state": [
      "方案取得进展，但接口安排的不确定性仍带来担忧"
    ],
    "open_loops": [
      "接口负责人和排期尚未明确"
    ]
  },
  "matters": [
    {
      "title": "项目方案评审",
      "source_event_nos": [1],
      "core_changes": [
        "方案通过，但接口排期仍未确定"
      ],
      "facts_and_progress": [
        "上午提交方案，随后完成评审"
      ],
      "emotions_and_state": [
        "评审前担心方案方向被否定",
        "方案通过后有所放松，但没有完全轻松"
      ],
      "actions_and_results": [
        {
          "action": "临时补充两个方案的风险对比",
          "result": "团队决定采用 A 方案"
        }
      ],
      "concerns_and_expectations": [
        {
          "kind": "CONCERN",
          "text": "接口负责人和排期仍不明确"
        }
      ],
      "follow_ups": [],
      "reflections_and_learning": [],
      "key_quotes": [
        "方案通过后没有完全轻松，因为接口还是没人给准话。"
      ]
    }
  ]
}
```

### 7.1 当天概览

`day_overview` 仅根据当天事项生成：

- `main_changes`：重要事项当天发生的实质变化；
- `overall_state`：由重要事项明确反映出的用户整体状态；
- `open_loops`：当天尚未闭合的重要问题或后续事项。

### 7.2 事项字段

| 字段 | 内容 |
|---|---|
| `title` | 能准确区分现实事项的简洁名称 |
| `source_event_nos` | 合并到该事项的临时事件序号 |
| `core_changes` | 该事项当天发生的实质变化 |
| `facts_and_progress` | 已发生事实、推进过程、阶段变化和当前状态 |
| `emotions_and_state` | 用户明确表达的情绪、感受和状态变化 |
| `actions_and_results` | 用户采取的具体行为及其明确结果 |
| `concerns_and_expectations` | 用户明确表达的关注、担忧或期待 |
| `follow_ups` | 明确需要继续观察或处理的内容 |
| `reflections_and_learning` | 用户明确表达的感悟、成长、认识或学习 |
| `key_quotes` | 逐字取自来源事件 `body`、`feeling` 或 `reflection` 的关键原句 |

除 `title` 和 `source_event_nos` 外，其余事项字段均允许为空数组。代码根据 `source_event_nos` 补齐真实 `source_event_ids`。

### 7.3 关注类型

`concerns_and_expectations.kind` 只允许：

- `ATTENTION`：正在持续关注；
- `CONCERN`：担忧或顾虑；
- `EXPECTATION`：期待或希望。

## 8. 同一事项合并规则

多个事件指向同一个现实对象、目标或问题时进行合并。

合并后按照来源顺序保留：

1. 初始状态；
2. 关键过程；
3. 用户采取的行为；
4. 行为产生的结果；
5. 情绪或认识的变化；
6. 当前状态；
7. 后续事项。

合并结果需要保留初始状态、失败尝试、中间转折和最终状态。不同对象或目标保持为独立事项，归属关系不明确的事件也保持独立。

## 9. 防止过度概括

模型必须保留原子化语义。

例如来源明确表达：

- 最初担心方案失败；
- 评审中通过补充材料推动决策；
- 方案通过后有所放松；
- 又因为接口排期产生新的担忧。

输出需要保留这四个阶段。以下句子缺少具体过程和转折：

> 完成方案评审，整体有压力但有所成长。

低信息表达包括：

- “情绪有所波动”；
- “事情取得进展”；
- “收获很多”；
- “得到了一些成长”；
- “仍需持续关注”。

概括性索引需要同时包含具体变化、对象和原因。

## 10. 模型系统提示词

```text
你是“每日周回顾素材整理器”。

你的任务是在完整保留原意和关键语义的前提下，把同一天的中高重要事件整理成可供周回顾使用的结构化素材。

必须遵守：

1. 内容来源为输入事件的 title、body、feeling、reflection 和 related_user_notes。
2. title 用于识别事项，具体事实、情绪和认识以其余内容为准。
3. source_event_nos 使用输入中已有的 event_no 原值。
4. 同一现实事项在当天被多次记录时可以合并，但必须保留：
   - 过程和时间顺序；
   - 中间转折和当前状态；
   - 情绪与状态的变化；
   - 用户采取的行为；
   - 行为产生的结果；
   - 关注、担忧和期待；
   - 后续事项；
   - 用户明确表达的感悟、成长和学习。
5. 每条独立含义分别输出，保留具体对象、过程、行为、结果和变化。
6. 心理原因、因果关系、感悟、成长和建议需要输入中的明确表述支持。
7. 担忧归入 CONCERN，期待归入 EXPECTATION，计划与已执行行为分别记录。
8. 事项内容覆盖前置过程、失败尝试、中间转折和最终结果。
9. 没有对应内容的数组字段返回空数组。
10. key_quotes 的每一项逐字等于该事项来源事件 body、feeling 或 reflection 中的一条完整原句。
11. 每个输入 event_no 必须且只能归入一个 matter。
12. day_overview 和 core_changes 用于快速阅读，完整事项内容用于周回顾分析。
13. day_overview 汇总本次输出中的 matters。
14. 事项数量、字段条数和总字数随有效信息量变化。
15. 输出为符合约定结构的纯 JSON。
```

## 11. 程序校验

### 11.1 结构校验

- 顶层及各级对象的字段与契约完全一致。
- 数组、字符串和枚举类型必须正确。
- 必填字段包含有效值。
- `ATTENTION`、`CONCERN`、`EXPECTATION` 等枚举必须合法。

### 11.2 来源校验

- 每个输入 `event_no` 恰好出现一次。
- 每个 `source_event_no` 属于当天输入的正整数集合。
- 代码必须能够将每个 `source_event_no` 映射回真实 `event_id`。
- 每条关键表述必须与该事项来源事件 `body`、`feeling` 或 `reflection` 中的一个数组元素完全相等。

### 11.3 失败处理

以下情况触发生成失败并丢弃本次结果：

- 存在未分配事件；
- 存在非法或重复的事件序号；
- 事件序号无法映射到真实事件；
- 关键原文被改写；
- 输出结构不符合契约。

程序校验负责保证结构、事件覆盖、序号映射和关键表述合法性。代表性样本测试和人工验收负责核对内容忠实度。

## 12. 周回顾消费约束

周回顾读取顺序可以是：

```text
day_overview
→ matters.core_changes
→ matters 的全部完整字段
→ 必要时核对 key_quotes
```

周回顾读取完整事项素材后形成结论。

周级结论必须能够沿以下路径追溯：

```text
周回顾结论
→ 每日事项
→ source_event_id
→ 结构化事件内容
```

## 13. 验收标准

### 13.1 功能验收

- 每个中高重要事件都进入且只进入一个事项。
- 同日同一事项的多次记录能够合并。
- 合并后仍保留过程、转折和最终状态。
- 情绪、行为、结果、关注、后续和感悟保持独立语义。
- 没有相关内容的字段保持为空。
- 每个事项均可定位到真实来源事件。
- 模型不接收或回传真实事件 ID，只使用临时 `event_no` 表达来源关系；真实事件 ID 由代码映射。
- 每个自然日只调用一次每日素材模型。

### 13.2 质量验收

- 每项事实和判断均有来源内容支持。
- 心理原因和成长结论均有用户明确表达支持。
- 总结包含具体对象、过程、行为、结果和变化。
- 重要过程和情绪转折完整保留。
- 关键原句与来源事件 `body`、`feeling` 或 `reflection` 中的一个数组元素完全一致。
- 当天概览与完整事项内容一致。

### 13.3 必测场景

- 一件事当天多次推进并发生转折；
- 同一天存在多个独立重要事件；
- 有情绪但没有感悟；
- 有感悟但没有后续事项；
- 行动成功、行动失败和结果未明；
- 担忧与事实同时出现；
- 期待尚未转化为计划；
- 同一段原文同时包含事实、情绪和关注；
- 多处记录表达重复语义；
- 大量细节下仍完整保留关键过程；
- 用户明确否定此前认识；
- 当天没有任何中高重要事件。

## 14. 代码调研结论

当前实现与目标设计存在五个结构性差异：

1. 冻结来源把事件标题、正文、感受和反思拼接为一个 `content` 字符串，模型无法区分原字段。
2. 每个有数据的自然日先调用每日事件提炼，再调用每日分析提炼，与单次调用目标冲突。
3. 每日结果拆分保存在 `event_document` 和 `analysis_document`，状态依赖 `EVENT_READY`、`ANALYSIS_READY` 两个恢复点。
4. 周事件组装当前读取每日事项的 `fact`，周分析当前读取旧每日分析文档；新素材需要显式接入周级链路。
5. 前端当前展示 `fact`、`open_points` 和旧分析字段；页面需要改为读取并展示完整事项素材。

因此，本次实施范围包括来源冻结、每日生成、周级消费、持久化、接口、页面和测试。

## 15. 已确认的实施边界

- 只处理 `effective_importance` 为 `HIGH` 或 `MEDIUM` 的事件。
- `effective_importance` 为 `LOW` 或空的事件不进入每日素材，每日素材阶段不重新评定重要度。
- 每个有中高重要事件的自然日只调用一次每日素材模型。
- 日程不进入每日素材模型，由周级链路独立聚合。
- 只有日程而没有中高重要事件时，仍允许生成周回顾。
- 本次采用破坏性迁移，不维护旧每日提炼契约。
- 删除全部旧每日提炼数据，但保留已经生成的周回顾、月回顾、分析、行动和版本。
- 页面统一展示新每日素材；迁移前生成的历史版本继续展示原有周回顾和月回顾主体。
- `key_quotes` 只引用传入事件 `body`、`feeling`、`reflection` 中的完整原句，不读取日记最初保存的 `original_text`。

## 16. 目标持久化结构

`review_daily_digests` 保留“一项任务、一个自然日一行”的边界，破坏性调整为：

| 字段 | 说明 |
|---|---|
| `id` | 每日素材记录 ID |
| `review_task_id` | 生成任务 |
| `review_version_id` | 提交后关联的回顾版本 |
| `source_set_id` | 冻结来源集合 |
| `digest_date` | 自然日 |
| `status` | `EMPTY`、`READY`、`FAILED` |
| `material_document` | 本文定义的完整每日素材，持久化时由代码补充内部键和来源 ID |
| `model_info` | 单次每日素材调用实际使用的模型信息 |
| `created_at`、`updated_at` | 审计时间 |

删除以下旧字段和状态：

- `event_document`；
- `analysis_document`；
- `event_model_info`；
- `analysis_model_info`；
- `EVENT_READY`；
- `ANALYSIS_READY`。

## 17. 破坏性迁移计划

新增 `029_review_daily_material.sql`，严格按以下顺序执行：

1. 部署前停止回顾任务 worker，确保迁移期间写入停止。
2. 删除 `review_daily_digests` 中的全部旧每日提炼记录。
3. 清空未完成完整生成任务的冻结来源和中间结果，使其下次执行时从 `FREEZE_SOURCES` 重新开始。
4. 将 `event_document` 重命名为 `material_document`。
5. 将 `event_model_info` 重命名为 `model_info`。
6. 删除 `analysis_document` 和 `analysis_model_info`。
7. 将状态约束改为 `EMPTY`、`READY`、`FAILED`。
8. 将模型环节配置从 `review_daily_event_digest`、`review_daily_analysis_digest` 收敛为 `review_daily_material`；新环节优先继承旧事件提炼环节的模型覆盖配置。
9. 启动新代码后再恢复回顾任务 worker。

迁移保留 `review_versions`、`reviews`、`review_actions`、`review_feedback` 和月回顾依赖。历史回顾主体保持可读，旧每日提炼明细随数据清理移除。

迁移前必须完成数据库备份。回滚单位为旧代码和迁移前数据库。

## 18. 后端实施计划

### 18.1 冻结结构化事件

修改 `backend/services/review_sources.py`：

- 冻结事件时继续保留当前用于来源查看的 `content`。
- 在事件来源 `snapshot` 中增加 `body`、`feeling`、`reflection` 和 `sort_order`。
- 所有字段在冻结时从 `DiaryEvent` 复制，生成阶段只读取冻结快照，禁止重新查询实时事件内容。
- 关联划线及评论继续作为独立冻结来源，通过 `snapshot.event_id` 关联到事件。

该调整复用现有 JSONB `snapshot`。

### 18.2 构造每日输入

在 `backend/services/review_generation.py` 中用新的每日输入构造器替换 `_daily_source_catalog`：

1. 按日期读取冻结来源。
2. 只选择事件类型的冻结来源，批注不能独立成为输入事件。
3. 筛选 `effective_importance ∈ {HIGH, MEDIUM}` 的事件。
4. 排除 `effective_importance` 为 `LOW` 或空的事件。
5. 日程不进入每日模型输入。
6. 根据 `event_id` 聚合关联用户划线、评论或修正，写入 `related_user_notes`；无法关联到输入事件的批注不进入模型输入。
7. 按冻结顺序生成从 1 开始的 `event_no`，并在代码内保存 `event_no → 冻结事件来源` 映射。

当天中高重要事件集合为空时保存 `EMPTY`，不调用每日素材模型。日程继续进入周级聚合链路。

### 18.3 单次模型调用与校验

修改 `backend/services/review_ai.py`：

- 删除旧每日事件提示词、每日分析提示词及其两个调用函数。
- 新增 `review_daily_material` 单次调用。
- 使用本文第 10 节提示词和第 7 节输出契约。
- 验证顶层及所有嵌套字段集合与契约完全一致。
- 验证每个输入 `event_no` 恰好出现一次。
- 验证 `source_event_nos` 不重复、不越界。
- 验证所有数组元素和枚举类型。
- 验证每个 `key_quotes` 值与对应来源事件 `body`、`feeling` 或 `reflection` 中的一个完整字符串完全相等。
- 结构校验失败时沿用当前全局模型重试机制；重试耗尽后记录当天及任务失败，并丢弃本次结果。

### 18.4 代码组装每日素材

模型校验通过后，由代码完成：

- 将 `source_event_nos` 映射为冻结事件来源 ID 和真实 `event_id`；
- 将与来源事件关联的批注来源 ID 一并写入事项 `source_ids`；
- 根据日期和排序后的冻结来源 ID 生成稳定 `item_key`；
- 保存 `digest_date`、`day_overview` 和完整事项字段；
- 从最终文档移除 `source_event_nos`，模型临时序号不得持久化；
- 写入单一 `model_info`；
- 将状态设置为 `READY` 并提交，作为自然日级恢复点。

任务恢复时复用结构校验通过的 `READY` 记录，不重复调用模型；`EMPTY` 不调用模型；`FAILED` 重新执行当天。

### 18.5 改造周级消费

修改 `backend/services/review_generation.py` 和 `backend/services/review_ai.py`：

- 周事件组织输入使用完整每日事项，不再读取旧 `fact` 字段。
- 事实节点由 `core_changes`、`facts_and_progress`、`actions_and_results` 中明确发生的结果共同构造。
- `emotions_and_state`、`concerns_and_expectations`、`follow_ups`、`reflections_and_learning` 和 `key_quotes` 作为每个事项的完整分析素材传入周分析。
- 每个事项独立生成一个周分析候选，不能把整天所有事项合并成一个候选。
- 周回顾仍通过每日事项 `item_key` 识别跨日主线。
- 周模型必须读取完整事项字段，`day_overview` 和 `core_changes` 只用作导航索引。

日程在代码中生成独立周级聚合项：

- 每个日程聚合由代码生成稳定 `item_key` 和全部来源 ID；
- 周事件组织统一接收“每日事项”和“日程聚合项”两种周级输入；
- 两种输入都使用代码生成的 `item_key`，模型只做主线归属；
- 日程聚合项只保存在周级输入结构中，不写入每日素材表；
- 周级输入存在任一每日事项或日程聚合项时生成周回顾，输入集合为空时标记 `SKIPPED_NO_DATA`。

### 18.6 模型配置

修改 `backend/services/model_management.py` 及相关管理端接口：

- 删除 `review_daily_event_digest` 和 `review_daily_analysis_digest` 的可见环节配置。
- 新增 `review_daily_material`，标签为“每日周回顾素材”。
- 设置用途继续使用 `review`。
- 管理端只显示新的单一每日环节。

## 21. 实施顺序与风险控制

严格按以下顺序实施：

1. 先补每日输入、模型校验和组装函数的纯单元测试。
2. 修改冻结快照并完成每日单次调用。
3. 改造周级消费，使用固定模型结果完成端到端后端测试。
4. 编写并审查破坏性迁移脚本。
5. 修改 ORM、API、模型配置和前端页面。
6. 执行后端测试、前端测试和生产构建。
7. 在测试数据库执行迁移，验证历史周/月回顾保留、旧每日提炼清空、新回顾成功生成。
8. 备份正式数据库、停止 worker、执行迁移、部署代码、恢复 worker。
9. 使用包含多事件和长内容的一周数据进行人工验收。

核心风险及控制措施：

| 风险 | 等级 | 控制措施 |
|---|---|---|
| 周分析遗漏新每日字段 | 高 | 周级输入集成测试直接断言完整字段 |
| 破坏性迁移需要数据库级回滚 | 高 | 部署前数据库备份，代码与数据库同步回滚 |
| 生成阶段读取实时事件造成版本漂移 | 高 | 全部结构化字段写入冻结 `snapshot`，生成阶段读取快照 |
| 模型事件覆盖异常 | 中 | `event_no` 全覆盖校验，失败时整次重试 |
| 长日记导致输出截断 | 中 | 完整 JSON 通过校验后写入；重试耗尽后记录明确失败状态 |
| 日程周级聚合接入异常 | 中 | 日程使用独立周级聚合项，并覆盖日程单独存在场景 |
| 关键原句被模型改写 | 低 | 与来源事件数组元素执行完全相等校验 |
| 管理端模型环节配置迁移遗漏 | 低 | 迁移模型环节配置并更新管理端列表测试 |
