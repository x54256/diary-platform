# 定期回顾分层提炼改造设计

> 文档状态：目标设计，尚未实现  
> 设计基线：2026-08-01《定期回顾需求规格》  
> 相关文档：[需求规格](../../需求规格/规划功能/定期回顾需求规格.md)、[现行系统设计](定期回顾系统设计.md)、[现行 AI 设计](定期回顾AI流水线与提示词设计.md)

## 1. 目标与边界

本改造把周回顾从“整周原始日记直接输入模型”改为“按自然日提炼，再做周级综合”。目标是减少周级模型上下文、避免网关超时，并保持每条结论可追溯到原始事件、划线、评论和日程。

不做日度回顾，不增加用户编辑每日提炼的入口，也不以固定事项数截断当天中高重要事件。每天多篇日记共同形成一份每日提炼；跨日关系只在周级识别。

### 1.1 模型与代码职责边界

模型只处理必须依赖语义理解的工作：事件重要性判断、同一事项归并、领域归类、事实压缩、跨日主线归并、分析判断和行动文本。代码负责所有可由规则确定的工作：输入日期、稳定 ID、数组与对象骨架、来源合法性、去重、枚举和状态校验、空项补齐、既有行动核查清单及持久化。

模型输出是最小语义结果，不直接作为 `event_document` 或 `analysis_document` 落库。代码在校验通过后将其映射为稳定的持久化文档；模型不得生成 `item_key`、`thread_key`、`node_key`、`focus_key`、`analysis_key`、`action_key` 等确定性标识。后续环节可以回传代码预置的 ID 以声明归属或引用，代码拒绝任何未知 ID。

## 2. 总体流程

```text
周期到期
  → 自动创建 PENDING_START 回顾任务
  → 用户点击“开始生成”
  → 冻结本周期原始来源
  → LangGraph 按 checkpoint 编排并恢复未完成节点
  → 每个自然日：每日事件层 → 每日分析层
  → 程序聚合本周日程
  → 周事件组织：形成 3–7 条主线及其他事项
  → 周分析与行动
  → 原子保存周版本及 7 份每日提炼
```

当某日没有可用的中高重要事件、划线或相关日程时，创建 `EMPTY` 每日提炼记录但不调用模型。这样周版本始终有 7 个日期槽位，且不会把“没有输入”解释为“当天没有发生事情”。

## 3. 任务与启动机制

### 3.1 状态机

```text
PENDING_START --用户启动--> QUEUED → RUNNING → SUCCEEDED
                                         ↘ FAILED
                                         ↘ SKIPPED_NO_DATA
```

- 定时器和历史周期补建只创建 `PENDING_START`，不得读取来源、校验模型配置、冻结数据或唤醒 worker。
- `POST /api/review-tasks/{id}/start` 由当前用户启动任务。接口校验模型配置、周期已到期、任务所属用户和下级依赖后，将任务原子地改为 `QUEUED` 并唤醒 worker。
- 完整重新生成和“更新分析与行动”由用户主动发起，可直接创建 `QUEUED`，因为该操作本身就是一次明确启动。
- 周/月/季/年首次任务的自动创建来源为 `AUTO`；用户补建历史任务来源为 `MANUAL`。两者都必须经过显式启动。

### 3.2 上级依赖

启动月、季、年任务前，系统必须检查本周期内全部必需下级周期：

- `SUCCEEDED` 与 `SKIPPED_NO_DATA` 视为已完成；
- `PENDING_START`、`QUEUED`、`RUNNING`、`FAILED` 或不存在，均阻止启动；
- 响应返回阻塞的周期、类型和任务状态，页面引导用户先完成下级任务；
- 不再生成带 `missing_periods` 的不完整上级回顾。

## 4. 数据模型

### 4.1 事件重要性

在 `diary_events` 增加以下字段，保留 AI 初判与用户调整的完整边界：

| 字段 | 含义 |
|---|---|
| `ai_importance` | `HIGH/MEDIUM/LOW`，日记分析生成的初始等级 |
| `ai_importance_reason` | AI 初判的一句依据 |
| `user_importance` | 用户覆盖等级，可空 |
| `user_importance_reason` | 用户可选调整原因 |
| `importance_updated_at` | 最近调整时间 |
| `importance_origin` | `DIARY_ANALYSIS/LEGACY_BACKFILL`，初始等级的产生方式 |

有效等级为 `COALESCE(user_importance, ai_importance)`。重要性只表示该事件对用户目标、情绪、行为、关系、认知、价值取舍或后续约束的实际影响，不从分析评分、事件篇幅、情绪强度或日程完成率推导。

存量事件以 `ai_importance IS NULL` 表示尚未评估。它们不默认降级为低或中重要性：首次参与周回顾时，所属日期的每日事件提炼调用先对该日全部未评估事件补判等级和依据，写入 `ai_importance`、`ai_importance_reason` 与 `importance_origin=LEGACY_BACKFILL`，再生成当天事项卡。该调用已存在于每日事件提炼流程，不新增模型请求或 `step_key`；未参与回顾的历史日记不做全库批量回填。来源更新检测忽略本次生成期间新增的 `LEGACY_BACKFILL`，但仍检测后续用户重要性修改和日记分析重新评估。

### 4.2 每日提炼

新增 `review_daily_digests`，一行对应一个任务中的一个自然日：

| 字段 | 含义 |
|---|---|
| `id` | UUID |
| `review_task_id` | 生成该提炼的任务 |
| `review_version_id` | 最终版本，生成中可空 |
| `source_set_id` | 该任务冻结的来源集合 |
| `digest_date` | 自然日 |
| `status` | `EMPTY/EVENT_READY/ANALYSIS_READY/FAILED` |
| `event_document` | 同日事项卡 JSONB |
| `analysis_document` | 同日分析卡 JSONB |
| `event_model_info` / `analysis_model_info` | 每日两步实际模型快照 |
| `created_at` / `updated_at` | 审计时间 |

唯一约束为 `(review_task_id, digest_date)`。`digest_date` 由任务循环写入；两个 document 均由代码将已校验的模型最小语义输出组装而成。任务恢复时复用已通过校验的 `ANALYSIS_READY` 提炼，只重跑失败或未完成的日期。周版本提交时，在同一事务把 7 条记录绑定到 `review_version_id`。

### 4.3 回顾任务扩展

- `ReviewTaskStatus` 增加 `PENDING_START`。
- `ReviewTaskStep` 改为 `FREEZE_SOURCES`、`DAILY_EVENT_DIGEST`、`DAILY_ANALYSIS_DIGEST`、`SCHEDULE_AGGREGATE`、`WEEK_EVENT_ORGANIZE`、`WEEK_ANALYSIS_ACTION`、`PERSIST_VERSION`。
- `review_tasks` 增加 `started_by_user_id`、`requested_start_at`；`started_at` 保留给 worker 实际开始执行时间。
- `event_result`、`analysis_result` 保留周级中间结果；每日中间结果只写 `review_daily_digests`，避免把 7 天 JSON 塞回任务单行。

## 5. 冻结来源与可追溯性

用户点击启动时，沿用 `ReviewSourceSet` 冻结原始来源。周任务冻结：当前结构化事件、有效事件重要性、当前有效分析与反馈、有效划线评论、日程、上一周已确认行动及必要的上一周主线状态。

划线评论的现有定位可直接复用：

- `EVENT_BODY/EVENT_FEELING/EVENT_REFLECTION` 划线已有 `event_id`、字段、精确范围、选中文本和上下文，直接归入该事件；
- `ANALYSIS_ITEM` 划线通过 `AnalysisItem.event_id` 归入事件级分析；日记级分析项没有 `event_id`，只作为该日分析层证据，不强行分配给某事件；
- 评论表达用户感想、认识、疑问或态度，只在分析层使用；不作为新增客观事实。

每日和周级模型均不得读取未冻结的数据库内容。每日事项卡、每日分析卡和周主线都保存直接证据 ID；页面沿“周主线 → 每日事项卡 → 原始事件/划线/评论/日程”展开。

## 6. 每日提炼契约

### 6.1 每日事件层

输入为当天所有有效中高重要事件、划线关联片段、必要日程事实，以及事件的有效等级与用户调整信息。若当天存在存量未评估事件，则本次调用额外接收这些事件，仅用于先完成历史重要性补判。同日多篇日记中的同一项目、人物关系、问题或目标合并为一个事项卡；只有当天的新进展被写入卡片。

模型只返回以下最小语义结果：

```json
{
  "importance_updates": [
    {"source_id": "...", "importance": "HIGH|MEDIUM|LOW", "reason": "..."}
  ],
  "matters": [
    {
      "title": "项目方案完成评审",
      "fact": "当天完成方案评审，决定采用 A 方案。",
      "current_status": "已进入执行准备",
      "open_points": ["等待接口排期确认"],
      "source_ids": ["..."]
    }
  ]
}
```

代码检查每个 `source_id` 均属于当日冻结来源、按规范化来源集合生成稳定 `item_key`，并根据来源类型拆分 `event_source_ids`、`annotation_source_ids`、`schedule_source_ids`。事件层只陈述冻结事实、用户明确自述和日程记录；不得写 AI 新推断的心理原因、人格结论或因果关系。

### 6.2 每日分析层

输入为代码组装的每日事件层、关联事件分析、评分状态、文字反馈、划线和评论。代码在输入中提供稳定 `item_key`；模型输出按该 key 对应的最小语义分析：

```json
{
  "matter_analyses": [
    {
      "item_key": "day-1",
      "user_attention": ["用户划线关注了决策取舍"],
      "preferred_explanations": ["..."],
      "prohibited_explanations": ["..."],
      "feedback_constraints": ["..."],
      "insufficient_evidence": ["..."],
      "evidence_ids": ["..."]
    }
  ]
}
```

代码补齐没有模型输出的事项为空分析、校验 `item_key` 与证据均来自输入事项，之后生成 `analysis_document`。评分预处理沿用现有规则：高分为可优先参考的候选解释，低分原结论不可复用，文字反馈优先于星级，继承未确认反馈不作为当前认可。每日分析层不拼接原分析全文，也不把用户评论写成客观事实。

## 7. 周级综合

### 7.1 日程聚合

程序按日程名称、日期、对象、动作、执行备注及已确认的事件关联生成主题聚合。输出只包含计划次数、已标记完成次数、日期和明确备注/异常。未完成只能表述为“截至生成时未标记完成”。

### 7.2 周事件组织

输入是 7 份每日事件层、每日分析层的必要引用、日程聚合、上一周已确认行动和必要的上一周主线状态。模型只输出每个每日 `item_key` 的主线归属、主线标题、领域、事实叙述、语义变化类型与必要关系，以及未入选事项。代码基于归属生成全局唯一的 `thread_key`、`node_key`、`focus_key`，按来源日期建立节点，合并同领域内容并校验来源与关系。

周级输入中的每日事项是派生事实，必须携带原始 `event_source_ids`、`annotation_source_ids` 与 `schedule_source_ids`。周模型只能基于事项卡内容形成主线；需要引用证据时引用事项卡的原始来源 ID。程序以原始 `root_fact_id` 去重，防止同一事件因每日卡、日程或既有分析重复计数。

“其他事项”承载没有进入主线的中重要事项及划线重点，只保存简短事实与来源定位，不丢弃内容。

### 7.3 周分析与行动

周分析只读取代码组装的已形成主线、每条主线的直接证据摘要、关联的每日分析卡和上周行动核查证据。它不得回读整周原始事件、逐篇分析或逐条日程。代码预置可引用的主线 ID、节点 ID、既有分析 ID、反馈 ID 和上一周期行动 ID；模型仅返回分析判断、行动文本、语义分类及这些既有 ID 的引用。代码生成 `analysis_key`、`action_key`，补齐每个上一周期行动的核查槽位，并执行证据与枚举校验。

## 8. 调用与失败恢复

完整周生成由 LangGraph 编排为“冻结来源 → 事件组织 → 周分析行动 → 持久化版本”阶段。事件组织阶段内，每个非空日期的“每日事件层 + 每日分析层”按日期串行执行；`ReviewDailyDigest` 的业务状态是日级幂等恢复依据。一个日期失败只重试该日期，成功日期不重跑。

调用顺序：

```text
冻结来源
  → 日 1 事件 → 日 1 分析
  → …
  → 日 7 事件 → 日 7 分析
  → 日程聚合
  → 周事件组织
  → 周分析行动
  → 原子提交
```

LangGraph 的 PostgreSQL checkpoint 只保存阶段执行位置与临时状态；`ReviewTask`、`ReviewSourceSet`、`ReviewDailyDigest`、`ReviewVersion` 才是业务事实来源。每个阶段先检查业务表：已完成且校验通过的产物直接复用；事件组织阶段再逐日检查 `ReviewDailyDigest`，仅处理未完成自然日。每日事件层和每日分析层分别原子落库，分析失败不得回滚已完成事件层。模型输出经代码映射并在同一业务步骤原子落库后才写入 checkpoint 成功状态。进程重启、租约过期或用户点击重试时，均将原任务重新入队并从最近一个未完成阶段恢复，不重复调用已成功日期或阶段。每日提炼使用独立最小输出契约；周级提示词从输入契约中移除“读取全量原始日记”的描述。模型或网关失败按全局 `LLM_MAX_ATTEMPTS` 重试当前步骤，使用相同冻结输入；不携带校验错误进行定向修复，重试耗尽后任务为 `FAILED`。

## 9. 接口与页面改造

- 新增 `POST /api/review-tasks/{task_id}/start`。
- `GET /api/review-tasks` 返回 `PENDING_START`，并提供可启动性、阻塞下级任务列表和“开始生成”权限。
- 自动创建的任务中心卡片显示“待启动”；没有完成下级依赖时禁用开始按钮并列出阻塞项。
- 周回顾详情展示“每日提炼”层级：每日事件文档按 `event_document.items` 显示本日事项，分析文档按 `analysis_document.items` 显示对应提示，不能按周级 `domains/event_threads` 结构读取；两者均只读并提供原始来源入口。
- 日记事件详情增加重要性等级、AI 依据、用户调整与可选原因的展示/修改入口；相关移动端控件字号保持至少 `16px`。

## 10. 实施顺序与验收

1. 数据迁移：事件重要性、`PENDING_START`、任务启动审计、每日提炼表。
2. 改造到期扫描与任务中心，确保自动创建不触发 worker。
3. 改造周来源冻结，纳入有效重要性、划线和评论。
4. 实现每日与周级的最小模型输出契约、代码映射器和稳定 ID 生成器。
5. 以 LangGraph 编排回顾任务，并以业务表状态实现节点幂等恢复。
6. 用每日提炼与日程聚合替换周级原始来源输入，更新周级验证规则。
7. 实现上级启动依赖阻塞及来源抽屉。
8. 完成迁移、任务状态、来源追溯、划线评论、评分反馈、无数据日期、失败恢复、模型不生成确定性结构以及 iOS Safari 表单交互测试。

验收时必须证明：自动到期只产生待启动任务；用户启动前没有模型调用或来源冻结；同日多篇日记只产生一份每日提炼；周级模型请求不含整周原始日记；模型不生成确定性 ID、日期或持久化结构骨架；任一周主线可定位到每日卡和原始来源；进程重启后复用已完成每日产物并从未完成节点恢复；下级未完成时上级无法启动。

## 11. 管理端模型配置

复用现有 `model_settings.setting_key=review` 作为回顾用途默认模型，并在 `model_step_settings` 增加以下可覆盖环节。每项均可独立选择渠道模型和思考开关；未覆盖时继承 `review` 默认配置。

| `step_key` | 管理端名称 | 调用位置 |
|---|---|---|
| `review_daily_event_digest` | 每日事件提炼 | 每个有输入的自然日 |
| `review_daily_analysis_digest` | 每日分析提炼 | 每个已生成事件层的自然日 |
| `review_event_organize` | 周回顾事件组织 | 7 份每日提炼与日程聚合后 |
| `review_analysis_action` | 周回顾分析与行动 | 周主线形成后 |

日记分析中的事件重要性仍使用既有日记分析环节配置，不新增回顾模型配置。

实现必须同步扩展后端的 `STEP_SETTING_KEYS`、`STEP_LABELS`、运行时 `resolve_model_setting` 校验、模型配置种子和管理端环节列表；模型测试接口必须允许以上 `step_key`。每次调用把实际解析出的模型、思考状态、`step_key` 和用量写入任务或每日提炼快照，供失败诊断和版本追溯。
