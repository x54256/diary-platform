# 定期回顾系统设计

> 文档状态：现行设计；第一阶段周/月已实现，季/年暂未启用。分层每日提炼与手动启动任务的目标改造见《定期回顾分层提炼改造设计》。
> 设计基线：2026-08-01 代码与《定期回顾需求规格》  
> 对应需求：[定期回顾需求规格](../../需求规格/规划功能/定期回顾需求规格.md)  
> AI 设计：[定期回顾 AI 流水线与提示词设计](定期回顾AI流水线与提示词设计.md)  
> 页面设计：[定期回顾页面与交互设计](定期回顾页面与交互设计.md)
> 目标改造：[定期回顾分层提炼改造设计](定期回顾分层提炼改造设计.md)

## 1. 设计结论

第一阶段实现周回顾和月回顾，数据结构同时为季度、年度回顾保留统一周期枚举。系统采用以下方案：

- 回顾正文使用 JSONB 保存，来源、依赖、反馈和行动使用关系表保存。
- 生成由持久化数据库任务驱动，进程内 worker 只负责领取和执行任务，应用重启后可以继续处理。
- AI 流水线只有“事件组织”和“分析与行动”两个生成环节，不设计独立 AI 校验环节。
- 提示词固定在代码中；周、月、季、年共用核心提示词，并叠加周期规则片段。
- 回顾使用独立的 `review` 模型用途，不复用日记整理或日记分析用途。
- 历史周期只允许用户手动发起生成，不自动补全。
- 每次生成、重新生成和事件层编辑都产生新版本，旧版本、来源、反馈、行动和对话不被覆盖。

## 2. 职责边界

### 2.1 模块职责

```text
回顾定时器
  → 创建幂等生成任务
  → 来源收集与冻结
  → 事件组织 AI
  → 分析与行动 AI
  → 确定性结构检查
  → 原子提交回顾版本
  → 应用内未读标记
```

推荐后端目录：

```text
backend/
├── models/review.py
├── schemas/review.py
├── routers/reviews.py
└── services/review/
    ├── scheduler.py
    ├── task_manager.py
    ├── period.py
    ├── source_builder.py
    ├── pipeline.py
    ├── prompts.py
    └── document.py
```

各模块只承担一项主要职责：

| 模块 | 职责 |
|---|---|
| `scheduler` | 计算已到期周期并幂等创建自动任务 |
| `task_manager` | 领取、恢复、重试和结束持久化任务 |
| `period` | 计算自然周期边界、上下级周期和上一同级周期 |
| `source_builder` | 按周期读取、规范化、冻结输入及来源链 |
| `pipeline` | 顺序执行两个 AI 环节并保存中间结果 |
| `prompts` | 保存固定提示词、周期片段和输出 Schema |
| `document` | 组装版本文档、派生摘要和分析过期状态 |

### 2.2 程序与 AI 的边界

程序负责可以确定计算的内容：

- 用户权限、自然周期边界和来源日期归属。
- 来源快照、底层事实去重和跨层级来源链。
- 当前评分是否有效及其使用级别。
- 不同日期、自然周、月份和季度的数量统计。
- JSON 解析、Schema、枚举、引用存在性和唯一性检查。
- 任务幂等、失败重试、版本号和事务提交。

AI 负责需要语义判断的内容：

- 重点事件筛选、六领域归属和跨日发展串联。
- 第一人称事实叙事。
- 七个角度的证据化分析、正面与建设性反馈。
- 上一同级行动的落实证据判断和下一周期候选行动。

确定性结构检查不是第三个 AI 环节，不评价内容质量、不改写回顾。检查失败时当前 AI 环节整体失败并按任务重试策略重试。

## 3. 周期生成

### 3.1 周期枚举

```text
WEEK
MONTH
QUARTER
YEAR
```

系统统一使用 `Asia/Shanghai` 计算周期：

- 周：周一至周日。
- 月：自然月。
- 季：1—3、4—6、7—9、10—12 月。
- 年：自然年。

数据库保存闭区间的 `period_start`、`period_end` 日期，不保存由服务器本地时区推导的模糊时间范围。

### 3.2 自动任务

定时器以分钟级轮询即可，不要求在 02:00 精确触发。每次轮询寻找“已经满足依赖且尚无任务”的周期：

1. 周回顾在周期结束后的周一 02:00 后可创建。
2. 月回顾等待包含月末日期的自然周结束，且该周任务已进入 `SUCCEEDED/FAILED/SKIPPED_NO_DATA` 任一终态。
3. 季度回顾等待最后一个月回顾生成尝试结束。
4. 年度回顾等待第四季度回顾生成尝试结束。

第一阶段定时器只启用周、月。功能启用前已经结束的历史周期不自动补任务；用户可在回顾任务中心选择周期手动生成。

同一用户、类型、起止日期只能有一个运行中任务。数据库唯一约束或领取事务必须保证多进程不会重复执行。

### 3.3 缺失依赖

上级周期等待下级周期的首次生成尝试结束，而不是等待其最终成功。下级失败或缺失时：

- 在依赖表记录缺失周期和状态。
- 使用其余有效下级版本继续生成。
- 在版本文档中保存 `missing_periods`，供页面披露。
- 不把缺失解释为对应周期没有事件或没有行动。

## 4. 生成流程

### 4.1 任务状态

```text
QUEUED → RUNNING → SUCCEEDED
                 ↘ FAILED
                 ↘ SKIPPED_NO_DATA
```

`current_step` 使用：

```text
FREEZE_SOURCES
LOAD_BASE_EVENT
EVENT_ORGANIZE
ANALYSIS_ACTION
PERSIST_VERSION
```

不设置 `VALIDATION` 步骤。

worker 领取任务时用数据库行锁更新 `RUNNING`、`started_at`、`lease_until` 和新的 `run_token`，模型调用期间持续心跳续租。每次保存中间结果、推进步骤和提交版本都必须以 `task_id + run_token + status=RUNNING` 为条件更新；租约失效的旧 worker 立即失去写权限。进程异常退出后，超过租约的任务回到 `QUEUED`；新 `run_token` 复用同一任务已通过校验的 `event_result`、`analysis_result` 和每日提炼，并从最近未完成步骤恢复。

模式与步骤、计数必须一致：`FULL` 在来源冻结后从 `EVENT_ORGANIZE` 开始；`ANALYSIS_ONLY` 在来源集合可用后始终从 `LOAD_BASE_EVENT` 开始。`ANALYSIS_ONLY.event_attempts` 必须保持 `0`，失败恢复和用户重试也不能把它推进到事件组织环节。

### 4.2 来源冻结

创建任务后、第一次调用模型前完成来源冻结。程序在一个数据库事务内创建完整来源集合及其成员，并同时设置 `source_snapshot_ready=true`；事务中断时整批回滚，恢复任务不得复用半套来源：

- 周回顾冻结本周结构化日记、当前分析轮次及反馈、当前可见日程、上一周最终有效版本和上一周已确认行动。
- 月回顾冻结涉及本月的周回顾最终有效版本和上一月最终有效版本。
- 季、年按相同规则冻结直接下级回顾和上一同级版本。
- 完整重新生成重新读取最新来源并创建新的来源集合。
- 仅更新分析和行动时，复用事件编辑版本的来源集合及事件文档，不读取最新日记或重新组织事件。
- 重试同一任务继续使用原冻结来源和原任务模式。

冻结后为每条原子证据生成 `source_id`，并保留 `root_fact_id`、底层事实日期和完整来源链。下级分析或主线依据多个底层事实时，拆成多条原子来源并用同一个 `origin_content_item_id` 关联，不能把多个底层事实塞进一个 `root_fact_id`。AI 不直接读取数据库实体，也不能自行决定一条来源是否属于本期。

### 4.3 两种任务模式

`generation_mode=FULL` 用于自动生成、首次手动生成和根据最新来源完整重新生成：

1. 冻结最新来源。
2. 逐日执行每日事件与每日分析提炼，再由 `review_week_event_organize_from_digests` 输出非空领域中的发展主线；独立重点事件表示为单节点主线。
3. 程序检查事件结构、枚举和来源引用，并分配版本内稳定 ID。
4. 程序按每条发展主线实际引用的原子来源计算日期、有效子周期数量和趋势资格。
5. `review_analysis_action` 输出跨主线信号候选、分析项、行动核查和候选行动。
6. 程序检查信号与其余确定性约束；未覆盖两个日期的 signal 记录警告但不废弃结果，保存完整新版本。

`generation_mode=ANALYSIS_ONLY` 只用于事件编辑版本的“更新分析和行动”：

1. 校验 `base_version_id` 指向 `analysis_stale=true` 的事件编辑版本。
2. 原样复制该版本 `event_document`、来源集合和依赖，不调用 `review_event_organize`。
3. 根据事件文档重新计算主线指标。
4. 只调用 `review_analysis_action`，重新生成分析、行动核查和候选行动。
5. 保存新版本并设置 `analysis_stale=false`；事件文档及用户修正来源不得被模型改写。

基准事件编辑版本中的 `narrative_correction_source_id` 必须指向同一来源集合内、`source_type=USER_FACT_CORRECTION`、`fact_kind=USER_CORRECTION` 且 `period_role=CURRENT` 的来源。缺少或不满足该约束时任务失败，不允许退回旧节点继续生成。

任一 AI 环节失败都不创建完成版本。任务保存安全错误码，页面只展示可操作的失败说明，不返回原始提示词、完整输入或模型密钥。

### 4.4 重试

第一版采用简单策略：

- 模型超时、限流、临时网络、JSON 解析或 Schema 失败均按全局 `LLM_MAX_ATTEMPTS` 重试当前环节；默认值为 1。
- 每次重试使用相同的完整冻结输入；不附带结构错误摘要，也不增加专用修复调用。
- 权限和配置缺失等确定性错误不自动重试。
- 来源为空时使用 `SKIPPED_NO_DATA`，不产生版本、不显示失败卡片；上级周期把它识别为“该下级周期没有有效输入”，不能与模型失败混同。
- 自动重试耗尽后标记 `FAILED`，用户可手动重试该任务。

## 5. 数据模型

### 5.1 `reviews`

一条记录表示某用户的一个固定周期。

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `user_id` | 所属用户 |
| `review_type` | `WEEK/MONTH/QUARTER/YEAR` |
| `period_start` / `period_end` | 自然周期日期 |
| `current_version_id` | 当前有效版本，可空 |
| `is_unread` | 自动生成成功后的应用内新标记 |
| `created_at` / `updated_at` | 审计时间 |

唯一约束：`(user_id, review_type, period_start, period_end)`。

### 5.2 `review_versions`

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `review_id` / `user_id` | 所属回顾和用户边界 |
| `version_no` | 回顾内递增版本号 |
| `version_type` | `GENERATED/REGENERATED/EVENT_EDITED/ANALYSIS_UPDATED` |
| `base_version_id` | 重新生成或编辑所基于的版本 |
| `source_set_id` | 本版本使用的不可变来源集合 |
| `event_document` | JSONB，事件层及发展节点 |
| `analysis_document` | JSONB，按领域组织的分析项 |
| `summary` | 列表摘要 |
| `analysis_stale` | 事件编辑后分析是否可能过期 |
| `superseded_at_creation` | 完成时基准版本已变化，未成为当前版本 |
| `missing_periods` | JSONB，缺失下级周期 |
| `event_model_info` / `analysis_model_info` | JSONB，实际模型和思考配置快照 |
| `created_at` | 版本生成时间 |

唯一约束：`(review_id, version_no)`。模型结果通过检查后，程序为每个分析项分配 UUID，并同步改写行动中的分析引用，再写入 JSONB。`summary` 不调用额外模型：按领域顺序取前三个 `core_focus.label`，不足时取主线标题，使用“、”连接并截断为 120 个字符。JSONB 只保存适合整体读取的文档，不承担跨版本来源查询和用户操作状态。

### 5.3 `review_tasks`

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `review_id` / `user_id` | 任务边界 |
| `trigger_type` | `AUTO/MANUAL/REGENERATE/RETRY` |
| `generation_mode` | `FULL/ANALYSIS_ONLY` |
| `base_version_id` | 重新生成依据版本 |
| `retry_of_task_id` | 兼容保留字段；当前重试复用原任务，不创建新任务 |
| `source_set_id` | 已冻结的来源集合 |
| `status` / `current_step` | 任务状态和当前步骤 |
| `freeze_attempts` / `event_attempts` / `analysis_attempts` | 分环节重试次数 |
| `available_at` | 下次可领取时间 |
| `lease_until` / `run_token` | 崩溃恢复租约与写入隔离令牌 |
| `source_snapshot_ready` | 来源是否已冻结 |
| `event_result` / `analysis_result` | JSONB，已校验的阶段中间结果与最终落库依据；同一任务重试和租约恢复时复用 |
| `error_code` / `error_message` | 脱敏失败信息 |
| `started_at` / `completed_at` | 执行时间 |
| `result_version_id` | 成功生成的版本，可空 |

运行中任务唯一性通过部分唯一索引或领取事务保证：同一回顾只允许一条 `QUEUED/RUNNING` 任务。中间结果与 `current_step` 必须在同一事务更新，避免状态已前进但结果未落库。

### 5.4 `review_source_sets` 与 `review_source_set_items`

`review_source_sets` 表示一次完整、不可变的来源冻结结果：

| 字段 | 说明 |
|---|---|
| `id` / `user_id` | 来源集合与用户 |
| `status` | `BUILDING/READY/ABANDONED` |
| `input_snapshot` | JSONB；冻结既有分析及反馈、上一期确认行动、下级行动、依赖和缺失周期等非原子输入 |
| `created_at` | 冻结时间 |

`review_source_set_items` 使用 `(source_set_id, source_id)` 关联来源集合与原子来源。任务和版本分别引用 `source_set_id`，来源本身不绑定任务或版本。事件编辑创建新的来源集合，复用原有来源关联并追加用户事实修正来源，因此不需要更换旧 `source_id` 或改写未变节点。

来源集合及成员必须在一个事务内从 `BUILDING` 变为 `READY`；事务中断整批回滚或标记 `ABANDONED`，不能把两次数据库读取混入同一集合。

### 5.5 `review_sources`

每行是一条不可变的原子冻结证据，不是原业务表的动态引用。

| 字段 | 说明 |
|---|---|
| `id` | `source_id`，供两个 AI 环节引用 |
| `user_id` | 所属用户 |
| `root_fact_id` | 最底层事实标识，用于跨层级去重 |
| `source_type` | `DIARY_EVENT/SCHEDULE_OCCURRENCE/LOWER_REVIEW_EVENT/LOWER_REVIEW_ANALYSIS/PRIOR_REVIEW_EVENT/USER_FACT_CORRECTION` |
| `root_source_type` | 底层真实类型，供跨层级行动核查 |
| `fact_kind` | `USER_FACT/USER_SELF_REPORT/SCHEDULE_RECORD/AI_ANALYSIS/USER_CORRECTION/REVIEW_DERIVED` |
| `source_date` | 最底层事实日期 |
| `period_role` / `relative_position` | `CURRENT`，或 `CONTEXT_ONLY + BEFORE/AFTER`；任务审计可另存 `OUT_OF_PERIOD` |
| `origin_review_id` / `origin_review_version_id` | 直接来自哪个下级回顾 |
| `origin_content_item_type/id/key` | 下级主线、分析项或行动项定位；`key` 保留原 `thread_key` 等模型键 |
| `lineage` | JSONB；每级保存 `review_id/review_version_id/content_item_id/source_id` |
| `content` | 本次生成使用的冻结摘录 |
| `snapshot` | JSONB，来源生成时必要字段 |

一条来源只能对应一个 `root_fact_id` 和一个 `source_date`。下级分析、主线或行动依据多个事实时，按底层事实拆成多条来源，并共享 `origin_content_item_id`。同一来源集合按 `root_fact_id + source_type + fact_kind + origin_content_item_id` 去重；来自不同下级回顾但指向同一底层事实的内容不得被计算成多份证据。

日期语义固定为：日记事件取 `Diary.diary_date`，只代表记录归属日期；日程取 `scheduled_date`；用户事实修正沿用被修正节点的归属日期并另存编辑时间。任何一类都不能把下级回顾生成日期或用户编辑日期当成底层事实日期。

### 5.6 `review_version_dependencies`

记录版本依赖的下级版本和上一同级版本：

| 字段 | 说明 |
|---|---|
| `version_id` | 当前版本 |
| `dependency_type` | `LOWER_PERIOD/PRIOR_SAME_LEVEL` |
| `dependency_review_id` / `dependency_version_id` | 依赖回顾与冻结版本，可空 |
| `period_start` / `period_end` | 依赖周期 |
| `status` | `AVAILABLE/MISSING/FAILED/SKIPPED_NO_DATA` |
| `context_only` | 是否只能作为连续性背景 |

下级生成新版本时只根据依赖表判断当前上级版本“来源已有新版本”，不自动重生成上级。

### 5.7 `review_feedback`

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `version_id` / `user_id` | 所属版本和用户 |
| `analysis_item_id` | 版本内稳定分析项 ID |
| `angle_code` | 七个固定分析角度之一 |
| `rating` | 1—5，可空 |
| `comment` | 文字反馈，可空 |
| `is_inherited` / `source_feedback_id` | 是否从旧版本带入及来源 |
| `created_at` / `updated_at` | 审计时间 |

程序接收模型字符串 `analysis_key` 后分配 UUID 并写回 `analysis_document.analysis_item_id`；写入反馈前必须验证该 UUID 实际存在于指定版本。唯一约束为 `(version_id, analysis_item_id)`，并检查 `rating` 与 `comment` 至少一个非空。

重生成时，只有新分析项明确输出 `source_analysis_item_id` 且该旧项属于基准版本，才把旧反馈复制为 `is_inherited=true`；无法确定映射的旧反馈只作为生成约束保存，不能挂到任意新项或冒充用户对新内容的确认。

事件编辑版本沿用旧分析文档时，按分析项一一复制反馈并标记 `is_inherited=true`，`source_feedback_id` 指向原反馈；页面要求用户重新确认。`ANALYSIS_UPDATED` 版本仍只对模型明确映射的分析项继承反馈，并保持继承状态；用户在新版本重新评分或填写反馈后，当前版本记录改为 `is_inherited=false`，不能沿用旧版本的确认状态。

### 5.8 `review_actions`

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键，作为 `action_id` |
| `version_id` / `user_id` | 所属版本和用户 |
| `primary_domain` / `related_domains` | 主要及相关领域 |
| `content` / `edited_content` | AI 候选内容及用户修改内容 |
| `rationale` | AI 生成的自然语言行动依据，供页面直接展示 |
| `status` | `CANDIDATE/CONFIRMED/IGNORED` |
| `source_action_id` / `is_inherited` | 跨版本来源行动和继承标记 |
| `basis_analysis_ids` / `basis_source_ids` | JSONB 依据 |
| `verification_rule` | JSONB，按 `root_source_type` 定义下一同级周期如何寻找证据 |
| `updated_at` | 用户操作时间 |

只有 `CONFIRMED` 行动进入下一同级周期核查。跨版本规则：

- 事件编辑完整复制当前版本行动，保留 `edited_content` 与 `CONFIRMED/IGNORED` 状态，并以 `source_action_id` 指回旧行动。
- 重新生成时，AI 新候选若与旧行动引用同一未决事项且内容等价，则程序合并为一项，保留用户编辑内容和确认状态并更新分析依据。
- 无法映射的旧 `CONFIRMED` 行动仍作为继承项保留，不得静默丢失；旧 `IGNORED` 行动不展示，但作为去重约束，防止模型立即生成同义候选。
- AI 新产生且无旧映射的行动保存为 `CANDIDATE`。

`ANALYSIS_UPDATED` 使用事件编辑版本作为基准执行同一映射规则：已确认行动即使没有新候选映射也继续保留；映射成功时更新其分析和事实依据，但保留用户编辑文本与确认状态。上一行动核查始终以本次模型结果新建，不从基准版本继承。

### 5.9 `review_action_checks`

行动核查只在此表保存权威状态，不重复写入 `analysis_document`：

| 字段 | 说明 |
|---|---|
| `id` / `version_id` / `user_id` | 核查记录和所属版本 |
| `previous_action_id` | 上一同级周期已确认行动 |
| `check_status` | `FULFILLED/PARTIALLY_FULFILLED/EXPLICITLY_NOT_FULFILLED/NOT_ASSESSABLE` |
| `explanation` | 自然语言核查结果 |
| `evidence_source_ids` | JSONB 核查依据 |

唯一约束：`(version_id, previous_action_id)`。`NOT_ASSESSABLE` 表示当前记录未发现足够证据，不等于未执行。

## 6. 文档结构

版本的两个 JSONB 文档共享稳定领域枚举：

```text
WORK_CAREER
HEALTH_WELLBEING
RELATIONSHIPS_SOCIAL
LEARNING_GROWTH
LIFE_RESOURCES
LEISURE_EXPERIENCE
```

事件文档按非空领域保存核心关注和发展主线，独立事件使用单节点主线表达；分析文档按非空领域保存通过门槛的重复信号和七角度分析项。候选行动以 `review_actions` 为准，行动核查以 `review_action_checks` 为准，读取详情时由服务层合并到对应领域，避免用户操作频繁重写整份 JSONB。

环节二原始输出不会整份写入 `analysis_document`。程序先为分析项分配 UUID 并改写引用，然后：

- `domains[].signals` 与 `domains[].analysis_items` 写入 `analysis_document`。
- `domains[].action_candidates` 转写到 `review_actions`，不在 JSONB 重复保存。
- `previous_action_checks` 转写到 `review_action_checks`，不在 JSONB 重复保存。

一个内容只在主要领域完整展示，相关领域只返回引用 ID。空领域和证据不足的分析角度不写入占位项。

## 7. 接口设计

第一阶段建议提供：

```http
GET    /api/reviews?type=WEEK|MONTH|QUARTER|YEAR
GET    /api/reviews-unread-status
GET    /api/reviews/{review_id}
GET    /api/reviews/{review_id}/versions
GET    /api/reviews/{review_id}/versions/{version_id}
POST   /api/reviews/{review_id}/regenerate
POST   /api/review-versions/{version_id}/regenerate-analysis
PATCH  /api/review-versions/{version_id}/event-document
PUT    /api/review-versions/{version_id}/feedback/{analysis_item_id}
PATCH  /api/review-versions/{version_id}/actions/{action_id}
GET    /api/review-versions/{version_id}/sources/{source_id}
POST   /api/reviews/{review_id}/read
GET    /api/review-tasks
POST   /api/review-tasks
GET    /api/review-tasks/{task_id}
POST   /api/review-tasks/{task_id}/retry
```

核心约束：

- 回顾列表不传 `type` 时返回全部已实现周期；传值时只返回对应类型。服务端统一按 `period_end DESC` 排序，结束日期相同按 `YEAR → QUARTER → MONTH → WEEK` 排序。
- `GET /review-tasks` 返回当前用户全部任务，支持 `status`、`cursor` 和 `limit`；`limit` 默认 30、最大 100。服务端按 `created_at DESC, id DESC` 提供稳定游标分页；前端再按“进行中 / 需要处理 / 已完成”分组，其中已完成组按 `completed_at DESC` 展示并默认折叠。
- `POST /review-tasks` 传周期类型和周期起始日期，由后端计算结束日期，验证周期已经结束、依赖已进入终态、类型已经实现且不存在同周期回顾或活动任务。
- 首次手动生成、完整重新生成和仅更新分析行动都立即返回任务标识；事件编辑同步返回新版本标识，不保持长连接等待模型。
- `POST /reviews/{review_id}/regenerate` 固定创建 `FULL` 任务并读取最新来源。
- `POST /review-versions/{version_id}/regenerate-analysis` 固定创建 `ANALYSIS_ONLY` 任务，只允许基于分析过期的事件编辑版本。
- `GET /review-tasks/{task_id}` 返回步骤、状态、脱敏错误和结果版本，供列表轮询进度。
- `retry` 只接受明确失败的任务 ID，将原任务重新入队并保留原 `generation_mode`、来源集合及已校验中间结果，从最近未完成步骤恢复。来源冻结未完成时重新冻结。需要最新业务数据时使用完整重新生成，不能把重试混成重新生成。
- 修改事件层时提交整个当前事件文档，路径中的 `version_id` 就是基准版本；后端用乐观锁拒绝基于过期版本覆盖。
- 所有查询和修改都同时校验资源 ID 与当前 `user_id`，不能只按资源 ID 查询后再返回。
- 来源接口只返回冻结摘录和可访问的业务对象定位信息，不绕过原对象权限。

## 8. 编辑、版本和对话

### 8.1 事件层编辑

保存编辑时：

1. 校验用户、当前版本和事件文档结构。
2. 第一版编辑接口只接受 `thread_id + narrative`，不接受客户端修改 `core_focus`、领域、状态、节点、关系、key 或任何来源 ID。
3. 服务端对叙事执行 diff，新增 `USER_FACT_CORRECTION` 来源，保存原叙事、新叙事、被修正主线、基准版本和创建时间；主线记录 `user_overridden=true` 与 `narrative_correction_source_id`。
4. 原节点、关系和来源只作为修正前历史继续保留；用户叙事成为该编辑版本的权威事实表达，后续重新生成把修正来源作为最高优先级输入。
5. 复用依赖并保存用户编辑后的事件文档。
6. 沿用旧分析文档并设置 `analysis_stale=true`。
7. 按 5.8 的规则继承行动，按 5.7 的规则继承反馈，不覆盖旧版本数据。
8. 锁定 `reviews` 行，分配版本号并原子更新 `current_version_id`。

用户编辑是事实修正，不反向修改日记或日程。

所有生成任务提交版本时也必须锁定 `reviews` 行，并比较任务的 `base_version_id` 与当前版本。若任务运行期间当前版本已变化，仍可保存结果为 `superseded_at_creation=true` 的历史版本，但不得更新 `current_version_id`；任务结果明确提示“生成期间已有更新”，不能静默覆盖较新的用户事实编辑。

### 8.2 根据事件修改更新分析和行动

事件编辑保存后不自动调用模型。用户主动发起 `ANALYSIS_ONLY` 任务时：

- `event_document` 必须逐字节复用基准版本，不允许模型返回或服务层重组事件层。
- 用户修正后的 `narrative` 是权威事实表达；旧节点和关系只提供修正前背景，冲突时不得覆盖用户叙事。
- 重新生成分析、上一行动核查和候选行动；已确认行动按来源映射继续保留。
- 完成版本类型为 `ANALYSIS_UPDATED`，`analysis_stale=false`，使用与基准版本相同的来源集合。
- 基准版本在任务期间不再是当前版本时，按并发版本规则保存为非当前历史版本，不覆盖新版本。

### 8.3 回顾对话

复用现有 `dialogs.source_type=review`，但 `source_id` 必须绑定 `review_version_id`，不能绑定可变化的 `review_id`。对话上下文从固定版本组装：

- 事件和分析文档。
- 当前版本行动、评分与文字反馈。
- 当前版本冻结来源摘录。

创建 `source_type=review` 对话时必须按 `review_version_id + user_id` 校验所有权，并复用该版本唯一的回顾对话；发送每条消息时再次校验版本与用户。当前 `dialogs` 中动态读取最近 7 天日记的 `review` 分支必须替换为上述固定版本上下文，且禁止把 `review_id` 当成版本 ID。旧版本对话继续保留，新版本创建独立对话。数据库为回顾对话增加 `(user_id, source_type, source_id)` 唯一约束或提供等效事务保证。

## 9. 模型配置

在 `model_settings` 增加 `review` 用途。第一版两个环节均从该用途解析模型；是否增加环节级模型覆盖可沿用现有 `model_step_settings` 机制：

```text
review_event_organize → review
review_analysis_action → review
```

实现必须同步修改当前代码中写死的 `SETTING_KEYS`、`SETTING_REQUIREMENTS`、`STEP_SETTING_KEYS`、`STEP_LABELS`，管理端用途标签、默认配置种子和数据库迁移，不能只插入一条 `model_settings` 记录。

提示词不放入数据库和管理端。每个环节开始调用前读取当前有效模型配置，并把实际模型名称、思考状态和调用时间冻结到完成版本。

## 10. 安全与日志

- 回顾、任务、版本、来源、反馈、行动和对话都以 `user_id` 为硬边界。
- 日记原文、完整来源摘录、完整提示词和完整回顾不写入普通应用日志。
- 模型调用日志记录任务 ID、环节、模型、耗时、Token、结果状态和脱敏错误。
- API 错误不返回数据库异常、模型密钥或其他用户的资源存在性。
- 回顾主体到版本、来源集合关联、反馈、行动、核查和依赖使用明确的数据库级联；来源被多个来源集合复用时，只有不存在任何关联后才可清理。当前项目没有用户删除接口，设计不假设已有统一账户级联策略；未来增加用户删除时必须在删除服务中显式清理回顾数据。单个旧版本第一版不提供删除入口。

## 11. 前端落点

- 底部“回顾”导航从占位页改为全部已实现周期混合时间线；第一阶段提供“全部 / 周 / 月”筛选。
- 详情按非空生活领域纵向展示“事件 → 分析 → 行动”，不拆成三个 Tab。
- 来源抽屉支持逐级打开下级回顾，最终定位到日记事件或日程日期。
- 版本切换始终同时切换文档、反馈、行动和对话入口。
- 事件编辑、反馈和行动编辑控件实际字号不小于 `16px`；必须在 iOS Safari 验证聚焦不触发页面放大。
