# 事件要点与发布业务案例

整理日期：2026-10-29。本文将旧知识沉淀案例中仍有验收价值的事件边界、信息覆盖、失败恢复和幂等要求适配到当前“来源事件—有序要点—关系证据”结构。它是功能验收案例，不是模型必须逐字生成的固定输出。

原方案的独立知识任务、`knowledge_atomic_events`、成功沉淀记录、`completed_stage=ATOMIC_EVENTS` 和 `/knowledge` 列表已由后续实现替代，不再保留为待开发流程。当前输入、生成和保存协议见第一层设计；通用需求见[事件知识管理需求](事件知识管理需求.md)。

## 1. 符号与场景边界

| 符号 | 含义 |
|---|---|
| D | 来源日记 |
| E | 结构化事件及稳定事件 ID |
| P | 对应本轮事件内的有序要点 |
| T / R | 应用内任务/运行，或具体 Skill 保存协议的标识；两者不能互换 |

以下例子不预设 `organized` 或 `analyzed` 都走同一入口，重要性准入、历史处理与 Skill 补充范围按调用方协议检查。示意要点的主旨与详细内容用于展示覆盖要求，不能据示意绕过来源和正式预检。

## 2. 单一完整事情：知识库模型讨论

### 来源

D1：2026-08-10，《知识库模型讨论》。结构化事件 E1《讨论知识库模型》：

> 我与同事林舟讨论了日记平台的知识库。我提出使用时间、人物、事项和洞察组织知识，并以现有日记事件作为基础。讨论后，我发现一条现有日记事件经常包含多个不同的事情，因此知识库还需要拆出知识事件。我认为应当先确定概念边界，再考虑数据库设计。

感受为空；反思为“应当先确定概念边界，再考虑数据库设计”。这些内容属于同一次讨论中连续形成的认识和决定，上游保留为同一个事件。

### 预期检查

- 要点均归属于 E1，不因观点数量或图谱关联数量生成多个同一来源事件。
- 主张“以现有事件为基础”“按时间、人物、事项、洞察组织”“事件边界需先确定”“概念先于数据库设计”均有对应表达。
- “我提出”“我发现”“我认为”的归属保持，不能改成已经实施的系统方案。
- 标题、主旨、详细内容承担不同阅读层次，但详细内容须保留同事身份、讨论对象、认识演进与最终取舍。
- 反思字段和正文的相同观点可以识别为重叠，不能因此丢失其属于本次反思的语境，也不能重复计为两次独立经历。

示意主旨可为“讨论知识库组织方式与事件边界”；详细内容应完整保留上述讨论过程。要点粒度与数量由当前提取规则决定，不将旧单一知识事件的数量约束套到要点数量。

## 3. 两件独立事情：买酱油后打游戏

D2：2026-08-11，《买酱油后打游戏》。上游已分为两个结构化事件。

E2《去商店买酱油》：

> 我先去打酱油，老板人挺好，多给了我一些。我给她 10 元，她找了我 2 元。

E3《回家和朋友打游戏》：

> 买完酱油后，我回家和朋友打游戏。

### 预期检查

| 来源 | 必须保留的内容 | 不允许的变化 |
|---|---|---|
| E2 | 购物行为、对老板的判断、额外给的酱油、付款10元和找零2元 | 不能只留下“买了酱油”；不能补写没有记录的动机、金额或结果 |
| E3 | 买酱油后的时间衔接、回家、与朋友打游戏 | 不能丢掉理解顺序所需的背景，也不把购物细节重复当作E3的新经历 |

E2、E3 的要点与证据必须按事件 ID 分别绑定，即使后续调整数组顺序或出现同名标题也不能串写。先后顺序本身不自动构成引发、后续或提及关系；是否建立联系须另按关系规则核验。

## 4. 触发与重复请求

### 应用内路径

用户在允许状态触发分析、仅建图或历史处理时：

1. 校验所属用户、来源有效性、当前活动任务和所需模型配置。
2. 建立任务及运行身份，冻结来源/配置或按实际入口准备来源。
3. 重复请求按现行活动任务协议返回或明确拒绝，不创建相互覆盖的任务。
4. 前端读取任务阶段与错误，失败恢复使用对应任务接口，不重新拼造内部状态。

当前正式模型为 GraphTask/GraphRun；旧案例的独立 T2、KD2 和 `thread_id` 不能作为当前数据库操作模板。

### Skill 路径

导出来源、生成稿、审阅、预检、确认与保存按对应 Skill 协议执行。确认绑定用户实际审阅的稿件和来源指纹；稿件或来源变化后重新预检，不能把前一版本的确认沿用到新稿。Skill 以其支持的分阶段事务发布，不宣称与完整应用内分析共用一次提交。

## 5. 多单元处理与恢复

旧案例 D3 有12个事件，曾按5/4/3个事件装成3批。此数量不是当前固定分批算法；保留的验收要求是来源单元不被为凑预算而截断、恢复跳过已验证完成的单元。

重放情境：

1. 前两组来源已得到合法结果并保存进度。
2. 第三组调用前中断，任务执行权过期。
3. 新执行者取得新的执行权，读取同一有效来源及已有进度。
4. 不重复发布前两组；已确认结果是否可复用须同时核验来源与配置兼容性。
5. 旧执行者迟到的模型响应不覆盖新执行者的进度或正式结果。

当前具体按事件、要点、事件对还是请求预算分组，由第一层工作流确定。超预算场景必须说明如何保留完整来源，不能把旧“单事件超预算仍强行调用”的设想写成所有渠道均可执行的保证。

## 6. 错误和来源变化

| 情境 | 验收重点 |
|---|---|
| 模型响应带包装、缺字段或格式非法 | 结构与语义校验分别识别；重试/修复次数由实际协议决定，不能直接发布候选 |
| 来源修订、事件ID集合或人物资料变化 | 按对应协议判定来源是否失效，重新导出/生成/预检；不能使用旧确认写入新来源 |
| 模型配置缺失或不可调用 | 明确失败并指出配置范围；不自动用其他用途模型或旧环境参数兜底 |
| 向量数量、维度或模型版本不符 | 阻止对应发布，保留可诊断的错误与恢复状态 |
| 历史关系端点已经过时或删除 | 重新核验依赖，不能写入不可追溯的关系 |
| 发布事务中途失败 | 对应发布范围内回滚，不能留下缺少必要事件/要点/证据的半成品 |

旧案例“只做结构校验、最多一次JSON修复”的约定已经被后续审核/复核机制替代；保留错误恢复场景，具体次数不复用为当前规则。

## 7. 已提交后中断与幂等

假设正式数据已提交，而进程在响应或后续清理前中断：

- 先查任务、运行与正式结果，区分“未执行”“执行失败”和“已成功但响应未知”。
- 已发布且完整的结果不能因没收到客户端回执而重复创建。
- 后续清理失败不撤销已提交的有效结果；恢复应沿协议补偿。
- 若存在过时版本和有效版本，查询不能混用不同运行的要点或证据。

当前运行进度保存在具体工作流的数据中，不再要求重建旧 LangGraph 独立知识任务成功 checkpoint 清理器。恢复验收应依据当前持久化对象，不能只检查页面显示“成功”。

## 8. 阅读与回溯

当前在日记详情检查事件要点、关系图和来源内容。E2、E3展示时，事件身份、顺序、来源日记和证据引用均须保持；模型文字不得任意作为HTML执行。

旧跨日记知识卡片的独有信息需求保留为候选浏览需求：发生时间、标题、最多三行内容、来源日记与来源事件，以及稳定分页。独立列表的路由、每页20条与容器宽度尚需重新产品设计，不将旧线框复制成现有界面。

## 9. 覆盖清单

本稿迁移保留了旧案例中的：单次讨论连续性、两独立事件的边界、付款找零细节、时间背景、来源1:1身份、完整输入、恢复不重复调用、租约与迟到响应、来源变化、事务发布、发布后中断、模型未配置和阅读回溯。

退出的是独立知识沉淀按钮、旧知识实体字段、旧任务/成功记录表、已移除知识页和仅结构校验的实现细节。这些内容已有替代方案，不继续作为当前开发清单；独有的验证问题由上述场景继续承载。
