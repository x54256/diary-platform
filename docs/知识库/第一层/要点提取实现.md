# 事件要点提取实现

核对基线：2026-10-29 仓库代码和要点 Skill。业务语义见[事件要点功能约定](事件要点功能约定.md)，任务与正式身份见[存储与任务实现](存储与任务实现.md)。

## 1. 设计与两条实现

| 责任 | 应用内任务 | 要点 Skill |
|---|---|---|
| 入口 / 准入 | 分析、历史建图、仅建图入口；仅中高重要事件 | 只读数据库导出或用户指定文本；整篇保存覆盖全部事件 |
| 提取事实 | 冻结事件 `body`，原标题、段落和原句编号 | 正文、感受、反思中的全部有效事件信息，去重重复派生内容 |
| 语义生成 | 生成 → 合并审核修正 → 有修正后独立复核，最多两轮 | 代理依规则成稿、复读、按需澄清并保留用户修订 |
| 硬校验 | 标题、序号、字段、原句覆盖、候选引用、状态与问题的一致性 | Markdown 格式、事件 ID / 顺序 / 覆盖、正文及文件与来源指纹 |
| 人工确认 | 自动流程；人工原文核验用于开发及质量验收 | 单独 / 本地路径整稿确认；云端完整流程有独立审阅规则 |
| 向量 | 每项完整详情，1024 维，配置和模型身份冻结 | 同样按完整详情生成；可复用完全匹配的同模型有效向量 |
| 完成状态 | 与关系及后续分析按入口统一发布为 `PUBLISHED` | 仅保存要点和向量为 `POINTS_READY`，不冒称关系完成 |
| 恢复 | 持久化任务、事件工作结果、审核轮次和调用记录 | 当前稿、来源包、确认指纹、独立同步任务及向量阶段断点 |

共同语义并不保证两种实现的事件范围、输入和审核覆盖相同。应用内当前提取不单独读取新增感受 / 反思字段；若这些字段包含正文之外的有效信息，存在输入覆盖差异。

## 2. 应用内生成与审核

执行入口为 [graph_points.extract_event](../../../backend/services/graph_points.py)，由 [graph_workflow](../../../backend/services/graph_workflow.py)逐事件调用。

1. 从完整正文构造有序段落，生成 `title + points`；每项只含连续 `no`、`summary`、`detail`。
2. 程序分句形成有序 `source_units`，保留段落归属；这是审核索引，不是预先由模型生成信息清单。
3. 独立的合并审核请求读取完整来源与当前候选，双向核对并返回审核和候选。无问题时候选必须逐字段保持原样。
4. 有修改时再作独立复核，只读取来源和修正版；通过后接受，否则下一轮合并修正接收具体复核意见并依据原文核实。
5. 每次最多两轮修正 / 复核，未通过抛出 `POINT_REVIEW_FAILED`，保留工作结果，不发布未通过候选。
6. 通过后分配稳定要点 UUID，再执行向量及后续关系处理。

当前协议为 `issues-v2`，旧任务仍可按冻结的 `legacy` 协议恢复：新版每项仅返回 `no + issues`，`summary_ok/detail_ok` 由程序推导。每个问题必须引用对应候选字段中的连续文本，并给出原句编号、语义差异与修正意见。原句检查编号和要点检查清单均须完整且按序。

审核指出的问题也可能错误。下一轮须重新依据原文核实，不能把审核意见本身当作事实。原句编号齐全和引用合法只证明协议结构，不证明真正理解、没有遗漏或没有误改。

### 2.1 配置与版本

[graph_runtime.freeze_config](../../../backend/services/graph_runtime.py)从 [event_point_optimized.json](../../../backend/scripts/fixtures/event_point_optimized.json)读取提示与指纹，验证基线后冻结协议、提示及模型设置。

- 生成、合并修正、复核三角色使用同一冻结模型配置；关系 A/B/C 为另一同组配置。
- 图谱语言调用要求当前渠道支持显式思考；实际模型从管理端 `graph` 及环节用途读取，不把某次 Qwen / Kimi 实验型号写为永久约束。
- 协议变更需保留旧解析器及执行分支，不能只换提示然后让旧任务用新字段恢复。
- 一次结构失败最多补答一次，具体错误进入重试请求；额度耗尽与服务失败保留实际错误，不无限尝试。

### 2.2 向量与预算

[embed_points](../../../backend/services/graph_relations.py)使用完整 `detail`，每条结果校验 1024 维、有限数值与非零模长。超出冻结字符预算时报错，不截断详情或取主旨代替。

模型身份与向量配置一起冻结。不同模型或身份不能混算余弦；同样维度不足以证明模型兼容。已经成功且通过校验的向量可从 checkpoint 复用，认证信息在运行时读取，不写入配置快照。

## 3. Skill 读取、成稿与预检

[diary-event-points](../../../skills/diary-event-points/SKILL.md)定义提取、澄清及交付规则；这里只描述实现，不执行该 Skill。

- [export_events](../../../skills/diary-event-points/scripts/export_events.py)按用户名、日期或日记 ID 定位，检查归属、有效整理和事件数组；同日多篇须选身份。
- 每次导出新建独立运行目录，保留 `source.json`、阅读视图及来源指纹。数据库失败不能自动换用本地旧稿。
- 稿件使用来源 ID、原标题与顺序；引入、琐事和独立计划不自动塞进相邻事件。整篇正式稿覆盖全部事件，不按低重要性过滤。
- 代理按共同业务约定处理中心、主旨、详情与关键含义；读取当前稿和已确认修订，不用旧版本覆盖用户编辑。
- 澄清记录放在稿外，区分原事实修正、当时补充和当前认识；本地来源快照不改写。

[store_points](../../../skills/diary-event-points/scripts/store_points.py)负责转换和预检：

1. 解析 Markdown 及逐事件要点，核对 ID、原标题、顺序和整篇覆盖。
2. 要求日记为 `organized` 或 `analyzed`、未删除、非脏数据、原文与整理修订有效，且无冲突活动任务。
3. 逐字段重读数据库事件，并与导出版本比较；已经存在有效 `POINTS_READY/PUBLISHED` 运行时不覆盖。
4. 绑定来源文件、Markdown、Skill、向量配置与确认包指纹。不同字段的 hash 用途不同，来源包校验不等于最终稿已获确认。
5. 正式保存前确认当前稿及要点外发范围；详情向量化会发送至配置的 embedding 服务，不能把只读预检当作已执行外发。

首次要点状态需要固定迁移 [051](../../../backend/migrations/051_event_points_ready.sql)支持。迁移、配置检测、预检和正式写入是不同操作，不能因提取任务自动变更数据库结构。

### 3.1 要点就绪与恢复

保存脚本使用专门环境标记的同步任务，不进入应用默认后台队列。候选和向量按事件保存 checkpoint，写入前再次获取用户和来源锁、核对来源、事件覆盖及完整向量，再统一写 `GraphRunEvent`、`GraphEventPoint` 并令运行 `POINTS_READY`、任务成功。

此时不生成关系，不触发后续日记分析，也不据此设置所有事件为已完整发布图谱。相同确认包通过任务身份和指纹识别已有结果；向量阶段失败可复用成功部分，不能重新发起不同来源却复用旧通过结论。

### 3.2 历史缺失事件补齐

[supplement_points](../../../skills/diary-event-points/scripts/supplement_points.py)用于在唯一有效旧运行中补入缺失事件及向量，保留原要点身份、向量和关系。它要求旧来源属于受支持的完整事件快照，并核对 checkpoint、现有节点、要点及来源；不提供任意覆盖既有要点的接口。

补齐不自动为新增事件识别关系，回执明确记录关系复核未运行。不能因要点覆盖已补齐就宣布历史关系图也已修复。

## 4. 关键差异与验证

| 边界 | 维护要求 |
|---|---|
| 生成全事件与中高过滤 | 分别验证范围，不以同一张覆盖统计表混算 |
| 正文与派生字段 | 验证新增感受 / 反思的来源去重和应用内输入缺口 |
| 澄清写入 | Skill 可使用明确澄清，但存储包并不提供通用受保护要点修订；新增事实先核实保存能力 |
| 模型自审与人工质量 | 程序通过、模型通过、正式保存与语义验收分开报告 |
| 旧已发布运行 | 默认不覆盖；补齐与替换是不同任务，不能删除旧证据后重建身份 |

回归入口为 [图谱要点协议测试](../../../backend/tests/test_graph_point_protocol.py)、[图谱规则测试](../../../backend/tests/test_graph_rules.py)、[要点 Skill 评估](../../../skills/diary-event-points/references/evaluation.md)及其存储 / 补齐测试。真实语义失败样本与未实现协议改造见[验证边界](验证边界与设计依据.md)和[后续设计](后续设计与实现差异.md)。
