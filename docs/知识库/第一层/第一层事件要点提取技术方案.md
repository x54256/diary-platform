# 第一层事件要点提取实现设计方案

状态：2026-10-15优化实现。新任务使用event-points-issues-v2-20261015审核协议，生成提示保持原样；程序计算审核状态，第二轮修正接收上轮独立复核意见。管理端仍使用qwen3.7-flash-2026-07-15，Kimi仅用于独立对照，未替换正式绑定。以下0731评分保留历史背景，新版验收结果另行记录。

## 1. 目标与范围

将日记事件正文整理成有序要点，作为知识图谱第一层后续人物、事件关系提取的事实基础。一个来源事件对应一个图谱事件，沿用原标题。

作为日记分析的前置子流程启动，已整理日记可进入；历史日记通过日期范围接口复用已有分析后逐日建图。两种入口均只处理有效重要性为中或高的事件。有效重要性优先取用户设置，未设置时取AI设置。输入使用用户完成编辑并点击分析时的事件正文，任务开始时冻结原标题、完整段落和来源摘要。

本方案定义单事件内容组织、生成、核验和修正。人物身份统一、事件关系、发生日期及整日发布由各自设计承接。

## 2. 最终方案：生成、审核修正合并、独立复核

```text
日记ID → 读取并冻结准入事件
       → 对每个事件：
           生成要点 → 程序结构检查
                    → 独立请求：审核初稿并修正 → 程序结构检查
                        ├─ 未发现问题：保留原候选并记录模型通过
                        └─ 发生修正：另一次请求独立复核
                            ├─ 通过：保存候选及模型通过状态
                            └─ 未通过：再次审核并修正，再独立复核
                                       最多两轮
       → 返回逐事件候选、审核问题和运行状态
       → 程序检查和模型核验通过后自动交给后续图谱处理
```

生成、审核修正合并、独立复核沿用同一冻结模型配置。审核修正请求先记录对输入候选的双向原文核验，再输出依据原文修正的完整候选。未发现问题时原样保留候选；发生修正后另行复核，审核初稿的结论不代表修正版已通过。

初稿无需修正为2次调用；一轮修正后通过为3次；两轮最多5次。每阶段结构失败允许额外重试一次，理论上限10次。程序分句和格式检查不调用模型。

第二轮合并请求接收原文、上轮候选和previous_review。模型须依据完整原文核实每项复核意见，在对应原句比较中记录依据，再修正实际问题；复核意见不作为必须采纳的标准答案。独立复核仍只接收原文和候选。

## 3. 业务输出

```json
{
  "title": "原标题",
  "points": [{"no": 1, "summary": "一句简明主旨", "detail": "完整忠实的自然重写"}]
}
```

| 字段 | 职责 |
|---|---|
| title | 沿用来源事件原标题 |
| no | 从1开始连续编号，保持原叙述顺序 |
| summary | 简明表达本项核心；所表达的判断自身忠实 |
| detail | 独立保留核心判断、变化、具体信息、转折和关键反例 |

按语义完整的主题组织。同一主题的背景、感受、原因、对比、转折和反例一起表达；叙述中心转向另一独立主题时分项。数量由内容决定。

保留原文人称。允许清理无信息的口语和重复、理顺语序及明确能从上下文确定的指代。保持人物、事实、观点归属、否定、确定性、程度、时间、条件和因果；不新增原文未表达的解释、动机或结论，不使用外部知识替换原文。

## 4. 输入准备

读取事件ID、原标题及完整正文。`diary_events.body`为字符串时先做JSON解析，确认得到数组再遍历，避免把字符当成段落。

生成请求只接收原标题与完整有序段落：

```json
{"title":"原标题","paragraphs":[{"id":1,"text":"完整原段落"}]}
```

审核额外接收候选和原句编号`source_units`。沿用基线分句规则`[^。！？]+[。！？]?`，每句保存连续编号、所属段落和原文。原句编号只用于出处定位，不决定生成主题。

审核输入为`{"source": {"title": "原标题", "paragraphs": [...], "source_units": [...]}, "candidate": {...}}`；第二轮合并修正输入再增加上轮独立复核的`previous_review`，该字段随检查点保存以支持失败恢复。

## 5. 固定提示词

当前基线：[event_point_optimized.json](../../../backend/scripts/fixtures/event_point_optimized.json)，版本`event-points-issues-v2-20261015`、协议`issues-v2`。旧任务继续读取其冻结文本和旧审核协议。

上一代冻结快照：[event_point_baseline.json](../../../backend/scripts/fixtures/event_point_baseline.json)。包含生成、审核、修正及实际合并请求四份提示、独立示例、提示SHA-256、模型参数和两轮修正上限。版本为`event-points-final-20261013-thinking`，状态为用户确认最终方案。后续修改从此版本开始，保存新的提示指纹。2026-10-12按用户要求优化审核语义判定与修正误判处理，生成提示保持不变；历史评分不代表新版质量。新版审核修正已使用deepseek-v4-flash-0731复用两份历史初稿复测，评分88、89，详见[复测报告](../../../knowledge-graph/validation-2026-08-26/combined-review-repair-deepseek-0731-semantic-20261012/复测报告.md)；真实示例生成提示尚未重新实测。本轮同时更换模型和提示，结果不能单独归因于提示优化。

### 5.1 生成

```text
将事件原文整理为有序要点，只依据原文。
按语义完整的主题组织内容，同一主题的背景、感受、原因、对比、转折和反例一起表达；叙述中心转向另一独立主题时分项。数量由内容决定。
保留原文人称。
summary用一句简明、自然的话说明本项核心意思。
detail对原文作完整、忠实、自然的重写，清理无信息的口语和重复，理顺语序；独立表达核心判断、变化与转折，保留具体信息及关键反例。
两个字段各自保持原有事实、观点归属、否定、确定性、程度、时间、条件和因果，不增加原文未表达的信息。
输出前检查忠实、完整、核心清楚、转折完整和语言自然。
输出JSON：{"title":"原标题","points":[{"no":1,"summary":"简明要点","detail":"详细内容"}]}。序号从1连续递增。
```

实际发送时后接三个完整真实案例：江西项目数据梳理与需求讨论、出差时利用信息差让同事同住、与德华讨论程序员职业与第二职业，要点数分别为7、3、3。案例正文和输出已固定在提示快照中，输出最初逐项取自[data.json](../../../knowledge-graph/data.json)，仅映射字段名，不改写内容。三个案例分别展示复杂叙述、经历与自我评价、他人观点与自身推测。

“怀念过去的日子”未加入示例，继续用于对照测试；三个示例事件不再用于独立质量评分。`prompts.generate`保存完整实际文本，独立示例文件与快照已同步替换；生成规则、审核和修正提示保持不变。原虚构示例版本保留在历史归档中，四份既有结果及评分属于该旧版本，真实案例版本尚未模型实测。

### 5.2 独立审核

先逐句定位候选对应判断，结合上下文区分实际限定与口语、举例，以语义变化作为失真标准；不能仅因省略或替换某个词就判错。summary允许省略背景；表达了某判断就必须保留其限定，detail正确不能补偿summary失真。详情检查有效信息、核心、变化、转折与反例。

输出结构：

```json
{
  "source_checks": [{"source_unit_id": 1, "comparison": "原句与实际候选的具体比较"}],
  "checks": [{
    "no": 1,
    "issues": [{
      "field": "summary", "candidate_quote": "候选实际片段", "source_index": 1,
      "difference": "具体语义差异", "repair": "依据原文的修正要求"
    }]
  }]
}
```

新版模型只返回no和issues，不返回summary_ok/detail_ok；程序校验后按issues中的field计算两字段状态，原始响应保持原样。完整审核提示取当前快照`prompts.review`，不加入案例检查答案。

### 5.3 修正

```text
依据原文核实审核意见并修正实际错误，输出完整结果。审核意见是待验证的问题；若候选与原文语义一致，该意见不成立，保留原表达。只接受有原文依据的修改，不为了修改而重写正确内容。保留原文人称。
保持主题组织及未出错的内容，修正概念、确定性、程度、因果和归属的偏差，清理无信息的重复口语。各项中心清楚、转折完整、表达自然。
summary用一句简明自然的话准确说明本项核心；detail完整忠实重写。两字段各自忠实，不新增信息。
输出JSON：{"title":"原标题","points":[{"no":1,"summary":"简明要点","detail":"详细内容"}]}。
```

审核与以上修正规则在同一次请求中依次执行，完整实际文本取基线`prompts.combined`。输入为原文及候选，输出结构如下：

```json
{"review":{"source_checks":[],"checks":[]},"candidate":{"title":"原标题","points":[]}}
```

`review`记录对输入候选的审核，`candidate`为完整修正版；数组内容沿用前述审核和要点结构。程序验证引用和字段状态，未发现问题时要求candidate与输入一致。发生修正后独立调用`prompts.review`复核，最多两轮，仍有问题则保留末次合法候选并报告失败。

## 6. 程序校验及失败处理

| 阶段 | 确定性检查 |
|---|---|
| 生成及合并输出中的candidate | 顶层及要点字段、原标题相等、非空数组、连续序号、非空文本 |
| 合并输出 | 顶层为review/candidate；review针对输入候选；无问题时candidate保持原样 |
| 审核 | 原句及要点检查完整、引用真实存在、原句编号有效、差异和修正要求非空 |
| 审核结论 | 模型仅输出问题清单；程序按字段计算ok。新版不接受模型额外返回ok；旧冻结任务仍严格校验原协议 |

结构失败时向相同模型提交原请求、前次输出和具体结构错误，只重试一次，不要求改变结论迎合格式。仍失败则记录结构失败，不自动放宽校验或改写原始响应。

服务或网络失败与语义质量失败分别记录。额度不足、模型不可调用或来源变化时停止当前任务。保留已成功阶段及失败类型，重试时核对来源、模型及提示版本。

模型“通过”只表示该次审核未发现问题。正式流程自动继续；人工原文审阅用于开发验证和验收。已被模型核验判定存在问题且未修复的候选不进入后续图谱处理。

## 10. 验证结论与验收

原文是唯一事实依据，data.json用于比较主题组织与自然表达；参考自身也有名称、限定及程度差异，不能作为唯一真值。

| 开发事件结果 | 第1份 | 第2份 |
|---|---:|---:|
| 历史Qwen独立修正 | 88 | 86 |
| 历史Kimi独立修正 | 88 | 88 |
| 历史Kimi旧提示合并审核修正 | 86 | 90 |
| 最终DeepSeek 0731新版合并审核修正 | 88 | 89 |

分数为助手对同一开发事件的主观评审：忠实40、完整25、主题15、表达20，不是准确率或独立盲评。最终版本修复主要限定和概念偏差，仍有标题冗长、口语及归属表达含糊。此次同时更换提示与模型，不能单独归因于提示优化。

最终0731复测复用了两份历史初稿，各执行两轮，共8次有效请求、0次结构重试，末次模型复核均通过；未测试新版真实示例从原文首次生成的质量。评分、调用摘要和限制见[最终复测报告](../../../knowledge-graph/validation-2026-08-26/combined-review-repair-deepseek-0731-semantic-20261012/复测报告.md)。旧方案取舍及本次最终确认保留于试错记录。

正式接入前使用多种未参与提示迭代的真实事件，逐段检查有效信息、限定、核心及反例，逐项检查标题和详情各自忠实、主题清楚及语言自然；并验证遗漏计划、虚构发言、计划改完成等受控错误。格式通过、模型自评通过和人工验收分别记录。
