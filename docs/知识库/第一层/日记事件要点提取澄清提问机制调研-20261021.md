# 日记事件要点提取：澄清提问机制调研

调研日期：2026-10-21。本次核查当前 Skill、整理阶段交互记录、要点入库脚本及公开一手研究；未修改 Skill、脚本或真实日记，未重新入库。公开检索只使用通用研究问题，没有向外部服务发送日记内容。

## 结论

**要点提取需要按需澄清的能力，但不宜增加每次必经的提问环节，也不宜直接照搬整理阶段的提问尺度。**

要点提取的目标，是将已有事件围绕中心组织，让内容更容易浏览、定位、阅读和引用。提问只有在保护这一目标所需的关键含义时才有价值。它不负责把经历补充完整，也不负责让作者当时尚未形成的认识得到答案。

当前 Skill 已有方向正确的原则，主要欠缺可操作的触发条件、正反示例及相应验证用例。研究支持“考虑任务收益和交互成本再决定是否澄清”，但没有直接证明日记要点阶段提问能提高多少质量，或每轮应该问几题。以下交互建议属于结合项目特点的设计推论，尚需试跑。

## 一、当前实现已经具备什么

### 1. 要点 Skill 已允许有条件提问

[当前 Skill](../../../skills/diary-event-points/SKILL.md)要求：

- 来源含混时保留含混程度；只有冲突或疑问妨碍关键理解时才集中询问，可以先完成不受影响的事件。
- 用户要求直接处理时，保留未解决表达并在正文之外说明，不填补事实。
- 用户明确修订可以作为依据，但新的当前反思不能写成事件发生时已有的认识。
- 默认核对后交付，不要求每项先确认；正式入库另有当前稿确认要求。

所以问题并非“完全没有提问机制”，而是“关键理解”缺少足够具体的判断示例。现有规则仍可能被执行成见到含混就问，或遇到真正影响含义的问题也一律保留。

### 2. 整理阶段可借鉴交互方式，不能直接复制任务目标

[整理 Skill](../../../skills/diary-organizer/SKILL.md#按需澄清关键疑问)已有完整稿后集中提问、回答后复读、移除已解决问题、停止追问已跳过问题、保留自由输入与“不记得，保留原样”等机制。这些交互约束适合复用。

但整理面对转写和原始叙述，要点提取面对已经整理的事件。后者应先充分利用现有事件上下文和已有确认，不重新向用户询问已确认的名称或经历。

[多轮提问测试报告](../../验证/日记整理Skill-多轮提问-20261021-110556/测试报告.md)中的两个合成场景，分别出现了 4→1→0 和 1→1→0 的事实提问过程。它只证明这两次整理试跑能继续处理遗留及新增疑问；没有证明要点阶段提问的收益，也没有覆盖真实用户负担、跳过问题或真实交互框。

### 3. 当前要点评估缺少正向提问覆盖

[评估用例](../../../skills/diary-event-points/evals/cases.json)已有明确禁止提问、要求保留不确定指代的场景，但缺少成组验证“必须问什么、何时停止、回答后如何更新”的用例。不能根据现有提取样例通过，就认定澄清交互已经验证充分。

## 二、一手研究能支持哪些判断

| 一手资料 | 可支持的判断 | 适用边界 |
| --- | --- | --- |
| [Clarify When Necessary，NAACL Findings 2025](https://aclanthology.org/2025.findings-naacl.306/) | 歧义存在与是否值得提问是两个判断；需考虑任务效果、用户偏好和交互成本。模型自身知识或能力不足也不都能靠用户澄清解决。 | 实验是问答、翻译和推断，含构造的澄清回答；没有验证私人日记或固定提问轮数。 |
| [Decontextualization: Making Sentences Stand-Alone，TACL 2021](https://aclanthology.org/2021.tacl-1.27/) | 借助已有上下文，使摘出的内容可独立理解，同时保持意义；部分叙述不能通过简单改写独立化。 | 主要研究英文百科句子，不是日记要点或交互提问实验。 |
| [Asking the Right Question at the Right Time，EACL 2024](https://aclanthology.org/2024.eacl-long.16/) | 协作绘图中，模型不确定性不直接对应人类的提问行为；针对任务中实际不确定性的提问可以改善效果。 | 不能据此认定照搬其他流程的题目、数量和时机适合日记。 |
| [Referential ambiguity and clarification requests，CRAC 2025](https://aclanthology.org/2025.crac-1.1/) | 搭建任务中，指代歧义与人类提问只弱相关，模型更容易围绕指代发问。检测到代词并不足以决定提问。 | 特定任务中的人类少问，不等于日记场景少问总是更好。 |
| [Extractive is not Faithful，ACL 2023](https://aclanthology.org/2023.acl-long.120/) | 摘录原句也可能因指代、篇章上下文缺失而失真。不能以“文字来自原文”替代语义核对。 | 没有验证向日记作者提问的效果，也不能推算本项目错误率。 |

综合这些研究，本项目更适合的处理顺序是：**查完整上下文和既有确认 → 修正表达或补足已有背景 → 判断是否仍有必须澄清的关键含义。** 这个具体顺序是设计建议，而非论文已验证的日记最佳流程。

## 三、什么情况下值得问

建议同时检查以下条件：

1. **确有未解决的含义问题。** 已读完整事件和相关确认，仍存在多个合理解释，或关键内容缺失、冲突而不能可靠表达；不能只是模型不喜欢原有措辞。
2. **它会实质改变内容。** 影响谁做了什么、观点属于谁、动作对象、关键时间、否定、条件或确定程度，或使某项中心无法准确识别。
3. **不能通过忠实组织解决。** 补入来源已有背景、调整边界、合并紧密内容或保留原有含混后，仍会妨碍关键理解。不能为了每项看起来完全自足而追问一切细节。
4. **问题有明确用途且可能得到答案。** 能指出回答将修正哪处文字；不是让用户替模型完成主旨概括，也不是逼用户回忆已经明确忘记的事情。

这不是强制把所有歧义消除。用户要求保留原样、跳过或不记得后，应停止该项追问。依然可以诚实保留不确定内容；是否适合入库要看最终文字是否忠实、是否满足既有确认要求，而非是否回答了所有问题。

| 情况 | 建议处理 |
| --- | --- |
| 前文已说明“他”是谁，拆分后丢了背景 | 从来源补入必要背景，自行修正。 |
| 拆成两项或合成一项均合理 | 由提取者按阅读与定位价值决定，不要求用户做编辑选择。 |
| “我猜她觉得是自己的责任” | 保留“我猜”和观点归属，不追问她真实的心理。 |
| “我还没想明白原因” | 这是原有认识状态，保留，不要求形成解释。 |
| 关键行为人不明且影响该项含义 | 满足上述条件时，询问具体行为人。 |
| 两处写法似乎冲突 | 先检查是否描述不同时间或阶段；仍有关键冲突才问。 |
| 名称写法不熟悉 | 先查来源和已有确认；不能只因模型不认识就问或擅自纠正。 |

尤其要区分：**模型不知道原文指谁，不等于作者说自己“不记得指谁”。** 没有作者依据时，不能把模型的疑问写成日记中的回忆状态。

## 四、问题和回答怎么处理

通常先完成可确定的稿件，再集中提出确实影响含义的问题；仅当疑问会使大部分提取建立在错误理解上时，先澄清再继续相关部分。这里不建议规定固定题数或轮数，以少打断、每题有实际作用为准。

合成例子：原文“陈明把报告交给李华，他后来修改了结论”，全文仍无法确定修改者，且这一行为是该项中心。

> 关于报告修改，原文写“陈明把报告交给李华，他后来修改了结论”。这里修改结论的是谁？
>
> 选项：陈明／李华／不记得，保留原样；允许自由输入。

问题应自带足够定位的原句和疑点，候选答案必须来自上下文。事实选项不标“推荐”，不能把默认选中、沉默或超时当成答案。不使用“你是不是因为害怕才……”等诱导解释，也不追加“还能补充什么”的开放采访。

收到回答后，先判断它是在更正原有事实、补充当时事实，还是表达现在的新认识；再更新受影响内容，并复读完整事件。回答可能解决多个疑问，也可能暴露新的关键冲突，只继续处理仍符合触发条件的问题。保留用户直接改稿的内容，不能用旧版本覆盖。

事实澄清与正式入库确认应分开理解：回答一道题，不等于确认完整稿或授权保存；已有明确入库约定和当前稿确认时，也不应再增加一次无必要的授权询问。

| 想不起选修过什么科目 | 保留回忆缺失，不把补齐课程当成提取前提。 |

## 六、来源留痕和入库的实际边界

当前 [store_points.py](../../../skills/diary-event-points/scripts/store_points.py) 的 `prepare` 与 `verify_packet` 会绑定来源快照、当前 Markdown、目标用户与日记、来源指纹、Skill 及配置指纹，并核对用户确认指纹。**目前没有独立澄清记录的路径与指纹字段。**

这不妨碍保存用户明确确认过的文字，但不能声称脚本已自动证明“某条新增信息来自哪次回答”。语义真实性仍依赖执行者核对及用户确认。

若后续正式增强澄清机制，建议仅在实际发生澄清时保存最小记录：事件 ID、来源片段、具体问题、用户实际回答、受影响文字，以及回答是更正、历史补充还是当前反思。保留原始 `source.json`，不将回答伪装成数据库原有内容，也不自动回写原事件。

若要求入库包对这些补充依据也可追溯，再扩展预检绑定澄清记录指纹；记录或稿件变更后生成新包，按既有规则确认。这属于后续实现建议，本次未改脚本，也不需要为无澄清任务强制创建空记录。

## 七、如何验证值得落地

先补小规模、独立于示例的合成用例，再评估是否修改规则：

- 原文上下文足够、只有拆分丢背景：应自行修正，零追问。
- 关键行为人不明、关键时间存在真实冲突：应问具体问题，未答前不猜。
- 原文自带推测、遗忘、未完成思考：应保留，不逼出确定答案。
- 已有确认、一个回答解决多题、用户跳过、用户禁止提问：不重复问，不把沉默当确认。
- 回答补充当时事实与表达当前反思：正确区分时间，保留来源记录。
- 合理编辑分歧：自行选择，不让用户代做拆分和主旨提炼。

对同一批未见过的用例，比较当前规则与增加上述触发条件的规则；如需检验过度提问风险，可增加“发现歧义就问”的对照。评估关键含义失真、有效信息覆盖、原文可解答却仍追问的次数、问题是否改变最终文字、重复提问及用户回答成本。

先由评审者核对是否忠实，再邀请用户评估提问是否值得打断；模拟回答不能代替真实用户成本。问题更多、回答更长或稿件更确定，都不自动代表质量提高。

建议下一步只对当前 Skill 补充一小段触发条件、少量正反示例及对应评估用例。没有证据支持把每次提取改成固定采访，也没有必要因这项调研重新询问或重新保存 0909 的内容。
