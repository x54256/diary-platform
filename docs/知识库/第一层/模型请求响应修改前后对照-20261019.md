程序负责：

- 发送前记住“这次 A 对应出差安排的真实事件，B 对应初到现场的真实事件”。
- 收到 A_TO_B 后转换为真实源事件、目标事件 UUID。

**为什么还保留 point_no？**它是当前文本中的短编号，用来定位证据。程序负责生成编号；模型只选择它所依据的那条内容。同标题事件仍由程序身份映射区分，不改用标题作为数据库标识。

**A、B 两次判断如何进行？**发送两次相互独立的上述输入，第二次不提供第一次结论；有结构化分歧才交给第三次裁决。一次只含两件事能移除串到第三事件的输入条件，不能保证模型永远不会误解这两件事。

**C54 实际响应摘录：**

```json
{
  "source_checks": [
    {
      "comparison": "candidate summary准确表达了小豪的困境（答应好但做不到，仍需要钱）；detail忠实对应原文。",
      "source_unit_id": 21
    }
  ],
  "checks": [
    {
      "no": 5,
      "issues": []
    }
  ]
}
```


当前的 30 句比较和 6 项检查即使都通过也要逐条输出。

### 修改后的请求和响应

**拟议请求：**仍发送完整原文与修正后的完整候选；正文只出现一次，编号沿用上一节。只把第 5 个 summary 换成程序应用后的新值，不带前次审核意见。完整输入见附件。

**拟议 system 指令：**独立检查当前候选是否忠实、是否遗漏。既检查原问题，也检查改写是否产生其他事实错误；不要因文字流畅就通过。

**拟议无问题响应：**

```json
{
  "edits": [],
  "additions": [],
  "structure_issue": null
}
```


程序据此判定没有待修问题。若复核再发现错误，则返回具体修改建议，交给下一轮依据原文核实，不直接写正式图谱。若前次意见本身错误，应保持原文支持的表达；两轮仍不通过就保留失败结果。

**这能解决什么？**减少正确内容被重新生成的机会，缩小修改范围，并保留独立核验。它不能保证模型一定正确；“女友花他的钱”和“记录者自己的经历”必须作为真实语义回归样本验证。

## 4. 三个结构错误，直接看原来的响应

### 4.1 C12：程序要两部分，模型只给了一部分

**当前要求的最外层是 review 和 candidate；实际返回的最外层键：**

```json
{
  "actual_top_level_keys": [
    "review"
  ],
  "validation_error": [
    "合并输出字段不一致"
  ]
}
```


实际完整 review 见附件。它缺少 candidate，程序无法取得修正版。

**拟议改法：**始终只返回一份 edits/additions/structure_issue；不要求先输出两套 JSON，再合并成嵌套对象。

### 4.2 C13：说没有问题，却把 5 个 detail 都改了

以下是实际响应中的第 1 项，以及程序记录的修改前后值：

```json
{
  "actual_review_item": {
    "no": 1,
    "issues": []
  },
  "before_detail": "第二天是周日中午，小廖妈妈的朋友的同事约我们吃饭，名义上是庆祝我们要结婚。我们去吃了早茶，食物主要是油滋麻花的点和一些海鲜。由于我吃不了海鲜，且油滋麻花吃多了也吃不下去，导致中午没有怎么吃饱。",
  "returned_detail": "第二天是周日中午，小廖他妈妈的朋友的同事约我们一起吃饭，说是我们结婚请我们吃个饭，反正就这意思。我们去吃的早茶，早茶就是油滋麻花的，要不就是一些海鲜。海鲜我还吃不了，油滋麻花的吃多了也吃不下，中午没怎么吃饱。",
  "validation_error": [
    "未发现问题却修改候选"
  ]
}
```


这次不只是第 1 项，5 项 detail 都发生了变化，但 issues 清单为空。

**拟议改法：**无问题时只返回空修改清单；程序根本不向候选应用变更。因此无问题却误改其他字段的通道被移除。

### 4.3 C14：输入叫 id，输出却要求 source_unit_id

以下为实际输入与实际返回的第一项：

```json
{
  "input_source_unit": {
    "id": 1,
    "paragraph_id": 1,
    "text": "第二天也就是周日，周日中午，小廖他妈妈的朋友的同事约我们一起吃饭，说是我们结婚请我们吃个饭，反正就这意思。"
  },
  "actual_returned_source_check": {
    "id": 1,
    "comparison": "忠实依据。原文表述为'说是我们结婚请我们吃个饭，反正就这意思'，候选译文处理为'名义上是庆祝我们要结婚'，准确捕捉了原文中对此事动机的揣测与模糊定性（'反正就这意思'），未改变事实或确定性。"
  },
  "validation_error": [
    "source_checks每项必须使用字段source_unit_id并填整数；不能用输入的id代替，实际字段：['id', 'comparison']"
  ]
}
```


模型沿用了输入的 id，程序却要求它改名成 source_unit_id。

**拟议改法：**程序给原句统一编号 source_no；模型只在需要说明问题时用 source_nos 引用，不再为全部原句回填编号和比较作文。单句编号与多句引用的区别由清晰的一个示例说明，不再设置输入输出的别名转换。

原协议还能检查“返回了多少句比较说明”，新协议取消这项输出要求；程序只能确保完整原文确实送入，不能证明模型逐句理解。是否漏检，要用含遗漏与失真的样本验收，不能用一串编号证明。

## 5. 初稿生成：保留内容工作，移除程序能补的字段

C02 的当前真实响应包含 title，以及各点的 no/summary/detail。下面仅展示第一个要点：

```json
{
  "title": "出差南通的行程安排与审批",
  "points": [
    {
      "no": 1,
      "detail": "本来计划今天去南通，但因领导昨天半夜才审批通过出差申请，所以改为下午出发。该申请流程周五发起时被项目经理拒绝；周六发给项目经理后才获批；随后流转到田银伟处，因其指出承担人选错需选项目经理而退回，我重新发起了流程。",
      "summary": "出差申请经历多次退回和延迟审批导致下午出发"
    }
  ]
}
```


**拟议响应相同内容只保留：**

```json
{
  "points": [
    {
      "summary": "出差申请经历多次退回和延迟审批导致下午出发",
      "detail": "本来计划今天去南通，但因领导昨天半夜才审批通过出差申请，所以改为下午出发。该申请流程周五发起时被项目经理拒绝；周六发给项目经理后才获批；随后流转到田银伟处，因其指出承担人选错需选项目经理而退回，我重新发起了流程。"
    }
  ]
}
```


原标题由程序从输入保留，序号按数组顺序生成。模型仍决定主题怎么组织、要点有几项、正文怎样忠实表达。

## 6. 改完后哪些仍需验证

- 单对 A/B 可以去掉 UUID 查表和第三事件干扰；仍要测试模型是否误解当前两件事。
- 引文真实不等于理由成立，需逐项检查关系与事实支持。
- 局部修改限制了误改范围，仍要验证修改本身正确。
- 取消逐句比较输出降低了报告负担，需对照遗漏检出率和误改率。
- 15 对关系改为单对 A/B 至少 30 次请求，不能先承诺关系阶段提速；整体耗时需真实回放。
