# 事件关系直接承接选择与召回改造设计

日期：2026-10-27。状态：设计稿。用户已确认目标方向，本文尚未实施。

## 1. 已确认的目标

- 正式图谱中的“后续事件”表达直接承接，间接延续保留判断记录。
- 允许分支与汇合，一个事件可以有多个直接前序。
- 跨越多个日期的连接仍可直接成立，判断依据是具体事项和动作承接。
- 引发、提及分别依据自身语义判断，不参与后续链的机械裁剪。
- 本轮只完成设计，不修改代码、正式关系或历史发布状态。

## 2. 当前实现的问题

当前 Skill 入口在 `skills/diary-event-relations/scripts/workflow.py` 中执行：

1. 每个当前事件与历史事件的全部要点计算余弦相似度，取最高要点组合分作为事件得分。
2. 分数至少0.4，保留Top 6，再并入分数至少0.5的全部历史事件。
3. 当天事件完整两两配对，历史候选逐对判断。
4. 成立的事件对直接进入关系稿和正式入库。

因此Top 6不是候选上限。10月26日午饭事件召回44个历史事件，整篇形成233对历史候选和55对当天候选。该运行正式保存32条后续关系，其中20条在已发布后续图中存在其他路径。这是结构冗余的诊断结果，不是20条应删除关系的真值。

根因分为两层：召回只按相似度选事件，没有利用分支和事项进展；判断只看每对是否存在延续，没有比较竞争前序。降低K或提高阈值不能替代直接承接选择。已有10月26日召回评估还记录了Top K漏掉明确联系的问题，必须同时检查漏召回。

后端旧流程 `backend/services/graph_relations.py` 另有一套召回实现，与Skill入口的历史准入和高分保留规则不同。首版改造范围是当前实际使用的Skill入口，旧入口需明确标识其协议版本，不能宣称已同步改造。

## 3. 判断单位：事件保留，承接落实到具体内容

一个事件可以同时谈离职、出差和生日，事件标题或共享人物不能代表同一事项。

正式端点继续使用事件ID，证据继续使用要点ID。每次识别临时组织“哪一组内容在推进同一个具体事项”，并保存归组依据和所用要点。首版不新增持久化事项实体、自动聚类中心或固定单链ID。

同一要点也能含多个事实。共享要点ID只能提示存在联系，不能独立证明两条边属于同一事项链。需要核对证据片段中的对象、目标和动作。

直接承接的判断问题是：当前新行动、状态或结果，具体继续了哪个前序状态？若A→B→D已经完整表达同一进展，A→D只说明“最早也与这件事有关”，则A→D记为间接延续。

若D明确恢复A中被搁置的安排，而B推进的是另一分支，A仍可直接连接D。若D同时接续两个独立分支，两个前序都保留。

## 4. 召回：内容覆盖与前序寻找分开

### 4.1 第一层：候选池

保留现有全历史准入和来源保护，向量继续复用正式要点，新增三类召回来源：

- 语义召回：保留当前事件得分，同时按当前要点保留命中，避免只有某一个主题占满名额。记录命中要点和得分来源，合并后按真实事件ID去重。
- 明确指向补召回：从正文的具体事项、对象、日期和回忆内容定位候选，再读取正式要点核实。用户确认的对应关系可进入该通道。日期、人名匹配本身不建边。
- 关系上下文补充：读取候选附近已有的后续前序和后继，补足判断直接承接所需的链条片段。历史只有正式要点、尚无关系时，仍参加内容召回。

三类候选及加入理由分别留痕。上下文事件不是自动关系候选，不强制新增其与当前事件的全部配对。

保持跨月份历史范围。时间接近只能参与排序，不作为硬截断条件。相似度至少0.5可作为进入候选池的依据，不再等同于必须逐对独立判定的指令。

### 4.2 第二层：组织审阅上下文

围绕当前内容，把候选及必要的历史链条放在同一个审阅组中。既有关系结构用于优先组织各条分支的末端，再给出必要前序背景。

- 末端优先是阅读顺序，不是删除所有旧节点。
- 相似但不属同一事项的候选分开；不同事项即使图上连通，也不能并组。
- 对已有跨阶段直连，将其作为待核对线索，不当作直接承接的既定结论。
- 同天候选也进入分组比较，不能只优化跨日召回而保留当天逐对直连的问题。
- 一组过大时按具体事项拆分；被拆开的竞争前序仍需在选择阶段汇总比较。

首版先保留候选池覆盖，验证分组和前序选择的正确性。审阅预算的硬裁剪放在离线评估之后；未阅读或未处理的候选明确记为执行未完成，不能记成无关系或未决。

## 5. 从逐对批准改为比较选择

每组先识别当前内容的新变化及候选各自的前序状态，再比较：

1. 哪些候选确属同一具体事项？
2. 当前变化直接接续哪些状态？
3. 其他较早候选是否已经通过这些前序得到完整表达？
4. 是否存在必须保留的独立分支、恢复旧安排或明确旧事引用？

关系成立不要求时间最近；不设置每个事件最多一个前序。选中多个前序时，分别说明它们各自贡献了什么承接内容。

后续、引发、提及使用同一候选上下文，但保留不同的成立依据。明确回忆旧事且不构成直接承接或引发时，按提及表达；不能把任意跨阶段后续改名为提及来继续保留。

分组上下文可以帮助排除间接边，但正式关系的事实依据仍必须来自该边双方要点。第三事件不能替双方补出动作、因果或动机。

## 6. 全组复核与间接延续记录

完成候选选择后，程序针对“后续事件”查找新边的替代路径，并把存在替代路径的边送入复核清单。程序只标记，不自动执行传递约简。

复核逐条确认：路径各段是否推进同一具体事项、是否发生分支切换，以及直连是否另有独立承接依据。已有路径包含引发或提及边时，不能用作后续替代路径。

有替代路径不直接判冗余；没有替代路径也不证明直接边正确。缺少中间记录时，仍依据当前与历史候选的直接语义判断，不能凭“库里没有B”强行把A认作直接前序。

最终判断增加 `INDIRECT_FOLLOWUP`，与以下状态区分：

| 状态 | 含义 | 正式建边 |
| --- | --- | --- |
| RELATED | 成立的直接后续、引发或提及 | 是 |
| INDIRECT_FOLLOWUP | 属于同一事项的间接延续，直接连接无独立增量 | 否 |
| NO_RELATION | 未发现符合定义的具体联系 | 否 |
| UNRESOLVED | 已读完，但存在影响判断的事实缺口 | 否 |

间接延续记录原事件对、事项依据、所选直接前序及适用的路径证据；没有现成路径时记录语义判断理由，不伪造路径。完整稿中单独折叠展示间接延续，不能混入无关系。

首版沿用checkpoint归档判断，正式关系表继续保存现有三种关系类型。新增状态需修改Skill工作流协议、稿件解析与入库转换，不必为间接判断新建关系表。

## 7. 冻结、先后与发布

- 来源包新增实际使用的历史关系上下文、双方要点身份与内容指纹、关联版本。冻结判断使用的关系范围、邻域查询条件及成员清单；预检和发布前按相同范围重查，比较新增、删除及版本变化，防止只核对原有边而漏掉新加入的上下文关系。
- 已发布历史边必须通过当前来源有效性检查；旧运行的宽泛“后续”不能直接当作已核验的直接承接。
- 日记日期用于历史检索，具体动作先后由正文、已核验发生日期和明确叙述判断。补记昨天、多日回忆和同篇事件不能仅按记录顺序排列。
- 后续边形成环时停止并核对事实、事项归属和先后，不能为凑无环结构随意删边。
- 新发布只新增当前已确认的正式边并归档本次判断，不隐式删除历史运行中的边。
- 补录较早日记、补入中间阶段或修订历史来源后，列出受影响的已发布边，另行生成重评稿；不能声称只处理新增日记就已完成全图修复。

## 8. 验证方案

用10月24日和26日的冻结来源做第一轮对照，先人工审定少量直接／间接样例，旧版正例不能全部作为新规则的直接边真值。固定一部分样例用于设计，另留日期或事项用于验证。

必须覆盖：

1. A→B→C→D，避免把全部早期节点连到D。
2. 两条分支共同汇合到D，正确保留多个直接前序。
3. 较早安排被恢复，保留时间跨度大的真实直接承接。
4. 同一事件含多个事项，不能因事件图可达就裁掉另一事项的边。
5. 有独立证据的引发或提及，不能随后续路径被删。
6. 历史没有关系、旧边错误、只有正式要点时，召回和判断仍可工作。
7. 日记补记、同日先后、迟到的中间事件和来源修订。
8. 明确引用在语义排名较低处，仍能通过补召回进入判断。

分别报告候选池覆盖、直接前序覆盖、正式边精确性、间接边误存、分支误删、未决及未完成数，以及读取详情量、调用量与耗时。只有被标注的参照集才能计算相应准确指标；关系总量下降不是质量提升的充分证据。

对照分开进行：现有召回＋逐对判断、现有候选池＋分组前序选择、新召回＋分组前序选择。这样才能区分选边收益和召回收益，不把两项变化混成一个指标。

## 9. 实施顺序与历史数据

1. 审定直接与间接的样例，完善本设计。
2. 增加判断协议、历史关系上下文冻结和只读校验。
3. 实现分组比较、多个前序选择、间接留档和替代路径复核。
4. 增加要点覆盖及明确指向补召回，再用固定参照评估候选量和遗漏。
5. 验证通过后接入新关系稿及发布；保留旧协议查询和历史归档。
6. 单独准备既有已发布关系的重评稿，展示保留、降为间接和删除的具体变化，经用户确认后执行历史替换。

当前已发布的10月24日15条关系和10月26日35条关系保持原状。本设计不授权删除其中20条有替代路径的后续边。
