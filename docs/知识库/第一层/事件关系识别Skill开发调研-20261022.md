## 3. 业务规则怎样写进 Skill

主文件只放能改变判断的规则，详细示例放参考资料。以下是需要继承的核心标准。

| 类型 | 成立条件 | 方向 |
| --- | --- | --- |
| 后续事件 | 同一具体事项出现新的行动、状态或结果，包括有证据的计划执行 | 前序 → 后续 |
| 引发事件 | 来源明确表达一方信息、体验或结果促使另一事项发生，也包括来源自己明示的推测联系 | 触发方 → 被触发方 |
| 提及事件 | 一方明确引用、回忆、比较或联想到另一具体事件，且不构成前两类 | 提及方 → 被提及方 |

每对按核心语义选择一种关系，先检查后续，再检查引发与提及；不能只按名称或关键词套类型。共同人物、项目、主题或时间相邻不够；同一现实经历在不同日记中的事件不合并；不根据 A→B、B→C 自动生成 A→C。

本轮明确的计划边界：来源确实形成了同一具体事项的新安排时，可以将“形成安排”本身作为新状态，但关系描述必须保留为打算，不能写成已执行。09-09 的心理学恢复意愿与 09-10 利用居家空闲继续课程的具体打算，是主审采用的边界样例；仅重复目标、只共享心理学主题，仍不足以建立后续关系。这是本次主审的规则解释，不是用户逐条确认的标签。

提及必须定位另一具体事件。“比如被 AI 搞得焦虑时”这样的概括性、条件性举例，不能自动定位为另一条工作和面试不自信的具体记录。本轮逐对组生成的这条额外候选未被主审采纳。

`EXPLICIT/SPECULATIVE` 表达来源如何陈述这条联系，不是模型置信度。明确说“可能因为某人要来而怀念过去”可以形成推测性引发关系；触发因素是来访信息，不能写成后来实际聚餐造成此前的怀念。

`RELATED`、`NO_RELATION`、`UNRESOLVED` 都是有效语义结果。缺失输出、读取失败、引用非法或处理中断属于执行未完成，不能记成无关系。同一事项再次出现但无法区分新进展与重复回顾时，可以未决；后续若有明确回忆证据，再判断提及。

依据：[实体模型](个人知识图谱第一层实体模型.md)、[关系技术方案第 5—7 节](第一层事件关系识别技术方案.md)。旧[五类关系需求规格](../../需求规格/规划功能/日记事件关系图谱需求规格.md)与当前设计不同，不作为本 Skill 的类型基线。

### 3.1 以双方完整要点判断，以最小充分要点举证

先阅读双方全部 `detail`，寻找实际联系，再判断类型、方向、归属和确定程度，最后选取证据。不能只阅读召回命中的一个片段，也不能先根据相似度断言有关系。

证据需同时满足：双方都有依据、单独读所选双方要点即可理解关系、删除任何一项都会损失必要支持、描述中的关键事实有据可查。建议关系结果附双方要点序号及必要的连续原文短引，脚本核对引用确实位于相应 `detail`；引用存在不能证明结论成立。

同篇上下文可以用于查明省略或发现要点缺口，但不得用第三事件充当本对的关系证据。若关系只能靠第三事件或要点中缺失的原文事实成立，应交付具体缺口，不绕过要点发布，也不由关系 Skill 自动改写已确认要点。

CoT-ER 对少样本实体关系抽取研究了显式证据推理，可作为先找依据再判断的参考；它没有验证本项目三类事件关系，不能套用论文准确率。[CoT-ER 原论文](https://arxiv.org/abs/2311.05922)

### 3.2 澄清只解决实际事实缺口

能够从完整要点确定的直接处理；多种等价描述或措辞由 agent 判断，不逐条请用户选择。关键指代、是否同一次经历或新进展确实影响关系时，先检查已有来源与用户确认，再集中提出必要问题。

问题应定位双方事件和具体疑点。未回答、超时或默认选项均不能作为事实确认；无法解决时保留 `UNRESOLVED`。区分“来源当时明确表达的推测”和“模型自行猜测”：前者保留，后者不能据此建边。用户新增事实另记澄清来源；若超出现有要点，先经要点修订路径落地，再重新识别受影响关系。

## 4. 已确定的核心流程及程序边界

```text
定位用户与单日日记，读取有效要点运行
→ 核对来源版本、准入覆盖与向量模型
→ 冻结当天要点及本次可用历史范围
→ 程序生成当天完整比较对与跨日召回对
→ 按日构建去重事件资料及明确配对清单，过长则拆批
→ agent 读取本批完整资料，逐对判断并记录结果
→ 从双方证据核对关系，同时回看负例与未决项是否漏判
→ 程序核对清单覆盖、方向映射与证据归属
→ 交付关系稿、未决问题及处理统计
→ 已有保存授权时执行仅补关系的发布；否则保留可审阅产物
```

这是已经选定的新 Skill 工作流程；只读工具及本地交付已实现，正式入库分支现已实现，但本次未在正式库执行。实际命令及结果协议以 Skill 参考资料为准。

### 4.1 保持现有召回基线，单独验证其局限

首版候选保持：当前用户、中高重要性、历史日记日期早于当前日、同向量模型；完整 `detail` 的精确余弦相似度，阈值 `0.4`；按历史事件聚合，事件分数取双方要点组合最大值，再取前五；当天不走召回过滤，完整两两比较。保存阈值外和前五外的诊断信息时，应仅在离线评估模式扩大范围。

语义相似度只是控制比较成本，不是联系证据。10 月 15 日六个已确认正例在 `0.4` 下最终只识别五个，且开发集尚未出现达标历史候选超过五个的真实竞争，不能承诺这组参数适用于整个九月。[最小优化验收](第一层最小优化实施与验收-20261015.md)

本轮两篇内部回放中，28 个跨日组合保留 18 对，主审采用的 3 条跨日候选均被召回；其余 10 对在完整配对审阅中没有发现符合定义的关系。此结果支持暂保留基线，不能替代更长历史池的召回验收。

### 4.2 只读试跑与正式逐日发布分开

**正式模式：**当天读取 `POINTS_READY`，历史只使用已经有效发布的运行。当天全部候选取得有效结果并完成检查后，原子发布，再处理下一日。`UNRESOLVED` 不等于执行失败；可以在完整留痕的前提下完成当日，关系表只写 `RELATED`。

**只读回放模式：**允许冻结指定 `POINTS_READY` 运行作为实验输入，使用本地日程清单记录哪些较早日期已经完成模拟处理。下一天只能使用这些完成日期及指定的已发布基线，不能把未来日期提前当作历史。模拟完成不修改数据库入图标志，不声称正式发布。这样可以先测试连续九月样本，而不必为做实验先发布真实图谱。

显式冻结历史基线：已有八月有效图谱是否纳入，由测试目标决定。九月内部实验与全历史正式运行分别报告，不为了容易通过测试而静默排除八月，也不混入其他用户。

逐日是对所选有效日记的顺序约束，不要求日历每天都有记录。同日多篇若存在歧义须按 ID 定位；本项目旧流程是单日记运行，不在本次暗中扩展为跨篇同日互比，相关需求需要单列。

### 4.3 已实现的只读工具接口与后续发布边界

| 能力 | 输入与输出 | 不承担的职责 |
| --- | --- | --- |
| 来源导出与候选准备 | 用户、日记 ID／日期、运行 ID、历史基线 → 冻结快照、命中记录、待判清单 | 不生成关系结论，不调用语言模型 |
| 资料读取与补读 | 本次运行目录、批次／pair ID → 去重事件完整要点、明确配对及局部映射；必要时回查某一对 | 不只返回摘要或高分命中片段，不强制逐对重复展示全文 |
| 结果检查与汇总 | 清单、当前结果 → 覆盖情况、引用错误、逐对进度和可读稿 | 不用正则判断事项相同或因果成立 |
| 本地状态、来源复验与交付 | 冻结包及当前结果 → 待完成清单、数据库时点复验记录、关系稿及身份映射 | 不将本地完成记为正式入图 |

当前实现为 `workflow.py` 子命令和 `db_source.py` 数据库适配。导出不打印向量数组；召回在受控脚本中精确计算，agent 只读取诊断。按仓库约束使用 `backend/venv/bin/python`，加载 `.env` 时切至 `backend`；只读数据库访问出现权限错误时按网络权限流程处理，不判定数据库故障。命令用法见 [Skill 工作流说明](../../../skills/diary-event-relations/references/workflow.md)。

### 4.4 资料去重与完整读取

同一批次内事件全文只出现一次，程序维护真实 UUID 与局部标识映射，agent 根据明确配对清单逐对作答。资料应紧凑呈现，避免展示向量及重复元数据；每次仍须提供所涉事件的全部要点，不能只给命中片段。

工具显示截断与模型上下文超预算都必须显式处理：补读缺失内容或拆批，不把截断的输入当作已经读完。单对自身超预算时明确报告，不截断要点或静默漏判。当前初始显示保护值为每批 12,000 个紧凑 JSON 字符、最多 12 对；它不是 Token 预算，也不是已证明最优的批大小，实际显示仍需检查完整性。

## 5. 输出、目录与恢复建议

已采用主名 `diary-event-relations`，统一工作根目录 `diary-event-relations/`，由自身 `settings.json` 指定。路径采用 `YYYY-MM-DD/日记ID/运行名/`，不与整理或要点目录混放，不覆盖旧运行。

```text
skills/diary-event-relations/
├── SKILL.md
├── settings.json
├── references/
│   ├── examples.md       # 少量正反例及容易混淆的边界
│   ├── workflow.md       # 来源、召回、分批和运行定位
│   ├── results.md        # 结果协议、短引、修订与恢复
│   └── evaluation.md     # 冻结参照与评估方法
└── scripts/             # 工作流、数据库适配与隔离测试
```

主文件包括用途、来源、三类语义边界、证据要求、工作流程、澄清与输出、保存授权边界。schema、数据库约束和大量失败案例按需阅读，不复制整套旧设计与提示词。官方编写指南强调项目特定知识、渐进加载和真实使用迭代，支持这种组织方式。[Best practices for skill creators](https://agentskills.io/skill-creation/best-practices)

每次运行保存来源要点快照、稳定的事件／要点／运行 ID 映射、候选命中、完整待判清单、逐对结果、可读关系稿及简短运行记录。大范围任务分日执行，日内按批读取去重资料，逐对形成结果，可按批落盘恢复；不要求每次工具调用等于一次新的模型请求。当前 agent 能记得前文，因此逐对作答不能宣称实现了上下文物理隔离。

长上下文研究说明相关信息位置可能影响表现，但不能据此认定本项目串对原因已经查明。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/) 本轮严格逐对读取造成每个事件全文呈现 10 次，未观察到相应质量收益，因此选择去重资料；内容池仍出现显示截断，故保留受控拆批及补读要求，不推导为越大批越好。

机器结果已按 [结果协议](../../../skills/diary-event-relations/references/results.md) 实现：顶层绑定来源包指纹，逐对包含 `pair_id`、`status`、`reason`、`relation`；`RELATED` 的关系包含方向、类型、确定性、双方非空证据和描述，其他状态 `relation=null`。证据使用要点序号和唯一连续原文短引，程序生成并映射事件、要点 UUID 及引用位置；agent 不靠标题配对。无关系和未决保留具体理由，不强制复制双侧全文。程序定位合法不等于语义正确。

结果由 JSON 派生 Markdown 阅读稿，避免分别编辑造成不一致；用户直接修改阅读稿时须明确导入与重新校验机制，不能发布时忽略修改。记录来源与结果指纹；来源、候选清单、历史基线、规则版本变化后，不按 pair ID 单独复用旧判断。恢复只处理缺失或失效的对，执行失败不自动转为语义未决；不无限重试追求一致答案。

## 6. 复核应怎样设计

首版已选择当前 agent 判断后按来源核对；不固定为三个模型角色。两种复核模式的职责为：

| 模式 | 用途 | 能证明什么 |
| --- | --- | --- |
| 当前 agent 识别后按来源双向核对全部候选 | 首版默认方式 | 普通复核后的可观察效果；不称独立审核 |
| 独立上下文重新判断相同候选，必要时处理分歧 | 开发评估及可选质量模式 | 可测首次遗漏、误连及复核引入错误；独立性取决于实际隔离 |

开发独立盲测时，判断者读取相同冻结要点、候选清单和规则，不读取初稿、预期标签或前次结论；覆盖全部候选，不能只检查正例，否则无法发现首次漏判。实际任务中的关键争议可以另行独立复核，但不把局部复核声称为全量盲判。若可用且已获相应工作授权，可以使用独立 agent；普通执行环境没有此能力时如实说明。若使用外部 API，另行记录实际渠道、模型、参数和用量；不把宿主 agent 的隐藏配置或不可得 Token 编造进审计。

旧代码按关系描述逐字相同判断一致。本轮两组内容池的三条正例都会因此进入裁决，其中两条的结构化字段完全一致，主要是描述措辞不同。新 Skill 的审阅先看状态、类型、方向、确定性及证据是否实质一致，再核对描述中的事实、主体及计划／执行，不用字符串相等或相似度充当语义裁决。证据集合不同可能都合理，也可能暴露遗漏，仍需回到来源。此项是新 Skill 的审阅原则，不表示旧生产比较器已经修改；10 月 19 日协议的其余建议仍不能整体视为已验证。[协议改进建议](事件建图模型协议简化与事实修正方案-待确认-20261019.md)

本轮也发现“我发录音、她发分析截图”被描述成“双方发送争吵录音”的主体漂移，说明总体结论一致仍须逐项核对动作与主体。默认复核必须包括无关系项是否遗漏明确联系、正例的描述是否忠实，以及未决项缺少什么事实。

CoVe 的结果支持隔离验证过程以减少初答影响，自纠论文则表明无外部反馈的自我修正并非可靠保证；两者都未验证当前 Skill 和中文私人日记。因此独立复核是待测手段，不能充当正确性证明。[Chain-of-Verification](https://arxiv.org/abs/2309.11495)、[Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798)

## 7. 已实现的正式保存设计

已实现 `storage.py` 及固定迁移 052，采用“保留原要点运行与 UUID，仅追加关系并推进该运行至 `PUBLISHED`”的结果模型。

1. **不复制已有要点。**复用原 `graph_run_events`、`graph_event_points` 与向量，写 `graph_event_relations`、`graph_relation_evidence`。关系所属运行仍为当前日原运行，以满足现有“至少一个端点属于关系所属运行”的约束。
2. **独立记录补关系的执行。**保留已成功的要点任务及配置，不伪造原任务重新执行。采用同步短事务，不新增后台任务或租约；原 checkpoint 的 `skill_relations` 命名空间保存完整来源、所有判断、引用位置、规则／结果／完整包指纹及关系 ID。现有 `GraphTask.current_run_id` 受 task/run 复合外键约束，不能直接让新任务领取其他任务的旧运行。迁移仅扩展来源枚举，原 checkpoint 其余内容保持。
3. **如实扩展结果来源。**正式 `final_source` 新增 `SKILL_AGENT`，完整来源 `SKILL_AGENT_REVIEW` 留在 checkpoint，显式写入命令绑定完整包指纹。不要将用户确认写成 `AGREEMENT` 或 `ADJUDICATED`，也不要将任意 agent 复读标成独立盲判。固定迁移已交付，浏览接口对该字段没有旧枚举限定。
4. **保留原有来源指纹。**先按原要点导入作用域核对来源，再另存关系任务的要点内容及身份指纹。不能覆盖 `GraphRun.source_sha256` 来迁就新发布入口。
5. **短事务原子发布。**重新核对用户、来源修订、要点身份和完整内容、历史运行有效性、候选与结果覆盖；锁定相关运行，写关系与证据，更新当日事件入图标志和 `published_at/status`。没有识别出边的日期也应可正常发布事件。提交前失败全部回滚，原运行保持 `POINTS_READY`。
6. **并发与恢复单列验收。**关系记录若独立于 `GraphTask`，旧任务的用户级活动唯一索引不会自动保护它；必须明确与原整理、分析、图谱任务的共同互斥规则。仅在新脚本里加一把旧入口不遵守的锁不能声称解决并发。重复同包返回原结果，提交结果未知先查状态；已发布后修订属于重建，不暗中覆盖。

该路径不改日记分析状态，不重新调用旧全流程发布函数；可以抽取共享的纯校验与关系写入逻辑，但不能复制旧流程后删除几段就默认具有相同事务保证。[当前模型与约束](../../../backend/models/graph.py)、[旧发布代码](../../../backend/services/graph_publish.py)、[当前浏览查询](../../../backend/routers/graph.py)

本轮已完成识别和入库工具开发、隔离 PostgreSQL 迁移／发布测试及正式来源只读预检，没有在正式库执行迁移或发布。未来用户已明确授权当前结果保存时沿用授权，不人为增加逐条或逐日重复确认。

### 8.1 已完成的首轮实验

三个独立 subagent 使用 09-09、09-10 的 11 个准入事件、83 条正式要点，按相同规则判断全部 55 对。一个严格逐对读取，另外两个分别读取去重内容池与配对清单，均未看到其他组答案或主审参照。主审另外核对来源；结构检查三组均无缺失、重复、非法端点或要点编号。

| 方式 | 输出 | 观察 |
| --- | --- | --- |
| 严格逐对读取 | 4 条关系、1 对未决、50 对无关系 | 额外产生 P13 提及候选，主审认为缺少唯一指向而未采纳；全文重复读取较多 |
| 去重内容池一 | 3 条关系、1 对未决、51 对无关系 | 与另一内容池组的状态、类型和方向一致；首次展示截断后补读 |
| 去重内容池二 | 3 条关系、1 对未决、51 对无关系 | 与另一组有描述、证据取舍差异，主审修正了一处主体措辞；首次展示截断后补读 |

主审最终采用三条后续关系：尝试恢复心理学课程→形成居家继续学习的打算；与颂梅争执及沟通→继续共同复盘；想恢复心理学却缺少推动办法→形成居家学习的新安排。第一、第三条分别引用不同前序事件，指向同一个后续事件，均未将打算写成已执行。另有一对同日恢复状态缺少先后依据，保留未决。[关系结果及双方证据](../../验证/事件关系Skill实验-20260909至0910-20261022/关系结果.md)

这些是主审依据来源采用的实验候选，不是用户逐条确认的真值。涉及学习计划的边界已预先标为争议范围，后续裁决不用于反向宣称实验准确率。两组内容池的大体一致也不是独立的正确性证明。

本轮未复现旧 Qwen 生产 API，没有验证正式 Skill 的自动触发效果或“有 Skill／无 Skill”收益；未覆盖引发、提及的已采用正例、长历史池、正式入库事务及恢复。执行耗时起止不完全一致，不能据此宣称稳定加速倍数。详见[完整报告及局限](../../验证/事件关系Skill实验-20260909至0910-20261022/实验报告与方案选择.md)。

### 8.3 把召回和判断分开测

| 环节 | 方法及指标 |
| --- | --- |
| 召回 | 参照范围完整配对作对照；计算确认正例进入 `0.4+前五` 的比例，区分低于阈值与被前五截掉；按实际部署向量模型冻结输入 |
| 判断 | 将固定候选给不同执行方式；记录误连、漏判、未决，以及类型、方向、确定性、描述和证据是否正确 |
| 端到端 | 另算从全部已确认关系到最终正确关系的比例；不能只报告“候选内准确率”掩盖召回遗漏 |
| 复核 | 记录修正了哪些首次错误、保留了哪些错误、引入了哪些新错误；不能只报告两次一致率 |
| 工程 | 候选是否全覆盖、重复／额外结果、重名事件、跨用户端点、失效来源、失败恢复、并发与事务回滚 |
| 成本 | 实际工具调用、输入规模、可取得的 Token 与耗时；宿主不可取得的数据记未知，不与 API 成本混算 |

对于 20—30 事件的小样本，全配对规模为 190—435 对；可分日分对审阅，不将整个样本一次塞入模型。召回对照必须包含未被系统召回的事件对，否则无法评价漏召回。新旧判断对照则使用同一候选集合，避免混入检索变化。

官方评估指南建议在干净上下文用真实任务比较有 Skill 和无 Skill 的结果，并依据可观察产物评判；本项目应同时做“不带新 Skill 的相同 agent”对照及旧 A/B/C 的历史基线核对，记录环境差异，不能混称单变量实验。[Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills)

### 8.4 必测边界及建议验收门槛

边界包括：计划执行、新进展与重复回顾、明确回忆、推测性引发、触发来自事件局部信息、标题不同但内容有联系、同人同项目却无关系、发生日期与日记日期不同、指代不明、相同标题、第三事件污染、已有关系不传递，以及空候选／无关系日期。

建议工程门槛：全部计划对都有有效结果；用户隔离、证据身份和来源失效拦截必须通过；恢复不重复写关系、不改变已有要点；部分失败不发布当日半套结果。语义门槛应对冻结参照逐项报告，已知关键正例漏判或关键负例误连不得被总体百分比掩盖；小样本没有出现错误也只说明该范围通过，不声称通用可靠。

继续对高风险核心样例重复执行并互换双方展示顺序，再看保留集；不一边读测试标签一边修改答案。正式验收门槛应在补充参照后冻结，不能用首轮试跑或判断一致率宣称整体准确率达标。
