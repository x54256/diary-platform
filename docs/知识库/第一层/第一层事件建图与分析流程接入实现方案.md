# 第一层事件建图与分析流程接入实现方案

更新日期：2026-10-14。

状态：实现方案草案。第1节为用户已确认的业务边界，其余章节为据此提出的实现设计，待审阅。本文不代表代码、迁移或数据库清理已经执行。

## 1. 已确认的业务边界

1. 本期包含事件要点、要点向量与事件之间的关系。
2. 正式流程全自动；人工原文审阅用于开发验证和验收。
3. 建图作为日记分析流程的开始。已整理日记可以触发分析。
4. 图谱只处理中、高重要性事件；有效重要性优先取用户设置，否则取AI设置。
5. 后续日记分析继续使用来源事件内容，图谱要点不替换其输入。
6. 当天完整分析成功后，图谱与分析结果一起正式生效。
7. 重新分析时，旧图谱结果标记过时，重新执行完整流程。
8. 历史日记通过Swagger接口指定日期范围，按日记日期逐日入图，复用已有分析结果。
9. 首版按时间顺序使用，不设计补录较早日期后重建或修复后续日期的流程。
10. 用户已完成数据备份；实施时直接删除旧知识库专属数据，旧知识沉淀和事项管理方案退出运行，不增加程序备份步骤。

当前依据为[实体模型](个人知识图谱第一层实体模型.md)、[要点提取方案](第一层事件要点提取技术方案.md)、[要点数据库设计](第一层事件要点数据库设计.md)及[事件关系识别方案](第一层事件关系识别技术方案.md)。配套文档已同步新分析准入、全自动处理及A/B共用v4提示规则。具体实现建议分别见[完整数据库设计](第一层事件图谱数据库完整设计.md)、[任务与接口设计](第一层建图任务与接口详细设计.md)、[分析接入与清理设计](第一层分析接入与旧方案清理详细设计.md)。

### 2.2 后续日记分析的职责

建图和后续分析读取同一次任务冻结的来源数据。中、高重要性筛选只规定本期图谱的准入范围，不据此改变后续分析的事件范围。

现有情绪与标签、核心分析、认知分析、行动项处理是需要逐项核对的既有能力。实现时重审其输入与保存接口，不能仅把旧流水线当作黑盒接在建图后面。

当前代码存在普通分析和反馈分析两个分支。两者都必须经过同一建图前置流程；反馈如何影响后续分析仍由其业务规则决定，不能绕过重分析时的图谱过时和重建处理。

当前标签和分析结果分别提交。接入时将正式保存收口到同一个发布事务，阶段函数返回结果或保存过程记录，不独立提交正式业务数据。

## 3. 两种入口共用一个建图子流程

### 3.1 日记分析入口

```text
校验用户、日记状态和整理结果
→ 创建任务，冻结本次来源和模型配置
→ 重分析时将旧图谱标记过时
→ 执行建图子流程
→ 执行后续日记分析
→ 检查来源和结果完整性
→ 短事务统一发布
→ 返回完成状态
```

### 3.2 历史入图入口

```text
接收起止日期，生成按日期排序的日记ID清单
→ 逐日读取正文与已有分析状态
→ 执行同一个建图子流程
→ 短事务发布当天图谱
→ 成功后处理下一日
```

日期清单用于调度，不提前加载所有日期正文。历史接口只处理已经完成分析的日记，不重新执行日记分析。已具有有效图谱的日记跳过；某一天失败则停止，保留此前成功日期，重试从失败日期继续。

### 3.3 子流程步骤

| 步骤 | 输入与输出 |
| --- | --- |
| 准备来源 | 冻结日记日期、来源事件ID、原标题、完整正文及有效重要性；筛选图谱准入事件 |
| 要点生成与核验 | 按冻结基线逐事件生成、审核修正及独立复核，保存最终合法候选与全过程 |
| 要点向量 | 对全部候选要点的完整 `detail` 生成同模型版本的1024维向量 |
| 候选发现 | 当前日完整两两比较；历史语义召回按事件聚合，阈值0.5，每个当前事件最多5个历史候选 |
| 关系判断 | A、B独立处理全部候选事件对；分歧交给C；程序校验覆盖、方向与双方证据 |
| 整体检查 | 所有准入事件处理完成、向量准备完整、计划事件对全部得到有效最终结果 |
| 返回候选 | 返回要点、向量、关系及判断记录，等待所属入口发布 |

当天事件全部完成要点核验后再判断关系。历史候选只读取当前用户、较早日记日期、已经正式发布且有效的图谱结果。

没有准入事件时返回合法空图谱；没有候选事件对时不调用关系模型。`UNRESOLVED` 表示业务证据不足，是合法判断记录，不生成图谱边；调用失败、缺失结果和无效结构属于执行失败。

发生日期未知时保留为空，不使用日记日期代替。本期不增加独立发生日期提取模型；后续若增加该能力，另行定义提取与核验方案。

| 阶段 | 提示来源 | 版本或字段 | 调用规则 |
| --- | --- | --- | --- |
| 要点生成 | [event_point_baseline.json](../../../backend/scripts/fixtures/event_point_baseline.json) | `event-points-final-20261013-thinking`，`prompts.generate` | 包含固定真实案例，接收原标题及完整有序正文 |
| 要点审核修正 | 同一要点快照 | `prompts.combined` | 同次请求审核输入候选并返回完整修正版；最多两轮 |
| 修正版独立复核 | 同一要点快照 | `prompts.review` | 发生修正后另起请求复核 |
| 关系判定A | [layer1_relation_batch_prompt_v4.txt](../../../backend/scripts/fixtures/layer1_relation_batch_prompt_v4.txt) | A v4 | 判断全部候选事件对 |
| 关系盲判B | [layer1_relation_batch_prompt_v4.txt](../../../backend/scripts/fixtures/layer1_relation_batch_prompt_v4.txt) | 与A完全相同的v4 | 独立判断全部候选对，不接收A输出，不追加B专属指令 |

快照中的 `prompts.repair` 为合并修正规则的留存文本，不是正常流程的独立调用阶段。结构重试使用原阶段提示，并保存追加的前次输出及具体结构错误。向量模型接收完整detail，不增加自然语言提示。

要点快照自带四份提示的 `prompt_sha256`，已核对其与实际文本一致。关系提示当前文件指纹如下，实施时用于基线核对：

## 4. 数据存储与过时状态

重新分析需要保留旧结果，因此正式要点必须属于一次建图运行，不能继续只按 `(event_id, no)` 唯一。

建议采用四张正式主体表，另以graph_relation_evidence保存可验证外键的双方证据；graph_tasks与graph_model_calls保存调度和调用审计。完整字段、约束及索引见[完整数据库设计](第一层事件图谱数据库完整设计.md)，共七张表。

| 表 | 职责及主要约束 |
| --- | --- |
| `graph_runs` | 保存所属用户、日记、任务、入口类型及建图运行状态；关联分析轮次；每篇日记至多一个有效已发布运行 |
| `graph_run_events` | 保存本次运行纳入的来源事件、可空发生日期；`(run_id, event_id)` 唯一 |
| `graph_event_points` | 保存运行ID、来源事件ID、序号、summary、detail、向量及模型标识；`(run_id, event_id, no)` 唯一 |
| `graph_event_relations` | 保存所属运行、双方事件及运行、关系类型、确定性、描述与双方要点ID；同次运行的无序事件对至多一条关系 |

要点序号在每个运行的事件内保持 `1..N` 连续。关系证据引用实际要点ID，并检查这些要点属于对应端点事件与运行；历史证据固定到实际参与判断的运行。

运行状态为 `QUEUED`、`RUNNING`、`FAILED`、`PUBLISHED`、`OBSOLETE`、`SKIPPED`，任务状态及转换见[任务与接口设计](第一层建图任务与接口详细设计.md)。执行阶段与正式有效性分开表达：过程记录用于恢复，只有 `PUBLISHED` 的正式数据进入图谱查询和召回。

沿用 `diary_events.is_in_graph` 作为当前有效入图标志。它与运行状态在发布或标记过时的同一事务中维护；该字段不承担版本和任务进度。

任务创建成功时，重新分析对应日记的旧已发布运行改为 `OBSOLETE`，清除其事件的有效入图标志。引用该过时运行的关系从有效查询中排除，不删除证据，不启动后续日期修复。新运行失败不会恢复旧运行有效性。

有效关系查询同时检查关系所属运行及双方端点运行。仅检查关系所属日期或单个事件入图标志不足以防止使用过时证据。

生成候选、审核报告、召回命中、A/B/C原始输出、完整请求及提示和模型快照保存为任务过程记录。正式发布前不把候选写入正式要点和关系表。成功后保留审计资料，临时恢复状态按独立清理策略处理。

## 5. 发布事务

日记分析发布时，一次短事务完成：

1. 锁定所属日记与本次任务，检查任务执行权、来源快照和发布状态。
2. 写入本次图谱运行的事件、完整要点、向量与关系。
3. 写入本次分析轮次、标签和行动项等后续分析正式结果。
4. 设置图谱运行已发布、事件有效入图、日记分析完成和分析任务完成；历史任务只在日期清单全部处理后完成。

历史接口发布只执行图谱相关写入和本次任务状态更新，不改写已有分析内容。

模型调用和向量请求全部在事务之外。发布前重新检查历史端点运行仍然有效；已过时则阻止发布并报告依赖变化，不能保存已失效证据。

同一任务重复进入发布时，先识别已经提交的运行，直接返回已有结果。事务提交后进程退出的恢复也必须走这一幂等检查，不重复创建要点、关系、分析轮次或行动项。

## 6. 任务与失败恢复

每个用户同一时刻只执行一个会改变图谱的任务；历史批量任务按日期串行。这一约束用于保证历史候选范围稳定。

新分析入口和历史入口共用任务执行、状态查询及恢复能力。graph_tasks作为统一调度依据；普通和反馈分析保留organize_tasks兼容状态投影，历史入口只创建graph_tasks。移除旧沉淀与升级任务类型，具体事务与恢复规则见任务接口设计。

| 失败位置 | 重试范围 |
| --- | --- |
| 单事件要点处理 | 恢复已成功阶段，只重新处理未完成事件或阶段 |
| 向量生成 | 复用同一冻结模型下已合法保存的结果，补齐失败要点 |
| 语义召回 | 重新执行失败事件的召回；不能将检索失败视为无关系 |
| A/B/C判断 | 保留结构有效的逐对结果，按已确认方案补判缺失或无效项 |
| 后续日记分析 | 复用已完成建图候选，恢复失败分析阶段 |
| 正式发布 | 只重试发布事务，复用前序结果 |
| 历史日期批量处理 | 保留已发布日期，继续失败日期及剩余日期 |

失败重试继续使用同一任务、来源快照及冻结配置。用户重新点击“重新分析”创建新运行，与恢复失败任务是两种操作。模型内部结构重试次数沿用已冻结方案，不因用户重试而覆盖原始失败记录。

来源在任务期间发生变化时，阻止继续发布，记录明确错误。运行期间通过任务锁定避免并发修改；不增加来源内容版本管理业务。

## 7. 接口契约草案

| 接口 | 职责 |
| --- | --- |
| 日记分析接口 | 创建包含建图前置步骤的分析任务；已分析日记再次调用执行完整重分析 |
| `POST /graph/history-build` | 接收起止日期，创建当前用户的历史入图任务，返回任务ID |
| `GET /graph/tasks/{task_id}` | 查询当前日期、阶段、完成日记数、失败原因与执行状态 |
| `POST /graph/tasks/{task_id}/retry` | 恢复失败任务，复用冻结输入及已成功阶段 |
| 图谱结果查询接口 | 按日记读取有效运行、事件要点和事件关系；历史运行按运行ID单独查询 |

接口采用异步任务，创建后立即返回，不让Swagger请求等待整段日期处理完成。日期范围校验起止顺序、用户归属及日记状态；日期无日记时跳过，未分析日记记录NOT_ANALYZED跳过原因。具体请求、响应、错误码及查询路径见任务接口设计。批量任务记录按日的处理结果，不把失败计为成功或跳过。

## 8. 旧数据删除

用户已完成数据备份，不开发程序备份或备份核验功能。本节为实施要求，不在设计阶段执行。

1. 列出旧知识库表、模型配置、任务恢复数据及其外键依赖，核对共享数据边界。
2. 停止旧任务，确保清理时无旧任务继续写入。
3. 执行新迁移，删除旧知识库专属表和配置，创建新图谱结构。
4. 部署移除旧入口及后台任务的新代码，验证无残留运行依赖。

迁移不得使用不受控的级联删除。源日记、已有分析、标签、日程、搜索数据和共享模型凭据不属于旧知识库数据删除范围。

### 8.1 数据库操作的位置与责任

| 操作 | 文件或执行位置 | 对应任务 |
| --- | --- | --- |
| 数据库扩展及服务端依赖准备 | PostgreSQL所在服务器或数据库容器；检查目标数据库扩展可用性 | T03设计和隔离验证、T15目标环境检查 |
| 建表、字段、约束、索引、注释及启用扩展 | 新增 `backend/migrations/` SQL迁移文件，在目标PostgreSQL数据库执行 | T03编写和隔离验证、T15正式执行 |
| 删除旧知识库表及专属配置 | 经审阅的新SQL迁移文件，在目标数据库执行 | T15 |
| 业务数据读取、要点与关系写入、过时标记 | 后端服务使用数据库会话执行 | T06至T13 |

模型声明不代替数据库迁移，应用Docker镜像构建不代替数据库服务器依赖安装。T03必须列出数据库前置依赖及实际执行方式，T15必须记录目标数据库执行结果。

本期图谱候选发现采用要点detail向量的纯语义召回，数据库依赖包含pgvector，不增加中文分词或关键词召回。中文分词属于另行定义的关键词检索能力；若后续纳入范围，必须分别设计服务端依赖、数据库分词配置、索引、数据重建和查询接入，不能只增加一个扩展就视为完成。
