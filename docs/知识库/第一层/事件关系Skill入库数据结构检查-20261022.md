## 1. 结论

**形成关系和证据所需的事实与身份信息已经足够，不需要重新识别关系；但当前文件不是可直接提交的完整入库包，现有数据库约束也不能原样接收 Skill 来源。**

判断“足够”以整个运行目录为单位：`source.json`、`results.json`、`resolved-results.json` 和运行清单共同提供身份、候选、结论及证据。单独拿 `resolved-results.json` 不够，它没有顶层用户、当前所属运行及负例端点。

需要补齐的是最终稿绑定、正式结果来源适配及完整判断归档，而不是让 agent 重新输出一遍经历或 UUID。入库流程的原子提交、执行记录和重试也仍需实现，不能与信息是否齐全混为一谈。

## 3. 已确认的结构缺口

### 3.1 Skill 来源不能直接映射现有 `final_source`

正式表 `graph_event_relations.final_source` 是 `VARCHAR(16)`，检查约束只接受 `AGREEMENT`、`ADJUDICATED`。当前本地 `review_origin=SKILL_AGENT_REVIEW` 既不在枚举内，长度也为 18，不能直接写入。

建议为正式字段增加符合长度的 Skill 来源代码，例如 `SKILL_AGENT`，并在执行审计中保留完整来源和实际核对方式；或者明确扩大字段及枚举。无论选择哪种，都须固定迁移及一致的应用模型，不能冒充旧双判一致，也不能只改 JSON 值绕过约束。

### 3.2 缺少绑定最终修订稿的结果指纹

现有 `package_sha256` 绑定来源事件、候选清单、规则和配置。对同一任务执行 `record --replace` 可以改变结论而保持这个输入包指纹不变。`verification.json` 也只绑定输入包和来源时点，不表示某一版结论已经被确认保存。

入库包应增加由程序计算的 `results_sha256`，绑定本次完整规范化结果；版本应覆盖来源包指纹、结果协议版本及实际结果内容。已有回放依赖的 `results_sha256` 不能代替当前日最终稿的指纹。

保存以这一版本做幂等与变更核对；用户已明确授权保存当前稿时直接沿用授权，不引入逐条重复确认，也不把指纹本身当作授权。关系 ID 和提交时间在首次实际保存时分配，重试复用，不要求 agent 编造。

### 3.3 入库接口的输入边界尚未确定

当前 `resolved-results.json` 顶层没有 `schema_version/user_id/current_run_id/diary_id`；无关系和未决条目也只含 `pair_id/status/reason/relation=null`，两端身份仍依赖来源包的 `pairs/events`。

可以二选一：

- 入库器接收整个运行目录，验证文件版本、指纹和派生关系，按来源包恢复全部身份。
- 程序导出独立且完整的入库包，包含用户、当前运行、来源包指纹、最终结果指纹、协议版本、双方真实端点及证据身份，并保留必要的来源引用。

建议第二种作为正式保存边界，继续让 agent 只生成局部标识的语义结果。入库包由程序从已核验运行目录导出，不让模型填写用户归属、运行身份或审核状态。若独立包仅保留文件路径，必须同时绑定文件内容，不能把路径当作不可变证据。

### 3.4 完整判断与短引审计需确定持久化位置

当前关系表只存 `RELATED`，证据表只指向要点，不存 `reason/quote/offset`。`NO_RELATION/UNRESOLVED` 以及逐对判断理由都保存在本地，直接只插入三条边会失去“这一天完整处理过哪些对”的记录。

需要在数据库中保留本次来源、候选、全部逐对结果、最终指纹及真实核对来源。可在保留原要点状态的前提下使用运行 checkpoint 的独立命名空间，或使用另行设计的关系执行记录；不一定要新建负例表，也不需要在关系表制造“无关系边”。已有旧 checkpoint 的用途和新记录的恢复规则必须明确。

短引信息可随上述审计 JSON 保存，当前 `graph_relation_evidence` 的要点级外键结构已经足以表达正式证据归属，不必为第一版强行增加引文列。若要持久化精确位置，应明确 `offset` 是 Python 字符串索引的 Unicode 码点位置、起点为 0，可另存终点或长度，并绑定对应详情内容指纹，避免被误解成 UTF-8 字节偏移。

## 5. 数据之外仍须实现的入库规则

- 不能直接调用[旧发布函数](../../../backend/services/graph_publish.py)：它会再次插入已经保存的运行事件和要点，应实现复用要点的仅补关系路径。
- 不能把本地 `replay` 完成当成历史已发布。正式接续时按日期原子发布，提交时复核历史端点的有效状态。当前包记录了 `history_mode` 和依赖，信息已经存在，但保存器仍需执行这项检查。
- 已发布运行的再次保存、同包重试、结果修订、并发任务和提交结果未知需要明确策略；当前唯一约束不足以自动提供业务幂等。
- 独立的关系执行若复用现有任务模型，需处理 `GraphTask.current_run_id` 与任务／运行的复合外键，不应重开已成功的要点任务来伪造执行过程。
- 来源时点复验不能代替提交事务中的锁定与再检查；检查通过后仍可能变化。

这些属于入库流程和执行模型的实现缺口。无需因此增加新的关系业务字段、重新生成要点或让模型承担数据库身份维护。
