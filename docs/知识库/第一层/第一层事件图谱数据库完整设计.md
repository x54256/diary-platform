# 第一层事件图谱数据库完整设计

更新日期：2026-10-14。状态：可供实现评审的设计草案，尚未编写或执行正式迁移。

业务边界以[流程接入方案第1节](第一层事件建图与分析流程接入实现方案.md)为准。本文确定数据库实现建议，不把建议标为用户已逐项确认。

## 1. 存储划分

采用七张表：`graph_tasks`、`graph_runs`、`graph_model_calls` 保存执行与审计；`graph_run_events`、`graph_event_points`、`graph_event_relations`、`graph_relation_evidence` 保存正式结果。

运行的冻结来源及恢复状态分别存于 `graph_runs.source_snapshot`、`graph_runs.checkpoint`，不新增候选表。每次调用单独保存以避免重试覆盖历史响应。关系证据明细独立成表，使每条证据具有真实外键，并能验证事件与运行归属。

以下全部 `id` 使用UUID主键，默认 `gen_random_uuid()`；时间字段使用TIMESTAMPTZ，默认当前UTC时间；业务日期使用DATE。必填文本同时检查非空白。外键默认RESTRICT，过程及正式结果不随源事件级联删除。JSONB对象、数组按字段声明增加类型检查。

## 2. 任务表 graph_tasks

| 字段 | 类型及可空性 | 含义 |
| --- | --- | --- |
| id | UUID，必填 | 任务ID |
| user_id | UUID，必填，引用users | 所属用户 |
| environment | TEXT，必填 | 执行环境，只用于任务领取 |
| entry_type | TEXT，必填 | ANALYSIS或HISTORY |
| organize_task_id | UUID，可空，引用organize_tasks，唯一 | ANALYSIS入口的兼容任务记录；HISTORY为空 |
| status | TEXT，必填 | QUEUED、RUNNING、SUCCEEDED、FAILED、SUPERSEDED |
| date_from、date_to | DATE，必填 | 包含起止日期；ANALYSIS为同一天 |
| current_run_id | UUID，可空 | 当前处理的运行；建表后增加引用graph_runs的外键 |
| available_at | TIMESTAMPTZ，必填 | 可领取时间 |
| lease_until | TIMESTAMPTZ，可空 | 领取租约 |
| run_token | UUID，可空 | 当前执行令牌 |
| retry_count | INTEGER，必填，默认0 | 用户恢复次数，非负 |
| config_snapshot | JSONB对象，必填 | 模型、渠道标识、提示全文与指纹、预算及召回参数；不含密钥 |
| error_code、error_message | TEXT，可空 | 最后一次失败 |
| created_at、updated_at | TIMESTAMPTZ，必填 | 创建和最后更新 |
| started_at、completed_at | TIMESTAMPTZ，可空 | 执行起止时间 |

约束：`date_from <= date_to`；入口与兼容任务关系满足 `(ANALYSIS且organize_task_id非空)或(HISTORY且为空)`；状态限定上述枚举。建表后增加复合外键 `(current_run_id,id)→graph_runs(id,task_id)`，确保游标属于该任务。

索引：`user_id`上的部分唯一索引，条件 `status IN ('QUEUED','RUNNING')`，跨环境限制同用户活动任务；领取索引 `(environment,status,available_at,created_at,id)`；查询索引 `(user_id,created_at DESC,id DESC)`。

## 3. 运行表 graph_runs

一行对应任务清单中的一天日记。批量任务创建时只保存ID和日期，正文在该日被领取后读取。

| 字段 | 类型及可空性 | 含义 |
| --- | --- | --- |
| id | UUID，必填 | 本轮运行ID |
| task_id | UUID，必填，引用graph_tasks | 所属任务 |
| user_id | UUID，必填，引用users | 所属用户 |
| diary_id | UUID，必填，引用diaries | 来源日记 |
| diary_date | DATE，必填 | 创建任务时确认的来源日期 |
| source_organized_id | UUID，可空，引用diary_organized | 该日准备来源后填写 |
| analysis_run_id | UUID，可空，引用analysis_runs | ANALYSIS为发布新轮次；HISTORY为冻结已有有效轮次 |
| analysis_mode | TEXT，可空 | ANALYSIS为ordinary或feedback；HISTORY为空 |
| status | TEXT，必填 | QUEUED、RUNNING、FAILED、PUBLISHED、OBSOLETE、SKIPPED |
| current_step | TEXT，可空 | 工作流阶段枚举，见任务与接口设计 |
| source_snapshot | JSONB对象，可空 | 完整冻结来源；准备成功后非空 |
| source_sha256 | TEXT，可空 | 来源规范化JSON的SHA-256，与snapshot同时有值 |
| checkpoint | JSONB对象，必填，默认{} | 候选、游标、有效逐对结果及后续分析产物 |
| error_code、error_message | TEXT，可空 | 当日失败信息 |
| skip_reason | TEXT，可空 | ALREADY_PUBLISHED或NOT_ANALYZED |
| created_at、updated_at | TIMESTAMPTZ，必填 | 运行记录时间 |
| published_at、obsolete_at | TIMESTAMPTZ，可空 | 发布、过时时间 |

唯一约束：`(task_id,diary_id)`；`(id,user_id)`、`(id,task_id)`供复合外键；`(user_id,diary_id)`的部分唯一索引，条件 `status='PUBLISHED'`。只允许一份当前有效结果。

其他检查：SHA为64位十六进制；PUBLISHED与OBSOLETE必须已有published_at；OBSOLETE必须有obsolete_at；SKIPPED必须有skip_reason。发布时检查本轮日记用户归属、分析轮次日记归属和来源日期未变化。

SKIPPED是批量调度记录，不代表已形成新图谱。QUEUED运行允许来源为空；无法准备来源的失败运行也允许为空，因此不用数据库条件要求所有FAILED均具有快照。

索引：`(task_id,diary_date,id)`用于有序调度；`(user_id,diary_date,id) WHERE status='PUBLISHED'`用于历史召回。UUID破同日排序只用于确定遍历顺序，不作为业务先后。

## 4. 模型调用表 graph_model_calls

| 字段 | 类型及可空性 | 含义 |
| --- | --- | --- |
| id | UUID，必填 | 调用ID |
| task_id | UUID，必填，引用graph_tasks | 所属任务 |
| run_id | UUID，必填，引用graph_runs | 所属日期运行 |
| stage | TEXT，必填 | POINT_GENERATE、POINT_COMBINED、POINT_REVIEW、EMBEDDING、RELATION_A、RELATION_B、RELATION_C及分析阶段 |
| unit_key | TEXT，必填 | 稳定事件、要点或批次键 |
| attempt_no | INTEGER，必填 | 同stage与unit_key内从1递增的实际服务请求次数 |
| status | TEXT，必填 | STARTED、SUCCEEDED、FAILED、UNKNOWN |
| request_snapshot | JSONB对象，必填 | 完整提示、业务输入、模型参数、预算；去除认证头 |
| response_text | TEXT，可空 | 原始响应，不覆盖前次响应 |
| parsed_result | JSONB，可空 | 解析结果 |
| validation_errors | JSONB数组，必填，默认[] | 程序检查结果 |
| input_tokens、output_tokens、reasoning_tokens | INTEGER，可空 | 渠道提供的非负Token计数 |
| error_code、error_message | TEXT，可空 | 调用错误 |
| created_at、completed_at | TIMESTAMPTZ | 创建必填，完成可空 |

唯一约束 `(run_id,stage,unit_key,attempt_no)`；复合外键 `(run_id,task_id)→graph_runs(id,task_id)`确保调用归属一致；索引 `(task_id,created_at,id)`、`(run_id,stage,unit_key)`。创建调用记录和实际请求分开：进程在请求后崩溃但无响应落库时记UNKNOWN，不能假设模型执行成功。

后续分析调用也接入同一审计契约；已有LLM日志作为运维日志保留，模型调用表为恢复与审计依据。向量调用无语言提示，request_snapshot明确记录完整detail与模型参数。

## 5. 正式事件和要点

### 5.1 graph_run_events

字段：`run_id UUID`、`event_id UUID`、`user_id UUID`均必填；`source_order INTEGER`必填且非负；`occurred_on DATE`可空。主键 `(run_id,event_id)`；唯一 `(run_id,event_id,user_id)`；外键 `(run_id,user_id)→graph_runs(id,user_id)`、`event_id→diary_events(id)`。正式保存时检查事件所属日记等于运行diary_id。

没有独立事件UUID，来源event_id就是图谱事件身份。发生日期无已核验来源时为空，本期不增加日期提取调用。

### 5.2 graph_event_points

| 字段 | 类型及可空性 | 含义 |
| --- | --- | --- |
| id | UUID，必填 | 固定证据身份 |
| run_id、event_id、user_id | UUID，必填 | 所属运行、来源事件和用户 |
| no | INTEGER，必填且大于0 | 该运行该事件的连续序号 |
| summary、detail | TEXT，必填且非空白 | 要点标题与详细内容 |
| embedding | VECTOR(1024)，必填 | 完整detail的向量 |
| embedding_model | TEXT，必填且非空白 | 模型及版本稳定标识 |
| created_at | TIMESTAMPTZ，必填 | 正式写入时间 |

唯一 `(run_id,event_id,no)`；唯一 `(id,run_id,event_id,user_id)`供证据复合外键；外键 `(run_id,event_id,user_id)→graph_run_events`。序号连续由正式保存程序检查，数据库唯一约束只防重复。

本方案正式保存前已完成向量准备，正式表向量必填；未完成向量的候选保存在checkpoint。复合唯一索引已支持按运行和事件读取，不重复建单列run_id索引。首版精确检索不建HNSW或IVFFlat。

## 6. 正式关系和证据

### 6.1 graph_event_relations

| 字段 | 类型及可空性 | 含义 |
| --- | --- | --- |
| id | UUID，必填 | 关系ID |
| run_id、user_id | UUID，必填 | 本次产生关系的运行与用户 |
| source_run_id、source_event_id | UUID，必填 | 起点所属运行与来源事件 |
| target_run_id、target_event_id | UUID，必填 | 终点所属运行与来源事件 |
| pair_event_low、pair_event_high | UUID，生成列 | 两端事件ID的LEAST与GREATEST，作为无序事件对键 |
| relation_type | TEXT，必填 | 后续事件、引发事件、提及事件 |
| certainty | TEXT，必填 | EXPLICIT或SPECULATIVE |
| description | TEXT，必填且非空白 | 忠实关系描述 |
| final_source | TEXT，必填 | AGREEMENT或ADJUDICATED |
| created_at | TIMESTAMPTZ，必填 | 正式写入时间 |

唯一 `(run_id,pair_event_low,pair_event_high)`；唯一 `(id,user_id,source_run_id,source_event_id,target_run_id,target_event_id)`供证据引用；检查两端事件不同、至少一端run_id为关系所属run_id。外键 `(run_id,user_id)→graph_runs`，两端 `(端点run_id,端点event_id,user_id)→graph_run_events`。

索引 `(user_id,source_event_id)`、`(user_id,target_event_id)`支持关系查询。模型relation方向原样映射为源和目标，不按LEAST/GREATEST或日期改写方向。

### 6.2 graph_relation_evidence

字段：`relation_id`、`user_id`、`source_run_id`、`source_event_id`、`target_run_id`、`target_event_id`、`point_id`、`point_run_id`、`point_event_id`均为必填UUID；`side TEXT`必填且为SOURCE或TARGET。

主键 `(relation_id,side,point_id)`。关系六列复合外键保证端点与关系一致；`(point_id,point_run_id,point_event_id,user_id)→graph_event_points`保证要点与事件、运行、用户一致。CHECK按side要求point端点等于source或target端点。

程序在发布前及读取候选时检查每条关系两侧至少一条证据，并拒绝重复或不存在的要点；不可把“一侧有证据”当作整条关系合法。序号通过join要点表获取，不在证据表重复保存。

NO_RELATION、UNRESOLVED保存在checkpoint.final_pair_results及调用审计，不写关系表。

## 7. 有效查询与召回算法

事件和要点：运行status=PUBLISHED；diaries未软删除；用户匹配；事件is_in_graph=true。关系除检查所属运行外，还检查双方运行PUBLISHED、双方日记未删除、双方事件is_in_graph=true。历史运行按ID查询允许OBSOLETE，但仍鉴权。

历史召回先检查用户已发布历史要点的向量版本一致性，遇到缺失或版本不符记录EMBEDDING_NOT_READY，不静默过滤后返回正常结果。当前与历史日期按来源diary_date严格比较。

对当前事件所有要点与合格历史要点计算 `1 - (current.embedding <=> historical.embedding)`。按历史event_id分组取MAX分数，过滤分数不低于0.5，按分数降序、event_id升序取5。命中证据使用相似度最高的要点组合；并列时按当前point_id、历史point_id升序选定，记录两个ID和分数。不在事件聚合前LIMIT。

当前尚未发布的向量来自checkpoint，通过绑定参数传入查询；不为了检索提前插入正式表。未知发生日期不影响来源日期过滤。

## 8. 迁移与目标环境执行

新增迁移文件建议命名为 `backend/migrations/050_event_graph.sql`。这是计划文件，当前尚未创建。实现前重新检查编号是否仍可用；所有COMMENT、索引及复合外键在同一迁移中定义。数据库需提供vector扩展和gen_random_uuid函数；不安装中文分词扩展。

执行顺序：停止旧写入及应用自动建表；核对表外键依赖和目标数据库身份；事务中删除旧专属配置与表、建立新结构、增加diary_events.is_in_graph；执行迁移后部署新模型和入口；验证应用不会重新创建旧表。代码与SQL应作为同一发布包，数据库迁移先于新应用接收任务。

旧表删除顺序：knowledge_event_reviews → knowledge_atomic_events → knowledge_deposits → knowledge_tasks → knowledge_matters。禁止DROP CASCADE；目标数据库存在清单之外的外键时先记录并更新清理清单，再执行对应删除语句。

需为 `analysis_runs.task_id` 增加非空范围唯一索引以防同一分析任务重复发布；执行前检查重复记录，存在重复时停止并报告，不自动删除已有分析。应用统一发布仍需先检查任务完成标记，不能依赖唯一冲突作为正常幂等控制。

不新增数据备份和恢复演练步骤，用户已备份。正式SQL通过受控执行命令使用既有连接配置，不输出连接串和认证信息。T03在隔离库执行并检查结构；T15才对目标数据库执行。

计划新增迁移入口 `backend/scripts/migrate_event_graph.py`，明确提供 `--check` 和 `--apply`：check只查询扩展、表和外键、现有分析任务重复记录；apply在旧应用停写后执行已审阅SQL并核对迁移结果。脚本从当前backend工作目录加载配置，只输出表名、检查项、行数与成功或失败，不输出配置全文。该脚本及以下命令属于实施产出，当前尚不可运行：

```bash
cd backend
venv/bin/python -m scripts.migrate_event_graph --check
venv/bin/python -m scripts.migrate_event_graph --apply
```

apply只执行指定050迁移，不重新顺序执行001至049。事务成功后复跑check验证新结构及旧表删除结果；重复apply先检查完整目标结构，已迁移时返回已完成，不重新删除有效新数据。部分结构与设计不符时失败，不用IF NOT EXISTS掩盖缺少约束。
