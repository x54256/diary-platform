# 第一层存储与任务实现

核对基线：2026-10-29 仓库模型、迁移、应用服务及 Skill 脚本；本次未连接真实数据库。字段与约束的当前源码见 [graph.py](../../../backend/models/graph.py)，不能用旧报告的执行回执代表当前部署已复核。

## 1. 身份与存储责任

| 对象 | 身份 / 作用 | 关键约束 |
|---|---|---|
| `graph_tasks` | 一次分析或历史范围任务，持有配置、环境、租约及当前游标 | 同用户最多一个 `QUEUED/RUNNING` 任务；入口与兼容任务身份一致 |
| `graph_runs` | 当前任务中一篇日记的一次运行，保存来源、checkpoint、分析轮次与发布状态 | 任务+日记唯一；同用户日记最多一个 `PUBLISHED` 运行 |
| `graph_model_calls` | 某阶段 / 单元 / 尝试的实际服务请求与响应 | 任务-运行复合归属，尝试号唯一且递增 |
| `graph_run_events` | 运行中的来源事件与顺序，实际发生日期可未知 | 运行-事件-用户复合身份，事件仍使用 `DiaryEvent.id` |
| `graph_event_points` | 稳定要点 UUID、连续序号、主旨、详情、完整详情向量与模型身份 | `(run_id,event_id,no)` 唯一，内容和模型非空，1024 维向量必填 |
| `graph_event_relations` | 当前运行生成的三类正式关系 | 当前运行无序事件对唯一；两端不同，至少一端属于生成运行 |
| `graph_relation_evidence` | 每条关系两侧要点身份 | 复合外键绑定关系、事件、运行和用户，side 与端点一致 |

关系方向按业务语义，不按无序去重键 `LEAST/GREATEST`、查询日期或画布位置重写。事件内序号用于阅读，正式引用使用要点 UUID 及其运行，不让重分析的新序号冒充旧证据。

`NO_RELATION`、`UNRESOLVED` 和 Skill 的 `INDIRECT_FOLLOWUP` 归档在 checkpoint / 入库包，不写成正式关系；`final_source` 现有代码允许 `AGREEMENT`、`ADJUDICATED`、`SKILL_AGENT`，不能把 Skill 保存冒充模型双判一致。

## 2. 应用内三类入口

| 入口 | 当前职责 |
|---|---|
| 日记分析 `/{diary_id}/analyze` | 建图作为前置，再执行普通 / 反馈分析与行动规划，统一发布 |
| 图谱 `/history-build` | 按日期处理已分析日记，保留已有分析，只构建图谱 |
| 图谱 `/build` | 仅建图，允许符合来源条件的已整理日记，不触发日记分析 |

实际 FastAPI 前缀和完整参数引用 [graph 路由](../../../backend/routers/graph.py)、[日记路由](../../../backend/routers/diaries.py)及 [graph schema](../../../backend/schemas/graph.py)。任务查询、失败重试、当前日记图谱、历史运行和事件邻域均由相应路由提供；公开响应只暴露任务进度与正式结果，不把完整冻结原文和模型审计当公开接口返回。

同一历史任务按 `(diary_date,diary_id)` 串行处理，当前篇完整发布后再处理下一篇。首次范围固定日记清单；已发布或状态不符合条件的历史篇按明确原因跳过。历史范围补录不会自动反向修复后续所有关系。

## 3. 状态、执行权与恢复

### 3.1 任务与运行

- 任务状态：`QUEUED → RUNNING → SUCCEEDED / FAILED`；被新任务替代的失败任务为 `SUPERSEDED`。
- 应用运行状态：`QUEUED → RUNNING → PUBLISHED`，失败为 `FAILED`，历史不处理为 `SKIPPED`；新分析建立时旧已发布运行可成为 `OBSOLETE`。
- 要点 Skill 还使用 `POINTS_READY`：正式要点和向量已保存，关系尚未完成，任务本身可以成功。
- `published_at`、`obsolete_at`、跳过原因和状态按模型约束保持一致。不存在“任务成功必然等于关系已完成”的跨入口统一含义。

### 3.2 租约和并发

[graph_tasks](../../../backend/services/graph_tasks.py)与 [graph_runtime](../../../backend/services/graph_runtime.py)使用用户锁、环境、可领取时间、执行 token 和租约检查所有权。认领者须在有效租约内携正确 token 保存，心跳延长当前执行权；进程退出后可按持久状态重新认领。

来源写入与任务创建复用用户 / 日记锁顺序。活动运行阻止相关写入；已存来源快照或已分析日记的正文写入被锁定，详见[日记维护](../../日记管理/录入与维护.md)。不能用删除旧运行或改日记状态绕过证据保护。

### 3.3 checkpoint 与真实调用

每个事件候选、审核轮次、向量、召回、A/B/C 已完成判断和分析阶段均存入 `GraphRun.checkpoint`。未通过候选不进入正式表；成功单元可以恢复复用。

实际模型调用保存脱敏请求、原始响应、解析结果、校验错误、token 用量和状态。`STARTED` 不等于调用尚未发生；故障后未收到结果的调用标为 `UNKNOWN`，服务端不能保证网络请求零重复。

恢复只接受失败且未被更新运行替代的任务，核对当前结构化事实指纹及用户无其他活动任务。`POINT_REVIEW_FAILED` 可显式重新开启失败事件的有限审核轮次；旧通过事件、有效向量和前一日正式结果保留。

冻结配置包括模型及渠道身份、提示和协议指纹、预算、召回参数，不含认证密钥；运行时重新读取可用渠道认证。人物资料和反馈也存于快照，但当前事实指纹不包含所有辅助输入，旧任务恢复不会自动采用新反馈，见[日记分析实现](../../日记管理/AI分析/实现设计.md)。

## 4. 发布事务与旧运行

[graph_publish](../../../backend/services/graph_publish.py)将应用内正式要点、向量、关系与证据，以及入口要求的日记分析和行动结果，在同一短事务内发布。

提交前重新校验来源事实、当前执行权、历史依赖运行和完整结果。双侧证据必须属于各自端点和用户；每个待判对有最终结果，未完成不能按无关系跳过。相同运行已发布时返回已有身份，不能重复创建正式要点和关系。

新分析创建时旧当前图谱标为过时，旧数据及证据身份保留；新任务失败不会自动恢复旧运行的有效标志。默认当前查询排除 `OBSOLETE`，历史运行接口用于查看旧证据。这一时间点与“仅成功发布后替换”的产品期待须区分。

本实现没有通用“补入较早日记后重建所有受影响后续日期”的自动修复功能。历史修订应列出影响范围、重评结果及发布策略，再使用受支持路径执行。

## 5. Skill 保存的不同阶段

### 5.1 要点保存

要点 Skill 用独立同步任务保存完整要点与向量，`POINTS_READY` 不触发关系或后续分析。当前保存会拒绝已有有效要点运行；历史缺失事件补齐有专门脚本，不提供任意替换所有已发布要点的后门。

### 5.2 关系保存

关系包同时绑定来源快照、全部规范判断、最终 Markdown、证据定位、依赖和完整冗余报告。`results_sha256` 绑定结果，`storage_sha256` 绑定独立完整包；来源包指纹不能代替最终结果授权。

保存前重新锁定用户、当前与历史要点运行、事件与证据；比较来源内容、向量模型 / 指纹、整个历史池和实际使用的后续关系上下文，捕捉新增、删除和变化。关系包脱离本地识别目录后仍可验证，不靠标题恢复身份。

一个事务仅创建 `RELATED` 的正式边及双侧证据，其余判断全部归档；当前运行设为 `PUBLISHED`，相关事件有效标记更新，不重算要点和向量。零关系也须保存完整检查结果并合法发布，不能捏造一条边满足流程。

显式替换已发布关系时，先归档旧正式边、证据、旧判断与时间，再替换本运行拥有的边；任何插入失败整体回滚。相同包幂等，未显式选择替换则不覆盖已有不同结果。

## 6. 读取、候选资格与页面差异

[当前图谱和事件邻域](../../../backend/routers/graph.py)允许读取最新 `POINTS_READY` 或 `PUBLISHED` 的要点；历史接口保留旧运行读取能力。

当前页面正式关系过滤要求关系所有者和双方运行都已发布、来源日记未删除、端点有效。关系 Skill 的历史候选资格则允许 `POINTS_READY`，不要求该历史关系先完成。因此关系可先合法入库，但在双端都满足展示条件前不一定进入当前关系图。不能把查询可见范围和识别 / 保存资格混为一谈。
