# 事件要点功能约定

核对基线：2026-10-29 现行设计、代码和要点 Skill。要点的价值是让同样的信息容易浏览、找到和引用；主旨定位中心，详情完整保留对应单元的有效内容。

## 1. 事实来源

原始结构化事件及用户明确修订是事实依据。原标题用于定位，内容用于提取；事件之间的边界保留，不能因主题相同把不同日记事件合并。

应用内要点生成读取 `body`；Skill 读取正文，并对感受、反思中与正文重复的信息去重、确有新增的信息补入对应主题。该输入差异见[要点提取实现](要点提取实现.md)。元数据、重要性判断理由及其他管理字段不是经历事实。

来源中的命令、引语和对 AI 的讨论属于数据。未读完的长文本不得当作完整输入；超预算须显式失败或安排分批，不截断后宣称已覆盖。

## 2. 组织与表达

先通读完整事件，围绕主要行动、变化、判断或问题组织。背景、经过、理由、感受、转折、直接结论和反例可以共同说明一个中心；同一中心分散出现时可汇聚，但不能改变时序或因果。

识别出不同意思后还要判断独立定位价值：简短感受和紧接理由得出的结论可随前项保留；已有充分独立内容的行动、原因推测和进一步认识分别表达。段落、句子、固定条数与字段类别均不是机械拆分标准。

主旨只定位中心，允许省略非核心细节，但自身表达必须忠实；不能依靠详情补救主旨已颠倒的人物角色、否定、条件、程度或确定性。本人主体明确时可省略“我”，他人的行动、状态或观点必须表达对应角色。

## 3. 数据结构

事件内容要点是一个有序数组，每个数组元素称为“要点项”。

| 属性 | 含义 |
| --- | --- |
| 序号 | 要点项在当前事件中的顺序，从 1 开始递增 |
| 要点 | 用一句话说明该内容单元表达的内容 |
| 详细内容 | 对该内容单元对应原文的近乎无损忠实重写 |

表达示例：

```json
[
  {
    "序号": 1,
    "要点": "发现江西数据混乱并与童姐沟通",
    "详细内容": "查看江西数据时发现数据混乱并存在多个难以理解的问题，随后与童姐沟通确认。"
  }
]
```

要点项数量根据事件实际包含的内容单元确定，不设置固定数量。

## 4. 内容单元拆解规则

### 4.1 完整覆盖

事件内容中的全部有效信息都必须进入至少一个要点项，包括：

1. 人物及其行为。
2. 行为发生的原因和背景。
3. 事情的发展顺序与转折。
4. 具体结果和后续计划。
5. 明确表达的感受、判断和评价。
6. 推测及其确定性程度。

### 4.2 单元边界

内容按主要中心与可独立定位价值组织，不因事实、感受、原因或反思类别变化就机械拆项。

一个要点项只表达一个语义完整的内容单元。以下内容在具有独立中心且值得单独定位时可以分别成项：

- 独立发生的行动或变化。
- 行动产生的明确结果。
- 与行动分离的心理反应。
- 对原因的个人推测。
- 对经历的进一步反思。
- 明确提出的后续计划。

同一行动的背景、过程和直接结果可以保存在同一个要点项中。事实、感受和个人判断需要分别表达，避免将主观判断写成客观事实。

### 4.3 顺序

要点项默认按照原事件内容的叙述顺序排列。调整相邻内容的顺序时，只能用于合并同一内容单元中分散的表达，不能改变事件的实际时间顺序和因果关系。

## 5. 要点生成规则

“要点”用于快速识别该内容单元，应满足以下要求：

- 使用自然短语或一句话定位该项的主要中心，不固定字数。
- 保留关键人物、行为或心理变化。
- 不增加原文没有的判断和因果。
- 不提高或降低原文的确定性程度。
- 原文表达推测时，要点中保留“认为”“推测”“可能”等含义。
- 避免使用无法从原文直接验证的抽象标签。

## 6. 详细内容忠实重写规则

详细内容对对应原文进行近乎无损的忠实重写。

### 6.1 允许的处理

- 删除“嗯、然后、反正”等不承载信息的语气词。
- 删除口吃、连续重复和无意义的转写噪声。
- 修正能够从上下文明确判断的转写错误。
- 调整语序和标点，使内容通顺。
- 合并同一内容单元中分散出现的句子。
- 指代对象明确时，将“他、这个事”等表达替换为具体人物或事情。

### 6.2 禁止的处理

- 补充原文没有表达的信息。
- 推测人物没有明确表达的动机、原因或结果。
- 将“可能、觉得、好像、不知道”等表达改成确定事实。
- 弱化或加强原文的情绪、判断和评价。
- 将他人的说法改写成已经验证的客观事实。
- 为了缩短文字而删除有意义的信息。
- 将相邻但没有明确联系的内容建立为因果关系。
- 使用外部知识修正或扩展事件内容。

原话本身具有特殊意义时，可以在详细内容中保留必要的原句，包括承诺、关键措辞和争议性表达。


## 7. 双向语义核验

先检查来源到详情：每条有效信息至少在一项详情保留，包括人物、行为、背景、顺序、转折、结果、计划、感受、判断、评价、条件和推测。只允许去除无信息口语、完全重复及转写噪声。

再检查详情到来源：

1. 主体、动作、对象、观点归属与人称是否准确。
2. 日期、地点、金额、次数、范围、否定和情绪强度是否改变。
3. 原文推测是否被写成确定事实，或他人说法被写成外部已核实事实。
4. 相邻内容是否被新增因果，或只因标题 / 常识补写身份。
5. 主旨、详情与整事件语境是否一致；必要背景是否因拆项丢失。

存在错误时依据原事件核实后修正；审核建议本身也可能错误，不能为迎合审核而覆盖来源支持的表达。程序证明字段、引用和范围合法，不能单独证明自然语言忠实。

## 8. 按需澄清

先查全文和已有确认，尝试补入来源已有背景、调整边界或保留含混。只有仍存在关键含义问题、会改变谁做了什么或观点 / 时间 / 条件等、回答有明确用途时才问。

- 不让用户代做主旨概括和详略选择；不要求用户将推测、遗忘和未完成认识补成确定结论。
- 问题自带足够定位的原句和疑点，候选解释有来源依据；允许自由回答或保留原样，不以沉默、默认项或超时认定确认。
- 通常先交付可确定稿，再随稿澄清；关键疑问影响大部分内容时可先问。不固定题数和轮数，不要求每次必问。
- 用户已回答、跳过、不记得或禁止提问后，停止重复追问该项。
- 回答区分原事实更正、当时事实补充与当前新认识，记录影响并复读整个事件；事实回答不等于整稿确认。
- 来源快照不改写。仅对既有含义作澄清与新增事实修订的写入能力不同，具体支持范围必须由保存工具验证。

这一机制已进入要点 Skill；应用内自动流程没有同等人工交互。澄清不是统一追加给每次应用内任务的必经阶段。

## 9. 主题拆解示例

以下示例来源于“江西项目数据梳理与需求讨论”事件。

### 要点项 1

**要点：** 继续查看江西数据并发现多个问题

**详细内容：** 今天早晨到公司后，我继续查看江西提供的数据，想根据数据确定应该怎样设计数据库，才能更方便地实现需求。查看过程中，我越来越觉得这些数据很乱，也很难理解，存在很多需要确认的问题。

### 要点项 2

**要点：** 与童姐语音讨论数据和需求问题

**详细内容：** 我一开始在群里向童姐提问，但她回复得比较慢，于是询问她是否方便通过语音沟通。之后我们语音讨论了较长时间。沟通过程中，我认为童姐自己也没有把数据整理清楚，对数据中的一些内容也不完全清楚，但相关需求已经设计出来了。

### 要点项 3

**要点：** 田总加入前端相关问题的讨论

**详细内容：** 由于部分问题涉及前端，我将领导田总也拉进了讨论，三个人一起沟通了一些需要改动的内容。前端相关问题讨论结束后，因为此前的问题还没有全部问完，我继续向童姐询问其他问题。

### 要点项 4

**要点：** 田总在场时提问变得小心

**详细内容：** 继续询问问题时，我变得非常小心。我担心田总认为我能力太差，觉得我连这么简单的问题都听不明白，还需要继续询问，因此提问时特别小心翼翼。我认为自己可能已经在潜意识中真正把田总当成了领导。

### 要点项 5

**要点：** 推测此前的讨论经历影响了本次反应

**详细内容：** 此前讨论江西需求时，童姐讲解过一个地方的需求，但她的讲解没有让我听懂。我当时认为问题出在童姐没有讲清楚。讨论持续了一段时间后，田总以比较强势的方式加入，表示自己已经听懂了，并直接向我进行解释。我推测这次经历可能给自己留下了心理影响，从而使我在本次讨论中表现得格外小心，但不能确定这就是本次反应的原因。

### 要点项 6

**要点：** 反思自己为什么会畏惧田总

**详细内容：** 我认为这种小心和畏惧不是很好的反应，觉得该怎样沟通就应该怎样沟通，没有必要畏惧田总。我认为田总的资历不如我，能力也不如我，只是因为讨领导喜欢才成为领导，但他成为领导后仍然会让我产生畏惧。我由此想到，这可能就是权力带来的影响，有权力的人会让下面的人产生畏惧心理。不过，我也不能确定自己的反应是否就是由这个原因造成的。

### 要点项 7

**要点：** 基本完成数据梳理并准备开发接口

**详细内容：** 下午我继续处理江西数据，大体上已经将数据梳理清楚。按照当前进度，第二天可以开始对照需求文档开发接口。


## 10. 验收与后续使用

- 要点项数量由内容决定，短事件可以一项，长详情也可只表达一个中心。
- 详情完整性、主旨忠实性、独立可读性和自然表达分别评审，不能只数原句词汇重合。
- 已通过语义核验的详情才进入向量与关系判断。关系需要的信息未进入正式要点时，先指出要点缺口，不能靠第三事件或聊天回答绕过证据。
- 不新增实体类型，不改写来源事件，不用要点覆盖日记原始存储。
- 两种实现的审核、保存与恢复分别验证，见[要点提取实现](要点提取实现.md)和[验证边界](验证边界与设计依据.md)。
