# 事件建图模型协议简化与事实修正方案

状态：待用户确认。整理日期：2026-10-19。

阅读入口：[模型请求与响应修改前后对照](模型请求响应修改前后对照-20261019.md)。先看真实输入输出与拟议格式，再看本文的代码改动和验收安排。

本方案依据 2026-08-17、08-18 两篇日记的真实调用记录、当前实现和公开研究形成。本轮只完成调研与方案设计；代码、正式图谱与旧任务均未改变。

## 1. 目标与推荐决策

把确定性的身份映射、编号、覆盖调度、结果合并、差异计算和发布交给程序；模型集中处理语义组织、事实比对及关系判断。

推荐实施三个相互配合的改动：

1. **关系单对输入。**每次请求只有事件 A、事件 B；程序保存 UUID、pair_id 和证据映射。模型选择方向 A_TO_B 或 B_TO_A，不查找或复制业务 UUID。
2. **审核返回局部修改。**生成仍输出主题要点；审核只报告有原文依据的修改和遗漏。程序应用字段替换，保留未修改内容；修改后独立复核完整事件。
3. **精简协议并保留程序校验。**取消完整通过清单、逐句比较作文、原标题复写和序号生成；冻结新协议版本、保留旧任务执行分支，先用隔离样本验证再切换新任务。

本次用户已确认“出差南通的行程安排与审批 → 初到南通项目现场”应为后续关系，纳入关系类型与方向的验收参照。确定性及最小证据范围仍需回到原文标注；用户反馈不写进模型提示作为该样本的指定答案。

## 3. 当前实现、实际错误、原因与改法

### 3.1 关系事件池与 UUID 配对

**当前实现。**`graph_relations.payload_for` 提供 events 事件池和 pairs 清单；模型通过事件 UUID 跨结构找文本。`judge` 将多个事件对一起请求；A、B 使用同一冻结模型、相同提示和同类输入，各自独立调用。

**实际错误。**C64、C66 中 `pair-638b3e9e2dfa87966278bca9` 的输入都是“初到南通项目现场 ↔ 出差安排”，但 A、B 均把后者解释为“小豪聊天”，输出 NO_RELATION。被错用的事件就在同批输入。另一对“误咬洁厕灵 ↔ 聚餐”也出现理由谈论其他配对。

**原因分析。**已证实请求端点正确、输出对象错位。UUID 查表、共享事件池及多对判断增加了程序性定位负担；相同输入组织和提示没有阻止同类错误。现有证据没有证明 UUID 单独导致错误，也不能量化去掉 UUID 后的改善。

**准备改成。**一次请求只呈现 A、B 两件事，包含原标题、记录日期、实际发生日期（已知时）及全部要点正文。程序保留真实端点与配对，不发送这些业务元数据。局部要点编号只供引用当前文本，不能移除后改用标题定位。方向由模型依据文本判断，不由 UUID 顺序、记录日期或 A/B 位置推断。

**验证。**同一文本只替换数据库 UUID，不得影响模型实际请求正文；同标题、A/B 交换、记录日期与发生日期不同均需正确映射。争议出差事件对作为后续关系正例复测，宠物诊疗预约与执行作为另一正例；相同城市而具体事项不同作为负例。

### 3.2 非相关结果只按状态认定一致

**当前实现。**`equivalent` 对非 RELATED 只比较 status；RELATED 比较完整关系字段，包括 description 和证据集合。`validate_pair` 对非相关结果只要求理由非空及 relation=null。

**实际错误。**两份谈错事件的 NO_RELATION 被接受；另一方面，误咬→洗牙的 A、B 虽同意关系，却因描述和证据不同进入 C。

**原因分析。**状态一致没有检验判断依据。非相关结果缺少可定位依据，而描述逐字一致又不等于语义一致。

**准备改成。**所有状态统一返回 A/B 两端的文本引用；程序核验引用属于当前端点。按状态、类型、方向、确定性及规范化引用位置比较结构化结论；不再把说明文字逐字相同作为一致条件。有结构化分歧才交给 C；两个判断结构相同仍不能宣称已证明事实正确。

**验证。**第三事件引用、引用不在对应端点、方向颠倒和非相关无依据均被拒绝。相同结构化结论只改说明措辞不触发 C；证据或结论有分歧触发 C。引用真实但不支持关系的反例纳入语义验收，不能只测字符串存在。

### 3.3 审核与完整修正版嵌套输出

**当前实现。**combined 提示先定义审核 JSON，再定义完整要点 JSON，最后要求合并成 review/candidate。即使无错误，也必须完整复写 candidate。`validate_combined` 要求无问题时新旧候选完全相同。

**实际错误。**C12“合并输出字段不一致”；C13“未发现问题却修改候选”；C09 存在问题项但 repair 为空。

**原因分析。**单次输出承担审核、说明、全文重写、嵌套合并和一致性维护。无问题时也暴露全部候选给重新生成。这是已确认的输出负担；对注意力影响的程度仍需实验。

**准备改成。**审核修正阶段主要返回 edits 和 additions 两个数组；无问题均为空。另用 structure_issue 记录局部编辑无法解决的主题结构问题，正常为 null。每个 edit 对应一个已有要点的一个字段，写明原句依据、具体差异和替换值。程序取得旧值，应用经验证的替换，其他字段保持原字节内容。不得让模型回传旧值、候选全文或总体通过状态。

**验证。**空修改清单不触发候选变更；字段版本过期、重复修改同一字段、未知字段或越界编号拒绝应用。修正前后差异必须与程序接受的 edits/additions 完全一致。

### 3.4 原句编号和完整检查作文

**当前实现。**输入原句是 id；输出要求 source_unit_id。模型要为每句返回 comparison，为每个候选返回 checks，无问题也要填写通过项。

**实际错误。**C14、C45 把 id 原样返回导致失败；C47 只返回原句 1，C49 只返回前 15 句，未覆盖全部 30 句；C46 问题字段不合法。

**原因分析。**编号改名属于协议自增负担。逐条复写检查清单同时要求模型做语义核验和枚举完整性维护。列表齐全只能证明返回了对应项，不能证明已正确理解全文。

**准备改成。**输入统一使用局部 source_no；输出仅在实际修改中引用 source_nos。程序构建并校验输入全文、审核范围和候选版本，不要求输出逐句比较作文或逐项通过清单。每次仍要求模型先从原文核对遗漏，再从候选核对增添和失真。

**验证。**保留同义改写、合法摘要省略与无信息口语清理正例，加入遗漏背景、转折、否定和观点限定的反例；比较新旧协议的遗漏检出率。取消检查列表会失去逐句文字审计痕迹，必须用原始请求、候选版本和实际问题记录补足过程可追溯性。

### 3.5 修正本身制造事实偏差

**当前实现。**模型可重写完整 candidate；有问题时进入独立复核，两轮仍不通过就失败。previous_review 会带给后续 combined。

**实际错误。**C52 指出修正版把女友花小豪的钱写成小豪花女方的钱；C45/C46 的审核意见还错误地把记录者本人经历归给小豪。后一响应因协议不合法被拒绝，不能算语义防线成功拦截。

**原因分析。**意见可能错误，完整重写又扩大了改动范围。多轮意见会影响后续修改，原文必须始终高于审核意见。

**准备改成。**程序只应用局部修改；任何修改均进入独立复核，输入为完整冻结原文与新候选，不给上一位审核者的判断和解释。复核发现问题时，其意见交给下一轮核实。两轮仍有问题则保留失败检查点；有争议修正版不分配正式要点 UUID、不生成其向量、不发布。

**验证。**错误审核意见、原来正确而修后错误、错误被修好但引入另一错误、正确同义改写、主体不明等分别标注。验收以原文支持为准，不能以审核者相互同意为准。

## 4. 程序与模型的具体分工

| 工作 | 程序承担 | 模型承担 |
| --- | --- | --- |
| 来源与身份 | 来源冻结、用户隔离、UUID、任务/运行 ID、事件对去重 | 阅读当前事件文本 |
| 编号 | 段落/原句局部编号、候选编号、引用映射 | 必要时选择对应的局部编号 |
| 生成 | 保留原标题、数组编号、非空与类型校验 | 主题组织、summary 与 detail 表达 |
| 审核 | 构建完整输入、记录版本与已执行阶段、校验响应 | 原文与候选的语义双向比较 |
| 修正 | 保存旧值、冲突校验、应用编辑、计算差异 | 提出有来源依据的必要替换或遗漏补充 |
| 关系 | 候选召回、配对、A/B 绑定、UUID 与证据定位 | 联系是否成立、关系类型、方向及确定性 |
| 通过与恢复 | 空问题与阶段状态推导、有限重试、检查点、发布门禁 | 返回真实语义结果，不填写程序状态 |
| 计量 | Token、耗时、重试次数与版本汇总 | 无需生成统计 |

程序不能仅凭类型、非空或引用存在证明语义正确；不将人物指代、同一事项识别、否定和因果交给正则表达式判定。

## 5. 关系新协议：一次只处理两件事

### 5.1 请求示例

以下为协议说明用缩写文本。正式请求发送双方全部要点，不截断，不混入第三事件；只发 detail，summary 的概括内容不重复发送。标题辅助定位，关系以 detail 为依据。

```json
{
  "event_a": {
    "title": "出差南通的行程安排与审批",
    "diary_date": "2026-08-17",
    "occurred_on": null,
    "points": [{"point_no": 1, "text": "本来计划今天去南通……所以改为下午出发。"}]
  },
  "event_b": {
    "title": "初到南通项目现场",
    "diary_date": "2026-08-18",
    "occurred_on": null,
    "points": [{"point_no": 1, "text": "今天是周二，是我第一天来到南通项目现场。"}]
  }
}
```

程序在调用上下文中保存 pair_id、A/B 的事件与运行 UUID，以及两端 point_no→point UUID 映射。上述映射不进入模型 user 消息；结构反馈中也不附业务 UUID。日记原文本身含有标识时保留原文，不能为隐藏元数据而改写来源。

### 5.2 返回示例及字段规则

```json
{
  "status": "RELATED",
  "relation_type": "后续事件",
  "direction": "A_TO_B",
  "certainty": "EXPLICIT",
  "evidence_a": [{"point_no": 1, "quote": "改为下午出发"}],
  "evidence_b": [{"point_no": 1, "quote": "我第一天来到南通项目现场"}],
  "reason": "前一事件记录出差安排，后一事件记录到达现场及开始工作。"
}
```

这个示例用于展示字段形式，不能替代对真实全文、确定性和最小证据的验收。

- status 沿用 RELATED、NO_RELATION、UNRESOLVED。
- RELATED 的 relation_type 沿用后续事件、引发事件、提及事件；direction 只有 A_TO_B、B_TO_A；certainty 沿用 EXPLICIT、SPECULATIVE 的现有业务定义。
- NO_RELATION/UNRESOLVED 的 relation_type、direction、certainty 均为 null。reason 说明具体依据或缺失信息；两端 evidence 各至少一条，引用与判断有关的内容。引用存在不能证明“无关系”，完整双向判断仍由模型完成。
- quote 是对应 detail 的连续原文，程序计算其位置；同一片段多次出现且位置有歧义时，要求更完整引用，不由程序任意选一个。
- 模型不返回 pair_id、事件 UUID、要点 UUID、完整事件标题或 description 的重复说明。RELATED 的 reason 经程序映射为正式 description。

### 5.3 程序处理顺序

1. 对冻结的每个候选对建立 A/B 映射，只发送该对完整文本。
2. A 与 B 两次独立请求；第二次不包含第一次结论。保留现有同组模型配置，先隔离输入复杂度变量。
3. 校验枚举、空值组合、局部编号及连续引用；每次只检查当前对，失败仅补答当前对一次。
4. 将引用转换为当前端点内的稳定位置；比较 status、type、direction、certainty、两侧规范引用集合。说明文字不逐字比较。
5. 存在结构化分歧时 C 只读取同一对文本和两个局部候选，重新判断；不带第三事件或业务 UUID。
6. 程序将结果转换成当前内部 pair_id/status/reason/relation 结构；调用现有发布校验。方向与 point_no 由程序映射至事件 UUID 和正式要点 UUID。
7. 新协议的原始引用和校验记录保留在 checkpoint；发布前重新检查与冻结事件池一致。不能仅在适配时校验一次。

引用集合不同会增加 C 调用；这是显式取舍，需统计额外调用量。相同引用与结论仍存在共同语义错误的风险，不能承诺双判必然正确。

### 5.4 调用数与耗时取舍

本次 15 对候选改为单对输入后，仅 A/B 就需要 30 次调用，另计 C 与失败补答；原方案关系阶段实际 6 次调用。单对方案降低模型定位与隔离负担，但增加请求开销，不能宣称关系阶段必然提速。

第一阶段保留串行执行，不把并发写检查点一起纳入协议变更。实测若关系耗时过高，再比较限并发 2 的方案；需单独解决结果合并和租约一致性。当天事件两两配对与历史召回阈值本次保留，避免同时改变候选范围。

## 6. 要点新协议：局部修改与完整事件复核

### 6.1 初稿生成

输入只含当前事件标题与按原文顺序排列的正文；输出只含 points 数组，每项 summary/detail。程序补回原标题及连续 no。主题数量和组织由模型确定，禁止程序按句机械拆成要点。

### 6.2 审核输入

程序从冻结正文构造 paragraphs，每段内按序提供 sentences，字段统一为 source_no/text。只提供一份正文，不再同时发送完整段落文本和重复原句全文。保留段落分组、原有标点与顺序，便于理解对话归属。候选以 point_no/summary/detail 提供。

本次每个事件最多 30 个原句，第一阶段按完整事件审核，不新增分块调度。超出上下文预算时沿用明确失败，不通过截断丢弃来源。分块策略另行评估，避免为精简输出反而增加大量调用。

### 6.3 审核修正返回

```json
{
  "edits": [
    {
      "point_no": 5,
      "field": "summary",
      "source_nos": [21],
      "problem": "候选颠倒了花钱的主体，原文说的是女友继续花小豪的钱。",
      "replacement": "我建议各花各的并利用策略沟通，但小豪表示女友答应改变却仍花他的钱"
    }
  ],
  "additions": [],
  "structure_issue": null
}
```

edits 每项只修改一个已有字段；field 仅 summary/detail。source_nos 是原文依据，problem 是具体语义差异，replacement 是该字段完整新值。旧值与差异由程序获取，不要求模型提供字符偏移、复制旧值或重新输出整项。

若同一主题遗漏内容，替换相应 detail；若遗漏整个独立主题，用 additions：每项包含 after_point_no、source_nos、problem、summary、detail。after_point_no 引用修改前候选的位置，0 表示放在首项前；同一位置有多个新增项时按 additions 中的数组顺序插入。程序生成新数组、再编号，不要求模型换算插入后的编号。

第一阶段编辑不支持删除或重排现有项；若发现重复或主题组织错误无法通过替换修复，structure_issue 返回具体结构问题，edits/additions 均为空。程序保存原因、使该事件审核失败，禁止把它当作空问题通过。本阶段不新增自动整篇重生成分支。现有 retry_task 只恢复检查点，不会清空候选，因此不能声称点恢复就能解决结构问题；这类失败需要新建未发布来源的任务重新生成，或另行确认事件重生成能力，不以空字符串或删除正确内容绕过校验。

### 6.4 程序应用与复核

1. 计算 source_hash、candidate_hash，绑定当前调用。两者由程序维护，不要求模型复写。
2. 校验响应结构，edits/additions 中的局部编号、来源范围和非空文本，禁止同字段重复编辑、空操作及未知字段。任一修改不合法时拒绝整份响应，避免应用一半而破坏候选内部一致性。
3. structure_issue 非空时保留失败状态；仅当其为 null、无修改且无新增时，候选保持原样，事件通过；不要求额外生成“通过”字段。
4. 有修改时，在程序内生成新候选，保存旧候选、操作、差异、新候选及两个版本摘要。修改候选仍为工作结果。
5. 独立复核读取完整原文和新候选，使用同一精简返回结构；不读取前次审核意见，不当场自动应用其 edits。structure_issue 为 null 且两数组为空才通过；有字段编辑问题则进入下一轮核实，结构问题则保留失败。
6. 下一轮 combined 收到具体意见后，必须重新依据原文核实；可以拒绝错误意见并保持原文支持的表达。轮次上限沿用两轮，未通过时保留检查点及复核意见。
7. 通过后再分配正式要点 UUID，沿用原有向量生成与发布流程。

独立复核的 replacement 是建议，应用前需依据原文重新核实。原句引用合法也不能保证建议正确；例如“我就说我的一些事”不支持把叙述者经历强行归给小豪。出现无法消歧的指代时保留原文表述，不能用常识补写身份。

原有协议通过“返回所有编号”检查输出覆盖；新协议通过程序保证发送全文、候选版本及阶段完成，但不再声称返回了逐句审核痕迹。两种方式都不能证明模型真正逐句理解，因此遗漏检出和误改率必须单独验收。

## 7. 结构化输出与失败恢复

### 7.1 输出能力适配

- 先在当前渠道、当前模型快照、当前思考配置下，用无私人内容的极简 Schema 测试参数接受、字段约束及截断行为。测试通过再分别验证生成、修改、关系三个真实协议。
- strict JSON Schema 可用时，冻结具体 Schema 和指纹，使用简单对象、数组、枚举、必填和 additionalProperties=false；跨字段关系、引用归属、候选版本仍由本地程序检查。
- 不可用时保留简化后的 JSON Object 协议和本地校验，在审计中记录实际模式；不得静默把失败的 strict 请求伪装成已启用 Schema。
- 结构化输出不验证事实。首次发布不附带关闭思考或切换模型；思考预算的优化另设实验变量。

### 7.2 重试与检查点

继续区分结构失败、语义未通过、模型服务失败、执行中断。结构失败保留最多一次补答，反馈精确说明字段或枚举问题，不把校验报错变成要求模型迎合某个事实结论。

要点恢复键包括协议版本、事件内部 ID、候选摘要、轮次、阶段；关系恢复键包括版本、内部 pair_id、双方内容摘要、角色、尝试。恢复键仅用于程序和审计。新候选不能复用旧候选的通过记录；映射变化后不能按 A/B 名称盲目复用旧结果。

已通过事件、已生成有效向量、已发布前一天沿用现有检查点复用。任务失败后的显式恢复规则先保留，不把无限自动重试作为提高成功率的措施。

## 9. 验证与实施顺序

### 9.1 确认方案后实施

1. 固定脱敏回归夹具、输入输出协议及手工语义参照。
2. 实现本地验证、编辑应用和单对映射，再接入冻结版本与旧任务兼容。
3. 用无私人内容验证实际渠道的结构化输出能力；记录支持模式，不依赖厂商文档推定。
4. 对本次 7 个事件、15 对关系进行不写正式表的真实模型回放。每个候选版本、返回结果、耗时和费用字段独立记录。
5. 核心失败样本至少重复 3 次，并测试 A/B 互换、重复标题及加入无关元数据；不能用一次正确证明稳定。
6. 对照通过后，仅新任务采用新版本；两篇已发布日记的修复另列可审查结果。

### 9.2 必须验证的失败样本

| 类别 | 样本与验收重点 |
| --- | --- |
| 串对 | 出差安排→初到现场应识别后续及正确方向；请求中无第三事件和业务 UUID |
| 正确关系 | 体检时预约次日洗牙→实际洗牙，证据映射到正确点 |
| 误建边 | 洗牙与聚餐不能仅因相邻时间建边；同城市但不同事项不能建边 |
| 主体颠倒 | “我的领导”不能变“我”；“我们”不能变“独自”；女友花他的钱不能反向 |
| 错误意见 | 正确的记录者经历不能因复核意见而改成小豪经历 |
| 观点归属 | “小豪自称受 PUA”不能改成记录者确认的客观事实 |
| 遗漏与增添 | 保留有效背景、转折、反例、否定与条件；允许合理摘要省略和口语清理 |
| 编辑原子性 | 未指定字段完全保留；过期候选、重复编辑、越界引用不应用 |
| 非相关证据 | 合法引用不等于成立；错误端点与第三事件证据必须拒绝 |
| 恢复发布 | 已通过结果复用、失败候选不发布、协议缓存隔离、旧任务恢复 |

### 9.3 指标与门槛

确定性程序约束必须全部通过；任何核心主体、观点归属错误或争议对串对复现，都阻止新版切换。原始来源忠实性与关系参照由逐项审读核验，不能再用“双判一致”充当验收答案。

对比记录：首轮协议通过率、补答次数、错误意见采纳率、修正引入错误率、遗漏检出率、关系误判率、C 调用率、总输入/输出/推理 Token、模型等待与任务墙钟时间。7 个事件和 15 对样本只覆盖已知问题；切换前再加入同标题、多人物、多次出差、时间倒叙等边界样本。

不预先承诺耗时降为某个数值；总时长需同时计入单对请求增加的开销。若质量提升但总时长变差，先报告实测取舍，再决定并发或批量策略。
