# 第一层旧脚本质量复测与原因调研

日期：2026-10-15。用户确认 A：使用当前 Flash 语言模型和 Flash 向量模型，复测此前出错的四个事件。只进行图谱实验，原提示、阈值、正式业务代码和业务数据保持原样。

结论：原要点脚本复现语义失真及审核漏检；独立余弦复算复现两组跨日关系漏召回；独立关系实验的原始响应复现误判。四个事件中三个获模型审核通过，一个因引用错误停止；模型通过的聚餐事件仍有人工对照发现的失真。关系 A/B 四次请求全部缺 reason，未进入 C，不能给出本轮完整关系流程的准确率。实际共 17 次服务请求。

关系实验的原 A/B/C 执行脚本未保留在仓库及可见 Git 历史中。Git 中能恢复的 `validate_event_relation_design_live.py` 使用更早的关系类型、全文与段落召回、旧知识库表，属于已废弃方案，不能冒充后来要点双判实验的原脚本。本次将其保存在本地作溯源，依据后续实验记录重建独立关系验证入口：本地余弦计算、独立 A/B 请求、分歧交 C；仅复用正式代码的结构与引用校验，不使用正式任务调度、召回 SQL 或发布逻辑。因此本次关系结果属于重建实验，不是原脚本的逐字复现。

关系实验原计划使用两组输入：前次实现验收最终候选、原要点脚本重新生成的候选。实际完成前次候选组；新生成组因一个事件未通过原脚本校验，没有继续组装四事件关系链路。前次候选保留已发现的语义问题，不等于旧实验人工核验过的要点。旧实验原始完整要点已清理，本次没有恢复其人工修正版，不能做“只换模型、其余完全相同”的因果对照。

为定位错误，四个事件的全部六个事件对都直接送入关系判断。正常召回是否纳入单独记录；这种强制送判用于检查判定能力，不能表述为正常召回成功。四组已有确认正例用于核对漏检，另两组不自动计为已确认负例。

运输参数差异也保留：原要点脚本的请求没有显式 max_tokens，正式实现设置输出上限；本地关系调用沿用原脚本的整批结构重试，而正式实现使用逐对补判。向量以完整 detail 批量编码，正式实现逐要点请求。本次可检查问题是否在独立流程出现，不能据此宣称两个执行器完全等价。

## 2. 验证方法

1. 对每个事件执行原脚本的生成、最多两轮审核修正及必要的独立复核。结构错误至多请求两次，失败如实记录。
2. 对最终保存候选人工逐字段对照原文，模型自评与人工语义结论分开记录。结构失败的输出不计为通过。
3. 使用本地 Python 余弦公式复算原已保存向量；另外调用当前 Flash 向量模型生成新向量，核对召回边界。
4. 将六个事件对强制送入独立 A/B/C，区分未召回、判无关系、待定和字段错误。
5. 比较前次候选与新候选，记录变化；单次通过不能证明稳定性，失败也不能直接归因于模型切换。

## 3. 网上研究与适用边界

### 3.1 语义失真与审核漏检

[CoVe 原论文](https://arxiv.org/html/2309.11495v2)发现，验证阶段继续关注已有生成内容时会重复其中的幻觉；将验证拆为独立问题、隔离初稿答案，可以在其测试任务中降低幻觉。论文同时明确该方法不能完全消除错误，并增加计算成本。

[QAGS](https://aclanthology.org/2020.acl-main.450/)通过对生成文本和源文本提出问题，比较答案来发现事实不一致。[QAFactEval](https://aclanthology.org/2022.naacl-main.187/)进一步研究问答式检查，指出问题生成和问题是否能由原文回答会影响结果，问答与蕴含式检查能提供互补信号。

[FActScore](https://arxiv.org/abs/2305.14251)将长文本拆成原子事实，再核对来源是否支持，说明整段“通过/不通过”不足以表达局部错误；其人物传记测试结果不能作为中文日记的效果指标。

对本项目的解释是：当前逐原句检查覆盖了原文，却仍由模型判断候选新增的主体、次数、原因是否忠实，字段合法无法证明新增事实被原文支持。现有复核虽然使用独立请求，但仍直接看候选，不等于 CoVe 中对答案隔离的事实问答。这里是依据代码和文献提出的机制解释，论文没有测试本项目所用 Flash 模型，不能将其当作已经证明的参数级根因。

可执行的改进候选：在已有审核请求内，将候选的事实拆为“谁、做什么、次数、时间、因果、确定性”，逐项返回原文支持片段；原文不能回答时保留原指代或删去新增限定。复核时先根据原文回答关键问题，再与候选比较，避免只问候选是否正确。证据引用仍需要语义检查，不能因引用存在就宣称蕴含成立。先用独立实验验证效果，再决定是否增加调用或修改正式提示。

### 3.2 语义相似度与关系召回

[Sentence Transformers 官方检索与重排说明](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)将密集召回定义为查找向量接近的文本，再对候选做更细判断。向量接近不是“后续、引发、提及”关系的业务定义。重排只能处理已召回候选，不能恢复已经被硬阈值删掉的事件。

本项目一次安排出差、一次记录现场工作、一次混合记录项目修复与个人开发，存在事项推进关系，但其文本主题与信息占比不同。当前最高余弦小于 0.5 就直接排除，模型判定阶段无法挽救这些漏检。这是可由召回记录直接证明的程序路径；具体分值下降不能只凭本轮归因于向量模型更弱。

可执行的改进候选：在冻结的确认关系集上离线扫描阈值与前 K，分别报告正例召回和新增候选数量；比较“保留阈值”与“只取前 K”后再选参数。不得因四个事件的历史池很小、全部送判成本很低，就宣布某个参数适合真实全量。需要补漏时再单独比较原文段落或具体事项锚点的贡献；本轮不直接恢复中文分词或另加检索系统。

### 3.3 A/B 一致与关系误判

[无外部反馈自纠错研究](https://arxiv.org/abs/2310.01798)在推理任务中发现，自纠错不能稳定提高表现；该研究的任务与“读取日记原文”不同，仅说明不能把重复检查当作正确性保证。[CoVe](https://arxiv.org/html/2309.11495v2)则展示了适当隔离与拆分可以改善结果，两者共同支持检查验证方式，而非简单增加同类调用。

同模型、同提示的独立请求可以得出同样错误；当前仅分歧交 C 的逻辑不会处理 A/B 一致漏判。若错误先发生在要点中，后续 A/B/C 又只读取要点，也不能可靠恢复原文事实。这两条是流程可确认的限制；A/B 是否在本轮具体同错，以实际响应为准。

可执行的改进候选：先核对要点是否保留联系，再检查每对事件两个方向的具体联系及允许的上下文消歧。下一版实验让验证器从来源证据定位联系，或对含具体事项线索的一致 NO_RELATION 加做证据核对，记录额外调用成本。不同模型、额外 C 或直接传原文均只是后续实验选项，当前没有证明它们必然提高质量。

### 3.4 字段缺失与输出约束

[百炼官方结构化输出文档](https://help.aliyun.com/zh/model-studio/qwen-structured-output)明确区分 JSON Object 与 JSON Schema：当前使用的 `json_object` 只约束合法 JSON，不保证键名、字段类型和必填字段；`json_schema` 可约束结构，文档支持列表包含 Qwen3.7-Flash 系列。

这解释了合法 JSON 仍能漏掉 reason 或把 source_unit_id 写成 id。可执行的改进候选是在独立实验中验证当前具体渠道、固定模型与思考模式的 strict JSON Schema 兼容性，成功后再决定是否接入。Schema 可以减少结构错误，无法证明关系类型、因果、方向和自然语言内容正确，业务校验仍须保留。本轮不修改请求格式。

## 4. 实测结果

### 4.1 原向量复算与新向量召回

本地独立余弦复算原保存向量，得到 0.51271637、0.42238485、0.45681261，与此前正式流程的三组跨日正例分数一致。两组正例低于 0.5 的现象在不运行正式召回 SQL 时仍然成立，因此这两例不能归因为正式 SQL 计算或前 5 截断错误。

使用相同前次要点重新请求 Flash 向量，结果如下：

| 已确认正例 | 旧保存向量独立复算 | 本轮新向量 | 阈值 0.5 下 |
| --- | ---: | ---: | --- |
| 聚餐督促阅读 ↔ 南通行程安排 | 0.39359318 | 0.39465944 | 同日完整比较覆盖，不受阈值过滤 |
| 南通行程安排 ↔ 初到项目现场 | 0.51271637 | 0.50467538 | 召回 |
| 南通行程安排 ↔ 出差工作推进 | 0.42238485 | 0.41350835 | 漏召回 |
| 初到项目现场 ↔ 出差工作推进 | 0.45681261 | 0.45247749 | 漏召回 |

新旧分值存在差异，但阈值两侧归属相同。本轮新向量采用批量请求，未做单条/批量与重复请求控制实验，分值差异原因没有定位，不能直接解释为模型随机性或渠道问题。

本轮四事件离线扫描：阈值 0.5 时覆盖 2/4 个确认正例、总候选 2 对；0.45 时覆盖 3/4、总候选 3 对；0.4 时覆盖 4/4、总候选 4 对。历史池只有四个事件，没有触发前 5 截断，也没有全量负例成本，0.4 只用于展示阈值影响，不作为正式参数建议。

### 4.2 首事件语义检查

原脚本对聚餐事件完成一次生成、一次合并审核修正、一次独立复核；模型最终给出 passed=true、iterations=1。人工对照最终 candidate 与原文仍发现：

| 原文 | 最终候选 | 问题 |
| --- | --- | --- |
| “油滋麻花的……油滋麻花的吃多了也吃不下” | “食物包括油炸麻花……油炸食品吃多了让人不适” | 将形容食物油腻的表达具体化成食品名，并加入身体不适的原因；原文没有这些具体事实 |
| “小廖叫我去新华书店……我就把这事说了” | “小廖带我去新华书店，提起他之前……声称要从现在开始阅读” | 将我提起阅读往事写成小廖提起，叙述动作主体改变 |
| “刚好下周我不在家” | summary 写“下周独自在家” | 我外出不等于小廖独处，增加其他人均不在的限定 |

初稿的“不消化”被合并审核识别并修改成“让人不适”，独立复核随后对四个要点的 summary/detail 全部给出 true。审核确实发生了，但修正引入或保留的无来源限定仍被放行。以上属于本次人工对照结论，不是新增用户确认标签。

### 4.3 其余原始执行记录

前次要点组：A、B 各两次请求，四次全部因 RELATED 条目缺少必填 reason 而失败。A 两次耗时 92.10、74.72 秒，B 两次耗时 107.93、70.80 秒；总计四次服务请求。未取得完整合法 A/B 结果，因此没有调用 C，没有最终关系指标，也没有正式发布。

保留的无效响应仍可用于诊断模型输出，但不作为被程序接受的最终结果：

| 正例 | A 首次 / 结构重试 | B 首次 / 结构重试 | 能确认的现象 |
| --- | --- | --- | --- |
| 聚餐阅读 ↔ 出差安排 | RELATED/后续；RELATED/引发 | RELATED/引发；RELATED/引发 | A 首次把阅读到出差写成后续，重试更写成“督促阅读触发出差取消改期”；B 首次也把聚餐指向出差作为引发方向。存在关系类型、方向和事实生成错误；B 重试改为出差指向督促阅读，但仍缺 reason |
| 出差安排 ↔ 初到现场 | RELATED；RELATED | RELATED；RELATED | 原始状态均识别有关联；不能因为状态相符就忽略描述增加日期、动作等问题 |
| 出差安排 ↔ 工作推进 | NO_RELATION；RELATED | RELATED；RELATED | 同一次结构重试改变了语义结论，不能将重试理解为只改字段 |
| 初到现场 ↔ 工作推进 | UNRESOLVED；UNRESOLVED | RELATED；RELATED | 强制送判后仍存在漏判及 A/B 状态不一致，不能只靠放宽召回解决 |

因此，独立实验已经复现“漏召回”和“模型关系输出误判”；完整 A/B/C 最终效果受到结构失败限制，不能表述为已经完成新一轮最终准确率验收。

### 4.4 出差安排事件的失败与最后候选

原脚本执行了生成、第一轮合并修正、独立复核，以及第二轮合并修正的两次结构尝试，共 5 次请求。第二轮两次均返回“候选引用不真实”：模型将 detail 的非连续片段用 `...` 拼成 candidate_quote，不符合必须引用连续候选原文的要求。脚本达到两次上限后结束该事件，继续处理其他事件，没有无限重试。

该事件最后合法保存的候选来自第一轮修正，模型独立复核未通过，不能视为最终通过。它仍存在如下问题：

- summary 写“经历多次退回与延迟”，原文只明确一次退回；第一轮复核给该要点 summary_ok=true。
- 原文“不知道是什么江/景区”，被写成“名为‘江’的景区”，将不知道具体名称变成了一个具体名称。
- 原文“应该晚上8点到”，被补全为“8点左右抵达住处”，添加未明确的到达地点。

第一轮复核确实识别了另一处因果归因问题，所以本例同时说明审核可以发现部分错误，也会漏掉其他错误。第二轮原始输出即使包含修正，也未通过引用校验，本报告不采用它覆盖上次合法候选。

## 5. 原因判断与解决顺序

| 问题 | 本轮已证明的直接原因或路径 | 下一步最小验证 |
| --- | --- | --- |
| 要点失真未拦住 | 模型在改写时增加事实，合并审核及独立复核仍给出通过；原脚本同样发生 | 在审核中逐项核对候选事实与原文支持，重点验证主体、次数、指代、原因；保留未改提示作为对照，既有反例与未见样本分别验收 |
| 跨日漏召回 | 两组正例的最高要点相似度低于硬阈值 0.5；独立计算与正式记录一致 | 用更完整确认集比较阈值和前 K，报告漏检与候选成本；本轮 0.4 只作为离线证据，不直接上线 |
| 关系误判 | 原始响应误读因果与方向，部分输出还忽略同一事项持续推进；失真要点又会作为下游唯一事实输入 | 先核对来源要点，固定候选后验证证据定位和方向；将一致漏判与分歧裁决分开统计；不直接追加更多同类重试 |
| 字段与引用错误 | json_object 未强制必填字段；引用使用省略号后不再是连续候选原文 | 先单独验证 strict JSON Schema 的当前渠道兼容性；连续引用仍由程序校验，反馈明确显示哪条引用不匹配 |

本轮没有比较旧 Pro/原向量模型，不能断言 Flash 模型切换是唯一根因；也没有证明改用另一个模型、换提示或新增验证调用就能解决。上述最小验证均为后续建议，本次只完成复测、证据核对与调研，正式方案保持原样。
