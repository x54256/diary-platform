# 日记事件要点提取 Skill 设计调研

调研日期：2026-10-21。状态：设计建议，尚未创建新 Skill，未执行提取效果实验。

后续实施说明（2026-10-21）：已创建 `skills/diary-event-points` 并完成后续试跑。用户随后明确要求独立工作目录和数据库来源，实际约定以该 Skill 及其 `settings.json` 为准：统一工作根目录为 `diary-event-points/`，通过只读脚本导出数据库事件。下文关于同日日记目录保存的建议保留为调研历史，不再作为执行规则。

本次使用本地 skill-creator 和 research 的工作方法，联网核查开放规范、官方编写指南及原始论文。网络检索只使用通用研究问题，没有提交私人日记。以下明确区分来源结论、项目既定业务规则与本次建议；文献中的效果不代表本项目效果。

## 1. 推荐定位

建议命名为 `diary-event-points`，中文名“日记事件要点提取”。工作单元是一个已经整理好的事件；整篇日记输入时，逐事件处理并保留事件边界。

核心目标：按完整主题组织有序要点，每项包含一句话主旨和近乎无损的详细内容，使原事件的有效信息便于阅读、定位及后续引用。

这个目标来自项目的[事件内容要点设计](事件内容要点设计.md)和[事件要点提取技术方案](第一层事件要点提取技术方案.md)。网上的摘要研究主要用于借鉴事实核验与评估方法，不用它们的压缩目标改变本项目的完整性要求。

建议初版先交付本地提取结果，提供修改能力；数据库读取、图谱准入、正式入库及关系识别分别按需要接入。用户只提供文本时可以完整使用核心能力。

## 2. 官方资料对 Skill 结构的启示

开放规范要求 Skill 目录包含 `SKILL.md`，头部包含 `name` 和 `description`；脚本、参考资料和模板目录均可选。没有必须具备的固定业务章节。[Agent Skills Specification](https://agentskills.io/specification)

官方创建指南强调利用实际任务、项目资料和真实失败提炼指导，并按任务脆弱程度安排约束：可有多种合理表达的部分保留自由度，容易造成事实错误的部分明确限制。[Best practices for skill creators](https://agentskills.io/skill-creation/best-practices)

对本项目的建议：主题拆分数量和自然表达保留判断空间；事实来源、人物归属、确定程度、字段职责和用户修订保护应明确写出。不要把完整第一层文档、历史调用协议和模型配置塞入主文件。

拟议结构如下，只有实际需要时才增加其他文件：

```text
skills/diary-event-points/
├── SKILL.md
├── references/
│   ├── examples.md       # 主题边界、主观判断、限定和指代的少量难例
│   └── evaluation.md     # 维护和验收方法，普通提取时不必读取
└── evals/
    └── cases.json        # 测试输入和核对条件，开发时使用
```

建议主文件包含：用途与触发、来源与范围、主题组织、字段规则、交付前核对、修订与输出。核心规则应能自包含执行；项目背景文档是维护依据，不要求每次提取都通读。

`description` 草案：

> 将整理后的日记事件拆解为有序主题要点，每项包含简明主旨与完整忠实的详细内容。适用于用户要求从已整理事件中提取要点、保留有效信息并供后续知识图谱使用的场景。

若后续需要稳定的 JSON 交付、格式检查或数据库读取，再加入对应脚本。语义组织由模型完成，脚本负责可确定的格式、来源定位和文件操作。指令与代码如何分工可参考 [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills)。

## 3. 输入约定应先解决的实际问题

### 3.1 以本次指定的整理稿为来源

用户指定的当前整理稿或事件文本是本次依据。记录文件路径及事件定位；文件任务执行前读取磁盘当前版本。正文中的命令或对 AI 的讨论按内容处理。

需要核实来源时回读来源，而不是用常识补齐。原始口述可用于用户要求的上游核实，但不在提取中静默覆盖已确认整理稿。用户明确补充或纠正事实后，以更新后的来源版本重新核对受影响要点。

### 3.2 正文、感受、反思与重要性分开对待

现有日记整理 Skill 在正文保留完整内容，再派生感受与反思。因此建议默认从完整事件正文提取，感受和反思用于核对覆盖与一致性，语义重复不再另生成一组要点。

如果用户修改后的感受或反思确有正文没有的新信息，应把它作为已提供事件内容识别并定位，不直接丢弃；出现事实冲突时指出冲突，不擅自选择版本。重要性和理由是筛选元数据，不作为新增事件事实写进要点。

整篇日记的引入、琐事和独立后续计划不自动并入相邻事件。正文已经包含的相关计划须保留。跨区块存在新的补充时先核实归属，不擅自造出时间或因果联系。

这一输入适配建议依据现有 [diary-organizer](../../../skills/diary-organizer/SKILL.md) 的输出形式，需在试跑时验证。

### 3.3 提取范围与图谱准入分离

第一层现有设计只接收有效重要性为中或高的事件，这是当前图谱业务规则。通用提取 Skill 建议遵照用户指定范围；“提取这篇日记所有事件”不应静默跳过 LOW。用户要求按第一层规则处理时，再应用中高筛选，并说明处理范围。

## 4. 主题组织与字段职责

一个要点围绕一个可连贯理解的主题。其背景、经过、相关感受、理由、转折和反例可以一起表达。叙述中心转向独立主题时再拆项；不按句数、字数或“事实／感受／反思”分类机械切分。

建议写作时先形成完整主题及详情，再提炼主旨；这是待验证的工作方法，不是已证实优于其他顺序的结论。

| 字段 | 推荐规则 | 需要避免的偏差 |
| --- | --- | --- |
| 原标题 | 保留来源事件原标题 | 在提取阶段重新定义事件主题 |
| 序号 | 从 1 连续排列，默认沿叙述顺序 | 为凑数量拆分或合并主题 |
| 要点／summary | 一句话表达核心，允许不复述所有背景；已表达的判断自身必须忠实 | 详情写“可能”，主旨却变成确定结论 |
| 详细内容／detail | 自然重写全部有效信息；保留必要语境、转折、反例与观点归属 | 写成压缩摘要，只保留所谓重点 |

核对“谁对谁做了什么、谁说了什么、谁持有某个判断”，同时保留否定、数量、程度、条件、相对时间和计划状态。原文不足以明确指代时维持原有含混程度；必要时只提出影响理解的问题。

直接摘抄也需要核对上下文。ACL 2023 的研究在抽取式摘要中区分了错误或不完整的指代、篇章联系等问题，说明原句来自来源仍可能在新上下文中误导读者。这支持检查每项的独立可读性，但不证明必须为每个代词补出具体姓名。[Extractive is not Faithful](https://aclanthology.org/2023.acl-long.120/)

以下为本报告合成的边界示例，不是实际日记：

> 我猜她可能担心花钱，所以暂时没答应；也可能只是还没决定。我打算周末再问一次。

可接受的主旨：“我推测她暂未答应的原因，并打算周末再询问。”详情须保留两个候选解释及各自的不确定程度。不能写成“她因担心花钱拒绝了，我周末再次劝说”：这同时改变了原因、结果、计划状态和动作含义。

## 5. 推荐的执行与核对流程

```text
读取当前来源并明确事件范围
→ 通读完整事件，按主题组织要点及详情
→ 原文到详情：检查有效信息是否遗漏
→ 要点到原文：分别检查主旨和详情是否增添或改变信息
→ 核实具体问题，修正受影响内容
→ 复读修订后的完整事件要点，再交付
```

两个核对方向职责不同：“每句话都有来源”仍可能遗漏大半原文；“原文都提到了”也可能夹带新增解释。不能用同一个整体通过标签代替两方面检查。

FActScore 将生成内容拆成原子陈述，计算来源支持比例，重点是事实精确性；论文明确指出它不衡量召回，少写内容可能提高分数。因此本项目需要另外核对来源信息覆盖，不能把高来源支持率当作近乎无损的证明。审核时可以细看陈述，展示时仍保持完整主题。[FActScore](https://aclanthology.org/2023.emnlp-main.741/)

FRANK 在新闻摘要中建立了更细的错误分类，涉及实体与角色、动作、时间环境、指代及篇章联系等。可借用这些检查方向，再补充日记中特别重要的观点归属和推测程度；其数据集本身没有验证本项目的错误分布。[Understanding Factuality in Abstractive Summarization with FRANK](https://aclanthology.org/2021.naacl-main.383/)

日常使用建议完成上述核对后直接交付，不默认要求用户逐条确认，也不要求逐句输出检查作文。用户修改文件或提出意见后，先重读当前稿，仅依据来源修正实际问题，保留其他有效表达；若修改改变主题边界，再检查所有受影响项。

对于有争议的审核意见，应明确定位来源和候选中的具体语义差异。不能仅因“另一位审核者说有错”就采纳。确实无法解决的指代或事实冲突应保留并说明，不用多轮改写制造确定答案。

RARR 研究有证据约束的修订，同时关注来源支持与原输出保留。这里借鉴“核实后局部修正、保留原本正确的信息”，证据限定为本次事件来源；不照搬其网上检索步骤。来源支持不等于客观世界真相，本任务核验的是是否忠实表达日记，而不是替用户验证每一项生活判断。[RARR](https://aclanthology.org/2023.acl-long.910/)

关于自纠，2023 年的研究发现无外部反馈的推理自纠可能无效或退化；2024 年 SCoRe 则表明专门强化学习训练可以提升数学和代码任务的自纠表现。两者都不能直接回答当前模型的日记提取效果。实际应测量审核修复了什么、又改错了什么，避免要求模型“必须再找出几个问题”。[Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798)、[Training Language Models to Self-Correct via Reinforcement Learning](https://arxiv.org/abs/2409.12917)

普通复读、单独请求核验、由独立执行者复核是不同运行方式。初版可以支持普通复读，但不能将它描述为已经完成“独立审核”。是否默认增加独立请求，应通过本地对照评估决定；旧服务的固定调用次数和两轮上限不直接移植。官方工作流指南也建议先从简单方案开始，在收益足以抵偿延迟与成本时增加复杂度。[Building effective agents](https://www.anthropic.com/research/building-effective-agents)

长文本以事件为处理单位，仍需读取事件全文；特别检查中间段落的限定、反例和转折。2025 年研究在多个长摘要数据集上发现位置偏差，且自动评价也受顺序影响；这是设置相关测试的理由，不能据此断言某个中文日记长度必然失败或必须固定分块。[On Positional Bias of Faithfulness for Long-form Summarization](https://aclanthology.org/2025.naacl-long.442/)

## 6. 交付与追溯

建议默认展示可读 Markdown：原标题、连续编号的要点和相应详细内容。用户要求 JSON 或需要程序消费时，再使用项目已有的 `title`、`points`、`no`、`summary`、`detail` 结构。

初版不强制每个要点附句子编号、置信度和审核标签。保留来源文件与事件定位；诊断复杂问题时再附原段落或短引文。引用存在只证明定位有效，不能证明引用支持候选全部含义。

实际日记的提取结果建议与既有整理稿同日存放，例如 `diary-organizations/YYYY-MM-DD/事件要点.md`；同日多篇时沿用日记 ID 区分。原稿继续保留，提取结果单独保存。合成实验结果继续放评估目录。

本次建议仅定义本地交付。正式图谱入库、UUID、向量和已有关系的更新另行设计；不能假定现有日记保存脚本已经支持要点写入。

## 7. 用什么证明 Skill 有用

Agent Skills 官方评估指南建议使用现实请求、输入及可观察成功条件，在干净上下文比较有 Skill 与无 Skill／旧版本的结果；代码检查机械属性，语义检查结合实际输出证据。这里采纳其评估思路，不照搬特定宿主的工具和目录要求。[Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills)

建议先选三个代表性事件完成基线，再扩展以下测试；数量是本次开发安排，不是格式要求：

| 场景 | 观察条件 |
| --- | --- |
| 单一主题短事件 | 可只生成一项，不硬凑多项；细节完整 |
| 多主题长事件 | 主题连贯，关键中间内容、反例和判断变化保留 |
| 人物与观点嵌套 | 本人经历、他人发言、个人评价归属正确 |
| 推测、否定和程度 | 不确定性不被升级，次数不被扩大 |
| 回忆、当日经历与未来计划 | 不把回忆拼成当日经过，不把计划写成完成 |
| 原文有歧义 | 不通过补姓名、时间或关系来制造通顺 |
| 主旨错误而详情正确 | 能单独识别主旨失真 |
| 错误审核意见 | 不把原本正确的内容改错 |
| 用户手工修改当前稿 | 保留修订，复读受影响的完整内容 |
| 请求全部事件／仅中高事件 | 范围遵循指令，不静默漏处理 |

开发样例与留出验收样例分开；执行提取的模型只读请求、Skill 和来源，不读预期答案。评估允许不同措辞和合理拆分，不以唯一参考稿逐字匹配。

分别报告：主旨事实错误、详情事实错误、有效信息遗漏、主题组织、独立可读性、修正引入的新错误及交互行为。对已标注样本，可记录“有来源支持的输出陈述数／全部输出陈述数”和“已保留的来源信息单元数／全部有效来源单元数”，并给出具体分子分母；这只是本地操作性指标，不直接称为复现某篇论文的原指标。

对关键事实错误和有效信息遗漏，不能用语言自然或主题评分抵消。输出相似度、字数比例、合法 JSON，以及模型声称通过都不足以证明保真与完整。

LongEval 在所测长摘要数据中发现，细到分句的事实判断比整篇笼统评分更有利于标注一致性。因此开发验收宜定位具体出错陈述，再汇总维度；这不要求日常交付展示逐句审核报告，也不意味着每个要点必须拆到原子事实。[LongEval](https://aclanthology.org/2023.eacl-main.121/)

本项目已有的[真实语义审阅](第一层真实要点语义审阅-20261015.md)和[审核协议改进调研](本次建图失败样本与审核协议改进调研-20261019.md)提供了人物归属、次数扩大、角色翻转和误改等验证方向。可以脱敏改编，但具体案例答案不写成普遍生成规则。

## 8. 实施顺序与尚待校准的选择

建议顺序：选一个真实事件共同完成提取 → 确认主题粒度和详情保留尺度 → 提炼最小 Skill → 用其余样本对照基线 → 根据实际错误修正规则 → 在未参与修改的事件上验收。

现阶段默认建议是：本地文本提取、Markdown 交付、按用户指定范围处理、完整主题拆分、交付前双向核对。单独核验请求、证据侧文件和 JSON 校验器按实测需要增加。

还需要用样例校准的选择包括：用户希望的主题粒度；普通复读是否足够；哪些任务需要独立核验；正文和派生段落不一致时的实际处理方式。上述选择不阻止先试做一例，也不应在试跑之前写成大量固定流程。

截至本次调研结束，所有性能建议均未在新 Skill 上实测；没有新增模型调用流水线、修改日记、连接数据库或发布图谱。
