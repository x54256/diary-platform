# 事件知识与关系图谱数据库设计（评审稿）

> 文档状态：评审稿
> 设计基线：2026-08-31 已确认需求与数据库讨论结论
> 评审范围：首次分析统一发布涉及的分析任务、事件知识、知识复核、正文向量、事件关系和关系证据
> 对应需求：[日记事件关系图谱需求规格](../../需求规格/规划功能/日记事件关系图谱需求规格.md)、[知识库管理需求规格](../../需求规格/规划功能/知识库管理需求规格.md)、[统一搜索语义增强增量需求规格](../../需求规格/用户端/日记管理/统一搜索语义增强增量需求规格.md)

## 1. 设计目标

本设计为以下统一流程提供数据库结构：

```text
organized 日记首次点击“AI 分析”
  → 标签提取
  → body 向量生成
  → 当前日记全部事件对关系识别
  → 历史候选召回与关系识别
  → 事件知识凝练与复核
  → 核心分析
  → 认知分析
  → 行动项规划
  → 单个数据库事务发布全部正式结果
```

数据库设计需要保证：

1. 一个来源结构化事件只生成一个事件知识。
2. 图谱边连接事件知识，关系判定证据追溯到来源结构化事件正文。
3. 图谱召回与统一搜索使用同一套纯 `body` 向量。
4. 首次分析失败不留下标签、分析、行动项、知识、向量或关系的部分正式结果。
5. `analyzed` 日记重新分析只生成新分析轮次，不修改事件知识、正文向量和图谱关系。
6. 不兼容旧知识沉淀和旧三层向量结构，允许破坏性迁移，不执行数据回填。

## 2. 已确认决策

1. 首次分析使用一个统一 LangGraph；所有节点结果先进入 checkpoint，最后由单一发布节点提交正式数据。
2. 当前日记内部关系一次提交全部事件和全部待判定事件对；超过模型输入预算时按事件对拆批，同一待判定事件对只进入一个批次。
3. 新事件知识解除对 `knowledge_tasks`、`knowledge_deposits` 的依赖。
4. 事件知识不保存知识向量；正文向量归属来源 `diary_events`。
5. 知识复核保持现有留痕范围，只保存 `issues` 和 `content_changed`；不保存第一次凝练的 `coverage`，也不保存关系证据到最终知识表达的映射。
6. LOW 关系以 `CANDIDATE` 保存；用户否决后保留记录并改为 `REJECTED`。
7. 旧知识、旧三层向量和旧知识任务不迁移、不回填。
8. 事项匹配停止运行；保留 `knowledge_atomic_events.matter_id` 和 `knowledge_matters` 以维持遗留事项只读查询，新流程不写入事项归属。
9. 同一方向、同一关系类型只保存一条关系；同一对事件允许不同关系类型，也允许分别保存正向和反向的有向关系。
10. 关系证据作为关系表的一个 `JSONB` 属性保存，不建立证据明细表。

## 3. 设计原则

### 3.1 正式数据与过程数据分离

- LangGraph checkpoint 保存冻结输入、批次游标、模型输出、向量结果、关系临时结果和知识候选结果。
- 正式业务表只保存最终分析结果、事件知识、复核问题、正文向量和关系。
- `coverage` 和关系证据保留检查是发布前校验数据，成功发布后随 checkpoint 清理。
- checkpoint 清理失败不回滚已提交的正式结果，由现有清理机制补偿。

### 3.2 来源不可变

首次分析成功后，事件知识、向量和关系证据共同依赖同一版 `diary_events.event_title + body`。来源原文和结构化事件保持不可修改、不可重新整理；重新分析不改变来源。

### 3.3 不复制正文

- 正文只保存在 `diary_events.body`。
- 向量表只保存正文位置和向量，不重复保存完整正文或自然段文本。
- 关系证据保存必要的原文连续引用，用于解释关系和防止来源展示受后续代码格式变化影响。

### 3.4 数据库约束优先

唯一性、枚举范围、非自环、同用户端点和向量粒度使用数据库约束保证。模型结果先通过程序校验，再进入最终事务。

## 4. 总体数据关系

```text
diaries
  ├─ 1:1 diary_organized
  │      └─ 1:N diary_events
  │              ├─ 1:1 knowledge_atomic_events
  │              └─ 1:N event_embedding_chunks
  │
  ├─ 1:N organize_tasks
  └─ 1:N analysis_runs
          ├─ 1:N analysis_items
          ├─ 1:N diary_action_items
          └─ 1:N knowledge_event_reviews       analysis_run_id

knowledge_atomic_events
  ├─ source 0:N event_knowledge_relations
  └─ target 0:N event_knowledge_relations
```

当前日记内部关系的两个端点可以同时是本次事务新建的事件知识。历史关系的一端是本次新建事件知识，另一端是已有历史事件知识。发布节点在事务开始前为本次事件知识预分配 UUID，再完成来源事件 ID 到知识事件 ID 的确定性映射。

## 5. 分析任务模式

### 5.1 `organize_tasks` 变更

复用现有 `analysis_mode` 字段，扩展其取值以区分首次分析与重新分析：

| 字段 | 类型 | 约束与用途 |
|---|---|---|
| `analysis_mode` | `VARCHAR(32)` | 分析任务取 `INITIAL / REANALYSIS / FEEDBACK_REANALYSIS`；整理任务为空 |
| `source_structured_revision` | `INTEGER` | 分析任务必填，冻结启动时结构化修订号 |
| `current_step` | `VARCHAR(50)` | 统一图当前节点 |

规则：

- 日记为 `organized` 时创建 `INITIAL` 任务。
- 日记为 `analyzed` 且不存在有效反馈时创建 `REANALYSIS` 任务。
- 日记为 `analyzed` 且存在有效反馈时创建 `FEEDBACK_REANALYSIS` 任务。
- 任务失败重试时沿用已冻结的 `analysis_mode` 和 `source_structured_revision`，不得根据重试时的日记状态重新选分支。
- 只有 `INITIAL` 执行知识、正文向量和关系节点。

### 5.2 `analysis_runs`

沿用现有分析轮次表。首次分析的 `analysis_run` 在最终发布事务中创建，知识复核记录通过 `analysis_run_id` 保留现有任务来源留痕。

`REANALYSIS` 和 `FEEDBACK_REANALYSIS` 产生新的 `analysis_runs`，但不会改写首次分析关联的图谱数据。

## 6. 事件知识

### 6.1 重建 `knowledge_atomic_events`

| 字段 | 类型 | 空值 | 说明 |
|---|---|---:|---|
| `id` | `UUID` | 否 | 主键，图谱节点 ID |
| `user_id` | `UUID` | 否 | 外键 `users.id`，用户隔离 |
| `diary_id` | `UUID` | 否 | 直接外键 `diaries.id` |
| `source_diary_event_id` | `UUID` | 否 | 外键 `diary_events.id`，一对一来源 |
| `title` | `VARCHAR(20)` | 否 | 事件知识标题 |
| `content` | `JSONB` | 否 | 非空自然段数组 |
| `occurred_on` | `DATE` | 否 | 事件发生日期 |
| `occurred_time` | `TIME` | 是 | 明确到分钟时填写 |
| `matter_id` | `UUID` | 是 | 遗留事项外键；新流程固定为空，仅供旧事项只读查询 |
| `created_at` | `TIMESTAMP` | 否 | 发布时间 |

约束与索引：

```sql
PRIMARY KEY (id);
UNIQUE (source_diary_event_id);
UNIQUE (id, user_id); -- 供关系表复合同用户外键使用
CHECK (char_length(title) BETWEEN 1 AND 20);
CHECK (jsonb_typeof(content) = 'array' AND jsonb_array_length(content) > 0);
INDEX (user_id, occurred_on DESC, occurred_time DESC NULLS LAST, created_at DESC, id DESC);
INDEX (diary_id);
INDEX (matter_id, occurred_on DESC, occurred_time DESC NULLS LAST, id DESC);
```

成员为非空字符串以及每个来源事件恰好生成一条结果，由发布服务在事务前校验。

删除规则：

- `diary_id`、`source_diary_event_id`、`matter_id` 使用 `ON DELETE RESTRICT`。
- 已进入图谱的事件知识不提供业务删除接口。

以下旧字段从新结构删除：

- `source_order`；
- `embedding`。

### 6.2 解除旧沉淀依赖

- `knowledge_atomic_events.diary_id` 不再引用 `knowledge_deposits(diary_id)`。
- 删除独立沉淀流程后，`knowledge_tasks`、`knowledge_deposits` 不再被新流程使用。
- 旧表是否直接 DROP 由破坏性迁移执行，不设计双写、兼容视图或数据转换。

## 7. 知识复核

### 7.1 调整 `knowledge_event_reviews`

保持当前正式留痕范围：

| 字段 | 类型 | 空值 | 说明 |
|---|---|---:|---|
| `id` | `UUID` | 否 | 主键 |
| `knowledge_event_id` | `UUID` | 否 | 外键 `knowledge_atomic_events.id`，唯一 |
| `analysis_run_id` | `UUID` | 否 | 外键 `analysis_runs.id`，替代旧 `knowledge_tasks.id` 外键 |
| `issues` | `JSONB` | 否 | 二次复核发现的问题数组 |
| `content_changed` | `BOOLEAN` | 否 | 最终结果是否修改第一次候选 |
| `created_at` | `TIMESTAMP` | 否 | 复核发布时间 |

约束：

```sql
UNIQUE (knowledge_event_id);
CHECK (jsonb_typeof(issues) = 'array');
```

`knowledge_event_id` 使用 `ON DELETE CASCADE`；`analysis_run_id` 使用 `ON DELETE RESTRICT`。

不增加以下字段：

- `coverage`；
- 关系证据保留检查结果；
- 候选知识副本；
- 最终知识副本。

## 8. 统一正文向量

### 8.1 重建 `event_embedding_chunks`

| 字段 | 类型 | 空值 | 说明 |
|---|---|---:|---|
| `id` | `UUID` | 否 | 主键 |
| `event_id` | `UUID` | 否 | 来源 `diary_events.id` |
| `chunk_type` | `VARCHAR(20)` | 否 | `FULL_BODY / BODY_PARAGRAPH` |
| `body_index` | `INTEGER` | 是 | 原 `body` 数组下标；完整正文为空 |
| `embedding_model_signature` | `VARCHAR(200)` | 否 | 模型与关键参数签名 |
| `embedding` | `VECTOR(1024)` | 否 | 检索向量 |
| `created_at` | `TIMESTAMP` | 否 | 生成时间 |

约束：

```sql
CHECK (
  (chunk_type = 'FULL_BODY' AND body_index IS NULL)
  OR
  (chunk_type = 'BODY_PARAGRAPH' AND body_index >= 0)
);

UNIQUE (event_id)
WHERE chunk_type = 'FULL_BODY';

UNIQUE (event_id, body_index)
WHERE chunk_type = 'BODY_PARAGRAPH';
```

索引：

```sql
INDEX (event_id);
HNSW (embedding vector_cosine_ops);
```

### 8.2 文本与下标规则

- `FULL_BODY`：按固定连接规则和原顺序连接全部非空 `body` 元素。
- `BODY_PARAGRAPH`：每个非空原数组元素生成一条向量，`body_index` 保留原始数组下标，不因过滤空元素而重新编号。
- 向量表不保存 `content`；搜索命中展示时从 `diary_events.body` 读取。
- 同一首次分析中的所有事件向量使用同一 `embedding_model_signature`。
- 查询向量仅与相同签名、相同维度的事件向量比较，禁止混用不同模型。

### 8.3 删除旧异步状态

首次分析同步生成向量并统一发布后，不再需要 `search_semantic_index_states` 的 `PENDING / READY` 状态。该表在破坏性迁移中删除。

每日 06:00 向量任务、24 小时静默窗口、存量自动对账和旧三层向量重建不再运行。`search_keyword_segments` 继续服务关键词分支，不受本表重建影响。

## 9. 事件关系

### 9.1 新增 `event_knowledge_relations`

| 字段 | 类型 | 空值 | 说明 |
|---|---|---:|---|
| `id` | `UUID` | 否 | 主键 |
| `user_id` | `UUID` | 否 | 用户隔离 |
| `source_knowledge_event_id` | `UUID` | 否 | 有向关系起点 |
| `target_knowledge_event_id` | `UUID` | 否 | 有向关系终点 |
| `relation_type` | `VARCHAR(20)` | 否 | 五类关系之一 |
| `status` | `VARCHAR(20)` | 否 | `CONFIRMED / CANDIDATE / REJECTED` |
| `confidence` | `VARCHAR(10)` | 否 | 模型原始 `HIGH / MEDIUM / LOW` |
| `continuation_result` | `VARCHAR(20)` | 是 | `EXECUTED / EXECUTED_FAILED` |
| `plan_source` | `VARCHAR(20)` | 是 | `SELF / THIRD_PARTY` |
| `reason` | `TEXT` | 否 | 关系类型成立的判定理由 |
| `evidence` | `JSONB` | 否 | 起点和终点的原文证据 |
| `reviewed_at` | `TIMESTAMP` | 是 | LOW 候选人工确认或否决时间 |
| `created_at` / `updated_at` | `TIMESTAMP` | 否 | 生命周期时间 |

核心约束：

```sql
CHECK (source_knowledge_event_id <> target_knowledge_event_id);
CHECK (relation_type IN ('CONTINUATION','CAUSAL','ASSOCIATION','THEMATIC','REFERENCE'));
CHECK (status IN ('CONFIRMED','CANDIDATE','REJECTED'));
CHECK (confidence IN ('HIGH','MEDIUM','LOW'));
CHECK (jsonb_typeof(evidence) = 'object');
UNIQUE (user_id, source_knowledge_event_id, target_knowledge_event_id, relation_type);
```

唯一约束只禁止同一方向、同一类型的重复边。例如可以同时保存 `A → B / CAUSAL`、`B → A / REFERENCE` 和 `A → B / CONTINUATION`。

方向规则：

- `CONTINUATION`、`CAUSAL`、`REFERENCE` 是有向关系，按模型判定保存起点和终点。
- `ASSOCIATION`、`THEMATIC` 是对称关系，发布服务按 UUID 固定顺序写入起点和终点，并同步交换两侧证据，防止同一种对称关系重复保存为 `A → B` 和 `B → A`。

状态与审核时间约束：

```sql
CHECK (
  (confidence IN ('HIGH','MEDIUM') AND status = 'CONFIRMED' AND reviewed_at IS NULL)
  OR
  (confidence = 'LOW' AND status = 'CANDIDATE' AND reviewed_at IS NULL)
  OR
  (confidence = 'LOW' AND status IN ('CONFIRMED','REJECTED') AND reviewed_at IS NOT NULL)
);
```

同用户约束使用复合外键保证：

```sql
FOREIGN KEY (source_knowledge_event_id, user_id)
  REFERENCES knowledge_atomic_events(id, user_id) ON DELETE RESTRICT;

FOREIGN KEY (target_knowledge_event_id, user_id)
  REFERENCES knowledge_atomic_events(id, user_id) ON DELETE RESTRICT;
```

业务检查约束：

- `relation_type <> 'CONTINUATION'` 时，`continuation_result` 和 `plan_source` 必须为空。
- HIGH、MEDIUM 初始状态必须为 `CONFIRMED`。
- LOW 初始状态必须为 `CANDIDATE`。
- LOW 人工确认后状态改为 `CONFIRMED`，人工否决后改为 `REJECTED`；两者都填写 `reviewed_at`。
- `confidence` 始终保存模型原始判断，人工操作不覆盖。
- `REJECTED` 不进入图谱查询结果，但保留审计记录。

查询索引：

```sql
INDEX (user_id, source_knowledge_event_id, status);
INDEX (user_id, target_knowledge_event_id, status);
INDEX (user_id, status, relation_type);
```

### 9.2 不保存无关系判定

模型判定为无关系的事件对只用于当前批次完整性校验，不进入正式业务表。首次分析不会重复建图，因此不需要负关系表。

## 10. 关系证据

关系证据需要表达：

- 证据属于关系的哪一个端点；
- 原文位于 `body` 哪个自然段；
- 支撑关系成立的逐字连续引用；
- 每侧支持最少一条、按需多条证据的能力。

不保存：

- 证据在事件知识中的位置；
- 事件知识中的对应改写；
- 单独的证据理由；
- 关系证据保留检查结果。

关系整体的解释保存在 `event_knowledge_relations.reason`。

### 10.1 存储结构

证据直接保存在 `event_knowledge_relations.evidence` 中：

```json
{
  "source": [
    {
      "body_index": 2,
      "quote": "今年公司收益下降"
    }
  ],
  "target": [
    {
      "body_index": 1,
      "quote": "管理层决定启动裁员"
    }
  ]
}
```

`source` 和 `target` 必须是非空数组。每条证据只保存原正文下标和连续引用；数组成员结构、下标合法性以及引用确实存在于对应正文，由发布服务在事务前校验。

证据依附于关系，没有独立查询、编辑和生命周期需求，因此作为关系属性即可满足追溯与展示要求。

## 11. 最终发布事务

### 11.1 事务外工作

以下工作全部在 LangGraph 节点中执行，结果写入 checkpoint：

- 模型配置和结构化修订冻结；
- 标签提取；
- embedding 调用；
- 当前日记事件对关系判定；
- 历史候选召回和关系判定；
- 事件知识凝练、`coverage` 校验和二次复核；
- 核心分析、认知分析和行动项规划；
- 所有模型输出的结构与来源引用校验。

### 11.2 单事务写入顺序

发布节点使用一个 `Session` 和一个事务：

1. 锁定 `diaries`、`diary_organized` 和当前 `organize_tasks`。
2. 校验日记仍为 `organized`、修订号未变化、任务执行权有效。
3. 插入本次 `analysis_runs` 和 `analysis_items`。
4. 更新日记元数据、心情和标签关联。
5. 写入行动项及其分析来源关联。
6. 插入全部 `knowledge_atomic_events`。
7. 插入全部 `knowledge_event_reviews`。
8. 插入全部 `event_embedding_chunks`。
9. 将来源事件关系映射为知识事件关系并插入正式边与 LOW 候选。
10. 将日记状态更新为 `analyzed`。
11. 将分析任务状态更新为 `completed`。
12. 提交事务。

任一步失败时整体回滚。标签不再单独提交，向量不再失败降级，事件知识不再提前发布。

### 11.3 幂等与重试

- 最终发布实现为 LangGraph 的 `PUBLISH` 节点。前序节点的结果已写入 checkpoint，只有 `PUBLISH` 成功后图才进入完成状态。
- `PUBLISH` 事务提交前失败或整体回滚：该节点抛出异常，不写入完成 checkpoint；用户重试同一任务和 thread 时从 `PUBLISH` 节点继续，无需重新调用前序模型。
- 数据库提交成功后，日记状态和任务状态同时完成。如果进程在提交成功后、LangGraph 记录节点完成前退出，重试时发布节点先读取任务状态；发现任务已完成后直接结束。
- 数据库唯一约束作为重复发布的最后防线。
- checkpoint 清理在事务提交后执行，清理失败不改变正式结果。

## 12. 重新分析边界

`REANALYSIS` 和 `FEEDBACK_REANALYSIS`：

- 创建新的 `analysis_runs` 和 `analysis_items`；
- 更新行动项和当前分析轮次；
- 按现有规则更新分析相关关键词片段；
- 不写 `knowledge_atomic_events`；
- 不写 `knowledge_event_reviews`；
- 不写 `event_embedding_chunks`；
- 不写或更新 `event_knowledge_relations`。

首次分析的知识复核记录继续引用对应 `analysis_run_id`；该轮次后续变为 `HISTORY` 时仍保留，不级联删除。

## 13. 破坏性迁移边界

本设计不提供旧数据兼容。迁移按以下边界执行：

1. 上线前由用户使用独立 SQL 清理旧知识数据。
2. 删除旧知识沉淀入口和后台 worker 启动逻辑。

## 14. 非数据库待审决策

### D-03 关系模型是否返回无关系判定

- **A（推荐）**：每个输入事件对都返回一条判定，其中 `relations` 是关系数组；空数组表示无关系，非空数组允许同一事件对包含多种关系。程序校验批次完整，数据库只保存数组中的关系。
- **B**：模型只返回识别出的关系数组，未返回的事件对直接视为无关系。

推荐 A：模型漏输出与明确判定无关系能够被区分。

### D-04 关系识别模型配置

- **A（推荐）**：增加 `event_relation_identify` 步骤，默认继承“分析”模型，允许管理端单独覆盖。
- **B**：直接使用“知识”模型，不增加独立步骤配置。

该决策影响 `model_management.STEP_SETTING_KEYS` 和管理端步骤配置，不改变关系表结构。
