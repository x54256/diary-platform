# 备份与恢复实现设计

核对基线：2026-10-29。对应[功能约定](功能约定.md)，当前格式版本和表清单以 [backup_restore.py](../../../backend/services/backup_restore.py) 为准。

## 1. 实现边界与对应关系

| 业务能力 | 实现 |
|---|---|
| 管理员访问、任务创建与记录 | [admin_backup.py](../../../backend/routers/admin_backup.py) |
| 表范围、筛选、包、预检与插入 | [backup_restore.py](../../../backend/services/backup_restore.py) |
| 每日触发、并行执行、失败重试 | [backup_scheduler.py](../../../backend/services/backup_scheduler.py) |
| 任务和报告持久化 | [backup.py](../../../backend/models/backup.py) |
| 确认、上传、进度和下载 | [管理页面](../../../frontend/pages/admin/backup-restore.vue) |
| 调度启动与停止 | [main.py](../../../backend/main.py) |

路由前缀 `/diary/api/admin/backup-restore`，全部复用 `require_admin`。导出、导入使用 FastAPI `BackgroundTasks` 执行同步任务，记录存数据库；当前未提供进程重启后导入/导出任务的断点续跑器。

## 2. 数据组织与筛选

`BACKUP_TABLES` 与 `IMPORT_ORDER` 为固定 schema v3 的 12 张表；业务含义见功能约定。`MODEL_BY_TABLE` 将普通表映射到 ORM，`diary_tags` 作为关联表单独处理。序列化按模型列取值，将 UUID、日期时间和枚举转为 JSON 值。

全量导出直接读取这些表的全部记录。筛选导出先收集 `Diary.id`：用户、起止日期组合为交集，再按日记、整理结果、事件、分析轮次追踪子表。用户和标签按所选日记归属收集；收藏同时涵盖所选日记及其事件。

全量和筛选路径均未将软删除行排除。筛选用户但无匹配日记时，不导出孤立用户记录。`organize_tasks` 保留实际状态，包括运行中；这只是数据序列化，不构成可恢复执行协议。

## 3. 导出事务与文件

1. 创建 `pending` 导出记录，后台转换为 `running` 并提交。
2. 创建系统临时目录，按表刷新任务记录并检查取消标记。
3. 读取该表行，写 UTF-8 JSONL，计算字节级 SHA-256 和数量。
4. 写 manifest，包括系统名、schema 版本、导出时间、记录 ID、包 ID、范围和表元数据。
5. 使用 `pyzipper.AESZipFile`、`WZ_AES` 和 ZIP deflate 加密所有数据文件与 manifest。
6. 将包写入 `BACKUP_DIR`，记录文件路径、包标识、成功状态和 7 天过期时间。

`BACKUP_STORAGE_PATH` 为绝对路径时直接使用，相对路径以 backend 目录解析；目录在服务模块载入时创建。每个包使用独立标识和文件名，临时目录随上下文退出删除。包密钥只从 `BACKUP_MASTER_KEY` 读取。

当前实现逐表将查询结果转为列表、文件摘要读取完整文件、最终读取完整 ZIP 再写目标目录。它不是全链路流式导出；大数据量时的内存及磁盘需求需单独评估。

取消只在每个表开始前刷新记录并检查。压缩/复制阶段没有持续取消检查；最后一次检查后的取消仍与最终成功写回存在竞争。当前不能保证点击取消后任何阶段都立即停止。

下载只接受成功记录、有效路径与文件名，并检查 `file_expires_at`；过期更新记录并拒绝。成功下载另外保存 `operation_type=download` 记录。

## 4. 预检与包完整性

上传接口将文件全文读入内存并保存为导入包，然后使用系统主密钥读取 ZIP。预检是同步执行，成功生成 `precheck` 记录及逐表统计。

`read_backup_payload` 按固定表清单读取 JSONL，解析 manifest 和每行 JSON。manifest 提供某表摘要时校验实际 SHA-256；当前摘要缺失时不会自动拒绝，不能声称强制执行全部摘要完整性要求。

`precheck_backup`：

- schema 版本必须精确等于当前值。
- 按包内 ID/关联键检测重复。
- 检查主键在数据库是否存在，存在计为跳过。
- 父记录可以在数据库或同包 ID 集合中存在。
- 捕获格式、UUID 和关联检查异常，按表统计新增、跳过、失败，摘要截取前 5 项。

预检不会实际试插入每行，也没有完整遍历模型必填字段和类型约束。包内父 ID 存在不能证明该父行正式导入必定成功；预检数量为预计值。

## 5. 正式导入及部分失败

正式导入要求成功预检记录及其文件路径，另建 `import` 记录，由后台执行。当前接口没有对预检记录的一次性消费约束；重复导入按主键跳过策略处理。

后台再次解密读取文件，按 `IMPORT_ORDER` 遍历：

1. 检查主键是否已存在。
2. 检查父数据此时已真实存在。
3. 将指定 UUID、日期、时间字段解析为 ORM 类型；历史 `draft/published` 日记状态映射为 `saved`。
4. 插入并 `flush/commit` 当前行。
5. 异常时回滚当前行、记录失败并继续。

每张表完成后保存一条 `BackupImportReport`，含数量、前 20 项失败/跳过摘要和 7 天到期时间。最终按失败数生成 `success` 或 `partial_failed`，保存逐表汇总。

这不是整个包的原子事务：已经提交的行不会因后续失败撤销。当前正式导入调用 `read_backup_payload`，没有再次执行 `precheck_backup` 的 schema 版本判断；它依赖成功预检记录与原保存文件未被更换。文件路径保护、完整性和导入前置不能仅靠客户端确认保证。

## 6. 定时调度与决策

[决策记录](定时备份决策.md)保留应用内调度、并行与单实例取舍。`next_scheduled_run` 将当前时刻转换到配置时区，构造当天触发点；已到或超过则移至次日，严格不补跑。

调度器每次等待后创建独立 asyncio task，再计算下次运行，不等待前一导出完成。同步导出在线程池执行。每次定时尝试查询 `admin` 用户，创建独立导出记录并调用完整导出服务；失败立即重试一次，重试会创建新的导出记录。

`start` 避免同一管理器实例重复启动并验证时间/时区；`stop` 取消等待调度并等待已启动任务。它没有数据库租约、跨进程锁或多副本去重机制；单 worker/单调度实例是已接受部署约束。

配置只列名称：`BACKUP_SCHEDULE_TIME`、`BACKUP_SCHEDULE_TIMEZONE`、`BACKUP_STORAGE_PATH`、`BACKUP_MASTER_KEY`。备份包持久化由部署卷保证，文档不保存密钥值。

## 7. 审计与恢复前置

`BackupRestoreRecord` 保存操作类型、状态、范围、阶段、操作人、文件信息、摘要和时间；模型有 `environment` 字段，但当前列表和单条查询未以环境过滤。`BackupImportReport` 保存逐表结果及期限。

- 列表按时间倒序取最近 100 条，当前未提供分页游标。
- 下载、预检、导入创建独立记录；取消更新原导出记录。
- 任务详情响应未返回操作人字段；报告读取未过滤 `expires_at`。
- 当前模块没有自动删除过期包、上传包、报告或 90 天审计的清理调度器。
- 导入前没有主动暂停语音任务或清除 MinIO 对象的协调步骤，也不校验所有未纳入表的跨模块关联。
- 加密密码字段使用部署端 Fernet 密钥；导出包能解密不代表密码密文能被目标环境的认证服务解密。

旧规格中“恢复前终止语音任务”“到期自动物理清理”等仍作为待完成约定保留。不能通过本轮文档整理把这些缺口标为已实现。

## 8. 验证与后续维护

现有[定时备份测试](../../../backend/tests/test_backup_scheduler.py)覆盖时间配置、启动不补跑和失败重试。两份旧临时 issue 的时间/重试/并行/目录约定已提炼至本组文档；并行调度和生产卷持久化需分别核验，不能用单元测试存在代替生产验证。

后续改动备份范围时，必须同时核对 schema 版本、表映射、筛选关联、导入顺序、父引用检查、类型转换和测试。报告摘要应只含标识与原因，避免把数据库异常中的敏感业务参数扩散到前端。
