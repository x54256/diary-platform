# 分析反馈与历史分析实施计划

## 1. 实施原则

- 直接切换到新分析模型，不保留旧接口兼容。
- 迁移当前仍存在的旧分析结果。
- 已被旧逻辑覆盖或删除的历史分析无法恢复。
- 先完成用户主链路，再预留管理端能力。
- 不提前实现 Prompt 反馈沉淀管理端。

## 2. 阶段计划

### Phase 1：数据库模型与迁移

目标：建立历史分析、分析项、反馈和软删除基础。

任务：

- 新增 `analysis_runs` 表。
- 新增 `analysis_items` 表。
- 新增 `analysis_feedback` 表。
- `diaries` 增加 `deleted_at`、`deleted_by`。
- 为 `analysis_runs` 增加每篇日记唯一 `CURRENT` 约束。
- 为 `analysis_feedback` 增加唯一约束。
- 为 `analysis_feedback` 增加继承状态字段。
- 编写旧数据迁移脚本。
- 迁移完成后移除旧分析存储字段或停止使用旧字段。

产出：

- 数据库迁移 SQL。
- SQLAlchemy 模型。
- 旧数据迁移逻辑。

验收：

- 现有 `diary_analysis` 可迁移为 `analysis_runs` 和 `analysis_items`。
- 现有 `diary_events.analysis` 可迁移为事件级 `analysis_items`。
- 每篇日记最多一个 `CURRENT` 分析轮次。
- 日记可软删除。

### Phase 2：后端读取模型改造

目标：详情接口返回新分析结构。

任务：

- 调整日记详情查询，读取当前 `CURRENT` 分析轮次。
- 按日记级和事件级组装分析类型块。
- 每个分析类型块带当前用户反馈。
- 废弃前端依赖的旧数组字段响应。
- 删除或停止使用 `diary_events.analysis` 的响应组装。

产出：

- 新响应 Schema。
- 日记详情接口改造。

验收：

- 日记详情能返回当前分析轮次。
- 日记级分析按类型块返回。
- 事件级分析按事件和类型块返回。
- 已反馈的类型块能返回反馈数据。

### Phase 3：反馈接口

目标：支持单条反馈提交和更新。

任务：

- 新增反馈保存接口。
- 校验 `rating` 范围为 1-5。
- 校验分析轮次属于当前用户。
- 校验事件级反馈的 `event_id` 属于当前日记。
- 低分必填由前端控制，后端仍允许 `comment` 为空。
- 同一用户、同一分析轮次、同一 scope、event、analysis_type 使用 upsert。

产出：

- 反馈保存接口。
- 反馈请求和响应 Schema。

验收：

- 4-5 星可无意见保存。
- 1-3 星如果前端提交了意见，可正常保存。
- 重复保存同一分析类型块会更新原记录。
- 越权提交反馈失败。

### Phase 4：分析保存逻辑改造

目标：新分析结果写入 `analysis_runs` 和 `analysis_items`。

任务：

- 改造普通分析保存逻辑。
- 普通分析成功后创建新 `analysis_run`。
- 将日记级分析拆成 `analysis_items`。
- 将事件级分析拆成 `analysis_items`。
- 旧 `CURRENT` 置为 `ARCHIVED`。
- 新分析轮次置为 `CURRENT`。
- 停止覆盖旧分析结果。

产出：

- 新分析保存服务。
- 分析项拆分工具函数。

验收：

- 普通分析成功后产生完整新分析轮次。
- 旧分析轮次不被删除。
- 前端能读取最新 `CURRENT` 分析。

### Phase 5：反馈版重新分析

目标：有低分文字反馈时执行定向重写。

任务：

- 点击重新分析时查询当前 `CURRENT` 分析轮次。
- 查询 `rating <= 3`、`comment` 非空且 `is_inherited=false` 的反馈。
- 无有效反馈时走普通完整分析流程。
- 有有效反馈时跳过环节 7。
- 新增反馈版环节 8 Prompt。
- 新增反馈版环节 9 Prompt。
- 反馈版环节不传原始日记。
- 反馈版环节输入结构化日记、上一轮分析、有效反馈和原环节要求。
- 有反馈类型块使用重写结果。
- 无反馈类型块沿用上一轮结果。
- 保存完整新分析轮次。
- 保存新分析轮次后复制上一轮反馈。
- 被本轮反馈重写的类型块复制为待确认反馈。
- 未被重写的类型块复制为已确认反馈。

产出：

- 反馈版环节 8 服务。
- 反馈版环节 9 服务。
- 反馈上下文组装逻辑。
- 结果合并逻辑。

验收：

- 有反馈重新分析不会重新生成心情和标签。
- 有反馈重新分析只重写对应分析类型块。
- 无反馈分析类型块内容沿用上一轮。
- 新轮次保存完整结果。
- 重新分析后页面仍显示上一轮反馈评分。
- 被修改的分析类型块显示待重新评分状态。
- 未修改的分析类型块保持已反馈状态。

### Phase 6：前端页面改造

目标：在分析类型标题右侧提供反馈入口。

任务：

- 调整前端类型定义，使用新分析轮次结构。
- 新增分析类型块组件。
- 新增星级反馈组件。
- 日记级分析页改为按类型块渲染。
- 事件卡片内分析改为按类型块渲染。
- 1-3 星点击后展开意见输入框。
- 4-5 星点击后立即保存。
- 已反馈状态支持查看和修改。
- 已修改待确认状态支持重新评分。
- 保存失败时提示并保留输入。

产出：

- 新分析展示组件。
- 新反馈组件。
- 日记分析页改造。
- 事件卡片分析区改造。

验收：

- 每个分析类型标题右侧有星级。
- 低分必须填写意见。
- 高分可直接保存。
- 已反馈可查看和修改。
- 已修改内容显示“已修改 / 重新评分”。
- 反馈保存失败不丢失输入。

### Phase 7：软删除改造

目标：删除日记改为软删除。

任务：

- 删除接口改为设置 `deleted_at`、`deleted_by`。
- 首页列表过滤软删除日记。
- 日历接口过滤软删除日记。
- 日记详情过滤软删除日记。
- 编辑接口禁止操作软删除日记。
- 整理接口禁止操作软删除日记。
- 分析接口禁止操作软删除日记。
- 任务状态接口禁止普通用户查看软删除日记任务。
- 标签下日记列表过滤软删除日记。

产出：

- 软删除接口改造。
- 查询过滤改造。

验收：

- 删除后普通用户不可见。
- 删除后数据仍在数据库中。
- 删除后不能编辑、整理、分析。

### Phase 8：备份恢复改造

目标：备份恢复覆盖新数据。

任务：

- 导出范围加入 `analysis_runs`。
- 导出范围加入 `analysis_items`。
- 导出范围加入 `analysis_feedback`。
- 导出 `diaries.deleted_at` 和 `diaries.deleted_by`。
- 导入预检增加新表关联校验。
- 导入顺序适配新表外键。
- 恢复时保留分析历史和反馈。

产出：

- 备份导出改造。
- 备份导入改造。
- manifest schema 更新。

验收：

- 备份包包含历史分析和反馈。
- 恢复后历史分析和反馈可查询。
- 软删除状态可恢复。

## 3. 数据迁移策略

### 3.1 可迁移数据

可迁移：

- 当前 `diary_analysis` 中仍存在的日记级分析。
- 当前 `diary_events.analysis` 中仍存在的事件级分析。

不可迁移：

- 已被旧逻辑覆盖删除的历史分析。

### 3.2 迁移步骤

1. 为每条 `diary_analysis` 创建一个 `analysis_run`。
2. `analysis_run.diary_id` 取对应 `diary_organized.diary_id`。
3. `analysis_run.task_id` 取旧 `diary_analysis.task_id`。
4. `analysis_run.mood` 取旧 `diary_analysis.mood`。
5. `analysis_run.status` 设置为 `CURRENT`。
6. 拆分旧日记级数组字段，写入 `analysis_items(scope=DIARY)`。
7. 拆分 `diary_events.analysis` JSON，写入 `analysis_items(scope=EVENT)`。
8. 迁移完成后，详情接口只读取新表。

## 4. 主要表结构草案

### 4.1 analysis_runs

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `diary_id` | 日记 ID |
| `diary_organized_id` | 整理结果 ID |
| `task_id` | 分析任务 ID |
| `mood` | 当前分析轮次心情 |
| `status` | `CURRENT` / `ARCHIVED` |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### 4.2 analysis_items

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `analysis_run_id` | 分析轮次 ID |
| `scope` | `DIARY` / `EVENT` |
| `event_id` | 事件级分析对应事件 ID |
| `analysis_type` | 分析类型枚举 |
| `content` | 分析正文 |
| `question` | 问题解答的问题文本 |
| `sort_order` | 展示顺序 |
| `created_at` | 创建时间 |

### 4.3 analysis_feedback

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `analysis_run_id` | 分析轮次 ID |
| `user_id` | 用户 ID |
| `scope` | `DIARY` / `EVENT` |
| `event_id` | 事件级反馈对应事件 ID |
| `analysis_type` | 分析类型枚举 |
| `rating` | 1-5 星 |
| `comment` | 反馈意见 |
| `is_inherited` | 是否为待确认的继承反馈 |
| `source_feedback_id` | 来源反馈 ID |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

唯一约束：

```text
user_id + analysis_run_id + scope + event_id + analysis_type
```

## 5. 风险点

- 当前旧分析结果只有最新版本，无法恢复历史版本。
- 软删除会影响所有日记查询，必须逐个接口补过滤。
- 反馈版重写需要严格限制作用范围，避免局部反馈污染其他分析类型。
- 备份恢复需要同步更新，否则新表数据会丢失。

## 6. 建议实施顺序

1. 数据库模型与迁移。
2. 后端详情读取新结构。
3. 分析保存写入新结构。
4. 反馈接口。
5. 前端反馈组件。
6. 反馈版重新分析。
7. 软删除。
8. 备份恢复。

原因：

- 先让新数据结构闭环。
- 再接反馈。
- 最后处理软删除和备份这种横切改造。
