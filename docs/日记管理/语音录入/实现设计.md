## 2. 设计与实现对应

| 功能约定 | 实现位置与机制 |
|---|---|
| 上传后绑定一篇日记 | `upload_item` 对批次重新加锁，首次上传成功时创建并绑定 `Diary(saved)` |
| 开始时固定最新输入 | `start_batch` 锁定批次，更新 `diary_date`、`base_text` 与绑定日记 |
| 音频顺序固定 | 前端排序；`update_item_order` 校验完整 ID 集合并写入连续 `sort_order` |
| 后台持续执行 | `TranscriptionTaskManager` 在应用启动注册，领取队列并执行异步任务 |
| 同批次词表绑定复用 | `_ensure_batch_vocabulary` 保存本地词表 ID 和指纹，后续音频复用该绑定；远端内容隔离仍有缺口 |
| 全部成功才合并全文 | `evaluate_batch` 判断，`finalize_batch` 行锁内重新检查全部有效项 |
| 重试避免重复处理成功项 | `retry_items` 仅将具有原文件的 `FAILED` 项重新置为 `QUEUED` |
| 重启后恢复 | `_recover_interrupted` 处理提交中和最终化状态，队列继续领取已有任务 |
| 取消、过期后丢弃迟到结果 | 写回前重新检查活动批次状态；当前取消能力与界面差异见功能约定 |
| 清理不撤销业务结果 | 数据事务先提交，音频删除失败保留对象键供定时补偿 |

## 3. 数据及状态

`TranscriptionBatch` 保存用户、环境、日期、文字快照、状态、绑定日记、词表 ID/指纹和时间信息；`TranscriptionItem` 保存顺序、文件元数据、对象键、状态、提供方任务、文本和错误摘要。

| 批次状态 | 含义 |
|---|---|
| `COLLECTING` | 正在上传、调整顺序；已有成功上传时日记已存在 |
| `QUEUED` | 已固定输入，等待执行 |
| `PROCESSING` | 存在活跃音频项 |
| `PARTIAL_FAILED` | 所有有效项结束且存在失败，可在保留期重试 |
| `FINALIZING` | 最终化状态，保留用于持久化流程与恢复 |
| `COMPLETED` | 合并文本已保存 |
| `CANCELLED` | 批次取消 |
| `EXPIRED` | 失败批次已过保留期 |

音频项状态为 `UPLOADING → UPLOADED → QUEUED → SUBMITTING → SUBMITTED/RUNNING → SUCCEEDED/FAILED`；允许移除的音频置为 `DELETED`。实际上传先落 MinIO，再保存 `UPLOADED`，前端另维护本地上传项。

关键约束：

- 批次 `diary_id` 唯一，避免多批次绑定同一日记。
- 同一 `environment + user_id + diary_date` 在 `QUEUED/PROCESSING/PARTIAL_FAILED/FINALIZING` 范围内唯一。
- 提供方 `provider_task_id` 唯一。
- 模型另有批次状态与更新时间索引；迁移中的约束以历史 SQL 为准，不用示意表替代数据库定义。
- 删除批次时，音频项随 ORM 关系级联删除；已绑定的日记不随批次删除。

## 4. 上传和开始事务

`create_batch` 保存页面初始日期、文字与 `COLLECTING` 状态。`upload_item` 校验所属用户、环境、扩展名、Content-Type、空文件、大小和顺序，再在线程池将文件流写入 MinIO。成功后重新锁定批次，确认仍可上传，创建音频项；批次没有 `diary_id` 时同一事务创建日记。

对象键由服务端构造；客户端文件名只取文件名部分并截取展示长度，不作为存储路径。数据库提交或顺序冲突失败后尝试删除已上传对象。存储异常当前返回 `500`，不能继续沿用旧文档“已实现 `507`”的描述。

`update_item_order` 必须收到所有未删除音频项的完整且不重复 ID 集合；只在 `COLLECTING` 且音频状态允许时修改。先写临时负序号、`flush` 后再写连续正序号，以避免交换顺序时碰撞迁移中的唯一约束。

`start_batch` 要求全部音频已上传并处于允许状态，锁批次后固定输入、更新绑定日记和 `content_revision`，将音频置为 `QUEUED` 后提交。活动日期约束冲突转换为 `409`。缺少日记绑定的历史批次在这里补建。

## 5. 后台执行与并发

任务管理器在 FastAPI 启动时恢复并开启调度。循环每秒运行，按开始时间与音频顺序领取任务，使用 `FOR UPDATE SKIP LOCKED`，只领取本环境的活动批次。单进程可用槽为配置上限减当前活跃任务数；默认上限 3，单位为音频项，跨日期和批次共享。

- 阻塞数据库和对象存储操作通过线程池执行。
- 第一次提交前确定本地用户词表绑定，生成限时 MinIO 预签名下载地址，每次请求只有一个文件 URL。
- 记录提供方任务 ID 后再进入轮询；`PENDING/RUNNING` 结果间隔 3 秒查询。
- 成功时立即下载结果并读取非空 `transcripts[].text`；当前只请求通道 0，空全文视为失败。
- 音频文本落库后尝试删对象，再重新评估批次；状态回写前检查批次仍处于活动状态。
- 每 5 个调度循环补偿检查可最终化批次；每 60 个循环执行保留期与残留文件清理。

并发槽和词表互斥锁属于进程内状态，不应据此声称实现了跨多应用进程的全局并发上限。语音请求没有业务级总轮询时长上限；部署需维持任务进程可用。

## 6. 词表同步

热词来源、去重与资料字段定义见[个人资料](../../个人资料/热词与人物关系.md)。当前词条权重为 4、语言为 `zh`，以完整集合生成稳定指纹。

1. 批次首次提交前，以进程内词表锁串行检查同步。
2. 用户已有指纹和目标模型均未变化时复用词表 ID。
3. 集合为空时尝试删除旧远程词表并保存空绑定。
4. 同模型的已有词表以完整集合更新；模型变化时创建新词表，并尝试清理旧词表。
5. 提供方明确不支持热词时，记录降级状态，不传 `vocabulary_id` 继续识别。
6. 把词表 ID 和指纹保存到批次。资料更新不直接改写本地批次字段，但不能据此保证远端词表内容不变。

同用户新批次在资料变化后可能调用 `update_vocabulary` 覆盖旧批次仍引用的同一个远端 ID。旧批次尚未提交的音频继续传入该 ID，缺少不可变远端版本或跨批次更新协调；本地指纹只是同步记录，不能证明提供方识别时实际使用哪版内容。

仅跳过“不支持热词”的指定异常，不能把所有词表错误都视为可忽略。词表仅影响识别提示，人物关系的具体语义不会被作为词条内容发送。

## 7. 提交、查询和结果重试

当前通过 `httpx.AsyncClient` 适配提供方 HTTP 协议，模型、API 基地址和密钥由 `transcription` 模型用途解析。保留 HTTP 适配有利于控制异步提交头、超时及日志，不引入同步 SDK 等待流程。

| 操作 | 当前行为 |
|---|---|
| 提交 | `POST {base}/services/audio/asr/transcription`，使用异步头，参数含通道 0、中文提示、关闭说话人分离及可选词表 |
| 查询 | `GET {base}/tasks/{provider_task_id}` |
| 结果 | 下载提供方结果地址，使用无提供方鉴权头的结果请求，提取并合并文本 |
| 超时 | 提交/查询读取 30 秒、连接 10 秒；结果下载读取 120 秒 |
| 自动重试 | 连接失败、明确 `429/5xx`、可重试查询/结果下载最多总计 3 次，间隔按指数退避 |
| 提交结果未知 | `ReadTimeout` 或协议错误转换为 `SUBMIT_RESULT_UNKNOWN`，不自动再次提交 |
| 手动重试 | 仅失败项且文件存在、批次尚未过期；清空旧提供方任务/错误，增加重试计数，重新排队 |

不能把不确定是否已受理的提交与安全可重试的查询混为一类，否则会重复产生提供方任务和费用。原文提到的提供方 URL 有效期及最大音频时长属于提供方规格，后续修改渠道时应按实际服务重新核对，不写作本系统强校验。

## 8. 最终化与一致性

`evaluate_batch` 忽略已删除音频，有活跃项则维持处理，有失败项则记录保留期，全部有效项成功才最终化；无有效项则转为取消。

`finalize_batch` 在单个事务中：

1. 行锁读取批次，仅接受可最终化状态。
2. 重新确认至少一个未删除音频且全部成功。
3. 按 `sort_order` 合并 `base_text` 与成功文本。
4. 正常路径更新已绑定且未删除日记的正文、日期与修订号，并清除脏标记。
5. 没有绑定日记的历史批次才在此补建日记。
6. 写 `COMPLETED`、完成时间，清除过期时间、`base_text` 及音频项转写全文，提交。

再次最终化已完成批次直接返回，防止重复更新或创建。对象删除独立于该事务，不因删除失败撤销日记。

当前已删除日记的最终化分支跳过正文更新，但仍将批次置为完成并清空转写全文。这是需要单独核对的生命周期边界，不能将其描述为“删除后仍必定保存全部识别结果”。

## 9. 重启恢复与清理

- `SUBMITTING` 项恢复为 `FAILED/SUBMIT_RESULT_UNKNOWN`，等待用户明确重试。
- 已持有 `provider_task_id` 的提交/运行项重新领取后继续查询，不重复提交。
- `FINALIZING`：有绑定日记时当前代码转为 `COMPLETED`；无绑定时转为处理并重新评估。提前绑定日记后，该恢复判断不能单凭 `diary_id` 证明全文已写入，列为待核对边界。
- 队列、处理中任务继续调度；失败批次保持可手动恢复。
- 收集超过 24 小时删除批次与文件；失败超过配置保留期转为 `EXPIRED` 并清理文本和文件。
- 成功或终态残留对象定时删除，成功后清空对象键；终态元数据超过 30 天物理删除。
- 终态清理不会回收已提前创建的日记。恢复及清理部分查询当前未限定 `TASK_ENVIRONMENT`，与常规领取的环境隔离不同，跨环境共享数据库部署必须列入复核。

## 10. 前端与接口边界

接口在 `/diary/api/transcription-batches` 下提供创建、活动批次查询、上传、开始、批次查询、排序、删除、单项/全部失败重试及取消。请求和响应字段直接参照[接口模型](../../../backend/schemas/transcription.py)，避免维护第二份 JSON 全量副本。

前端上传使用 XHR 获取进度并读取 `X-Access-Token` 续期，普通操作复用 `useApi`。默认并行上传 3 个；进入活动批次恢复时立即查询。正常状态刷新后 20 秒再查，失败后 4 秒重试；页面隐藏不安排新轮询，恢复可见时立即查一次。

当前 `cancel_batch` 在批次完成或已绑定日记时拒绝取消，未绑定时才清理对象、清空文字、返回原日期和 `base_text`。上传成功提前绑定日记后，页面取消入口与接口拒绝产生冲突；详见[功能约定中的差异](功能约定.md#9-已核实的设计与实现差异)。

## 11. 配置与部署

配置字段及默认值以 [Settings](../../../backend/config.py) 为准：

| 配置 | 作用/当前默认 |
|---|---|
| `TRANSCRIPTION_MAX_FILE_SIZE` | 单文件字节上限，314572800 |
| `TRANSCRIPTION_MAX_CONCURRENCY` | 进程内识别并发，3 |
| `TRANSCRIPTION_FAILED_RETENTION_DAYS` | 失败保留天数，7 |
| `TRANSCRIPTION_DOWNLOAD_TOKEN_HOURS` | 预签名 URL 有效小时，24 |
| `MINIO_ENDPOINT` / `MINIO_PUBLIC_ENDPOINT` | 应用上传与提供方读取地址 |
| `MINIO_SECURE` / `MINIO_PUBLIC_SECURE` | 两条链路的协议 |
| `MINIO_BUCKET` / `MINIO_UPLOAD_PREFIX` | 对象容器和前缀 |
| `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | 对象存储认证，由部署环境提供 |
| `APP_ENV` | 常规批次读写和任务领取的环境标识 |

MinIO 数据目录必须持久化；公共 Endpoint 必须能被提供方访问。签名地址只提供限时读取权限，不替代网络可达性。生产链路应使用 HTTPS；不在文档、日志或客户端暴露认证值。
