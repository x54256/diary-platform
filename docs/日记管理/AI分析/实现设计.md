# AI 分析实现设计

核对基线：2026-10-29 仓库代码及分析 Skill。共同业务设计见[功能约定](功能约定.md)。本文件按当前入口说明两种实现，不将历史 LangGraph 入口当成当前页面实际调用链。

## 1. 设计与两种实现的对应

| 设计责任 | 应用内实现 | Skill 实现 |
|---|---|---|
| 定位来源 | 当前用户日记、结构化结果、既有分析及有效反馈 | 只读定位并导出日记、人物资料、来源版本和稳定事件 ID |
| 支持范围 | 首次、普通重新分析、反馈重新分析 | 第一版仅 `organized` 且没有任何分析轮次的首次分析 |
| 分析事实 | 当前结构化事件，人物资料提供语境 | 导出事件，用户澄清改变事实时须先修订整理来源并重新导出 |
| 处理步骤 | 建图闭环 → 元数据 → 核心 → 认知 → 行动规划 → 发布；反馈跳过元数据模型 | 核心 → 认知 → 当前稿来源清单 → 行动规划 → 复读与确认 |
| 图谱 | 同一任务先生成 / 检查要点、向量和关系 | 当前分析保存不触发建图，保留已有图谱 |
| 元数据和标签 | 普通模式生成；反馈模式沿用 | 保留已有标题、摘要、地点、标签和心情 |
| 输出与校验 | 严格结构、事件覆盖、反馈目标和日程 schema 校验 | Markdown 栏目、事件 ID、来源摘录、推荐日程及转换包校验 |
| 保存 | 图谱与分析在同一短事务发布，归档旧分析、继承反馈 | 确认包保存首轮分析、行动项及事件关联，读回核验 |
| 恢复 | 冻结配置 / 来源、任务租约、checkpoint 和调用记录 | 当前完整稿、冻结导出、指纹包及实际回执；失败先查询结果 |
| 人工确认 | 用户触发后后台执行并保存 | 本地 / 单独调用整稿确认，云端完整流程采用独立审阅约定 |

## 2. 应用内任务入口与来源冻结

[日记路由](../../../backend/routers/diaries.py)的 `analyze_diary` 调用 [graph_tasks.create_analysis](../../../backend/services/graph_tasks.py)，创建 `OrganizeTask`、`GraphTask` 和 `GraphRun` 后返回任务身份和进度。应用启动时运行持久化图谱任务管理器，不通过旧 `_run_analyze` 协程完成当前页面分析。

- 获取用户锁，保证同一用户活动分析 / 建图任务串行。同日记已存在活动分析任务时复用，其他活动任务拒绝并行。
- 只接受本人未删除、具有结构化结果的 `organized` / `analyzed` 日记。
- 冻结当前模型 / 提示词配置、结构化来源、事件 ID 与顺序、重要性、人物资料、分析日期、上轮结果和当时有效反馈。
- 根据冻结反馈决定 `ordinary` / `feedback`。新任务使同日记旧失败任务被替代；调用重试接口才恢复同一旧任务。
- 日记日期表示记录所属日，分析日期按上海时区冻结，用于推荐安排的日期校验。

## 3. 执行、输出校验与发布

### 3.1 当前主链路

[graph_workflow.execute_task](../../../backend/services/graph_workflow.py)加载冻结来源，按事件重要性对 `MEDIUM` / `HIGH` 事件执行要点提取，生成向量、发现候选和识别关系，再调用 [graph_analysis.analyze](../../../backend/services/graph_analysis.py)。

```text
PREPARE_SOURCE → 事件要点 / 审核 → 向量 → 候选与关系 → 图谱整体检查
              → 元数据 → 核心分析 → 认知分析 → 行动规划 → PUBLISH
```

图谱部分的细节引用[知识库文档](../../知识库/README.md)。分析节点使用全部结构化事件，不因低重要性事件未入图而直接丢弃该事件的分析。

### 3.2 普通与反馈模式

| 环节 | 输入与校验 | 保存到 checkpoint 的结果 |
|---|---|---|
| 元数据 | 结构化日记；标题、摘要、地点、心情为字符串，事件标签完整覆盖 ID、原标题及五类标签 | `analysis_metadata` |
| 核心 | 事件与人物资料；事件级及日记级核心字段、事件覆盖和字符串数组校验 | `analysis_result`、`core_complete` |
| 认知 | 结构化日记与人物资料；认知字段、问答对象、事件覆盖校验，日记级不生成问答 | `analysis_result`、`cognition_complete` |
| 行动规划 | 后续计划与建议来源清单；来源摘录、标题、日程 schema、冻结日期校验 | `analysis_result.action_items`、`actions_complete` |

当前提示词和分析设计分别位于 [analysis_pipeline](../../../backend/services/analysis_pipeline.py)的规则 / 模板常量，`graph_analysis.prompts` 追加稳定事件 ID 与反馈重写协议。程序对输入输出的硬约束优先于模板中的旧事件定位示例。

反馈模式不重新调用元数据模型，沿用冻结的上一轮元数据和标签。针对核心、认知分别计算重写目标，只调用存在目标的环节。事件级反馈会扩展为日记级同类型目标；验证重写集合恰好覆盖要求，禁止多改和漏改，再合并未改写内容。行动规划仍在随后执行。

### 3.3 正式发布与分析历史

[graph_publish.publish](../../../backend/services/graph_publish.py)在短事务内：

1. 检查任务所有权、发布幂等及日记仍存在。
2. 重新计算当前结构化事实来源指纹，拒绝变更来源和过期历史证据。
3. 确认图谱整体检查和行动阶段完成，再写要点、向量、关系及证据。
4. 调用 `_persist_tags` 和 `_save_analysis_result` 保存标签、完整分析轮次、条目、反馈继承和行动项。
5. 设置日记 `analyzed`、任务成功和运行 `PUBLISHED` 后统一提交。

标签 / 分析写入出错时回滚统一发布事务，不能将旧审计中的“标签失败后继续提交分析”描述为当前闭环。元数据、事件标签、分析项由后端按稳定事件 ID 绑定；前端不做标题或下标匹配。

分析轮次与反馈继承由 [analysis_history](../../../backend/services/analysis_history.py)维护：归档旧当前轮次，创建新轮次及有序条目；反馈保留来源链，被重写块需重新评价。分析批注按位置键与文本内容核对，未变内容重指向新条目，已变内容标记失效，见[批注](../批注.md)。

行动项保存使用 [action_items](../../../backend/services/action_items.py)，正式日程同步仍由用户触发。当前应用内保存由建议文本摘要关联分析项，重复建议文本的来源匹配应作为单独边界回归。

### 3.4 失败恢复与运行证据

- `GraphRun.checkpoint` 保存已通过要点、向量、关系判断、分析阶段和最终结果；已完成阶段恢复时复用。
- 任务具有租约、心跳、可用时间与环境边界，任务管理器按持久状态认领；恢复不能把请求是否返回当成任务是否执行。
- `retry_task` 只接受失败任务，校验无其他活动任务、未被新运行替代且结构化事实指纹未变，再把原任务排队。结果未知的旧模型调用标为 `UNKNOWN`，不能假定未调用。
- 每次模型调用的请求、响应和阶段证据存入 `GraphModelCall`，运行身份、来源和结果绑定在数据库中。图谱细节以实际运行证据为准。
- 恢复沿用冻结人物资料、上轮结果和反馈。事实来源指纹并不包含这些全部辅助输入；用户修改反馈或资料后不会自动进入旧任务，需明确选择新任务。

### 3.5 历史执行接口与维护边界

`analysis_pipeline.py` 仍保留 `run_analysis_pipeline`、`run_feedback_reanalysis_pipeline` 及部分 LangGraph 节点，当前页面入口不走这些函数。其提示词、结果保存和行动输入构造仍被图谱分析复用，不能因入口变化整体删除该文件。

这些历史执行函数使用 PostgreSQL LangGraph checkpoint，线程 ID 为任务 ID，支持完整结果复用及中断节点恢复。排查当前应用内分析时先确认入口，避免把两套 checkpoint 机制混为一谈。

## 4. Skill 入口与审阅路径

[diary-analyzer](../../../skills/diary-analyzer/SKILL.md)或完整 [diary-workflow](../../../skills/diary-workflow/SKILL.md)进入分析阶段后：

1. [store_analysis.find / export](../../../skills/diary-analyzer/scripts/store_analysis.py)只读定位目标并导出结构化日记、人物资料、稳定事件 ID、来源修订和冻结分析日期。
2. 按[核心规则](../../../skills/diary-analyzer/references/core-analysis.md)与[认知规则](../../../skills/diary-analyzer/references/cognition-analysis.md)形成完整可修订的 `分析稿.md`。每个来源事件均保留栏目，无内容留空；问题解答仅设事件级。
3. 先保存核心与认知部分，再运行转换器的 `--sources-only` 生成当前稿来源清单，依据[行动规划规则](../../../skills/diary-analyzer/references/action-planning.md)生成行动和连续来源摘录。
4. 复读来源、推导、条目去重、行动原子性及日期；展示完整稿及待澄清问题。用户修订后的当前稿优先，局部认可不代替整篇最终确认。
5. 转换、预检并按当前确认的包保存；数据库来源改变时重新导出，不能手改来源 JSON 绕过保护。

Skill 的语义分析由调用它的代理依规则完成，不调用应用内后台分析任务，也不固定成服务端三次模型调用。仅生成 JSON 或包不能证明语义正确。

### 4.1 资格与写入保护

当前第一版要求：本人未删除日记处于 `organized`，已有整理结果且修订有效、没有任何分析轮次、没有该用户活动图谱任务或该日记运行任务。已经分析的日记停止，不能靠删除历史或改状态继续保存。

[markdown_to_json](../../../skills/diary-analyzer/scripts/markdown_to_json.py)绑定事件 ID、原标题、完整栏目、问答和行动来源，使用后端 `ActionSchedulePayload` 复核推荐日程，不静默丢弃不支持的字段。

预检包绑定导出、源文件、Markdown 及其指纹。写入时获取用户锁、日记锁、整理和事件锁，重新导出比较数据库来源及人物资料；稿件、包或日期变化后需重新预检。推荐日期早于保存时上海日期会拒绝保存，冻结分析日期不替代保存时效检查。

### 4.2 保存与恢复

确认后的首轮分析保存生成完成态 `OrganizeTask`、`CURRENT AnalysisRun`、日记级 / 事件级分析项、行动项及其事件关联。原文、整理内容、元数据、标签和已有图谱保持原值；保存后更新日记 `analyzed`。

脚本按真实事件 ID 精确保存建议关联，使用建议来源键区分同名或同文建议，再读回分析条目、行动内容、推荐日程和来源数量。任何不一致由事务整体回滚。用户确认、指纹核对和数据库实际提交是不同环节，回执须报告实际保存结果。

失败先查询数据库是否已产生分析轮次，不盲目重试。保存已经成功时资格检查会拒绝再次首轮保存，需要核对回执而不是删除旧结果。

数据传输见[db / API 配置](../../../skills/diary-workflow/references/api-mode.md)，云端完整工作流的审阅例外见[云端规则](../../../skills/diary-workflow/references/cloud-review.md)。单独调用和本地路径继续整稿确认；传输模式变化不豁免来源、身份和稿件核对。

## 5. 日志、测试与审计结论沉淀

7 月审计以旧后台协程与 LangGraph 入口为基线，其路径和行号已过期。仍有效的排查要求归纳为：

- 能将请求、任务、运行、模型调用、来源、分析轮次和发布结果关联；查看 `chain_id`、`request_id`、task / run ID、step、模型、耗时与错误类型。
- 区分新执行、旧状态恢复、完整结果复用、未知调用结果和新任务替代。
- 对照标签、分析、行动、反馈继承和事务提交结果，不以模型响应成功等同于正式发布。
- 反馈输入和重写目标可追溯；来源变化后明确旧任务还是新任务。
- 专用 AI 日志与 root logger 的处理器会同时参与输出，实际是否产生重复记录需运行验证；上游网关提供哪些请求标识及重试信息也需受控检查。

当前代码已有请求日志、节点 / checkpoint 事件、模型耗时与 token 记录、结果保存摘要，以及 `GraphModelCall` 数据库证据。代码位置为[日志上下文](../../../backend/utils/log_context.py)、[LLM 指标](../../../backend/services/llm_metrics.py)、[pipeline](../../../backend/services/pipeline.py)、[graph_runtime](../../../backend/services/graph_runtime.py)。这些静态实现说明不能代替生产运行覆盖验证。

| 验证范围 | 入口 |
|---|---|
| 分析语义约束与行动来源 | [分析提示词测试](../../../backend/tests/test_analysis_prompt_rules.py)、[行动项测试](../../../backend/tests/test_action_items.py) |
| 应用内事务、恢复和模型输出 | [图谱数据库测试](../../../backend/tests/test_graph_database.py)，必须使用明确配置的隔离数据库 |
| Skill 转换、事件覆盖、来源保护、读回和回滚 | [分析存储测试](../../../skills/diary-analyzer/scripts/test_analysis_storage.py)、[评估说明](../../../skills/diary-analyzer/references/evaluation.md) |

旧提示词断言若与现行规则失配，需核对目标规则后维护测试，不能把断言本身当作新业务规范。生产数据库不用于清理型测试。

## 6. 已核实差异与后续决策

| 项目 | 设计与实现关系 |
|---|---|
| 元数据与标签 | 应用内普通模式生成，Skill 保留已有值。是否由独立前置步骤统一补齐需另作明确设计 |
| 重分析 | 应用内支持，Skill 首版不支持；不能把反馈能力标为两条实现均覆盖 |
| 事件反馈传播 | 原需求仅改单块，当前应用内联动日记级同类型分析；需统一目标规则 |
| 问答范围 | 原需求包含日记级问题解答，当前两条实现均只生成事件级 |
| 来源有效性 | Skill 显式拒绝脏整理和修订不一致；应用内 `create_analysis` 未作等同资格校验，需核对入口保护 |
| 辅助输入版本 | 旧任务沿用冻结人物资料与反馈，retry 的事实指纹不包含所有辅助输入；变更后需新任务或明确恢复约定 |
| 行动来源 | 应用内保存按建议文本摘要汇总分析项，Skill 按事件范围与来源键精确匹配；重复文本需专项核验 |
| 图谱与分析发布 | 应用内统一闭环，Skill 独立保存且不重做图谱；功能入口应明确说明实际处理范围 |
