# AI 整理实现设计

核对基线：2026-10-29 仓库代码及整理 Skill。共同设计见[功能约定](功能约定.md)，本文件说明设计如何落实到应用内与 Skill 两条路径，以及尚未统一的行为。

## 1. 责任对应

| 功能设计 | 应用内实现 | Skill 实现 |
|---|---|---|
| 原文和人物语境 | 原文、日期及只读人物关系进入服务端 State | 导出原文和人物资料；当前稿结合明确澄清修订 |
| 保真重组 | 5 个串行节点，清洗与内容审核可通过配置跳过 | 理解全文、形成稿件、按需澄清、复读修订，不固定模型调用次数 |
| 结果结构 | 内部对象校验后写结构化表并生成展示 Markdown | `整理稿.md` 通过转换器得到对象，检查段落、列表与重要性格式 |
| 事实与质量校验 | 模型审核、程序结构校验及来源写入守卫 | 规则复读、用户审稿、转换校验、来源与稿件指纹预检 |
| 人工确认 | 点击整理后由后台完成并自动保存 | 整篇最终稿确认后保存，局部认可不等于整稿确认；云端总流程有独立审阅规则 |
| 恢复 | 复用任务 ID 和 PostgreSQL checkpoint | 复用当前稿、澄清记录、导出与包，核对保存回执再重试 |

## 2. 应用内入口与流水线

入口为[日记路由](../../../backend/routers/diaries.py)的 `organize_diary`。它锁定当前用户的未删除日记，检查状态、活动图谱任务和内容锁。有效运行任务直接复用；创建超过 15 分钟的运行任务会标记失败；最近失败整理任务复用原 ID，否则新建任务。

后台 `_run_organize` 使用独立数据库会话调用 [AIService.organize_diary](../../../backend/services/ai.py)，后者进入 [run_pipeline](../../../backend/services/pipeline.py)。任务进度写入 `OrganizeTask.current_step`，页面轮询整理状态。

```text
text_clean → clean_check → event_organize → template_fill → content_check
```

| 节点 | 主要输入与产物 | 缺省 temperature |
|---|---|---:|
| `text_clean` | 原文、日期、人物关系 → 通顺的清洗文本 | 0.3 |
| `clean_check` | 原文、清洗文本 → 核实后的文本与清洗检查记录 | 0.3 |
| `event_organize` | 审核后的文本、日期 → 引入、事件原稿、琐事、计划 | 0.5 |
| `template_fill` | 事件原稿、日期 → 正文 / 感受 / 反思数组及重要性 | 0.5 |
| `content_check` | 原文与结构化结果 → 修订结果与内容检查记录 | 0.3 |

运行模型、渠道、思考参数和可用性通过管理端用途与环节配置解析。当前使用兼容 OpenAI 的 `ChatOpenAI`；数据库 checkpointer 使用 psycopg 异步连接及 `AsyncPostgresSaver`。不要按早期文档中的单一模型或固定驱动替换计划配置生产环境。

清洗审核和内容审核的开关见[整理设置](../../../backend/services/organize_settings.py)。关闭审核时跳过对应模型检查并透传结果，不能将结构可用等同于语义审核通过。内容审核沿用结构化环节的事件重要性，当前按数组位置复制重要性，需关注审核变更事件顺序时的对应风险。

### 2.1 状态、提示词和结构校验

State 保存输入身份、日期、人物关系及各阶段产物。节点按职责只读取所需输入，具体键和输出格式以 `PipelineState`、节点函数及 [AI 提示词](../../../backend/services/ai.py)中的 `CLEAN_PROMPT`、`CLEAN_CHECK_PROMPT`、`EVENT_ORGANIZE_PROMPT`、`TEMPLATE_FILL_PROMPT`、`CHECK_PROMPT` 为准。

`_invoke_llm` 记录模型调用、耗时与 token 指标，并解析 JSON；事件结构通过 `_validate_events` 校验。不能只以 JSON 可解析或字段存在证明信息完整、人物归属和重要性正确。

### 2.2 保存与替换

- 后台边界过滤非对象的事件和检查记录，生成展示 Markdown；写入前重新读取未删除日记并检查活动来源。
- 首次创建 `DiaryOrganized`；再次整理复用一对一整理记录，递增结构化修订，保存对应原文修订。
- 重新整理会清除旧事件、旧事件收藏、标签关联、事件批注及评论、旧检查记录，然后按新顺序创建事件。事件 UUID 不是原事件的稳定续用。
- 新事件初始标签为空；事件重要性及理由写入 `ai_importance`、`ai_importance_reason`，来源为 `DIARY_ORGANIZE`。
- 结构化结果、检查记录、状态 `organized`、清除脏标记以及任务完成状态在同一事务提交。失败先回滚结果事务，再记录任务失败；此前已保存的整理结果不因本次失败自动消失。
- 内容检查记录用于排查质量问题，不进入日记正文。记录项目、状态、问题、前后片段及理由等字段，具体字段引用日记模型。
- 业务提交后再清理 checkpoint，清理失败只记录告警，不将已保存结果伪报为失败。

### 2.3 checkpoint 与任务恢复

[run_graph_with_checkpoint](../../../backend/services/pipeline.py)以 `task_id` 为 LangGraph `thread_id`：无已有状态时传入初始输入；有待执行节点时恢复；完整图已完成但业务落库未完成时复用完整结果。新字段只补齐 checkpoint 中缺失的值，已有输入和中间结果保留。

应用启动恢复会处理卡死任务。后台任务不属于 HTTP 请求生命周期；重试应以任务实际状态为准，不能因请求断开就重复创建。

## 3. Skill 入口、稿件与确认

入口为[日记整理 Skill](../../../skills/diary-organizer/SKILL.md)，完整四阶段流程由[diary-workflow](../../../skills/diary-workflow/SKILL.md)编排。此处记录实现关系，具体执行命令和授权规则以相应入口及[存储说明](../../../skills/diary-organizer/references/storage.md)为准。

- 先区分纯文本整理、首次保存、整篇替换和既有内容定点复核。项目任务按用户、日期和日记 ID 定位，同日多篇需核实目标。
- 读取原文、人物资料、来源快照及可保存能力；无法整篇保存时仍可交付本地稿，但必须先说明能力边界。
- 当前完整稿和澄清记录分别保存为 `整理稿.md`、`澄清记录.md`，位于日记日期对应的工作目录。修订读取当前磁盘稿，保留人工编辑。
- 先展示完整稿，再按需澄清；影响整体理解的关键疑问才在成稿前确认。澄清最多四题并附选项，回答后复读完整稿。
- 人物资料只修正明确称呼与指代，证据与推测分开。风险标色、时间标签等默认不强制生成；这与应用内提示词不同。

### 3.1 转换、预检与保存

[markdown_to_json](../../../skills/diary-organizer/scripts/markdown_to_json.py)解析结构、段落与重要性；[store_diary](../../../skills/diary-organizer/scripts/store_diary.py)负责身份、状态、依赖、指纹和数据库写入。

预检包绑定原文修订、结构化修订、存储状态指纹、Markdown 和澄清记录指纹。保存时重新解析文件、核对包与确认指纹、重新检查数据库来源，并锁定日记及已有整理记录和事件；变化后须重新预检并确认受影响稿件，不能修改旧指纹继续写入。

整篇保存使用同类整理与事件模型，状态变为 `organized`，保留原文。存在分析记录、批注、事件收藏、事件标签或行动项关联时，`check_dependencies` 拒绝整篇替换，避免猜测新旧事件映射。

[review_diary](../../../skills/diary-organizer/scripts/review_diary.py)另提供既有结构化结果的定点复核路径：导出当前结果、校验 changes、生成修订包，在来源锁及版本核对通过后调用共享的 `apply_organized_update`。它不等于 `store_diary` 支持任意事件补丁。

### 3.2 数据访问与恢复

本地 db 与应用 API 两种传输由[数据访问配置](../../../skills/diary-workflow/references/api-mode.md)控制，共同使用转换、指纹和保存约束。API 模式不读取数据库认证配置，接口失败不自动切回直接数据库写入。

完整云端流程的审阅与续接采用[云端审阅规则](../../../skills/diary-workflow/references/cloud-review.md)；单独调用与本地流程遵循对应整稿确认约定。确认只绑定实际看过的版本。失败先核对数据库和回执，保留来源及稿件，不盲目重写。

## 4. 验证设计

| 层次 | 验证内容 |
|---|---|
| 共同语义 | 原文完整性、人物角色、事件归属、含混程度、重要性影响依据、感受与反思来源 |
| 应用内结构 | 节点输入输出、事件数组、审核开关、状态进度、checkpoint 及保存事务 |
| Skill 结构与存储 | 转换、包指纹、稿件 / 来源变化、整篇依赖保护、定点修订、事务回滚 |
| 交付 | 长文本无静默截断、用户当前稿保留、问题在稿外、最终确认与回执一致 |

应用内关键回归入口为[整理提示词规则测试](../../../backend/tests/test_organize_prompt_rules.py)；Skill 验证入口为[整理存储测试](../../../skills/diary-organizer/scripts/test_diary_storage.py)及[评估说明](../../../skills/diary-organizer/references/evaluation.md)。断言通过不代替真实语义审阅。

## 5. 日志与排查

旧日志审计中仍有效的要求是：一次任务能够关联入口、执行阶段、模型调用、恢复动作、事务结果和最终状态。当前请求上下文、模型指标与 checkpoint 事件已提供部分证据，实际字段见[日志上下文](../../../backend/utils/log_context.py)、[LLM 指标](../../../backend/services/llm_metrics.py)和流水线日志。

排查时优先使用任务 ID、日记 ID、步骤、模型、耗时、错误类型与恢复动作。专用 AI logger 和 root logger 均有处理器；是否在实际环境产生重复记录、上游网关能返回哪些请求标识，需要受控运行核对。完整正文及模型认证信息不得用于普通错误响应。

## 6. 已核实差异与待处理问题

| 项目 | 当前事实 | 维护要求 |
|---|---|---|
| 人工确认 | 应用内自动保存；Skill 具有稿件确认及云端审阅规则 | 分别描述，不把 Skill 的每稿确认直接写成应用内现状 |
| 整篇替换 | 应用内清理旧事件关联；Skill 对已有用户关联拒绝替换 | 统一关联保护策略前，不能宣称两者等价 |
| 模糊表达 | 旧规则中既要求正文不写“原文未明确”，又有要求补此说明的例子；Skill 通过稿外澄清处理 | 保留歧义事实和用户确定程度，统一展示规则需明确决策 |
| 文本标记 | 应用内提示词要求重点 / 风险及时间标记；Skill 默认普通文字，按用户要求生成标记 | 展示层需支持已有标记，但不能将两种输出格式宣称完全一致 |
| 来源版本与恢复 | 整理 checkpoint 按 ID 复用，已有原文、日期等输入不覆盖 | 来源修改后旧 checkpoint 的重用需增加版本校验 |
| 发布一致性 | 后台保存更新对应原文修订，但未用任务开始时原文指纹核对模型输入 | 继续核对后台任务期间的输入变化保护，不能将修订号写入等同于输入校验 |
| 事件对应 | 内容审核按下标沿用重要性 | 核对审核拆合或重排事件是否导致对应错位 |

## 7. 过程评审沉淀与回归依据

整理 Skill 的评审、通畅性对照、多轮提问试跑、标题规则修订和十月稿件复核中的长期结论归入以下维护要求，原始日记和逐轮试跑输出不复制进功能文档。

| 结论 | 当前规则 / 验证承载 |
|---|---|
| 用户直接改稿后先读取当前文件，局部范围保护不免除其余表达的必要复读 | Skill 主文件、[联动复查](../../../skills/diary-organizer/references/revision-review.md)、E11 与 E19—E23 |
| 名称更正后同步修正残缺表达，但含混对象不能为了通畅被补成确定事实 | E22 / E23，按实际交付文本核验 |
| 标题独立阅读应正确表达人物、动作、发起 / 执行 / 接受角色 | 功能约定的标题规则、[示例](../../../skills/diary-organizer/references/examples.md)、E24 / E25 |
| 正文更新后同步复核标题、感受、反思、重要性与整篇计划；已完成或放弃的动作不继续列为未来承诺 | [联动复查](../../../skills/diary-organizer/references/revision-review.md)及功能约定的计划边界 |
| 先核实可保存能力，分开只读来源与整篇替换资格；已有锁或关联不绕过 | `load_source` / `load_target`、存储隔离测试 |
| 多轮答复后重新识别遗留与新增问题，不凑题、不重复已回答问题，仍需适用流程要求的整稿审阅 | Skill 主文件与[语义评估](../../../skills/diary-organizer/references/evaluation.md) |
| 原文只有转写时，近音纠错属于上下文推测，不能宣称听过音频 | 功能约定的纠错边界与 Skill 主文件 |
| 同一题材依实际影响分级，LOW 不等于不值得保留，不以强行拆并改变等级分布 | 重要性约定、成对分级示例 |
| 文稿格式与存储能力分开：自定义交付不应为通过转换而覆盖用户稿 | Skill 输出分支与转换预检 |

旧材料的单次文本试跑、模拟用户回答和脚本测试属于不同证据层次：试跑不证明稳定通过率，模拟对话不证明实际提问工具行为，脚本通过不证明语义质量。重跑时记录实际规则版本、模型与运行条件，比较真实输出和禁写事实，而非采信代理自评或文件读取记录。

评审参考采用口述材料保真、作者参与修订与来源核验等思路，私人日记具体约定以本项目为准。相关研究入口为 [NPS 转写资料](https://www.nps.gov/articles/000/oral-history-resources-interview-transcribing.htm)、[OHA 最佳实践](https://oralhistory.org/best-practices/)、[FRANK](https://aclanthology.org/2021.naacl-main.383/) 和 [QAFactEval](https://aclanthology.org/2022.naacl-main.187/)；这些资料不构成本项目的质量认证或成功率证明。

仓库 Skill 源文件可被读取，不等于宿主已注册或安装。后续接入应核对实际发现路径及安装配置；文档整理不自动更改安装。维护技能结构时区分开放格式、宿主行为和项目规则，具体依赖与使用方式继续由 Skill 的维护资料承载。
