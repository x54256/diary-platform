# AI 整理功能约定

本文定义应用内整理与日记整理 Skill 共同服务的功能设计。核对基线：2026-10-29 仓库代码及规则文件。两种实现的支持范围、处理机制和差异见[实现设计](实现设计.md)。

## 1. 目标、输入与输出

整理将原始记录变成保真、可读、可编辑的结构化日记。输入包括原文、日记日期及能够核实的人物资料；用户对原文的明确更正和澄清是事实依据，需与原始表达区分记录。

- 原文、用户表达的确定程度、情绪强度和推理过程优先于简洁。
- 允许修正错字、语病、重复、断句、时间顺序和口语表达；逻辑连接只能表达已有关系，不能新增事实、动机、结果或成长。
- 上下文足以确定的转写错误可修正；无法确定的人名、对象、时间和因果保留原意，需澄清的内容留在稿外记录。
- 输出包括原文已有的引入、有序事件、琐事、后续计划；事件包含标题、正文、可选感受、可选反思与成长、重要性及理由。
- 应用内结构化对象用于存储和后续处理；Skill 默认交付可阅读、可修订的 Markdown，经转换后进入同一类整理模型。
- 标题、摘要、地点、心情和标签的生成 / 更新范围由[分析实现对照](../AI分析/实现设计.md)说明；它们不应由整理阶段凭空补齐。

整理输出属于事实表达，分析允许的解释性推导在[AI 分析功能约定](../AI分析/功能约定.md)中独立定义。

## 2. 内容与结构规则

**总体原则**

- 结构化日记是证据层，目标是把口述流水账整理成清晰、稳定、可追溯、可阅读的日记记录。
- 可以修正错别字、语病、不通顺表达，可以合并重复内容，可以调整内容顺序。
- 不允许补充原文没有表达的动机、结果、感受、反思或经验。
- 不展示原文没有明确表达的内容，不写：`原文未明确`。
- 重复表达只保留信息最完整、表达最清楚的一版。
- 含混内容保留原意和确定程度，影响关键理解时通过澄清确定，不强行解释成明确结论。
- 用户展示格式以自然叙事为主，避免把事实信息拆成表单。
- 整理不是总结。生活细节、人物互动、玩笑、情绪表达、临时转念、观点推演、具体计划默认保留，不能因为不影响主线就删除。
- 观点类内容必须保留推理过程，不能只保留结论。
- 原文中无法归入事件、琐事、后续计划的开场白或闲聊内容，应提取为日记开头的背景引入段。
- 引入段仅整理原文已有内容，AI 不主动生成。
- **最高准则**：尊重事实但不过度尊重原文。整理结果必须让人能看懂，这是给人读的。
- **剔除无信息价值的口头语言**：语音转文字中大量存在不属于日记内容的语言噪音（录音过程自语、叙述过渡、走神重复、无意义填充等），只要不承载事件、情感或认知信息，都应剔除。
- **事件描述围绕事件本身，用书面逻辑组织**：事件正文只包含与事件相关的信息（时间、地点、人物、经过、感受、思考），用书面逻辑重新组织表达，按时间先后单向叙述，补全隐含的逻辑关系，结合上下文修正语音识别错误，确保可读性。

  样例（以下均为上述原则的具体推导，不作为独立规则）：
  - 元叙述（关于写日记行为本身的表述，如"闲着也是闲着就说两句""刚讲到哪了"）不承载事件信息，应剔除
  - 口语过渡语（如"再讲一个今天早晨的事"）中"今天早上"是事件时间信息要保留，"再讲一个...的事"是叙述噪音要去掉
  - 口语中隐含的逻辑转折需补全连接词（如"下楼腿都在抖，走起路来就好很多"→"下楼腿都在抖，但走起路来就好很多"）
  - 时间线来回跳跃（如今→昨→今→明）应按实际时间先后单向重组
  - 语音识别乱码需结合上下文推测修正（如"spilm和看奶"→"Scrum 和看板"）
  - 同一信息只保留一次，不因原文在多处提及就重复出现

**事件拆分规则**

- 采用**自然日记整理格式**，一篇日记可以拆分为多个事件。
- 事件按**目标**拆分为主：只要“想解决的问题 / 想完成的事”不同，就拆成不同事件。
- 时间、地点、人物、场景、主题作为辅助判断，不作为主拆分标准。
- 没有展开讲、但有记录价值的内容归入“琐事”。
- 明确指向未来安排的内容归入“后续计划”。
- 与事件有关的已表达安排保留其叙事语境，并提取到后续计划；独立计划直接列入后续计划，不能把计划写成已发生的结果。
- 不把未展开的工作进展、生活插曲强行并入不相关事件。
- 同一段原文中涉及多个独立工作事项（如软件过程文档、东莞项目收尾、前端 DUS 工作），即使原文未明确分隔，也应依据事项本质拆分为独立事件。

**单个事件展示格式**

```markdown
## 事件：事件标题

事件正文。把背景、动机、过程、结果合并成一段或多段自然语言，按阅读顺序整理，不强制拆字段。

### 感受

### 反思与成长
```

**完整整理结构**

整理后的日记按以下顺序组织：

1. **开头引入段**（可选）：原文中无法归入事件、琐事、后续计划的开场白或闲聊内容的整理版
2. **事件**（一个或多个）：`## 事件：事件标题`
3. **琐事**（可选）：`## 琐事`
4. **后续计划**（可选）：`## 后续计划`

> 日记分析（心情、标签、分析六部分）不在整理结构中，而是在 AI 智能分析阶段独立生成（见"AI 智能分析"章节）。

**事件正文表达规则**

- 事件正文承载原来的背景、动机、过程、结果。
- 事件正文写成自然段，不默认使用编号。
- 只有原文步骤非常清晰、且编号能明显提升可读性时，才使用编号。
- 事件正文可以包含当时发生的即时感受，但不展开心理分析。
- 事实信息优先合并写，避免被拆成过细字段。
- 生活细节默认保留，包括具体行为、人物互动、玩笑、吐槽、临时插曲和有记忆点的表达。
- 思考类事件要保留思考链条，包括触发原因、推理过程、尝试方向、工具选择、判断变化和阶段性结论。
- 观点类事件要保留观点推演，包括原始判断、支撑理由、类比、转折、保留意见和后续认知方向。
- 事件标题要具体概括“发生了什么”，不使用过泛的主题词。
- 事件标题优先使用“具体人物 / 具体对象 + 具体动作 / 变化”的句式。

示例：

```markdown
## 事件：今天早晨林萧鹏问我版本管理平台是否有用，他准备把它重新做出来

今天早晨林萧鹏突然问我管理平台当时用起来感觉怎么样，有没有效果。我说有效果，但后来被合并到超图后就被否定了。他说现在准备重新搞一套，因为他在做 AI 项目版本管理时也遇到了一些问题。我想把原来的版本管理平台捡起来继续做，一方面是给自己一个学习软件开发全流程的机会，另一方面也是把之前没完成的遗憾补上。
```

**琐事展示格式**

```markdown
## 琐事

1. 琐事内容一
2. 琐事内容二
3. 琐事内容三
```

- 标题固定为 `## 琐事`。
- 内容使用编号列表。
- 琐事为可选块，只有原文存在未展开但有记录价值的内容时才展示。
- 琐事是未展开、可用短条目完整表达的记录；不是价值较低的事件。不能仅按 LOW、字数或题材决定归类。
- 已归入事件的内容不得再出现在琐事中（去重约束）。

**后续计划展示格式**

```markdown
## 后续计划

1. 计划内容一
2. 计划内容二
```

- 标题固定为 `## 后续计划`。
- 内容使用编号列表。
- 后续计划为可选块，只有原文存在明确指向未来安排的内容时才展示。
- 后续计划按重要性排序，而非按原文时间顺序排列。
- 反思中明确表达的未来行动意向同步列入后续计划；经验总结、应该怎样做或对他人的建议，不能在未表达行动意向时自动转为用户计划。
- 后续计划条目需改写为语义清晰的书面表述，不保留口语化的模糊表达。

**感受表达规则**

- 事件正文里可以写具体经过中的即时感受。
- 独立的感受字段提取用户已表达的核心感受，并保留理解它所必需的触发背景；不同含义分别保存。
- 感受与反思不再次复述完整过程，正文仍保留完整细节和推演；与派生字段必要的重复允许存在。
- 只有原文明确表达情绪时，才展示感受字段。

示例：

```markdown
### 感受
这件事里的情绪从烦躁、被忽视，转为被回应后的轻松和高兴。
```

**反思与成长表达规则**

- "反思与成长"可以承载反思、感悟、成长、自我认识等内容，但展示时不拆成内部小标题。
- 只有原文明确表达了对应内容时才整理。
- 原文没有明确表达时，不展示该字段。
- 有多条反思时，使用编号列表展示。
- 只有一条反思时可展示自然段，存储仍保持条目数组。

示例：

```markdown
### 反思与成长
我意识到以后遇到这种不回应的情况，不能一直重复找同一个人，而是要更早判断是否需要换一种推进方式。
```


## 3. 人物、标题与含混内容

- 原文中的有效称呼保留，不因人物资料存在主名而统一替换。关系和性别用于理解指代及修正明确的转写错误，不补写原文未表达的人际关系或背景。
- 人物未匹配、性别未知或指代存在多个解释时保留原文；明确的人物更正优先于旧资料。
- 标题与正文维持相同事实、角色和确定程度。角色称呼、对话主体及动作对象必须核对，不能为简短或统一名称改变谁做了什么。
- 疑问与候选解释写在澄清记录中，不混入正式正文作为已确定事实。用户确认后联动复读全文，保留人工修订。
- 旧稿对“保留模糊原意”和“在正文标注原文未明确”同时作出要求；当前 Skill 采用稿外澄清方式。统一的展示策略见实现设计的差异表，整理文档不替用户消解原有冲突。

## 4. 事件重要性

重要性评价事件对用户目标、情绪、行为、关系、认知 / 价值观或后续安排的实际影响，不评价内容长度、规模或分析质量。

| 等级 | 约定 |
|---|---|
| `LOW` | 日常活动、常规推进、短暂感受或一般互动，没有具体的超常影响；重复但无新进展的记录也可为 LOW |
| `MEDIUM` | 出现具体问题、进展或变化，实际影响了选择、行为、情绪、关系、认识或安排，影响程度有限 |
| `HIGH` | 关键决定、明显转折、重要关系变化、强烈情绪、重大困难或强约束，且有显著影响的具体依据 |

- 先识别具体影响，再判程度；完成普通步骤、增加一般待办、表达普通好恶不自动升级。
- 认知影响也是实际影响。具体新理解、判断修正或困惑得到解释可构成影响，不要求已经行动；复述知识和重复旧观点不自动升级。
- 反复冲突、持续压力若本次仍有强烈情绪或重要边界影响，按本次影响判断，不要求已经产生最终关系结果。
- 独立成事件、篇幅长、有感受、反思、计划或涉及健康、金钱和家人等主题，都不自动提升等级。
- 各事件独立判断，不规定比例或按当天排名。计划按已体现的影响判断，预期收益不能写成已发生结果。
- 理由写一句可核实的影响依据；缺乏明确影响时为 `LOW：未识别到明确的用户影响`。

用户可覆盖 AI 重要性；下游读取 `user_importance` 优先、其次 `ai_importance`。应用内和 Skill 的存储位置与审核行为见实现设计。

## 5. 状态、交付与验收

状态及来源锁统一见[录入与维护](../录入与维护.md)。重复整理、整篇替换和定点修订的范围需由具体实现先核实，不能因日记仍为 `organized` 就承诺可覆盖。

- 结构完整：正文、感受、反思按独立含义存成有序条目，空字段按格式省略或使用空数组，正文仍保留完整原意。
- 信息保真：事实、人物互动、生活细节、计划、推理链、观点转折和用户不确定表达均有保留；重复仅合并表达，不删新增含义。
- 分类正确：独立目标拆为事件；未展开但值得记忆的内容归琐事；未来安排进入后续计划。
- 可读性：清除录音自语和无信息填充，修正明显转写错误，叙事连贯，不能用摘要替代长段经历。
- 派生字段：感受和反思必须有原文或明确澄清依据，只有行为或身体表现时不推导新的感受。
- 保存安全：稿件、来源、用户、日期和替换范围一致；预检只说明可转换及写入条件，不代替语义质量审阅与用户确认。
- 长文本分段处理保留跨段关联，不能静默截断。

关键案例及边界按两种实现分别核验，单一路径通过不代表另一条路径已对齐。
