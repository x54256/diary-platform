## 2. 数据与来源

`DiaryActionItem` 保存所属用户、日记、生成轮次、名称、推荐日程、完成状态、手工修改标记与软删除时间。来源类型为 `PLAN`、`SUGGESTION` 或 `MERGED`。

来源以 `source_refs` 保存快照，包括带来源键和原文的条目、计划来源、分析来源键和实际分析项 ID。索引仅说明当次来源位置，原文摘录与稳定键共同用于追溯，不把计划数组下标当永久身份。

当前生成输入为计划与事件级/日记级可行动建议分配来源键，形如 `plan:位置:文本摘要`、`suggestion:event:事件位置:文本摘要` 和 `suggestion:diary:文本摘要`。输入和 JSON 协议以源码为准，文档不重复复制模型提示词与完整字段结构。

`DiaryActionEventLink` 在新行动保存时固化事件关联：纯计划来源不建立事件关联；带事件分析项的建议或合并来源，按真实 `AnalysisItem.event_id` 去重保存。历史行动不在查询时隐式回填。

`DiaryActionScheduleLink` 单独保存关联历史和当前关联，包含任务 ID、任务快照 ID、完成锚点及解除原因。两个部分唯一索引保证同一行动项和同一日程任务各自最多有一条 `unlinked_at IS NULL` 的有效关联。日程外键删除置空作为兜底，业务删除仍须显式结束关联。

选择独立关联表，是因为行动项可以多次建立、解除、重新建立日程联系；在日程任务上只放一个来源字段无法完整表达这段历史。

## 3. 功能设计与两种生成实现

| 设计要求 | 应用内实现 | 分析 Skill 实现 |
|---|---|---|
| 输入基于计划与当前分析建议 | 当前图谱分析阶段组合已冻结的日记与分析结果 | 从导出的来源及完整分析稿解析行动与依据 |
| 原子化与合并保留依据 | 行动规划提示词要求只输出可独立完成事项，按来源键校验 | Markdown 转换器校验来源摘录/来源键，预检完整分析稿 |
| 推荐合法日程 | 生成协议与校验；发布协调服务保存 | 预检检查日期与日程字段，保存前再次检查日期新鲜度 |
| 分析和行动完整发布 | `graph_publish` 同事务保存分析轮次与行动结果 | `persist_result` 同事务保存分析、行动并读回比对 |
| 用户选择后才创建日程 | 结果发布后进入行动面板，再请求同步 API | 保存完成后同样复用行动面板和同步 API |
| 重分析保护已执行行动 | 共用 `apply_action_planning_result` | 当前 Skill 首次分析保存路径使用同一服务；不能据此宣称已有完整反馈重分析工作流 |

应用内行动规划失败会使所在分析任务失败，进度和恢复属于[日记分析实现](../日记管理/AI分析/实现设计.md)。模型用途为 `analysis`，环节键为 `action_planning`，由统一模型运行时解析；原草案写独立 `ACTION_PLANNING` 用途已不对应当前配置。

输出原子性属于语义约束，程序不通过“并且”等连接词机械拆分句子。输入“整理本周工作并预约牙医”应形成两个可分别完成的行动；“周回顾并制定下周计划”若共同构成一次不可分割的例行活动，可以保留一个行动。

## 4. 保存与旧结果协调

`apply_action_planning_result` 查询未删除旧行动，保护以下任一条件满足的记录：已完成、手工修改、有有效日程关联、来源含计划（`PLAN`/`MERGED`）。其余旧记录作为可替换项软删除。

新结果跳过空标题和与保护项同名的行动，保存来源与推荐字段，并固化来源事件关系。该服务当前对部分异常值有兜底：开始日期过期移至服务器当天、未知循环类型回退 `NONE`、无法转为整数的次数清空。上游严格校验仍须保留，不能依赖这些兜底证明模型输出完整合格。

分析、行动项及发布状态在调用方事务中提交；任一验证或保存异常应回滚整轮发布。历史已分析日记没有行动项时，只查询不会触发模型；重新生成由明确的分析操作控制。

## 5. 行动接口与同步事务

全部路径位于应用 API 前缀下，接口模型以源码为准：

| 方法与相对路径 | 职责 |
|---|---|
| `GET /diaries/{diary_id}/actions` | 仅对本人未删除、已分析日记返回行动项 |
| `PUT /diary-actions/{action_id}` | 修改名称或推荐日程，设置手工修改标记 |
| `PUT /diary-actions/{action_id}/completion` | 完成/取消并同步完成锚点 |
| `POST /diaries/{diary_id}/actions/sync` | 按用户确认的完整推荐参数创建日程关联 |
| `DELETE /diary-actions/{action_id}` | 解除关联、软删除行动，保留日程 |

查询和维护均使用用户归属过滤。批量同步拒绝重复行动 ID，逐项核对同属当前日记；已有有效关联直接返回，不重复创建。没有关联时创建日程任务和近期实例，写入关联，全部条目处理完成后一次提交。未捕获异常由请求会话回滚，因此不能将尚未提交的中间条目视为已成功。

当前批量同步没有显式行锁；唯一约束防止冲突，但并发重复提交的异常转换仍存在差距，见第 8 节。同步会设置 `user_modified=true`；已完成的未同步行动，会把首个锚点实例保持为完成。

## 6. 关联与双向更新

### 完成锚点

- 未同步行动直接更新自己的完成状态。
- 有关联且有锚点时，行动页完成同步更新锚点；日程页只有完成锚点变化才回写行动项。
- 单次任务锚定唯一实例；循环任务锚定首次有效实例，完成表示开始落实，后续实例不改变该 Checkbox。
- 循环锚点被单次删除后，从当前已经持久化且尚存在的后续实例选择下一条；没有下一条时当前实现解除关联。

### 字段更新

行动页只改名称时更新任务名称及 `pending` 实例名称；提交完整推荐日程时更新原任务规则，删除当前及未来 `pending` 实例，再重新生成近期范围和后续维护任务，随后重选锚点。

日程页单次例外按 `scope=single` 不回写通用行动字段；后续修改拆出新任务时，`sync_action_after_task_replaced` 迁移有效关联、重选锚点并回写推荐字段。此处是否进入拆分分支取决于日程路由的规则变化检测，不完全等同于 `scope`，详见日程实现设计。

双向同步使用同一数据库会话中的内部函数，不通过互相调用 HTTP 接口实现，因此不产生两个 API 相互触发的递归流程。

### 删除与重新同步

| 操作 | 行为 |
|---|---|
| 删除行动项 | 关联结束，原因 `ACTION_DELETED`；行动软删除；日程保留 |
| 删除单次日程实例 | 关联结束；行动保留最后字段，可重新同步 |
| 删除循环非锚点实例 | 关联保留 |
| 删除循环锚点 | 选择已生成的下一实例；无候选时结束关联 |
| 删除循环当前及以后 | 结束关联；行动保留 |
| 重新同步 | 创建新任务和新关联行，旧关联保留历史 |

当前解除原因多数保存为 `SCHEDULE_DELETED`，原草案单列的 `FOLLOWING_DELETED` 没有覆盖所有后续删除路径。查询根据是否存在有效或历史关联展示 `synced`、`unsynced`、`schedule_deleted`。

## 7. 前端交互

已分析日记显示“日记 / 分析 / 行动”面板；无行动时展示空状态。`DiaryActionPanel` 提供完成、名称编辑、来源摘录、删除以及同步面板，循环项提示首次实例完成表示开始落实。

同步面板列出没有有效关联的候选，用户可逐项修改名称、日期、时间、循环与结束条件，确认后批量请求同步接口。当前新候选默认选中，关联已删除的候选默认不选；原草案的“默认不全选”目标未对齐。

移动端控件实际字号至少 16px，不能禁用用户缩放。此次文档整理不修改前端，不代表已完成真实 iOS Safari 聚焦验收。

## 8. 设计与实现差异

| 设计约定 | 当前源码事实 | 影响与后续维护 |
|---|---|---|
| 同步面板不默认替用户选择 | 未同步新候选默认选中；仅曾删关联的候选默认不选 | 用户仍须确认提交，但选择初值与原约定不同 |
| 已关联行动修改使用后续任务替换，保留已发生及手工修改实例 | 行动路由直接更新原任务，重建当天及未来全部 `pending`；未过滤手工修改标记 | 手工例外保护不完整；必须作为后续修复项 |
| 单次日程修改回写行动所有字段 | 未改规则分支更新实例，但回写从任务定义取值，任务定义未同步更新 | 行动字段可能仍是旧名称/时间；不能声称完整双向一致已验收 |
| 并发同步与完成使用行锁或版本号 | 代码未显式使用 `FOR UPDATE` 或版本列 | 唯一索引仍兜底有效关联，竞态错误响应和丢失更新需独立验证 |
| 日程同步可选首个符合规则的实例 | `_create_schedule_task` 要求开始日期当日存在实例 | 开始日期不符合工作日/休息日或其他规则时会拒绝同步，不能默认自动顺延 |
| 删除循环锚点持续保留任务关联 | 只在已生成范围寻找下一实例，无候选即解除 | 远期间隔或次数耗尽场景要核对产品预期 |
| 原草案的来源 JSON 示例与独立服务类 | 当前使用真实来源键/摘录及函数式 `action_items.py` | 以当前存储与函数边界维护，保留原业务来源目标 |

以上是静态核对发现的实现差异，本轮不修改业务代码。共用来源、原子化、保护规则仍以功能约定为目标。
