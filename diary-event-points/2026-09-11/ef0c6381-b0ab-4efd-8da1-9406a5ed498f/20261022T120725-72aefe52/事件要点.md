## 事件：整理“工程化使用 CBB 服务管理”的方法论

<!-- event_id: 18b7236f-d927-4581-a087-a814a6bc63b7 -->

### 1. 为经验分享反复细化设计思路，才让 AI 产出像样文档

今天剩余时间主要整理“工程化使用 CBB 服务管理”的方法：查询接口交给它时，怎样维护数据库设计及版本，以及本地接口资产和版本。

最初与 coder 沟通、开专家团，耗了好多 token，结果稀碎。下午例会要经验分享，我重写设计思路让 Codex 改，仍稀碎，最后把思路写得更细，才产出像样文档。

### 2. 认为 CBB 接走查询接口后，结构与数据维护仍应由自己的应用负责

传统后端通常负责数据库表结构、数据维护和对外查询，不一定是单一应用，但这些能力至少由后端应用提供。表结构可用 xdata-db-init 按初始化脚本维护，保存、查询也由后台提供。

CBB 服务管理接走查询逻辑，有些像 OLAP 工具：不维护结构和数据，而是连接数据源，按业务逻辑写 SQL、对外提供接口。理论上，表结构维护、数据保存仍应由我们的应用承担。

### 3. 直接连库且没有留痕，导致现场迁移和增量更新困难

此前时间紧，加上想当然，我直接用数据库客户端改结构、写 SQL、导数据，没有记录。在公司似乎没问题，到现场却不知道如何初始化表、导数据，只好备份整个公司库再导到现场。

后来结构、数据变化如何增量同步，也没好办法。CBB 配置 SQL 改了，哪些接口改过、哪些需更新都没记录。这些粗糙做法让换环境时无法按步骤复现，也不便增量更新。

### 4. 用资产化、版本化和自动化支持复现与更新

我把解决思路对应到“一切皆代码”：用代码或结构化文档记录全过程，换环境也能按步骤配置结构、数据和接口。引入版本，记清从第一版升第二版要做什么，支持增量更新或回退，不能每次让现场删整个库从头来。

在我理解中，Everything is Code 包含资产化、版本化、自动化。资产化是留档以逐步复现，版本化支持增量更新、回退，自动化则让过程自动执行。即使当前数据库或 CBB 崩掉，也能凭资产恢复整个业务和应用能力，不完全依赖当前环境。

### 5. 重新用 Java 后台维护数据库结构和数据

具体仍拉回传统 Java 后台方案：一是用 db.sql 这类脚本保存数据库结构，后台启动时执行初始化和维护；二是由后台提供数据导入、更新接口，无论导 Excel，还是启动任务计算结果入库，都提供类似 OLTP 的能力，替代直接连库改结构、维护数据。

### 6. 用接口设计文档留存 CBB 资产，并记录版本差异

以前查询接口在 Controller，现在配置在 CBB。若只存在服务管理中，系统崩了就找不到资产；它的版本管理也不够好，不能每次更新都让现场删除已有接口，再按公司配置逐个添加。

所以我决定用结构化接口设计文档表示 CBB 接口，记录每版有哪些接口和带版本号的修订记录，主要支持增量更新，也考虑回退。加上结构脚本与数据维护能力，三部分资产就都有了。

### 7. 保留数据库设计过程及需求、接口、使用方之间的关联

既然维护数据库脚本，也留数据库设计文档，修订记录版本号与 SQL 脚本一一对应。脚本和建表语句是最终结果、物理模型，文档则保留需求如何变成结构。简单需求看物理设计也许就能对应，不必展开概念、逻辑设计，但保留过程也没问题。

需求与数据库的联系由数据库设计文档保存；接口与需求、数据库、前端使用方的联系由接口文档保存，例如对应什么需求、为何拆接口、用哪些表、哪些前端用、业务逻辑是什么。每个接口还可加测试链接和参数拼法，点击就能看结果是否正确。其他辅助问题暂想不起，重点先解决结构与接口维护。

### 8. 用 AI skill 半自动更新 CBB 接口，现场仍需手工操作

结构脚本配合 xdata-parent 的 xdata-db-initial 可以自动更新表结构，但接口文档不能直接自动同步 CBB。我让 AI 做了 skill，按接口修订记录识别新增、修改、删除，再操作 CBB 保存。还得我主动说一声，算半自动，我觉得也算自动化；现场用不了 AI，仍要手动按文档配置。

这不算理想，正常可做成 Java 后台功能或脚本，让公司、现场都能用。不过 skill 能在本地把保存、测试和语法、运行报错后的自动修复串起来，我不用管太多，算偷懒。我仍觉得用脚本或 Java 应用接口做更新更正确。

### 9. 沿用 Maven 稳定版本与 tag，让发布包对应明确代码

重新引入 Java 后台，也就重新有 Maven 版本，如 1.0.0、1.0.1、1.1.0。我继续复用原规范：结构、导入方式、接口等稳定后，从 1.0.0-SNAPSHOT 转为 1.0.0，打 tag、发布包，让包与代码明确对应，再把稳定版发各项目。

即使我在开发 1.0.1-SNAPSHOT，别人仍能用 1.0.0；新版有 bug 可用旧版，不用等我把当前开发和修 bug 全完成才发包。

### 10. 应用版本留档便于回退，也便于维护旧版本

起初我觉得新版可能联动改前端、数据库等，不是把 Java 的 Git commit 回历史位置就行。后来想想也可以，只是没那么方便。这已超出 CBB 使用，涉及为何做应用版本管理。

主要价值还是留档：新版出问题能退旧版；旧版出问题，使用方又没必要或不想升级，也能找到对应代码做 hot fix，快速发修复版。因此我仍保留应用版本。

### 11. 设想正式发布后固定接口版本，以兼容旧前端

接口版本类似路径 /v1、/v2。我的设想是，1.0.0-SNAPSHOT 开发期间，/v1/user 怎么改都不升级接口版本，告诉前端一起改即可，一般尚未正式给别人用。

一旦 1.0.0 发布，/v1/user 就固定，以后不改，只能废弃或删除。到 1.0.1-SNAPSHOT 若发现错误或业务需变，就新增 /v2/user、废弃原接口，新前端接 V2；1.0.1 发布时，前端用 V2，后台同时留 V1、V2。

这样是为兼容现场旧前端：只能控制自己的后台，控制不了前端。新前端若有问题不能部署，后台仍可先升，旧 1.0.0 前端继续调用。这里的前提是表结构没变、只改业务逻辑，通过接口版本向下兼容。
