## 事件：整理“工程化使用 CBB 服务管理”的方法论

<!-- event_id: 18b7236f-d927-4581-a087-a814a6bc63b7 -->

今天剩下的时间，主要都在整理之前用 CBB 服务管理做东西时，数据库设计及其版本、接口设计及其版本该怎么维护。我把它当作一套工程方法论：当查询接口由 CBB 服务管理提供时，怎样管理数据库结构，以及本地留存的接口资产和版本。

一开始我和 coder 沟通，还开了专家团，花了好多好多 token，最后做出来的东西稀碎。下午例会要做经验分享，没办法，我又整理了一遍自己的设计思路，跟 Codex 说，让它改，结果改得也稀碎。后来我又把设计思路写得更细致了一些，才出来了个像样的文档。

这套东西的背景，是传统后端应用一般会负责数据库表结构、数据的维护，以及对外查询接口的提供。不一定由单一应用完成，但至少是由后端应用来提供这些能力。表结构可以用 xdata-db-init 根据数据库初始化脚本进行维护；保存、查询等接口也由后端应用提供。

现在用了 CBB 服务管理后，它接走了查询接口这部分逻辑。它有点像 OLAP 工具：不负责维护数据结构和数据，而是连接数据源，根据业务逻辑写 SQL，再对外提供接口。理论上，表结构的维护和数据保存这部分能力，仍然应该由我们自己的应用承担。

但之前做的时候，一方面迫于时间压力，另一方面也是想当然，我直接用数据库客户端连库，修改表结构、写 SQL、导入数据，没有把这些操作记录下来。在公司用时，可能觉得没什么问题，一旦要拿到现场，就会遇到问题：表结构怎么初始化，数据怎么导入？当时的办法就是在公司备份整个库，再导入现场。

接下来又有增量更新的问题。公司这边的表结构和数据发生变化后，怎么同步到现场？目前没有很好的办法。接口也是一样，配置的 SQL 改了以后，怎么更新到现场？哪些改了、哪些没改，哪些需要更新、哪些不需要，也没有清楚的记录。

这些问题都来自之前那种粗糙的管理方式：直接连库维护表结构，导入、更新、删除数据，整个过程没有留痕，所以换个环境时没法按步骤复现，也不方便增量更新。

我的想法对应“一切皆代码”：把整个操作过程用代码或者结构化文档记录下来。有了记录，不管换到什么环境，都可以按步骤把数据库结构、数据和接口配置出来。再引入版本的概念，记录从第一个版本升级到第二个版本需要做哪些操作，方便增量更新，或者版本回退。总不能每次更新，都让现场删掉整个库，再按照最新文档从头操作一遍。

具体做法，还是把这部分拉回传统 Java 后台应用的方案。

第一，数据库结构初始化和维护，继续由 Java 后台负责，用 db.sql 这样的数据库脚本留存结构，在启动时执行。

第二，数据导入和更新，通过 Java 后台提供接口。无论是导入 Excel，还是启动计算任务后把结果入库，应用仍然提供类似 OLTP 程序的能力。这两部分替代我之前直接连库修改结构和维护数据的做法。

第三，查询接口比较特殊。以前接口写在自己的 Controller 里，现在实际配置在 CBB 服务管理里。如果只保存在那里，服务管理一旦崩了，这些接口资产也就找不到了。而且它的版本管理做得不够好：现场已经部署了一批接口，总不能每次更新都让现场把它们全删掉，再照公司最新的配置一个一个添加。

所以我决定建立接口设计文档，用结构化文档表示 CBB 上的接口，把它们资产化，再做版本管理。文档记录每个版本有哪些接口，并配上有版本号的修订记录，主要用来解决增量更新问题，也考虑版本回退。

这样，数据库结构脚本、数据维护能力、接口文档这三部分就都有了。留存这些资产，是为了换一个地方，或者现有数据库、CBB 服务管理崩掉后，仍然能按照流程一步一步把整个业务和应用能力复原出来，不至于完全依赖当前环境。版本化则是为了解决后续增量更新的问题。

核心问题之外，还可以补一些辅助内容。

既然已经维护数据库脚本，干脆也把数据库设计文档留存下来。我的想法是，设计文档修订记录的版本号，与数据库 SQL 脚本的版本号一一对应。脚本是最终结果，建表语句反映的是物理模型；设计文档则可以保留从需求一步一步到数据库结构的设计过程。简单需求可能看物理设计就能直接对应上，不一定需要展开中间的概念设计、逻辑设计，但把设计过程留存下来当然也没有问题。

还要建立多方之间的关联。需求与数据库之间的关系，通过数据库设计文档留存；接口与需求、数据库、前端使用方之间的关系，通过接口文档留存。文档里可以写清楚：对应哪个需求，为什么拆出这个接口，用到哪些表，哪些前端在用，以及接口的业务逻辑。

另外，还可以为每个接口增加测试链接，写清参数怎么拼、链接是什么。到时候直接点击，就能查看结果对不对。其他辅助问题我一时想不起来，先这样，重点还是先解决表结构和接口怎么维护的问题。

在我的理解里，“Everything is Code”主要有三个概念：资产化、版本化、自动化。资产化就是留档，能一步一步复现这套东西；版本化是支持增量更新或者版本回退；自动化则是让这些过程自动执行。

数据库结构这部分，有脚本，再加上 xdata-parent 里的 xdata-db-initial，就可以自动更新表结构。但接口是通过 CBB 服务管理维护的，接口文档本身没法直接自动同步过去。

我现在采用的方案，是让 AI 做了一个 skill。新增接口时，让 AI 看接口文档的修订记录，识别新增、修改、删除了哪些内容，再去操作 CBB 服务管理，完成接口保存。因为还需要我主动告诉它一声，也可以说是半自动化，不过我觉得也算自动化。到了现场，由于用不了 AI，还是得手动按文档操作。

用 skill 的方式其实不算理想。正常来说，可以把这部分做成 Java 后台功能，或者用脚本实现接口更新。这样就不会出现在公司因为能用 AI agent，所以可以自动做，到了现场却不行的情况。

不过 skill 有一个好处：本地测试时，让 AI 把接口保存上去，如果有语法问题，或者在服务管理里测试时报错，它能继续自动修复。我不用管那么多，整套流程都交给它，也算偷了个懒。但我还是觉得，通过脚本或 Java 应用提供接口来做更新，会是比较正确的方案。

另外，我也考虑了应用版本和接口版本。

之前那种粗糙的做法没有 Java 后台，只有 CBB 服务管理。现在重新引入 Java 应用，也就重新有了 Maven 应用版本，例如 1.0.0、1.0.1、1.1.0。我在设计里继续复用原来的版本管理规范：当数据库表结构、数据导入方式、接口等功能稳定后，从 1.0.0-SNAPSHOT 变成 1.0.0，打 tag，发布部署包，让构建包与代码建立明确的对应关系，再把稳定版本分发给各个项目使用。

这样，即使我还在开发 1.0.1-SNAPSHOT，别人也能先用稳定的 1.0.0；新版本有 bug，也可以使用旧版本，不必等我把当前开发中的东西全部做完、把 bug 改完才能发包。

一开始我觉得，做新版本时可能联动改了前端、数据库等很多东西，不是把 Java 代码的 Git commit 回到某个历史位置就行。后来想想，其实也可以，只是没有那么方便。这已经不完全是怎么使用 CBB 服务管理的问题了，而是在讨论为什么应用要做版本管理。

我觉得主要价值还是留档。一方面，新版本有问题时，可以退回某个旧版本；另一方面，旧版本出了问题，但使用方没必要或不想升级到最新版本时，可以找到旧版本对应的代码做 hot fix，快速发一个修复版本。所以这套设计里，我仍然保留了应用版本的概念。

接口版本则类似 Java 接口路径上的 /v1、/v2。比如还在开发 1.0.0-SNAPSHOT 时，有一个 /v1/user 接口，只要这个正式版本还没发布，怎么修改接口都不升级它的版本号，改动后告诉前端一起调整就行。因为还在开发，一般也没有正式交给别人使用。

一旦 1.0.0 正式发布，/v1/user 就固定下来。按我的这套想法，以后就不再改它，只能废弃或者删除。如果到了 1.0.1-SNAPSHOT，发现接口有地方写错了，或者业务逻辑需要改动，就新增 /v2/user，把原接口标记为废弃，让新版本前端对接 V2。等 1.0.1 发布时，前端用 V2，后端同时保留 V1 和 V2。

我认为这样做的作用，是兼容现场的旧前端。我们只能控制自己的后台，没法控制前端。如果现场新版本前端有问题，无法正常部署，后台仍然可以先升级，旧的 1.0.0 前端还可以继续调用新版后台。这里我考虑的前提，是数据库表结构没有改、只改业务逻辑的情况，通过接口版本化，实现对旧前端应用的向下兼容。

### 感受

为了下午的经验分享，我花了很多 token 和 AI 反复沟通，结果做出来、改出来的东西都稀碎，只能继续把自己的设计思路写得更细。

### 反思与成长

查询接口交给 CBB 服务管理后，数据库结构和数据维护的责任并没有跟着消失。之前直接连库操作、没有留痕的方式，暴露出了环境迁移和增量更新的问题。

我把解决思路归结为资产化、版本化和自动化：先留存能够复现的脚本、接口文档和必要的维护能力，再记录版本差异。设计文档还可以保留从需求到实现的过程，以及需求、数据库、接口和使用方之间的关系。

AI skill 能帮我把配置、测试、报错修复串起来，但如果要让公司和现场都能使用，脚本或 Java 应用会是更合适的自动化方式。

## 事件：技术分享中的反馈，让我想到亲身经历和理解痛点的差别

<!-- event_id: 60253ec4-e484-41ec-993f-356ab5c3cfd8 -->

今天宣讲时，肖静问，这套流程为什么还要做数据库设计，能不能直接用指标管理。我说可以，确实可以。其实我这次的数据库设计，也相当于重新设计了一套指标系统。只是有些特殊表，指标系统用不了，还是需要自己建。后面如果公司 CBB 提供了指标系统，就可以直接用他们的。

肖静还说，如果数据结构、表设计、需求和数据都能确定，那整个流程其实可以让实施、让项目组借助 AI 来完成，不需要开发来做。我说是的，我大部分时间本来就在梳理需求和数据，做的根本就不是开发的事。一个指标表的结构设计其实很简单，和 AI 讲清楚，让它设计就行。这些工作确实可以由项目组借助 AI 把整套流程走通，减轻我们的工作量。

他也说，自己对这些东西不太理解，很多痛点没有切身体会。我觉得这确实是实际情况：他可能知道存在这种情况、存在这样的痛点，但没有经历过，就不知道到底有多痛，也就不容易理解。

会议结束后，刘周伟来找我，说这套东西太有用了。他实际经历过把 CBB 功能迁到现场时遇到的一系列问题，所以体会过这些困难。我说，我这就是一个案例嘛。

今天我也和颂梅聊到这个。比如于海昕，他也知道就业环境不好，但更多还是轻描淡写，因为这些事情没有落到他自己和家里人身上。失业没有落到他身上，他现在依旧摆烂着，还能拿高薪，体会不到那种处境。

但其实我自己也体会不到，真正失业之后的无助到底有多痛苦。我只知道有这么一种社会现象，不知道它具体有多痛。没有经历过，可能更多只是知道有这个痛点；究竟多痛，还是不太清楚。有些东西，只有实际体会过，或者共情能力很强的人，才能理解。当然，这也就是我随便碎嘴说一下。

### 反思与成长

知道一个问题存在，和亲身经历它，是两回事。从同事对迁移问题的不同反应，到我和于海昕对失业处境的理解，都让我想到：没有实际经历，往往只能知道有这个痛点，未必知道究竟有多痛。
