# 内容分项与修改后的联动复查

本地、云端、文件修改与数据库修改均适用。

## 应用字段与分项

事件正文为 DiaryEvent.body；“感受”为 DiaryEvent.feeling；“反思与成长”为 DiaryEvent.reflection；页面底部整篇“后续计划”为 DiaryOrganized.plans。四者均为字符串数组，数据库 Text 字段保存 JSON 数组。

感受与反思分别按独立含义组织数组元素。两种独立感受、两条独立认识须分为两项，不能仅用句号串在同一个元素中。单项可以包含触发背景、原因、解释及多个句子；同一含义不机械拆碎。无内容保持空数组。Markdown 感受、反思与成长统一以每项一条的列表表达，续行缩进；plans 同样每项一条。

例如原文同时表达“找到原因后轻松”和“想到剩余工作仍疲惫”，应为：

```json
{"feeling":["找到原因后松了一口气。","想到剩余工作，仍感到疲惫。"]}
```

一句“想到剩余工作，仍感到疲惫。需要先休息一下。”是否应拆分取决于它表达的是同一体验的解释，还是独立计划；结合事实和栏目职责判断。程序检查数组类型、空项和稿件格式，Agent 逐项审阅语义，不按句号机械分割。

## 修改后的检查顺序

1. 修改前读取当前稿、来源和实际保存版本；修订前保留备份。用户已经改过时读取当前磁盘或数据库，不用聊天记忆或旧缓存覆盖。
2. 以用户明确修订和最新来源为依据，按稳定事件 ID 比较改动；未入库的文件按本次稿件原有身份定位。无法确定身份、事件新增删除或标题重名时先核实。
3. 事件 body 改动后检查对应 feeling、reflection，并检查整篇 plans。感受或反思被修改时也复核其与正文、其他栏目及相关计划是否一致。引入或琐事发生变化时检查其对事件归属及整篇计划的影响。
4. 保留用户对所有栏目的直接修改。去除已失去事实依据的旧提取，按修订后的明确表达更新；不把分析推测写成本人已经表达的感受、成长或承诺。不为填栏目追问。
5. 当前文本仍有关键歧义才提问；每轮最多四题并附选项。无须改动也写明具体复查结论。复查期间保持原稿与人工修改，不自动重新生成整篇。
6. 文件与数据库各有修改时做三方核对：上次共同版本、当前文件、当前数据库。互不冲突的修改保留；同处冲突询问用户，不默认任一方覆盖另一方。
7. 本地沿用当前阶段的确认与保存约定；云端完整 workflow 遵守先保存暂停及通知后自动联动保存规则。保存后从数据库重新导出，作为要点、关系、分析的事实来源。

数据库读取及定点修订使用 scripts/review_diary.py export/diff/prepare/save，命令和包格式见 workflow 的 cloud-review.md，db 模式也可使用。定点保存不重建事件，不修改未提交字段，复验完整来源、结构化版本和已有来源锁。已有正式要点或分析冻结的来源不能直接修订；先说明限制和影响范围，不偷偷废弃下游结果。

通用自查：正文是否仍完整保留原本属于事件的感受、反思与计划；派生栏目是否有事实依据；不同含义是否分项；人工修改是否保留；本次修改是否完成联动复查。文件读取、转换、指纹或测试通过都不能代替语义审阅。
