# 日记完整处理

## 数据访问模式

开始前读取[数据访问与云端配置](references/api-mode.md)。默认 `DIARY_DATA_MODE=db`；云端配置 `DIARY_DATA_MODE=api` 后，原脚本通过应用接口读写，命令中的 `backend/venv/bin/python` 改为 `python3`。API 模式不加载数据库配置，接口失败不切回数据库；来源指纹和失败恢复规则继续执行；确认时机按以下模式规则执行。

**执行规则优先级**：用户调用完整 diary-workflow 且使用 API 模式时，先读取[云端审阅与自动续接规则](references/cloud-review.md)，该规则优先于本文逐稿确认与逐阶段等待要求；单独调用子 Skill 和本地 db 流程继续原确认规则。文件或数据库修订后，均遵循[通用联动复查](../diary-organizer/references/revision-review.md)。



用户只调用本 Skill 一次，即授权本流程按顺序使用以下四个子 Skill。本地逐阶段保留审稿与确认；云端按审阅分支暂停和续接。具备续接条件后保存成功直接继续下一阶段，不再要求用户点名子 Skill 或确认是否继续。

| 阶段 | 读取并遵循的子 Skill | 完成依据 |
| --- | --- | --- |
| 整理 | [diary-organizer](../diary-organizer/SKILL.md) | 当前原文对应的有效整理结果已保存 |
| 要点提取 | [diary-event-points](../diary-event-points/SKILL.md) | 全部事件要点及向量已正式保存，运行为 POINTS_READY 或 PUBLISHED |
| 关系识别 | [diary-event-relations](../diary-event-relations/SKILL.md) | 完成候选判断及全部冗余复核，当前运行已发布为 PUBLISHED；允许零条关系 |
| 分析 | [diary-analyzer](../diary-analyzer/SKILL.md) | 当前整理版本对应的 CURRENT 分析轮次已保存，日记为 analyzed |

在进入某阶段时读取对应子 Skill 及其要求的参考资料，不一次加载全部规则。格式、语义核对、澄清、来源保护、预检和保存均执行该子 Skill 的现有流程，不复制维护第二套规则。

## 定位与续接

本 Skill 位于项目的 `skills/diary-workflow/`；通过发现链接加载时，解析真实路径，定位同时含 `backend/` 和 `skills/` 的项目根目录。以下命令在项目根目录执行，使用 `backend/venv/bin/python`。

默认用户名为 `x5456`，日期或日记 ID 优先复用本次对话明确的目标。缺少日期／ID时再问；同日多篇列出候选让用户选择。绑定日记 ID 后，后续命令始终使用该 ID，不因相同日期重新选中其他日记。

开始、断点恢复和每次入库成功后，先只读检查进度：

```bash
backend/venv/bin/python skills/diary-workflow/scripts/status.py \
  --username x5456 --date YYYY-MM-DD

backend/venv/bin/python skills/diary-workflow/scripts/status.py \
  --username x5456 --diary-id DIARY_UUID
```

脚本只输出身份、阶段状态、数量及阻塞原因；复用关系 Skill 的来源与向量校验，不输出正文、向量或认证信息，不调用外部服务。网络失败按项目权限流程重试只读查询。阶段判断是当前时点的路由依据，实际保存仍由子 Skill 再次预检。

- `next_stage` 为 `organize / points / relations / analyze`：从该阶段继续，复用前面已验证的有效结果。即使分析已存在而图谱尚未完成，也只补缺少的阶段，保留已有有效分析。
- `next_stage` 为 `review`：人工审阅尚未完成或须联动复查，按云端规则处理，不能直接进入要点。
- `next_stage` 为 `complete`：报告四阶段均已完成，不重新生成任何结果。
- `selection_required=true`：先确认唯一目标，再检查该 ID；没有候选时核实日期或 ID，不编造目标。
- `blocked=true`：说明具体原因。来源过期、多个有效运行、缺失或无效向量、分析版本冲突等不能通过自动覆盖旧结果解决。
- 发现未完成任务时，读取原阶段的本地记录、包及任务状态，按子 Skill 的恢复入口处理；已有活动任务不重复创建。失败写入先查询实际结果，不盲目重试。

阶段文件继续放在各子 Skill 规定的目录。额外在 `diary-workflows/YYYY-MM-DD/日记ID/流程记录.md` 维护一份简短交接记录：目标身份、已保存阶段及回执 ID、当前阶段、当前稿／来源／包路径和指纹、实际澄清与整稿确认依据、待答问题及必要的外发授权范围。已有记录先读后更新；本地记录辅助恢复，数据库有效结果才是完成依据。

当前阶段已有待审稿时，先读取磁盘当前稿及其来源、预检包和实际确认记录，续接审阅、澄清或保存，不自动重新导出和生成另一份稿。用户的确认只绑定其实际看过的版本；发现来源或稿件变化时按子 Skill 重新预检，并确认变化后的内容。

## 每阶段的交互循环

1. 执行当前阶段，交付完整可读稿或文件链接，附真正需要澄清的问题；无问题也须复读核对。不以摘要替代完整稿。
2. 回答澄清或提出修改时，按子 Skill 修订当前稿、保留人工修改并完成复查；局部回答不算整稿确认。
3. 交付最终稿前完成只读预检，说明目标日期、阶段、事件／要点／关系／行动数量及首次保存或替换范围。展示后等待用户对本阶段整篇稿确认，不提前处理依赖尚未入库结果的下一阶段。
4. 用户明确说当前稿“没问题”“可以了”“入库”，或说“没有待澄清问题就入库”且确实没有问题时，按已展示的对应稿及包保存，无需再次申请相同入库授权。纯粹“没有更多补充”、仅回答问题或仅确认修改方案，不能视为整稿确认。
5. 收到写入成功回执后核对实际状态，更新交接记录，直接进入下一个未完成阶段并生成下一份完整稿。中间只作简短进度说明，不以“需要继续吗”结束。分析保存后报告整篇完成。

用户暂停、限定只做到某阶段或改变目标时遵从其最新指令。继续恢复时先检查当前数据库和磁盘稿，不从旧记忆覆盖新修改。用户明确要求重做或替换已有结果时，先核对受影响范围并采用相应子 Skill 支持的修订方式；已锁定来源或不支持重分析时如实停止，不绕过约束。

## 外发与权限

要点入库会将完整详情发送给配置的 `graph_embedding` 服务。进入要点阶段时提前只读核实并说明服务地址、模型和内容范围，复用本任务已明确授权的相同目的地与范围；工具或审批要求额外授权时，先完成本地稿和预检，再就具体外发请求确认。目的地或范围变化后重新取得相应授权，不把总入口调用当作任意外发许可。

需要数据库迁移时按子 Skill 的固定迁移及权限流程执行。总入口自身不写数据库；只读进度脚本不提供写入参数。各阶段正式写入仍使用已有保存脚本及匹配指纹。
