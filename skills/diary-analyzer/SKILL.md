# 日记分析

## 数据访问模式

开始前读取[数据访问与云端配置](../diary-workflow/references/api-mode.md)。默认 `DIARY_DATA_MODE=db`；云端配置 `DIARY_DATA_MODE=api` 后，原脚本通过应用接口读写，命令中的 `backend/venv/bin/python` 改为 `python3`。API 模式不加载数据库配置，接口失败不切回数据库；逐阶段审阅、整稿确认、来源指纹及失败恢复规则继续执行。

**执行规则优先级**：用户调用完整 diary-workflow 且使用 API 模式时，先读取[云端审阅与自动续接规则](../diary-workflow/references/cloud-review.md)，该规则优先于本文逐稿确认与逐阶段等待要求；单独调用本 Skill 和本地 db 流程继续原确认规则。文件或数据库修订后，均遵循[通用联动复查](../diary-organizer/references/revision-review.md)。



## 任务边界

- 仅手动调用；用户显式调用 [diary-workflow](../diary-workflow/SKILL.md) 时，已授权总入口在分析阶段使用本 Skill，无需再单独点名。第一版仅处理状态为 `organized`、没有任何分析轮次、整理修订有效的日记。已分析日记停止，不通过删除旧轮次或修改状态绕过限制。
- 从数据库读取结构化日记和人物关系。日记事件是分析事实依据；人物资料用于理解身份、关系与指代，无法匹配时保留原意。
- 包含核心分析、认知分析和行动规划。入库保存分析轮次、分析条目、行动项及其事件关联，更新分析状态与搜索索引。原文、整理内容、元数据、标签和已有图谱保持原值。
- 保存推荐日程到行动项，不自动创建正式日程任务；本流程不触发建图或后台 AI 分析。
- 稿件与来源文件统一放到项目根目录 `diary-analyses/YYYY-MM-DD/`，日期为日记所属日期。同日多篇时使用日记 UUID 子目录；修订复用已有目录，预检包采用新文件名。

## 工作流程

### 1. 核实来源

按 [读取与入库说明](references/storage.md) 的 `find`、`export` 命令只读定位并导出。默认用户名 `x5456`；用户指定时使用指定用户。日期未明确年份且上下文无法确定时询问。多条候选由用户选择，零条时核实日期，不自动选择其他记录。

来源导出包含稳定事件 ID、正文、感受、反思、后续计划、人物关系及状态指纹。以导出文件作为输入，禁止手工补造或改写导出文件。文件读完后再分析，不凭历史聊天记忆代替当前来源。所有数据库操作使用 `backend/venv/bin/python`（Python 3.11）；存储脚本会进入后端目录加载配置。

### 2. 分析并形成完整稿

先阅读 [Markdown 格式](references/markdown-format.md)，按以下职责依次处理：

1. 阅读 [核心分析规则](references/core-analysis.md)，完成情绪、行为与决策、关注点与需求、可行动建议的事件级与日记级分析。
2. 阅读 [认知分析规则](references/cognition-analysis.md)，完成认知校准、问题解答、认知完善。问题解答只设置事件级栏目。
3. 阅读 [行动规划规则](references/action-planning.md)。先完成并保存核心与认知部分，保留空的行动规划标题；执行转换器 `--sources-only` 生成本稿来源清单，再依据计划和可行动建议完成行动项、连续来源摘录和推荐日程。

每阶段读取对应规则，不把代码中的 JSON 输出模板当作 Markdown 格式。事件 ID 与标题直接复用；即使没有内容，保留该事件全部栏目并留空。只在有当前事件证据时输出，允许整个模块为空。事件级独立分析，其他事件仅用于日记级归纳。建议须具体、低成本，不用空泛鼓励填充。

日期区分日记日期与冻结分析日期，以 `Asia/Shanghai` 理解相对日期。推荐值与确定计划区分表达，不把推断的频率或日期写成用户已经承诺的安排。

### 3. 复读与修订

保存为 `分析稿.md`，交付前核对：

- 每条分析能对应当前事件的事实、明确表达或有依据的有限推断；没有证据的删除。
- 问题确实来自事件，认知完善以原有观点为基础；事件事实不被其他事件或旧分析污染。
- 同一主线不拆碎，不同条目不重复；行动来源准确，单条行动可独立完成，推荐日期与循环完整。
- 逐项核对所有事件 ID、原标题及完整栏目；可执行转换校验，但脚本通过不代表分析内容正确。

展示完整稿并附文件链接，说明待确认的分析理解与推荐安排。需要澄清时每轮最多四题，每题附清晰选项；不为填满模块提问。人物动机、情绪和需求的分析推断不写回日记来源。用户补充事实改变原整理依据时，停止入库，先在整理流程中更新数据库来源并重新导出，不直接修改来源 JSON。

收到修改意见后更新当前完整稿，复读受影响部分；建议调整后重新生成来源清单并核对关联行动。展示修订稿，直至用户确认整篇最终稿。仅对局部内容的认可不算整篇最终确认。

### 4. 预检与确认后保存

所有修订完成后执行 [只读预检](references/storage.md)，生成绑定来源和 Markdown 指纹的入库包。明确说明目标用户、日记日期、事件数、分析条目与行动项范围；此时未写数据库。

本工作流约定确认后入库。用户明确确认当前整篇最终稿“没问题”“可以保存”后直接保存对应包，不再重复征求同一授权。确认前仅可转换、预检和只读核验，禁止使用 `--write`。指纹绑定文件，不代替用户确认。

来源、人物资料、稿件或日期推荐发生变化时，停止使用旧包；核对变更、重新预检，并取得变更后稿件的确认。入库失败时先只读检查是否已产生分析轮次，禁止盲目重试。输出实际脚本回执，不把本地文件生成或预检通过称为已入库。

## 维护与验证

目录拆分是一个 skill 内的规则组织，不要求额外 skill 或子代理。仅维护本 skill 及必要脚本；实际分析规则来自当前后端提示词，规则变更须明确提出，不能将已失配的后端提示词断言测试当成现行规则。

按 [验证说明](references/evaluation.md) 执行转换、来源保护和隔离事务验证；不连接真实数据库执行测试写入。仓库源目录并不代表宿主已安装，按路径读取可直接使用，本任务不自动更改安装配置。
