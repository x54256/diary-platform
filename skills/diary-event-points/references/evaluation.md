# 维护与评估

本文件用于开发与修改 Skill，普通提取不执行本评估流程。

## 结构与资源检查

使用可用的 skill-creator `quick_validate.py` 校验 Skill，另检查本地链接可达、JSON 用例可解析。结构合规不能证明语义质量。

数据库导出脚本修改后，从项目根目录运行隔离测试，不连接真实数据库：

```bash
backend/venv/bin/python -m unittest discover -s skills/diary-event-points/scripts -p 'test_export_events.py' -v
```

覆盖用户归属、同日多篇歧义、过期整理、JSON 数组解析、事件范围、全部事件覆盖、来源只含实际使用字段、只读事务、来源指纹、新运行防覆盖和错误输出脱敏。数据库真实验收与这些隔离测试分别记录；数据库网络权限被拒不等于数据库故障。

## 行为试跑

入库脚本变更后运行 `backend/venv/bin/python -m unittest discover -s skills/diary-event-points/scripts -p 'test_store_points.py' -v`。使用隔离数据库验证原文不改写、审核来源、用户归属、来源及文件变化拒绝、全部事件覆盖、无关元数据变化不影响保存、旧包仅供状态查询、只读默认、同包幂等、事务回滚、失败恢复、向量复用，以及仅调用向量模型后保存为 `POINTS_READY`。外部调用使用替身；这不代表真实服务或 PostgreSQL 约束已验收。真实写入须有用户授权。

`../evals/cases.json` 包含合成输入及核对条件。执行者只获得 Skill、用户请求与输入，不获得核对条件或预期答案。使用独立临时目录，禁止连接数据库、在线模型服务或修改真实日记。

比较相同请求与输入在无 Skill／旧 Skill 和当前 Skill 下的实际输出，使用相同模型与可比条件。需要独立执行者时使用干净上下文；单次同上下文复读应如实标注。记录实际输出及失败证据，不以“已检查”作为通过依据。

首次可先试跑 C01—C03；调整拆分和表达尺度时加入 C06—C08，涉及修订或筛选时加入 C04—C05。语义判断允许合理的不同措辞和拆分，不要求唯一要点数量。完整示例已用于指导生成，不再作为未见验收样本。

分别检查：

- 整体使用价值：相比原始事件，浏览主旨能否更容易看清内容构成，并定位、阅读和引用某一部分。条目数、改写幅度及是否沿用原段落不作为质量指标；区分实际妨碍理解或使用的问题与合理的不同组织方式。
- 来源覆盖：有效信息是否在详情中保留，包括新增派生信息、具体数值、理由、转折、反例、计划与未定论。
- 主旨忠实：主旨自身的人物、归属、否定、条件、程度与不确定性正确。
- 详情忠实：动作、角色、次数、时间与因果有来源依据；不新增解释或结果。
- 单元边界：每项有一个可独立定位的中心；不能只因相关就把行动进展、独立反应、原因推测与进一步认识一并塞入长项，也不把简短感受和直接结果机械切碎。
- 拆分后可读性：在所属事件标题下独立阅读各项，能理解对象、触发背景和主要内容。紧接理由的短结论不能悬空，判断需保留最低限度的具体依据；允许合并或补最少背景，不以出现某个连接词就判错，也不为独立可读补出来源没有的事实。
- 主旨定位：简短、中心明确；需要的归属与限定保留，不要求完整句或固定字数，不将背景、经过、结论全部列入主旨。
- 详情重写：围绕主旨自然组织信息、去除同义重复和无信息口语，保持独立可读及必要推演；不能靠整段照录或删除有效信息来满足检查。
- 修订与操作：保存用户修改，审核意见需核实，范围遵从指令，不连接无关服务。

若有审核与修正阶段，比较初稿和末稿，分别记录修复、未修复及新引入的错误。无争议的正确内容不应因“还要优化一次”而重写。

事实错误和有效信息遗漏不能用语言分数抵消。程序能检查字段、类型、序号、标题；语义须回到来源逐项判断。小样本只报告具体通过／失败和限制，不外推整体准确率。

回归时先处理实际错误，再复跑相关用例。留出未参与规则修改的事件验收，不把案例指定答案写进生成规则。
