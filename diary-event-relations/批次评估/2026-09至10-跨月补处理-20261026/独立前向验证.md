# 日记关系准备工作流独立前向验证

验证日期：2026-10-26。以下原始试跑之后代码又调整了“尚无正式要点”的处理；当前最终结论见文末补充试跑。原始结论：在本次实际隔离 CLI 试跑中，十月准备请求能直接读取九月及较早十月的 POINTS_READY 正式要点，不依赖历史关系稿或 PUBLISHED 状态；全历史池来源复验也确实覆盖未入选候选的向量变化。未发现该请求下的实质实现偏差。

## 方法与范围

先读取当前 `skills/diary-event-relations/SKILL.md` 与 workflow 说明，再构造用户请求“为 2026-10-18 生成关系准备包”。使用项目要求的 Python 3.11 `backend/venv/bin/python`。从现有测试辅助只借用 SQLite 表结构，另行生成全新用户、日期和事件行。场景数据库位于 `/tmp/history-forward-check/scenario.sqlite`，有九月 17 日的 3 个事件、十月 4 日的 4 个事件、十月 18 日的 1 个事件；所有运行均为 POINTS_READY，`is_in_graph=0`，未构造关系表或任何历史关系稿。

实际调用 `workflow.main()` 的原始 CLI 参数解析、`db_source.backend_engine`、数据库只读上下文、召回、批次打包、status/read/verify。唯一包装是将 `write_package(snapshot)` 的输出根目录参数重定向至 `/tmp/history-forward-check/packages`，避免默认路径写入工作区；没有替换数据库加载、历史选择、召回或复验逻辑。临时 backend 的 database.py 只创建连接到隔离 SQLite 的 SQLAlchemy engine。生产数据库完全未访问，未调用任何外部服务，未修改 Skill 或产品文件。

## 实际执行结果

1. `find --username forward-user --date 2026-10-18` 成功列出当前日记及唯一正式运行。
2. `prepare` 成功，历史模式为 `database`。source.json 的 history_selection 是 `before=2026-10-18`、`month_boundary=false`、`run_count=2`、`event_count=7`、`point_count=7`。history_inventory 包含 2026-09-17 和 2026-10-04 两个正式运行及其完整内容指纹。
3. 当前事件召回前五历史事件，形成 5 对；5 个候选同时覆盖九月与较早十月，source 事件数为 6。另 2 个历史事件没有进入候选，但仍保留在历史池覆盖统计与指纹内。
4. `status` 成功返回待处理 B001；`read --batch B001 --pending-only` 成功输出完整 6 个事件的要点详情和 5 个明确配对。输入没有向量数组。
5. 初次 `verify` 成功，在本地写出 verified_against_database=true 的 verification.json。
6. 只修改一个**未进入 source.events / 候选批次**的历史要点向量（仍为有效同模型 1024 维非零有限向量），再次 verify 退出码 1，明确报“数据库历史范围、正式要点或向量已变化，请新建运行”；旧 verification.json 确实被删除。证明全池指纹复验没有仅核对入选候选。
7. 恢复该向量后 verify 再次成功。随后增加 2026-09-02 的有效正式要点运行，原包 verify 退出码 1，报告同样的历史来源变化；跨月新增历史不会被漏检。
8. 将新增九月 2 日日记的唯一正式运行改成 DRAFT（保留日记 organized），prepare 明确退出码 1，指出该已整理历史日记缺少正式要点或有多个有效运行，没有静默排除。恢复 POINTS_READY 后，新 prepare 再次成功。

## 限制

本次证实 SQLite 实际 CLI 和只读适配路径，不等价于真实 PostgreSQL 数据内容或事务隔离的验证。没有读取正式数据库，因此未确认真实用户是否恰有缺失要点、重复有效运行、模型不一致或脏来源等数据阻塞。测试只验证准备包、读取及来源复验，没有生成语义判断、关系稿或入库包，也没有检查关系判断质量。召回使用同模型人工向量，验证的是历史范围、前五截取与全池复验，不评价真实嵌入相似度质量。


## 当前实现补充前向试跑（历史覆盖缺口规则调整后）

再次读取修改后的 Skill 和实际代码，使用相同真实 CLI 包装方式重建独立 SQLite 场景，没有改动项目文件或正式数据库。除九月与较早十月有效正式要点外，再加 2026-08-17 的 1 个有效 POINTS_READY 事件，以及 2026-07-12 的已整理日记但其运行仅为 DRAFT。本次请求仍为十月 18 日准备关系包，用户补处理范围为九月和十月。

实际结果：

- prepare 成功。history_selection 显式包含三个有效正式运行、八个历史事件／要点，month_boundary=false；八月正式事件确实出现在实际 recall.hits，且其运行在 history_inventory 内。有效历史并未被授权补处理月份截断。
- 七月缺口在 history_inventory 与 history_selection.gaps 中都存在，带 diary_id、diary_date=2026-07-12 和 gap=NO_FORMAL_POINTS，event_count / point_count=0。status 也返回 history_selection，因此正常读取状态时可见缺口。没有提取或生成缺口要点，没有外部服务调用。
- 对带缺口包执行 verify 成功；将隔离七月运行补齐为合法 POINTS_READY 后，旧包 verify 退出码 1，报历史范围／正式要点／向量已变化，旧成功回执被删除。随后新的 prepare 成功，覆盖增加为四个有效运行、九个历史事件／要点，gaps=[]。
- 新包未入选候选的历史事件向量变成非法两维后，prepare 退出码 1，报向量维度必须为 1024，仍然不静默排除已有正式要点。
- 将已有正式要点的八月日记设为 is_dirty=1 后，prepare 退出码 1，报日记整理来源已失效。
- 再构造八月同篇两个有效正式运行，prepare 退出码 1，明确报历史日记存在多个有效运行。

当前最终结论：要求的跨月有效正式要点召回、范围外缺口显式保留及后续补齐导致来源失效均符合当前 Skill；本次没有发现实质偏差。先前原始试跑第 8 条“尚无正式要点必定导致 prepare 失败”的行为已被本次缺口机制取代，不应继续当作当前结论。

补充证据：`/tmp/history-forward-check/supplement.py`、`/tmp/history-forward-check/supplement-cli-log.json`、`/tmp/history-forward-check/supplement-summary.json`。具体有效包路径见 supplement-summary.json。隔离数据库最后被故意留下重复运行错误，以保存最后一项负面场景，重新复现可运行 supplement.py 从头重建。

限制补充：CLI 本身没有接收用户授权补处理月份的参数，无法自动区分七月或九月缺口是否属于用户本次范围；“范围内先补、范围外报告”仍由执行 Skill 的 agent 按用户上下文落实。本次七月缺口为范围外，允许继续准备且显式报告。没有据此假称全部历史已覆盖。仍未验证 PostgreSQL 和正式数据，也未执行语义关系判断或入库。
